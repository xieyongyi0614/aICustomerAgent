# 微信公众号接入可行性审查

> **审查对象**：将本 Agent 接入微信公众号，供他人使用系统部分功能
> **约束前提**（用户明确）：① 个人开发者；② **不做企业认证**；③ **成本 0 元**
> **审查性质**：只读调研 + 可行性分析（**未修改任何代码**）
> **事实基准**：微信官方文档与开放社区答复（检索日期 2026-09-22）；项目侧代码实测
> **审查日期**：2026-09-22

---

## 0. 结论摘要

**判定：技术上能接，但在上述三条约束下，微信公众号不是承载「他人可用」的合适载体——存在四个致命约束，其中两个在平台规则层无法绕开。**

| # | 致命约束 | 层级 | 能否绕过 |
|---|---|---|---|
| **①** | 个人订阅号的消息被**折叠进「订阅号」文件夹**，无红点、无独立会话入口 | **产品层** | ❌ 无法绕过（账号类型决定） |
| **②** | **5 秒同步应答**窗口 vs 本系统前台一次应答 **5 次 LLM 调用** | 技术层 | ⚠️ 需专门做「快路径」且仍很勉强 |
| **③** | 个人订阅号**无客服消息接口** → 超时后无法异步补发 | 平台层 | ❌ 无法绕过（需认证） |
| **④** | 个人订阅号**无模板消息接口** → 主动能力（日结 / 周报 / 超支预警）全部无法投递 | 平台层 | ❌ 无法绕过（需认证） |

**核心事实**：微信官方明确「**个人类型公众号 / 服务号暂时不支持微信认证**」，且个人主体**只能注册订阅号**（服务号必须企业或机构主体）。这意味着 ②③④ 是**结构性封死**的，不是配置问题。

**因此建议**：
1. **不要**把公众号当作「完整的第二通道」来规划；
2. 若坚持 0 成本，可把个人订阅号定位为**窄功能命令入口**（如只做「记账 / 查账」），并接受体验折损（详见 §5 方案 A）；
3. **主动能力（日结 / 周报 / 预警 / 自主消息）继续走飞书**——飞书通道已真实链路验证，能力完整；
4. 若确实需要「微信里的完整机器人体验」，**唯一正解是认证服务号**，其前置是**具备营业执照主体**（企业或个体工商户）+ 300 元/年认证费。这与「不做企业认证」冲突，需重新决策（§5 方案 D）。

## 1. 平台规则事实核查

### 1.1 账号类型与认证

| 事实 | 依据 |
|---|---|
| 个人主体**只能注册订阅号**；服务号必须企业或机构主体 | 微信官方/公开资料一致 |
| **个人类型公众号（原订阅号）/ 服务号暂不支持微信认证** | 腾讯客服 FAQ（`kf.qq.com/faq/1612197nEJNR161219BB7Jne.html`）明确「个人类型公众号/服务号暂时不支持微信认证」 |
| 认证费 300 元/次、期限 1 年；认证后才有「自定义菜单（可跳转外部链接）/ 部分开发接口 / 多客服 / 卡券 / 广告主」等特权 | 同上 |
| 一个身份证最多注册 **2 个**订阅号，注销后也无法再注册 | 公开资料 |
| 订阅号与服务号**不可互转**（服务号可转订阅号，不可逆） | 公开资料 |

### 1.2 未认证 / 个人订阅号的接口权限（决定性）

微信开放社区答复（`developers.weixin.qq.com/community/develop/doc/0006e63d1a0c9896c5c3adc296b000`）与第三方权限表交叉核对：

| 能力 | 个人（未认证）订阅号 | 认证订阅号 | 认证服务号 |
|---|---|---|---|
| 接收普通消息 / 事件推送 | ✅ | ✅ | ✅ |
| **被动回复消息**（同步 XML 响应） | ✅ | ✅ | ✅ |
| 获取 access_token | ✅ | ✅ | ✅ |
| **客服消息（异步主动回复，48 小时窗口）** | ❌ | ✅ | ✅ |
| **模板消息（业务通知）** | ❌ | ❌ | ✅ |
| 群发接口 | ❌ | ✅ | ✅ |
| 自定义菜单**接口** | ❌ | ✅ | ✅ |
| 自定义菜单**跳转外部链接** | ❌ | ✅ | ✅ |
| 网页授权（拿 openid / 用户信息） | ❌ | ✅ | ✅ |
| 生成带参数二维码 / 短链 | ❌ | ❌ | ✅ |
| 获取用户基本信息 / 用户列表 | ❌ | ✅ | ✅ |
| 微信支付 / 卡券 / 小店 | ❌ | 需申请 | 需申请 |

> **官方原话**：未认证账号「**无法使用客服接口、模板消息等需认证的接口**；**自定义菜单仅支持文本消息且不可跳转外链**」。
> **关于菜单外链**：腾讯云开发者社区文章明确「❌ 不支持设置外链：**未认证的订阅号、个人类型公众号**；其自定义菜单的『跳转网页』仅支持公众号内部素材、历史消息等页面」。

### 1.3 关键机制约束

| 机制 | 规则 | 依据 |
|---|---|---|
| **被动回复超时** | 微信服务器**5 秒内收不到响应即断连**，并重新发起请求，**总共重试三次**；超时/异常数据会向用户下发「该公众号暂时无法提供服务」 | 微信官方《被动回复用户消息》《接收普通消息》 |
| 主动放弃回复 | 可「直接回复 success」或「回复空串」，微信不重试——但**用户什么也收不到**；官方注明此时「可以使用客服消息接口进行异步回复」 | 同上 |
| **去重** | 有 `MsgId` 的消息推荐按 `MsgId` 排重；事件消息按 `FromUserName + CreateTime` 排重 | 同上 |
| 服务器配置 URL | 必须以 `http://` 或 `https://` 开头，**分别只支持 80 / 443 端口**；URL 不可指定端口 | 官方《消息与事件推送介绍》 |
| JS 接口安全域名 | 需 **ICP 备案** + 仅 https；但这是 **JS-SDK 域名**的要求，**服务器配置本身官方未强制备案** | 官方《公众号与服务号》配置项说明 |
| 消息加解密 | 明文 / 兼容 / 安全三种模式；安全模式为 AES 加解密（纯密文） | 官方文档 |
| 消息折叠 | 订阅号所有推送统一折叠进「订阅号」文件夹，**不出现于微信聊天列表、无红点提醒**，用户须主动点击查看，触达率低 | 公开资料一致 |

## 2. 四层冲突逐条分析

### 2.1 产品层：订阅号不是「聊天入口」❌ 最致命

这是**比技术限制更根本**的问题。订阅号的消息被折叠进「订阅号」文件夹：

- 用户在微信聊天列表**看不到**你的公众号会话；
- 新消息**没有红点**、**没有置顶**；
- 用户要回复你，必须先点「订阅号」文件夹 → 找到你的号 → 点进去。

**后果**：把一个「对话式 Agent」放进订阅号，等于把机器人藏进一个用户很少打开的二级文件夹。这不是体验瑕疵，而是**产品形态不匹配**。

> 微信的「聊天式服务」体验是**服务号专属**的（消息独立显示在聊天列表）。这也是微信把订阅号定位为「内容传播」、服务号定位为「功能服务」的原因。

### 2.2 技术层：5 秒 vs 5 次 LLM 调用 ⚠️ 勉强可做

**项目实测**：前台一次用户消息共 **5 次 LLM 调用**——

| 阶段 | 调用 | 说明 |
|---|---|---|
| `turn_decisions` | `role_router` / `turn_analyzer` / `scene_intent` / `intention` | 4 链 `asyncio.gather` **并行**（`application/chat_pipeline.py:512-521`） |
| `reply_generation` | `answer_chain.astream` | 1 次**流式**关键段（`:731`） |

再叠加 `chat_pipeline` 的 22 步管线（状态装配 / 世界切片 / 上下文构建 / 记忆召回 / 决策 / 行为策略 / 风格装配…），**整个前台链路远超 5 秒**。

**既有可用的压缩手段**：

| 机制 | 位置 | 可复用性 |
|---|---|---|
| 通道级 LLM profile 覆盖 | `feishu_llm_profile`（`settings/feishu.py:48`）→ 适配器 `llm_factory.get_llm(profile)`（`channels/feishu/adapter.py:270`） | ✅ 可照加 `wechat_llm_profile`，指最快模型 |
| 轻量 LLM 降档 | `light_llm_profile`（`settings/agent_runtime.py:11`）+ `_build_light_llm`（`llm_gateway.py:146-169`） | ✅ 可直接用 |
| 前台 LLM 预算 | `foreground_run_llm_budget: int = 8`（`:9`），软模式超限仅置 `degraded` | ✅ 可调 |
| 超时参数 | `feishu_router_timeout_seconds=5.0` / `feishu_timeout_seconds=10.0`（`settings/feishu.py:46,49`）；全局 `llm_request_timeout_seconds=60`（`settings/llm.py:64`） | ✅ 可按通道设 |
| **按 Profile 裁剪阶段** | `runtime_loop_optional_stages` + `ProfileSpec.optional_stages`（`profiles.py:20-30`） | ⚠️ **`foreground_chat` 未声明任何 optional_stages，目前无现成快速路径** |

**结论**：即便用最快模型 + 通道级 profile，**4 并行链 + 1 流式回答压在 4 秒内（留 1 秒网络余量）是高风险目标**。要么新增一条「通道快路径 Profile」（只跑 perception → reply_generation，跳过 4 链决策），要么限制功能范围（见 §5 方案 A）。

### 2.3 功能层：主动能力全部失效 ❌

无客服消息、无模板消息，意味着以下能力**在公众号上完全无法投递**：

| 受影响能力 | 归属 | 现状 |
|---|---|---|
| 日结 / 周报推送 | V4.0 PLA-011 | 依赖 `proactive_delivery` + 通道出口 |
| 超支预警 | V4.0 PLA-013 | 同上 |
| 关系里程碑 / 纪念日消息 | V8.5 | 主动投递 |
| 自主行为主动消息 | V7 / V2.0.0 | 主动投递 |

**当前已实现的 V3.0 出站网关（`agent_runtime/outbound.py`）也需要 `ChannelAdapter.send` 才能投递——个人订阅号没有可用 send 通路**（客服消息不可用；被动回复只能回应，不能主动发起）。

**注意**：这是一个必须在架构层显式登记的结论——微信通道的 `ChannelAdapter.send` 在个人订阅号形态下**名义存在但实际不可用**，与 `channels/base.py` 契约隐含的「适配器可发送」假设不符。

### 2.4 治理层：0 成本与部署要求

| 项 | 事实 | 0 成本影响 |
|---|---|---|
| 公众号注册 | 个人订阅号免费 | ✅ 0 |
| 认证费 | 300 元/年（个人无法认证） | ✅ 无需支出 |
| 服务器公网可达 | URL 必须公网可访问、**仅 80 / 443 端口** | ⚠️ 需工程手段（见 §3） |
| ICP 备案 | **服务器配置官方未强制**（备案要求写在 JS 接口安全域名处）；但**国内机房的 80/443 对未备案域名会被拦截** | ⚠️ 实操上：要么备案（免费但需国内服务器），要么用境外 / 隧道 |
| 消息加解密 | 安全模式需 AES-256-CBC | ⚠️ 需新增 Python 依赖（`cryptography` 或 `pycryptodome`，pip 安装免费） |

| 手段 | 成本 | 说明 |
|---|---|---|
| 自有域名 + Cloudflare Tunnel | 域名约 ¥30~70/年（若已有域名则 0） | 免费提供 HTTPS(443) 隧道到本地/内网服务；无需公网 IP、无需备案 |

## 4. 对项目的架构影响

### 4.1 好消息：通道契约与注册点几乎零改动

项目采用「通道无关契约 + 适配器」模式，新增通道的复用面很大（均经实测）：

| 面 | 结论 |
|---|---|
| `channels/base.py` 契约 | **零改动**——7 个 frozen dataclass + `ChannelAdapter` Protocol，仅标准库、零 `app.*` 依赖 |
| `services/channel_identity_service.py` | **零改动**——`build_internal_user_id` / `build_session_id` 均为 `f"{channel}:{external_id}"`（`:22-29`），新通道只需传 `channel="wechat"` |
| 通道注册点（4+4 处） | **各追加一行**——`main.py:67,73,80,91`（proactive_delivery / channel_tools / outbound_gateway / 持久化幂等）、`agent_runtime/outbound.py:48`、`agent_runtime/inbound.py:34-47`、`api/v1/router.py:19-20`、`services/tool/channel_tools.py:55,128` |
| 参考范本 | `channels/feishu/` 共 11 个文件（client / errors / events / inbox / identity / adapter / delivery / outbound / shards），职责分离清晰，可直接对齐 |

**待新建**：`channels/wechat/`——验签 + AES 解密 + XML 解析 + `MsgId` 去重 + 应答构造 + 错误分类；`api/v1/wechat.py` 回调端点。

### 4.2 两个必须点明的架构发现

**发现 1：微信的「被动回复」无法复用飞书的「立即 200 + 后台 task」模式。**

飞书入站是「立即 200 + `spawn_background` 处理」（`api/v1/feishu.py:136-141`），因为飞书允许后续通过 API 主动发消息。**微信不然**：被动回复必须**在同一 HTTP 响应体里**返回 XML；返回 200 空体虽然微信不重试，但**用户收不到任何东西**，而异步补发依赖客服消息（个人订阅号没有）。

→ **微信通道需要一条新的「同步应答」路径**，与既有异步编排模式并存。这是本通道与飞书最大的结构性差异。

**发现 2：个人订阅号形态下，`ChannelAdapter.send` 名义存在但不可用。**

被动回复只能「回应」，不能「主动发起」；主动发起依赖客服消息（无权限）。因此微信适配器**只实现了契约的一半**，这必须在架构层显式登记，否则会误以为它支持主动投递（出站网关会静默失败）。

### 4.3 与 V4.0 的交叉点（价值最高的落点）

V4.0 的 PLA-009（账本能力）与 PLA-015（查询 API）交付的是**结构化、窄面、低延迟可控**的能力，恰好适合做微信窄入口：

- 「记账」「查账」是**短意图**，理论上可以走单次 LLM 的快路径；
- 账本是 append-only，**重复消息天然安全**（`idempotency_key` 幂等已在 PLA-005 落地）——这对微信「重试三次」是天然防御；
- 需要新增的只是「通道快路径 Profile」+ 通道适配器。

## 5. 推荐方案（分层）

### 方案 A（0 成本，推荐）：个人订阅号做「窄命令入口」

| 项 | 设计 |
|---|---|
| 定位 | 只做**单轮、窄面**命令：记账 / 查账 / 订正（正好是 V4.0 PLA 的能力面） |
| 应答 | **同步被动回复**，严格预算：目标 < 4.0s，硬超时回兜底文案 |
| 快路径 | 新增通道级 Profile：只跑 `perception → reply_generation`（跳过 4 链决策），`wechat_llm_profile` 指向最快模型，`foreground_run_llm_budget` 收紧 |
| 幂等 | 复用账本 `idempotency_key`（PLA-005 已有），天然抵御微信 3 次重试 |
| 主动能力 | **明确不做**——日结 / 周报 / 预警继续走飞书 |
| 体验预期 | 消息折叠在订阅号文件夹、无红点——**必须在产品层接受这一点** |
| 功能上限 | 不做复杂多轮、不做关系/自主行为、不做长回复（被动回复文本长度有限） |

### 方案 B（0 成本，互补）：图文 + H5 作为完整功能入口

- 订阅号每天可在后台**手动群发 1 次图文**（群发接口不可用，但后台编辑模式可以）；
- 图文正文 / 「阅读原文」可挂**外部链接**（菜单不能跳外链，但图文内可以），指向你自己的 H5；
- H5 里跑**完整系统**（不受 5 秒限制、可流式、可多轮），但**无主动推送**；
- 缺点：入口深、需手动群发、用户路径长。

### 方案 C（开发期必需）：先用测试号验证 5 秒可行性

- 测试号**免费、接口权限最全（含客服消息）**，适合在开发期验证「快路径能否压在 5 秒内」；
- **但绝不能对外**（限 20 个测试者、有有效期、官方定位为测试）。
- **建议把它作为第一步 PoC**：先证明 5 秒可达，再决定值不值得投入适配器开发。

### 方案 D（唯一完整解，需重新决策）

若「微信里的完整机器人体验」是硬需求，则唯一正解是**认证服务号**：
- 前置：**具备营业执照主体**（企业**或个体工商户**）；
- 成本：营业执照（个体工商户办理成本通常远低于公司）+ 认证费 300 元/年；
- 收益：客服消息（48h 窗口异步回复，彻底解决 5 秒问题）+ 模板消息（日结/预警可投递）+ 网页授权（H5 拿 openid）+ 菜单外链 + 聊天列表独立入口。

> 这已超出「不做企业认证 + 0 成本」的约束，因此**需要你重新决策**。我把它列出是因为它决定了另外三个方案的天花板。

## 7. 红线（不做的事）

1. **不使用非官方微信个人号协议**（WeChaty / iPad 协议等）——违反 ToS，封号风险，且与项目「合规优先」的取向冲突。
2. **不把测试号用于对外服务**——限 20 人、有有效期、官方禁止。
3. **不绕过认证限制「变通」获取客服 / 模板消息能力**——平台层封死，任何变通方案都是违规。
4. **不直接裸暴露后端**——必须经验签 + 建议安全模式加密 + 严格去重；优先用转发层隔离。
5. **不为接微信而砍掉 V4.0 的主动能力设计**——PLA-011 / PLA-013 继续按计划做，投递走飞书。
6. **不把 5 秒超时当作可忽略的风险**——超时用户会收到「该公众号暂时无法提供服务」，这是可见故障。
