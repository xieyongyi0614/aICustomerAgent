## 2. Goal

打通"世界事件 → 自治反应"的触发与素材两条路：V2.3 事件类型进入 escalation 白名单（高重要性事件即时升级为 event_driven Run）；autonomous_tick 的 world_facts 叠加 EventImpact 裁决包、当前日程块与活跃处境，让主动行为有"世界此刻在发生什么"的完整素材。

## 3. Background

V2.1 的 `run_event_pregate` 按 `v21_event_escalation_types` 白名单把 outbox 事件升级为 event_driven Run——架构 §1.3 明确"event_driven Profile 已是入口，Runtime 无需改形"。V2.3 只需扩展白名单取值与 world_facts 内容，天气变冷 → 主动提醒（§8.3 walkthrough）即由既有机器完成。

## 4. Scope

- escalation 白名单扩展：`v21_event_escalation_types ∪ v23_event_escalation_types`（后者受 `v23_event_detection_enabled` 门控），接线点在 run_event_pregate/trigger_router 的白名单装配处。
- `world_engine.collect_facts` 扩展：输出 EventImpact 裁决包（Top N by urgency）、当前日程块、part/天气、active 处境摘要（autonomy 素材包）。
- `autonomy_policy` 扩展（纯函数）：夜间抑制规则（part=night 且非高 care → 主动性降档）；care 提升规则（高 care_relevance → timing/interest 加权）。
- `v23_event_detection_enabled` + 总闸门控。

## 5. Non Scope

- decision_pipeline 文件改动（WS-014）。
- proactive_executor / proactive_chain 文案链改动（既有）。
- 新 trigger_type（trigger_registry 三类型沿用）。

## 6. Technical Design

### 6.1 escalation 白名单

```text
effective_whitelist = set(v21_event_escalation_types)
if v23_event_detection_enabled:
    effective_whitelist |= set(v23_event_escalation_types.split(","))
# 命中事件（user_condition/weather_change/calendar_event/goal_completed）
# → outbox pending → run_event_pregate 升级 event_driven Run（TriggerType=world_event，既有）
```

补充门槛：事件 importance ≥ medium 才进入升级（在 pregate 白名单命中后追加判定，Flag 内）。

### 6.2 autonomy 素材包（collect_facts 扩展）

```text
world_facts（既有键保留） += {
  "impacts": [ {event_id, type, urgency, care_relevance, topic_value, goal_opportunity} ],  # Top3 by urgency
  "current_block": {activity, part, location_id} | None,
  "active_situations": [ {dimension, summary, intensity} ],   # ≤3
  "day_part": "evening", "weather": "sunny",
}
```

装配点：`collect_facts` 内调用 `event_impact.evaluate`（事件行来自既有 active/due 查询），纯读零写。

### 6.3 autonomy_policy 规则（纯函数扩展）

- `night_suppression(facts, candidate)`：part=night 且 urgency<high 且 care_relevance<0.7 → interest/timing 评分乘性衰减（常量 0.5），原因留 policy trace。
- `care_boost(facts, candidate)`：存在 care_relevance≥0.8 的 impact 且候选类型为 care 向 → timing +0.1。
- 规则函数带 `v23_enabled` 开关参数：False 时等价于无操作（既有策略路径逐字节不变）。

### 6.4 数据流

```text
高重要性事件 → outbox → pregate（白名单+importance）→ event_driven Run
                                                        ↓
闲置 tick → collect_facts（素材包）→ autonomy_policy（夜间/care 规则）
                                        ↓
                              decision_pipeline（WS-014 增强 timing/候选）
```

## 12. Acceptance Criteria

**功能验收**

1. user_condition（high）事件 → event_driven Run 产生（loop_runs 出现该行，TriggerType=world_event）。
2. importance=low 的 weather_change 不触发升级（门槛生效），仅待 idle tick 素材拾取。
3. autonomous_tick 的 decision 审计中候选可见素材包影响（policy trace 含 night_suppression/care_boost 命中记录）。
4. 深夜 + 低 urgency 候选被抑制；care 高事件在夜间仍可触发（豁免路径）。

**数据验收**

5. 白名单合并为只读计算，settings 两键不被改写；world_facts 只读零写。

**接口验收**

无新增接口；`v21_event_escalation_types` 语义在 v23 关闭时逐字节不变（回归）。

**异常情况**

- v23 白名单含未知类型 → 解析时忽略该项并 trace（不炸 pregate）。
- evaluate_batch 对空事件集返回空素材包（policy 规则自然旁路）。

## 13. Testing Requirement

- **Unit Test**：白名单并集/门槛；夜间抑制与 care_boost 规则矩阵；素材包形状与 Top N。
- **Integration Test**：event_driven Run 全链（事件→Run→decision→proactive 落 proactive_actions）；idle tick 素材包进入候选。
- **Scenario Test**：架构 §8.3 walkthrough 复刻——降温（high）事件当 tick 升级 → 产出"提醒添衣"向候选；Flag off 时 pregate/policy 与 V2.2.0 行为一致。
