## 2. Goal

把世界从"只有家"扩展为"有家、公司、咖啡店、公园、旅行地"的场景体系：扩展 LocationRegistry，为每地点定义 SceneProfile（氛围/语气偏置/话题可供性/表达上限/能量基线），并交付 MovementResolver 作为位置变更的唯一裁决入口（用户叙事 > 日程推进）。

## 3. Background

P4：地点只有 home 静态层级，current_location 几乎不变化，场景不影响表达与情绪。架构 §5.5 将 Scene 系统定为"三个消费面（风格/行为/情绪）+ 一个资产层"。本 Task 交付资产层与位置裁决；消费接线在 WS-008（日程移动）、WS-016（风格/情绪）完成。

## 4. Scope

- 扩展 `app/character/asuna/world.py`：在既有 home 层级之外新增地点根（school / company / cafe / park / travel 类），沿用既有层级结构与中文别名/可供性格式。
- 新增 `app/character/asuna/scene_profiles.py`：`SCENE_PROFILES`（location_id → SceneProfile 值对象）+ 未注册地点的默认 profile。

## 6. Technical Design

### 6.1 LocationRegistry 扩展

- 既有 `HOME_LOCATIONS` 保留原样；新增 `WORLD_LOCATIONS`：`school`（教室/图书馆/操场…）、`company`（工位/会议室…）、`cafe`（堂区/露台…）、`park`（步道/长椅…）、`travel_seaside` / `travel_hotel`（旅行地点，供 DailyPlan 用户影响与未来剧情使用）。
- 每地点沿用 V8 资产格式：id 层级、中文名、别名表、可供性（available actions/items 线索）。提供 `find_location(user_input)` 复用既有别名匹配逻辑（如已有同名函数则扩展其检索域，Preserve 优先）。

### 6.2 SceneProfile 值对象

```text
SceneProfile = {
  location_id, atmosphere_tags: [str],
  tone_bias: str,                 # 如 "casual" / "focused" / "intimate"
  topic_affordances: [str],       # 咖啡店: ["闲聊","分享","日常"] 公司: ["工作","吐槽"]
  expressiveness_cap: "subtle"|"natural"|"rich",   # 表达上限（只降不升）
  energy_bias: int,               # -2..+2，state_engine 基线信号
  mood_bias: str | None,          # 可选情绪倾向（如 park → " content"）
}
DEFAULT_SCENE_PROFILE：中性档（tone_bias="neutral"、cap="rich"、bias=0）。
```

### 6.3 MovementResolver（位置变更唯一裁决）

```text
apply(user_id, target_location_id, source, reason) -> MoveResult
  source ∈ "user_narrative" | "schedule"
  1. 校验 target 在注册表（含别名解析）；非法 → 拒绝并留 trace
  2. 仲裁：查询最近一条 location_change 事件，
     若其 source="user_narrative" 且处于同一 part 窗口内 → schedule 来源移动被跳过
  3. target == current_location → no-op
  4. 经 world_engine.set_location 更新（复用 V8）
  5. 发事件：type="life_event", source=移动来源, importance=low,
     payload={kind:"location_change", from, to, reason}, 幂等键 location:{date}:{to_part}:{to}
```

**数据流**：解释器（用户叙事，V8 既有路径，本 Task 仅在其后追加 resolver 记账——Flag off 时追加段不执行）与 WS-008 日程推进都汇聚到 `apply`，保证 location_change 事件口径唯一。

## 12. Acceptance Criteria

**功能验收**

1. 新地点经别名可解析（如"咖啡店/cafe"→ cafe.main）；未知地点被拒绝且留 trace。
2. MovementResolver：目标与当前相同 → no-op；用户叙事移动后同 part 内日程移动被跳过；不同 part 放行。
3. 每次成功移动产生恰一条 location_change 事件（幂等键防重）。
4. SCENE_PROFILES 覆盖全部注册地点；引用不存在的 location_id 时校验失败。

**数据验收**

5. `worlds.current_location` 更新经 set_location（事务语义不变）；home 层级地点 id 与既有完全一致。

**接口验收**

无新增接口；`GET /debug/world/locations/{id}/objects` 对新地点可用（空列表合法）。

**异常情况**

- 并发移动（叙事与日程同 tick）→ 仲裁顺序稳定（叙事优先），结果可复现。
- profile 缺失 → DEFAULT_SCENE_PROFILE 兜底，不抛错。

## 13. Testing Requirement

- **Unit Test**：别名解析、仲裁矩阵（来源 × part 窗口）、幂等键、profile 完整性校验、DEFAULT 兜底。
- **Integration Test**：set_location + 事件落库联动；解释器路径 Flag 开/关对照。
- **Scenario Test**：家→咖啡店→家一日移动链，location_change 序列与 current_location 终态正确；Flag off 时与 V2.2.0 行为逐字节一致（无记账事件）。
