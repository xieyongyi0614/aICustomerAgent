## 1.1 Goal

关闭「只登记不执行」断层：维护步对到期 `action_schedules` 做 **认领 → 执行 → 终态收口**，使「明天早上提醒我学习」链路在自动化测试中端到端可跑。

目标链路：

```text
life_loop 维护步
  → list_due_schedules(now)
  → 原子认领（scheduled/due → due/executing）
  → ActionManager.execute(action_id)
  → 终态成功：mark_schedule_executed
  → 失败：按 failure_kind 退避 / 保持可重试
  → trigger 行同步收口（与 REF-005 协同）
```

## 1.2 问题回顾（audit D02）

| 基线 | 后果 |
|---|---|
| `consume_due_schedule` 仅 `mark_schedule_executed`，生产零调用 | 到期不执行 |
| `step_action_schedule` 只把 trigger 登记为 due | 「延迟/定时执行」不可用 |
| 端到端承诺止于队列查询 | B4 只关一半 |

## 1.3 与其他模块关系

| 方向 | 模块 | 关系 |
|---|---|---|
| 依赖 | REF-001 | 执行结果全形态 |
| 并行/紧耦合 | REF-005 | trigger 终态必须与 schedule 执行同步 |
| 调用 | `ActionManager.execute` | 实际执行 |
| 挂载 | `life_loop` 维护序列 | 不新开进程 |
| 读写 | `action_schedules` / `trigger_registry` | 认领与收口 |

# 3. Scope

## 3.1 In Scope

- 维护步内增加「到期执行」阶段（在登记之后或合并为一步认领执行）
- 原子认领：参照 trigger_registry / outbox 的 CAS 写法，避免双 worker 双认领（当前单进程可简化，但语义要写清）
- 成功：`mark_schedule_executed` + Action 终态
- 失败：不把 schedule 错误标成 `executed`；遵循 Action 层重试/退避
- `test_v26_schedule_execution.py`（T3 部分）
- 端到端：Plan → create_reminder + schedule → now ≥ scheduled_at → 维护步 → 世界事件/成功结果

## 3.2 Out of Scope

- 独立 Action Worker / `SKIP LOCKED` 多进程（P2-1）
- cron 重复排期语义扩展（`uq_action_schedules_action` 仍一 Action 一调度）
- `ActionSchedule` 加列（若认领用 status CAS + 既有字段足够，则不迁移；确需 `attempt_count` 时单开最小迁移并写进本卡变更记录）
- Manager 退避守卫（P1-6）

# 4. 实现要点

## 4.1 维护步伪流程

```text
step_due_action_execution(now):
  if not (v26_action_execution_enabled and v26_action_scheduler_enabled):
    return skipped
  due = list_due_schedules(now, limit=N)
  for item in due:
    record = get_record(item.action_id)
    if record is None or record.status in TERMINAL:
      mark_schedule_executed 或 cancel（防孤儿 schedule）
      continue
    claimed = claim_schedule(item, now)   # CAS
    if not claimed:
      continue
    result = await ActionManager.execute(item.action_id)
    if record 终态成功:
      mark_schedule_executed
    elif 终态失败:
      mark_schedule 失败语义（保持 due 重试或 cancelled，按 failure_kind）
    else:
      # executing/重试中：不标 executed
      pass
```

## 4.2 与既有 `step_action_schedule` 的关系

两种可选（实现时二选一并写进代码 docstring）：

- **A（推荐）**：扩展 `step_action_schedule`：登记后同轮立即尝试执行到期项（减少空转一轮）
- **B**：登记步与执行步分离，执行步挂 life_loop 序列下一步

**要求**：off 时仍立即 `skipped`；on 时「到期即有机会当轮执行」。

## 4.3 幂等

- 同一 `action_id` 重复认领失败（已有 `uq_action_schedules_action`）
- execute 依赖 Action 层 `dedupe_key` / 状态机，避免重复世界写
- 消费端不二次 `register` 已终结 schedule（与 REF-005 对齐）

## 4.4 优先级与限流

- 使用既有 `priority, scheduled_at` 排序
- `limit` 保守（如 10–20），防维护步饿死

# 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 维护步变重（扫+执行+LLM/工具） | limit；执行超时沿用 `action_execution_timeout_seconds`；失败不抛穿维护步 |
| 与对话链路争用 | 调用方/Manager 锁契约维持 life_loop per-user 锁内执行 |
| 只实现执行仍残留 trigger 滞留 | 与 REF-005 同 PR 或紧邻 PR，禁止只关一半 |

回滚：去掉执行阶段，恢复纯登记 `step_action_schedule`。
