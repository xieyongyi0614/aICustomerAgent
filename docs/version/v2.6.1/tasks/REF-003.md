## 1.1 Goal

让反馈从「写入 `record.result` 后无人读」变为「生产唯一入口 + 至少三面真实消费者」：

1. **唯一入口**：主路径 `integrate_result` 改为调用 `integration.apply_result_feedback`
2. **Autonomy**：`collect_facts` 能读到反馈投影（`feedback_kinds` / 执行结果）
3. **Reflection**：工具证据窗能基于完整 `ActionResult`（依赖 REF-001 的 `tool_id`/`observations`）
4. **Planning**：经 `integration.to_plan_step_outcome` 回写 `PlanStepOutcome`（生产调用，非仅测试）

## 1.2 问题回顾（audit D05）

| 基线 | 后果 |
|---|---|
| `apply_result_feedback` 无生产调用 | 契约与运行时分叉 |
| 主路径内联复制反馈逻辑 | 修契约不进生产 |
| `feedback_kinds` / `temporary_execution` 零消费者 | 反馈闭环名存实亡 |
| `from_plan_step_outcome` 等投影生产零调用 | 计划回写断链 |

# 4. 实现要点

## 4.1 唯一入口接线

目标调用链：

```text
execute 完成
  → integration.apply_result_feedback(record, result)
      → action_engine.integrate_result(record, enhanced)   # 状态/渠道
      → result.feedback_payload(enhanced)                  # 投影
      → payload["temporary_execution"] / plan_step
```

**禁止**：`integrate_result` 内再复制一份 feedback 投影写回 `record.result`。

注意 audit R2：投影写回 `record.result` 时字段扩写依赖 pydantic `extra=ignore`。本卡保持兼容，但：

- 不要把非契约键提升为权威 schema
- 文档标注「`record.result` 在 feedback on 时可能含扩展键」

## 4.2 三面消费者最小集

| 面 | 最小可验收行为 |
|---|---|
| Autonomy | facts/决策输入能看到最近行动 `status` + `feedback_kinds`（或明确读 `record.result` 扩展键） |
| Reflection | 工具窗 facts 含 `tool_id` 与 observations（在 REF-001 绿之后） |
| Planning | 计划步失败/成功 → `PlanStepOutcome` 字段由投影填充（`result_kind` / attempt 等既有字段） |

**不要求**：V2.7 级经验记忆写入。

## 4.3 Flag 语义

- `v26_action_feedback_enabled=off`：走 legacy（`integrate_result` 旧行为）
- on：走 v26 投影 + 消费者可见

Flag off 逐字节回归仍适用。

# 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 接线后 `record.result` 形态变化导致下游解析失败 | 保留契约键；扩展键 extra=ignore；T1 已锁全形态 |
| 递归：`apply_result_feedback` 反向 import `action_engine` 再被调 | 保持函数级 import（既有）；或后续 P1-7 端口化 |
| 消费者「假接线」（只读不改行为） | 验收要求可观察行为变化（facts 内容 / outcome 字段），不是 only hasattr |

回滚：恢复 `integrate_result` 内联分支，断开消费者读点。
