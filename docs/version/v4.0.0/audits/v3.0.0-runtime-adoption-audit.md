## 4. 风险：三套路径并存

若不裁决运行时采用方向，V4.0 落地后会形成三套并行调度路径：

```text
① 前台：AgentLoop.run() + profile.stages          ← 已默认生效 ✅
② 后台：_legacy_run_autonomous_cycle              ← 仍默认生效 ⚠️
③ 六段：_run_six_stage_loop() + stages/*          ← 影子，默认不生效 🔒
④ 回退：chat_pipeline._drive_foreground_linear    ← C-2 kill switch 🚪
```

**风险**：新功能若各自选不同路径接入，将出现「同一能力在三条链路上行为不一致」，且违反 V3.0 铁律「无第二套 Agent Pipeline」。**因此 V4.0 必须在架构层裁决，并把后台收编作为独立任务。**

## 5. 采用裁决（问题 ②）

> 完整裁决见 `docs/version/v4.0.0/architecture.md` §2.2 / §2.3。此处为审计侧结论。

| # | 裁决 | 一句话理由 |
|---|---|---|
| **R1** | 开发基线 = **Agent Runtime 的 Profile 阶段序列**（`profiles.py` + `AgentLoop.run()`） | 前台已默认此路径；收编成本已付；ADV-7 禁止第二套 Pipeline |
| **R2** | **禁止**以 `_drive_foreground_linear` 为开发基线 | 它是 kill switch（不建台账、不发事件、不冻上下文），不是能力扩展面 |
| **R3** | **禁止**依赖 `stages/*` 六段影子实现 | `SHADOW_STAGE_IMPLEMENTATION = True`，未接入生产 `run()` |
| **R4** | **后台必须收编**（独立任务 PLA-018） | 否则三套路径并存；且节律 / 预警需挂 Runtime 维护步 |
| **R5** | **六段循环本版不激活**，保持影子 | V4.0 的价值在数据正确性而非循环形态；方案 A 需先建 C-2 e2e 安全网 |

### 5.1 新功能接入方式（唯一合法姿势，四条）

1. 新增能力 = **注册新 Profile 阶段**或接入既有阶段的段本体（段序列只在 `profiles.py` 声明）。
2. 跨域副作用 = 走 **Update / handoff**（复用 `application/post_process` 步骤注册），不新增第二轮询。
3. 持久化 = 走对应域的**唯一写面仓储**；Run 台账只写 `loop_runs`。
4. 定时 / 节律 / 预警 = 挂**既有维护步或 `trigger_registry`**，不新增常驻循环。

### 5.2 对 V4.0 任务的具体影响

| Task | 受本裁决的影响 |
|---|---|
| **PLA-018（新增）** | 后台收编独立成任务（P0，Phase 1）：置 `runtime_autonomous_cycle_enabled = True` 并验收零回归 |
| PLA-009（能力接入） | 记账经 Action Engine → Tool Registry 既有治理链，**不新增编排** |
| PLA-011（节律投递） | 挂 `life_loop` 维护步 + 既有 Outbound，**不新增常驻循环**；依赖 PLA-018 |
| PLA-013（超支预警） | 挂 `trigger_registry`，**不新增常驻循环**；依赖 PLA-011 |
| PLA-015（查询 API） | 必须零 `repositories` / langchain 依赖（**不扩大**遗留 I-3） |
| PLA-017（验收） | 零回归采用「**零回归判定**」而非「全绿判定」（沿用 V3.0 因 I-2 形成的口径）；**须确保 PG 用例真实执行**（D-4 教训） |

## 7. 审计结论

1. **V3.0.0 Agent Runtime 的「地基」是真实的、完整的、可用的**：契约、会话、状态、上下文、事件、出入站归一、恢复、执行历史、迁移 `0052` 全部落地；前台已默认跑在它上面；Preserve 面零改动有 diff 为证。这批工作质量高，且**在验收中主动发现并修复了一个发布阻断级迁移缺陷（D-1）**，还连带揪出了长期静默 skip 的环境盲区（D-4）——这两件事本身就说明验收是动真格的。

2. **但它交付的不是「六段认知闭环」**：六段被显式裁决为影子实现（H-1 裁决 B）并隔离出生产导出面；后台自治仍走 legacy。**V3.0 = 运行时骨架 + 前台收编，不等于认知循环上线。**

3. **因此后续开发的正确姿势是**：以 **Profile 阶段序列 + 段本体**为扩展面（R1/R4），**不用** kill switch 线性旧链，**不用**六段影子实现。V4.0 通过 **PLA-018** 把后台补上，消除三套路径风险。

4. **对 V4.0 的净影响**：
   - 新增 1 个任务（PLA-018 后台收编）；
   - PLA-011 / PLA-013 的挂载点明确为「维护步 + `trigger_registry`」，不得新增常驻循环；
   - PLA-015 承担「不扩大 api→repositories 违规」的显式断言；
   - PLA-017 的零回归沿用 V3.0 的「零回归判定」口径，并新增「PG 用例真实执行」前置检查。
