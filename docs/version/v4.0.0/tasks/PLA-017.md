## 2. Background

### 2.1 为什么「账目精确性人工核对」是本版本的核心

架构评审引用了项目自身的一次真实故障（`docs/household-inventory-review.md`）：

> 库存里有 **6 个鸡蛋**，角色却说「没了。刚才那枚刚好用完」；还凭空出现了不存在的番茄汤。
> 结论：**「即使给了『以清单为准』的引导语，LLM 仍编造。说明需要系统侧强制，而非只依赖提示。」**
> 「把**鸡蛋**换成**钱**，这就是记账功能上线后必然出现的故障。」

V4.0 的全部设计（账本独立于记忆、金额整数分、抽取证据校验、聚合零 LLM、推送模板渲染、零新增开关）都是围绕这条教训展开的。**因此验收必须直接对这条教训做判定**：拿真实对话跑一遍，人工核对每一个数字。

**这不是「测试覆盖率」问题，而是「这个产品能不能用」问题。** 自动化断言能证明「金额来自结构化字段」，但只有人工核对能证明「抽取理解对了」。

### 2.2 零回归采用「判定口径」而非「全绿口径」

V3.0 验收报告记录了现实约束（`遗留问题登记 I-2`）：

> G7 零回归 **FAIL**——既存 18 项失败（v24 簇 13 + v2 aut005 1 + v21 agent008 1 + v8 性能 1 + v7.8 性能 1 + v23 PG 迁移 2）。**零回归（相对基线）成立**，但 §6.1 G7 判据要求「全绿」。

V4.0 沿用**基线对照法**口径：`当前失败集 ⊆ 基线失败集` 即判定零回归成立，并要求 V4.0 自身引入的失败数为 **0**。测试结果表须逐项标注「既存 / 新引入」。

### 2.3 必须吸取的 D-4 教训：PG 用例不许静默 skip

V3.0 的发布阻断缺陷（`D-1`：迁移 `0045` 在 PG 上无法执行）**长期未被发现**，根因是环境缺陷 `D-4`：

> 容器 `template1` 排序规则版本错配 → `CREATE DATABASE` 直接失败 → 所有 PG 用例的 `_ensure_test_database()` 只容忍 `"already exists"` → 一律返回 `None` → **整批 PG 用例静默 skip**。

V4.0 要加 **2 个迁移 4 张表**，因此**「PG 用例非全 skip」是本任务的前置检查项**（G16），且迁移必须真实 PG 双向空跑。

### 2.4 在 V4.0 中的位置

末端验收；是「V4.0 能不能上线」的判定者。

## 3. Scope

### 3.1 In Scope

1. **全量断言汇总执行**：PLA-001 ~ PLA-016 + PLA-018 的全部 Expected Output 断言，逐条执行并留证据（用例名 / 命令 / 输出摘要）。
2. **G1~G16 十六道 Gate 逐条判定**（见 §6.1）。
3. **账目精确性人工核对（核心）**：
   - 构造 **≥50 笔真实对话记账样本**，覆盖：
     | 场景类 | 样本要求 |
     |---|---|
     | 基础支出 / 收入 | 各 ≥5 笔，含不同表述（「花了 20」「付了 20 块」「20 元的快餐」） |
     | 中文数字 | ≥3 笔（「二十块」「一百五」），口径按实现冻结如实记录 |
     | 相对时间 | ≥5 笔（「中午」「昨晚」「上周五」） |
     | 类目歧义 / 未归类 | ≥5 笔（「楼下那家面馆」「买了点东西」） |
     | 大额触发确认 | ≥3 笔（≥100 元） |
     | 订正 / 撤销 | ≥5 笔（改金额、改类目、撤销） |
     | 转账 | ≥3 笔（不计入消费） |
     | 冲正后聚合 | ≥3 笔（验证净额） |
     | 反例（非记账语句） | ≥5 笔（「我记得你说过」不得误记） |
   - **人工核对每条**：抽取金额 / 方向 / 类目 / 时间 与原文是否一致；**零幻觉数字**（不允许出现原文没有的数字）；
   - 核对结果表进验收报告（样本 → 期望 → 实际 → 判定）。
4. **治理面人工验证**：导出（可对账）+ 删除（零残留）+ 金额不进 prompt 快照。
5. **Preserve 零改动证明**：以 `git diff` 为证（清单见 §6.3）。
6. **交付文档**：
   - `acceptance-report.md`：Gate 结果 + 证据 + 缺陷记录（含「已修复 / 待排期」分类）+ 未过项 + 发布裁决；
   - `regression-checklist.md`：真实模型人工回归清单（对话记账 / 澄清 / 订正 / 冲正 / 日结 / 周报 / 预算 / 超支 / 查询 / 导出删除）。
7. **基线回写**：`docs/current-system-architecture-baseline.md` 按项目纪律回写 V4.0 已实现形态（§1 能力、§2 分层、§3 模块、§6 数据、§7 配置、§9 技术债、§10 ADR、§11 演进）。
8. **文档链接同步**：`AGENTS.md` / `apps/backend/AGENTS.md`（迁移链尾 `0052` → `0054`、settings 模块数 21 → 23、版本入口指向 V4.0.0）。
9. **运行时口径勘误登记**：在 V4.0 验收文档中登记 V3.0 的两处口径差异（不变量 8 的 PASS 为测试态口径；影子矩阵漏 2 字段），**不修改 V3.0 冻结报告**。

### 3.2 Out of Scope（明确禁止扩张）

- **不新增任何功能**（验收任务只产出证据与文档）。
- **不修改任何 Preserve 模块**；不为「让 Gate 通过」而放宽断言。
- **不做性能优化**（只记录基线，不设优化目标）。
- **不清零 V3.0 既存 18 项失败**（属独立技术债簇，见 Backlog 登记）。
- **不修 V3.0 遗留 L1（`debug_view` 端点）/ L2（Context 冻结传参）/ L3（`api→repositories` 存量 26 处）**。
- **不修改 `docs/version/v3.0.0/**`**（冻结报告）。
- 不改 flag-removal 台账的清理动作（V4.0 只登记，不执行清理）。

## 4. Technical Design Requirements

### 4.1 验收方法与裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **零回归采用基线对照法**：`当前失败集 ⊆ 基线失败集`，且 V4.0 引入失败数 == 0 | 延续 V3.0 因既存 18 项失败形成的口径（I-2）；要求「全绿」在当前仓库状态下不可达，会变成永久红门 |
| D2 | 结果表**逐项标注**「既存 / 新引入」 | 防止把 flaky 或既存失败误判为回归（V3.0 已记录多个 flaky 案例） |
| D3 | **PG 用例非全 skip 是前置检查**（G16） | D-4 教训：静默 skip 会掩盖发布阻断缺陷 |
| D4 | 迁移必须**真实 PG 双向空跑** | 同上；`0045` 型缺陷只有在真实 PG 上才暴露 |
| D5 | 账目精确性采用**人工核对 + 样本表**，不只看自动化 | 自动化能证明「数字来自结构化字段」，不能证明「理解对了」 |
| D6 | 未过项**显式登记并归因**，不隐藏 | 对齐 V3.0 报告的做法（未过项 / 缺陷记录 / 遗留登记分段清晰） |
| D7 | 发布裁决用明确的**状态词**（如 `CONDITIONAL` / `RELEASABLE`）+ 阻塞条件 | 便于决策；避免含糊结论 |
| D8 | 实时模型人工回归**必须执行**，不可用自动化替代 | 项目既有约定（各版本 regression-checklist） |
| D9 | 基线回写是**发布动作的一部分**，与验收同批完成 | 项目纪律：「架构演进先更新基线」 |
| D10 | 验收阶段**零代码改动**（除发现发布阻断缺陷的修复，须登记） | 保持验收的独立性与可信度（对齐 V3.0 RT-020 的做法） |

### 4.2 验收流程

```text
① 前置检查
    ├─ PG 可用：TEST_DATABASE_URL 有效，PG 用例非全 skip（G16 前置）
    └─ 工作区干净：git status --short 无未跟踪产物

② 自动化执行（六组）
    ├─ Fast：    pytest -m "(unit or api) and not slow" -q
    ├─ V4.0 新增：pytest tests/v40 -q
    ├─ Integration：pytest -m integration -q
    ├─ E2E：     pytest -m e2e -q
    ├─ Golden：  pytest -m golden -q
    └─ 既有版本目录：pytest tests/v2 tests/v21 ... tests/v9 -q

③ 迁移实测
    └─ alembic upgrade head → downgrade 0053 → upgrade head → downgrade base → upgrade head

④ 零回归判定
    └─ 基线对照（文件级备份 → 还原干净基线 → 同命令 → 恢复）→ 失败集比对

⑤ 账目精确性人工核对（≥50 笔样本）

⑥ 治理面人工验证（导出可对账 / 删除零残留 / 金额不进 prompt）

⑦ Preserve diff 核验（清单见 §6.3）

⑧ 产出文档 + 基线回写 + 链接同步
```

### 4.3 依赖

- 允许依赖：全仓测试基建、`TEST_DATABASE_URL`、真实模型（人工回归）、既有 `docs/` 结构。
- **禁止**：修改业务代码（除登记过的发布阻断缺陷修复）、修改冻结文档、放宽断言。

## 6. Acceptance Criteria

### 6.1 版本级 Gate（G1~G16）

| Gate | 判据 | 验证方式 |
|---|---|---|
| **G1 用户实体就位** | `users` 表落地、默认用户幂等播种、既有调用零行为变化 | 迁移用例 + 兼容回归 |
| **G2 账目精确性（核心）** | ≥50 笔样本人工核对**零幻觉数字**、类目漂移在阈值内 | 人工核对表（进验收报告） |
| **G3 不可遗忘** | 账本三表无 TTL / 过期 / 衰减列；任意时间点可查 | 结构断言 + 时间跨度用例 |
| **G4 幂等与冲正** | 同 `idempotency_key` 仅 1 行；冲正后净额归零且原行未变 | `test_ledger_repository.py` |
| **G5 金额精度** | 全仓账本路径零 `float`；分元换算无损 | 静态扫描 + 往返用例 |
| **G6 账目不入记忆** | `memories` / `memory_candidates` 零金额明细 | 静态 + 端到端扫描 |
| **G7 零 LLM 数字** | 聚合 / 日结 / 周报 / 预警路径无 LLM 生成数字 | AST 断言 + golden 快照 |
| **G8 治理合规** | 导出完整可对账；删除零残留；金额不进 Prompt 快照 | 治理用例 + 快照断言 |
| **G9 越权防护** | 跨用户读写被拒；客户端 `user_id` 被拒 | API 越权用例 |
| **G10 单一写面** | 账本写只经 `ledger_repository`；预算只经 `goal_repository` | 静态断言 |
| **G11 Preserve 零改动** | §6.3 清单 diff 为空 | `git diff` + 对照测试 |
| **G12 零回归（判定口径）** | 当前失败集 ⊆ 基线失败集；V4.0 引入失败 == 0 | 基线对照法 + 六组结果表 |
| **G12b 零新增功能开关** | `core/settings/` 无新增 `*_enabled` 功能位 | 静态断言 + 字段清单核对 |
| **G13 迁移可空跑** | `0053` / `0054` 可空跑回滚；`MIGRATION_HEAD == "0054"`；`SCHEMA_TABLE_COUNT == 49` | 迁移测试 + 真实 PG |
| **G14 钉测收敛** | 链头钉测单点化；加迁移改动文件数 ≤ 3 | 静态断言 + PLA-001 验收 |
| **G15 运行时单一路径** | 后台已统一到 Agent Runtime；零第二条自治编排路径；六段仍为影子 | 静态断言 + `test_runtime_background_cutover.py` |
| **G16 PG 真实执行** | PG 用例**非全 skip**；两个迁移真实 PG 正放 / 逆放通过 | 命令输出核验 |

1. 各 Task 的 Expected Output 断言**全部有可执行用例**（不允许口头保证）。

5. 测试遵守 `docs/TESTING.md`（Focused → Module → 必要时 Fast）。
6. 无临时文件残留；提交信息符合约定（单行 ≤ 30 字）。

### 7.2 人工核对

- **账目精确性**：≥50 笔样本，逐条填「样本 / 期望 / 实际 / 判定」表。
- **真实模型回归**：`regression-checklist.md` 的十类场景逐项执行并记录。
