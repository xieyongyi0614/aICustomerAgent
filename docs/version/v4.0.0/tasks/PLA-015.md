## 2. Background

### 2.1 为什么「只做表现」在本任务格外重要

账本域有一个天然诱惑：查询接口看起来「直接查表最省事」。但项目既有分层纪律明确：

```
api/v1/  →  application  →  services  →  repositories  →  core
（表现层）    （编排）        （领域）      （唯一 DB 面）
```

而 V3.0 验收报告 `遗留问题登记 I-3` 记录了一个既存违规：

> `app/api/**` 反向依赖 `app/repositories` —— 5 个文件 26 处（`action.py` / `action_execution.py` / `debug.py` / `proactive.py` / `world.py`）。V3.0 未触碰 `app/api/**`，属既存形态……建议作为独立技术债登记，不在本版本处置。

因此本任务承担一个明确责任：**新增的 API 文件必须完全合规**，不把 26 处变成 30 处。这写进 §8 的 AC 与静态断言。

### 2.2 现状

- `api/v1/router.py` 现有路由：chat / debug / feishu / action / state / history / llm / proactive / world；
- 面向用户的读接口只有只读调试视图（`history.py:48` `GET /memories`、`state.py:53` `GET /state`）；
- **无任何聚合 / 报表接口**，也**无账本相关端点**。

### 2.3 在 V4.0 中的位置

- 是 PLA-016（前端视图）的唯一数据来源（前端只经 API，不直连后端内部）；
- 是「用户能查、能改」这一产品能力的落点——没有它，账本对用户是黑盒。

## 3. Scope

### 3.1 In Scope

1. **端点清单**（`api/v1/ledger.py`）：

   | 方法 | 路径 | 语义 | 落点（services） |
   |---|---|---|---|
   | `GET` | `/ledger/summary` | 周期聚合（`period=month\|week\|custom` + `since`/`until` + 可选 `group_by`） | `services/ledger/query.summary` |
   | `GET` | `/ledger/entries` | 条目查询（分页 + 过滤：`category_id` / `account_id` / `direction` / 时间区间） | `services/ledger/query.list_entries` |
   | `POST` | `/ledger/entries` | **手动记账**（结构化 body） | `services/action/capabilities/ledger`（经治理链）或 `services/ledger/service.record_entry` |
   | `POST` | `/ledger/entries/{id}/reverse` | **订正 / 撤销**（body 含 `reason`） | `services/ledger/correction` |
   | `GET` | `/ledger/categories` | 类目树（含用户自定义与别名） | `services/ledger/category`（只读面） |
   | `GET` | `/ledger/budgets` | 预算列表（含消耗与剩余） | `services/ledger/budget.check_all_budgets` |
   | `PUT` | `/ledger/budgets` | 设置 / 更新预算 | `services/ledger/budget.upsert_budget` |

2. **Schema**（`api/v1/schemas.py`，沿既有组织方式）：
   - 请求：`LedgerEntryCreateRequest`（金额为 **integer 分**、方向枚举、可选类目 / 账户 / 时间 / 商户 / 备注）、`LedgerReverseRequest`（`reason`、可选 `new_values`）、`BudgetUpsertRequest`；
   - 响应：`LedgerSummaryResponse`、`LedgerEntryListResponse`（含 `total` / `limit` / `offset`）、`LedgerEntryResponse`、`LedgerCategoryResponse`、`BudgetResponse`；
   - **金额出口统一**：响应中的可读金额一律经 `services/ledger/format.format_minor`，且**同时提供 `*_minor`（整数）与 `*_text`（格式化字符串）**两字段——前端不需要自己算，也避免各端格式化不一致。
3. **身份与越权**：
   - 用户身份**只从既有身份机制解析**（请求参数 / 渠道身份映射），**绝不信任客户端传入的 `user_id`**；
   - 请求体 / query 中若出现 `user_id` 字段 → 忽略或拒绝（Detail 冻结为拒绝，更显式）；
   - 跨用户读取 / 订正一律拒绝（PLA-002 的归属判定 + PLA-001 的用户隔离）。
4. **分层合规**：`api/v1/ledger.py` 只允许 import `application` / `services` / `schemas` / `core.settings`；**禁止** `repositories` / `langchain` / `core.db`。
5. **分页与上限**：`limit` 有默认值与**硬上限**（防超大查询）；`offset` 分页；超限请求 → 400 或截断（Detail 冻结为 400，更显式）。
6. **错误语义**：统一错误 → HTTP 映射（404 资源不存在 / 400 参数非法 / 403 越权 / 409 幂等冲突按既有约定 / 500 内部错误）；**不透传堆栈**。

### 3.2 Out of Scope（明确禁止扩张）

- **不做鉴权体系**（架构裁决 0.7）：只保证「作用于自己」，不解决「你是谁」。
- **不做高级查询 DSL / 任意 SQL**：只暴露声明好的过滤维度。
- **不做导出**（归 PLA-003 治理面 `GET /life/export`）。
- **不做图表 / 可视化数据契约**（前端自行渲染；后端只给结构化数据）。
- **不做批量接口**（批量订正 / 批量导入）。
- **不做 WebSocket / 流式查询**（账本查询是短请求）。
- **不改既有路由与响应契约**（`debug` / `chat` / `state` / `history` 等一律零改动）；**不顺手修 I-3 的既有 26 处**（属独立技术债，本版本只承诺「不扩大」）。
- **不新增任何功能开关**（§0.9）。
- 不改 services / repositories / 账本域模块（PLA-004~014 冻结；只调用）。

## 4. Technical Design Requirements

### 4.1 接口契约（示例）

```python
# POST /ledger/entries
class LedgerEntryCreateRequest(BaseModel):
    amount_minor: int = Field(gt=0)                  # 整数分，>0
    direction: Literal["expense", "income", "transfer"]
    category_id: str | None = None
    account_id: str | None = None
    occurred_at: datetime | None = None
    merchant: str | None = None
    note: str | None = None
    idempotency_key: str | None = None               # 缺省由服务端按内容生成


# GET /ledger/summary response（节选）
class LedgerSummaryResponse(BaseModel):
    period: PeriodResponse
    expense_minor: int
    expense_text: str                                # format_minor 结果
    income_minor: int
    income_text: str
    net_minor: int
    net_text: str
    transfer_minor: int
    by_category: list[CategoryTotalResponse]
    entry_count: int
    reversal_count: int
    compared_to_previous: ComparisonResponse | None
```

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | `api/v1/ledger.py` **零 `repositories` / langchain 依赖** | 分层纪律；也是对 V3.0 遗留 I-3 的「不扩大」承诺（本任务的显式责任） |
| D2 | 身份**只从既有机制解析**，请求中的 `user_id` **一律拒绝** | 越权红线；显式拒绝比静默忽略更容易发现问题 |
| D3 | 金额响应**双字段**（`*_minor` + `*_text`） | 前端不重复实现格式化；避免各端格式不一致（PLA-006 的 `format_minor` 是唯一入口） |
| D4 | `POST /ledger/entries` **走治理链**（能力 / 服务），不直调仓储 | 与 PLA-009 一致：记账是受治理的行动 |
| D5 | 手动记账 `source="manual"` | 区分来源，支撑溯源与统计（PLA-004 已定义枚举） |
| D6 | `idempotency_key` 可缺省，由服务端**确定性生成** | API 友好且不牺牲幂等；生成规则确定性（同用户 + 同内容 + 同时间窗） |
| D7 | 分页 `limit` 有**硬上限**，超限 → 400 | 防止一次拉全表；显式报错优于静默截断 |
| D8 | 错误不透传堆栈；403 / 400 / 404 语义明确 | 安全与可测 |
| D9 | **不新增功能开关**；端点交付即可用 | §0.9 |
| D10 | 不顺手修既有 26 处 `api→repositories` 违规 | 范围纪律：本任务只保证新增文件合规；存量治理属独立批次（Backlog 已登记） |

### 4.3 数据流

```text
GET /ledger/summary?period=month
   → 身份解析（不信任客户端 user_id）
   → services/ledger/query.summary(user_id, period)
   → services/ledger/format.format_minor（金额转文本）
   → LedgerSummaryResponse（*_minor + *_text）
   → 200 JSON

POST /ledger/entries/{id}/reverse
   → 身份解析 + 归属校验（PLA-002 assert_access）
   → services/ledger/correction.cancel_entry(entry_id, reason, idempotency_key)
   → 200 CorrectionResponse / 403（越权）/ 404（不存在）

PUT /ledger/budgets
   → services/ledger/budget.upsert_budget(spec)
   → 只经 goal_repository 计划面（services 内部完成）
   → 200 BudgetResponse
```

## 5. Implementation Plan

1. **Schema 先行**：`api/v1/schemas.py` 增账本请求 / 响应模型（金额双字段约定）。
2. **端点实现**：`api/v1/ledger.py`——7 个端点，**全部薄封装**（解析 → 调 services → 装配响应）。

4. **身份与越权**：统一依赖注入解析当前用户；请求体 `user_id` 拒绝。
5. **分页硬上限**：在 schema 层用 `Field(le=...)` 约束。
6. **错误映射**：与既有 API 的错误处理风格一致。
7. **分层护栏**：新增用例做 AST 断言（零 `repositories` / langchain / `core.db`）。
8. **测试**（§7），Focused → Module → Fast。
9. **既有路由零变化核验**：跑既有 API 测试 + 对比 `/api/v1/debug/*` 响应。
