## 2. Background

### 2.1 为什么这一相投产比最高

系统已建成完整的主动服务体系，记账**不需要新增任何投递基建**：

| 既有资产 | 证据 | 本任务如何复用 |
|---|---|---|
| 后台自治周期与维护步 | `application/life_loop.py::_run_maintenance`（按间隔调度 `world_maintenance` / `world_simulation` / `action_retry` / `action_schedule` / `outbox_consume` / `trigger_reconcile`） | 节律检查挂为新维护步 |
| 触发登记 | `trigger_registry` 表 + Trigger Router | 节律触发登记 |
| 主动投递去重 | `proactive_actions.dedupe_key` 幂等 | 同周期去重 |
| 免打扰与节流 | quiet hours / cooldown / `life_loop_storm_daily_limit` / `_should_skip_user_facing` | 直接遵守，不改动 |
| 出站出口 | `agent_runtime/outbound.py` → `ChannelAdapter.send`；飞书 `delivery.py` 已真实链路验证 | 统一出站 |
| 聚合数据源 | PLA-006 `summary` / `trend` / `top_categories` | 数字唯一来源 |

### 2.2 为什么要先有 PLA-018

节律要挂在**维护步**上，而维护步的调度归属后台自治周期。若后台仍走 legacy（`runtime_autonomous_cycle_enabled = False`），新能力会挂在 legacy 链上，形成「同一能力两条链路」（架构不变量 12 违规）。**PLA-018 先把调度路径统一，本任务再挂载。**

### 2.3 在 V4.0 中的位置

- 依赖 PLA-006（数据）、PLA-009（能力与治理）、PLA-018（挂载面）；
- 是 PLA-013（超支预警）的**直接前置**——预警必须先有「可靠投递 + 可靠聚合」；
- 是 `tasks.md` §4.2 交付顺序第 6 步。

## 3. Scope

### 3.1 In Scope

1. **节律定义与触发**：

   | 类型 | 触发时点 | 内容结构 |
   |---|---|---|
   | 日结 | `ledger_digest_send_time` 的日时刻（默认 `21:30`） | 今日合计 / 分方向 / 类目 top-3 / 与昨日对比 / 条目数与冲正数 / 当日明细摘要（前 N 条） |
   | 周报 | `SUN` + 配置时刻 | 本周合计 / 周内每日趋势 / 类目 top-5 / 与上周对比 / 未归类占比 |

   - 挂 `life_loop` **维护步**（新增一步，按间隔调度）；或经 `trigger_registry` 登记——**两者择一，按 Detail 冻结**（推荐维护步：与既有 `world_*` 维护步形态一致）。
   - **不新增常驻循环**（架构 §2.3 第 4 条）。
2. **模板渲染**（`prompts/` + `services/ledger/digest.py`）：
   - 全部文案由**模板**渲染，数字以占位符注入，**占位符值只能来自 PLA-006 的 `LedgerSummary`**；
   - 服务提供：`render_daily(user_id, *, period, now) -> str` / `render_weekly(...) -> str`；
   - 金额格式化统一走 PLA-006 的 `format_minor`。
3. **投递**：
   - 经既有 `proactive_delivery` / `agent_runtime.outbound` 出口；
   - `dedupe_key` = `f"ledger_digest:{kind}:{period_start.isoformat()}"`（同周期幂等）；
   - 遵守既有 quiet hours / cooldown / 每日上限；**不修改这些机制**。
4. **空账期处理**：该周期**零条目**时是否推送 → 按 Detail 冻结（推荐：不推送，避免噪音；但「周报零条目」可推送一次以提示记账习惯未建立）。
5. **零数字生成保证**：`services/ledger/digest.py` **不得 import 任何 LLM 组件**（静态断言）；推送文案中不出现「约」「大概」「可能」等推断词（由模板固化）。

### 3.2 Out of Scope（明确禁止扩张）

- **不做图表 / 富媒体卡片**（首版纯文本）。
- **不做多用户广播**（单人用户模型，架构 §1.1）。
- **不做 LLM 摘要 / 自然语言解读**（数字零幻觉是硬约束；解读类内容如需，属后续版本并需单独设计护栏）。
- **不改投递幂等、免打扰、节流、风暴限流机制**（只遵守）。
- **不新增常驻循环 / 不新增后台 worker**；维持步清单只允许**追加一步**。
- **不做用户可配置的推送频率**（首版用 `ledger_digest_send_time` 调时刻；频率开关属功能位，§0.9 禁止）。
- **不做钉钉 / 微信等新渠道**（渠道扩展归 Channel Adapter 体系）。
- **不新增任何功能开关**（§0.9）：日结 / 周报**交付即生效**。
- 不改账本表、写面、聚合、能力语义（PLA-004~010 冻结）。

## 4. Technical Design Requirements

### 4.1 接口契约

```python
@dataclass(frozen=True, slots=True)
class DigestPayload:
    kind: str                     # "daily" | "weekly"
    period: Period
    title: str
    body: str
    dedupe_key: str
    summary: LedgerSummary        # 数字来源（只读引用）


def build_daily_digest(user_id: str, *, now: datetime,
                       settings: LedgerSettings) -> DigestPayload | None:
    """零条目时返回 None（不推送）。"""


def build_weekly_digest(user_id: str, *, now: datetime,
                        settings: LedgerSettings) -> DigestPayload | None: ...


def should_send(payload: DigestPayload, *, now: datetime) -> bool:
    """检查是否到达发送时刻、是否重复（dedupe_key）、是否在免打扰窗口。"""


def deliver_digest(payload: DigestPayload, *, now: datetime) -> SendResult:
    """经既有主动投递出口；失败返回 SendResult(ok=False)，不抛异常。"""
```

**挂接（`application/life_loop.py`）**：`_run_maintenance` 增 `ledger_digest` 一步，按间隔调度；步骤内部对每个用户调用 `build_*_digest` + `should_send` + `deliver_digest`。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **数字只来自 `LedgerSummary`**，模板只做占位符替换 | 架构 §4.6「零幻觉」：推送是用户最容易记住的数字来源，错一次就失去信任 |
| D2 | `digest.py` **不得 import 任何 LLM 组件** | 用静态断言把「零 LLM 数字」变成机械保证，而不是纪律口号 |
| D3 | 挂**维护步**而非新增常驻循环 | 架构 §2.3 第 4 条：定时 / 节律挂既有维护步或 `trigger_registry` |
| D4 | `dedupe_key` 含**周期起点**，同周期只推一次 | 维护步可能因重启 / 重试被多次触发；幂等键是唯一防线 |
| D5 | 零条目 → **不推送**（日结）；周报零条目 → 按冻结口径（推荐也跳过） | 避免「今天没花钱」这类无信息噪音；宁少勿滥 |
| D6 | 发送时刻是**参数**（`ledger_digest_send_time`），不是开关 | §0.9：时间可调，功能不可关 |
| D7 | 投递失败**不冒泡**（返回 `SendResult(ok=False)`） | 对齐既有投递语义：投递失败不阻断 Run |
| D8 | 文案不使用推断词（「约」「大概」） | 账务播报必须确定；模板固化措辞 |
| D9 | 免打扰窗口内**只跳过、不补发** | 避免「补发洪峰」；错过即错过，下个周期正常 |

### 4.3 数据流

```text
life_loop._run_maintenance（既有维护循环）
   → 维护步 ledger_digest（按间隔）
        for user in 活跃用户:
             payload = build_daily_digest(user, now, settings)
                 零条目 → None → 跳过
             should_send(payload, now)
                 False（未到时刻 / 已推送 / 免打扰）→ 跳过
             deliver_digest(payload, now)
                 → proactive_delivery → Outbound Gateway → ChannelAdapter.send
                 → dedupe_key 落 proactive_actions（幂等）
                 → SendResult（失败不抛）

数字链路：
   build_*_digest → PLA-006 summary/trend/top_categories → format_minor → 模板占位符
   （全程无 LLM 参与）
```

### 4.4 依赖

- 允许依赖：`app.services.ledger.query` / `format`、`app.services.proactive_*`（既有投递）、`app.application.agent_runtime.outbound`、`app.prompts`（模板）、`app.core.settings`。
- **禁止**依赖：任何 LLM 组件（`app.chains` / `llm_factory` / `ChatOpenAI`）——**这是本任务的硬红线**；`app.channels.<impl>`（出站只经 Outbound Gateway）。

## 5. Implementation Plan

1. **模板**：`prompts/` 增日结 / 周报模板（含占位符约定表）；生成 golden 快照。
2. **节律构建**：`services/ledger/digest.py`——`DigestPayload` + `build_daily_digest` / `build_weekly_digest` / `should_send` / `deliver_digest`。

5. **设置**：`core/settings/ledger.py` 增 `ledger_digest_send_time: str = ""`；登记 `tests/v40/support.py`。
6. **零 LLM 静态护栏**：在测试中加 AST 断言（`digest.py` 无 LLM import）。
7. **测试**（§7），Focused → Module → Fast。
8. **手工验证**：在真实飞书链路发一次日结（对齐既有验收做法），确认文案与数字。
