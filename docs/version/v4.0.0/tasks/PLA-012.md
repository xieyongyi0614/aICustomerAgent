## 2. Background

### 2.1 为什么预算不该建新表

系统已具备完整的「目标驱动」能力（V2.5 Planning System + V2.1 Goal Stack）：

| 既有能力 | 位置 | 预算场景下的对应 |
|---|---|---|
| 目标分层（short_term / medium / long_term） | `character_goals.horizon` | 「本月餐饮预算」= short_term 目标 |
| 目标领域分类 | `character_goals.domain` / `layer` | 新增 `domain="budget"`（沿用既有字段，**不加列**） |
| 计划拆解 | `services/planning/decompose.py` | 预算 → 「每日检查消耗」计划步骤 |
| 规划七道闸 | `services/planning/engine.py::PlanningEngine` | 预算检查走同一套闸（attempt_cap / 形状 / 步数 / 能力对齐 / 工具可解析 / 工具在面 / LLM 失败） |
| 计划观察与修订 | `plan_observer` / `PlanRevisionPolicy` | 超支 → 观察 → 重规划（既有回路） |
| 计划单一写面 | `goal_repository` 计划面 | 预算写入的唯一通道 |

**结论**：为预算单独建表会同时违反「零新表承诺」（架构 §10.8）与「单一写面」（§10.5），并且会与 Goal Stack 争夺「目标」的真相源。

### 2.2 预算与账本的关系

| 概念 | 真相源 |
|---|---|
| 「花了多少」 | **账本**（`ledger_entries` + PLA-006 聚合） |
| 「允许多少」 | **目标**（`character_goals`，经 `goal_repository`） |
| 「是否超支」 | 二者相减的**派生判定**（本任务），不落表 |

三者责任分离，互不越界——这是本任务的核心设计原则。

### 2.3 在 V4.0 中的位置

- PLA-013（超支预警）的直接前置；
- 是 `tasks.md` §4.2 交付顺序第 6 步的组成部分。

## 3. Scope

### 3.1 In Scope

1. **预算的领域视图**（`services/ledger/budget.py`）：

   ```python
   @dataclass(frozen=True, slots=True)
   class BudgetSpec:
       user_id: str
       scope: str                 # "total" | "category"
       category_id: str | None    # scope == "category" 时必填
       period: str                # "month" | "week"（自然月 / 自然周，口径与 PLA-006 一致）
       limit_minor: int           # 预算额度（整数分）
       goal_id: str               # 承载它的 goal
       currency: str
   ```

   - **读**：`list_budgets(user_id, *, period=None) -> list[BudgetSpec]`——从 `character_goals` 读取 `domain="budget"` 的目标并**投影**为 `BudgetSpec`；
   - **写**：`upsert_budget(spec, *, now) -> BudgetSpec`——**只经 `goal_repository` 计划面**（新建 / 更新 goal，不写任何新表）；
   - **删**：`archive_budget(goal_id, *, now)`——经 `goal_repository` 置终态（不物理删除）。
2. **预算检查**（承载体 = **plan step**）：

   ```python
   @dataclass(frozen=True, slots=True)
   class BudgetCheck:
       budget: BudgetSpec
       consumed_minor: int        # 来自 PLA-006 summary（净额口径）
       remaining_minor: int
       ratio: float               # consumed / limit
       breached: bool
       reason: str                # "ok" | "over_limit" | "near_limit" | "no_data"


   def check_budget(user_id: str, spec: BudgetSpec, *, now: datetime) -> BudgetCheck: ...
   def check_all_budgets(user_id: str, *, now: datetime) -> list[BudgetCheck]: ...
   ```
   - 注册为 Planning 的**一个 plan step 类型**（如 `budget_check`），由 `services/planning/scheduler.py` 只读消费；
   - 消耗口径**必须**与 PLA-006 的 `expense_minor` 一致（含冲正双向计入；`transfer` 不计入）。
3. **失败理由契约扩展**（`services/planning/goal_contract.py`）：新增预算类失败理由（如 `over_budget` / `budget_exhausted`），与既有 `FailureKind` 风格一致。
4. **前台只读**：前台 Run 中预算检查只读（长期化写入只发生在后台，既有铁律）。

### 3.2 Out of Scope（明确禁止扩张）

- **不重写 Planning 引擎 / 七道闸 / 拆解 / 观察 / 修订**（Preserve）。
- **不建预算表**；不给 `character_goals` 加列（沿用既有 `domain` / `layer` / `horizon` 字段承载）。
- **不做预算推荐算法**（「建议你餐饮预算设为 1200」属后续版本）。
- **不做跨用户预算**（共享预算 / 家庭预算）。
- **不做多币种预算**（首版单币种，与 PLA-004 一致）。
- **不做预算的历史版本 / 调额审计**（goal 的既有状态流转已提供基本轨迹）。
- **不做预算的提醒排期**（提醒归 PLA-013）。
- **不新增任何功能开关**（§0.9）；**不新增表**（§10.8）。
- 不改账本域任何模块（PLA-004~006 冻结）。

## 4. Technical Design Requirements

### 4.1 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | 预算**承载于 `character_goals`**（`domain="budget"`），**不建表、不加列** | 零新表承诺；Goal Stack 已是「目标」的真相源，另立真相源会造成双写与漂移 |
| D2 | 预算写入**只经 `goal_repository` 计划面** | 单一写面纪律（架构 §10.5） |
| D3 | 预算消耗口径**复用 PLA-006 `summary`**，不自行求和 | 「花了多少」只能有一个答案来源；自行聚合必然出现两套数字 |
| D4 | `transfer` **不计入**预算消耗 | 转账不是消费；计入会让预算被无谓消耗 |
| D5 | 检查逻辑注册为 **plan step**，由既有 scheduler 消费 | 复用 Planning 的调度 / 观察 / 修订回路，不新造执行器 |
| D6 | 超支判定为**派生值**（`BudgetCheck`），不落表 | 「是否超支」随时间变化，落表会产生大量失效行；派生更简单也更准 |
| D7 | 前台**只读** | 既有铁律：前台目标栈只读，长期化写入只在后台 |
| D8 | 周期语义与 PLA-006 **完全一致**（自然月 / 自然周 / 本地时区） | 口径不一致会导致「预算说超了、报表说没超」的自相矛盾 |
| D9 | 删除 = **归档**（置终态），不物理删除 | 保留历史目标轨迹；与 goal 既有生命周期一致 |
| D10 | 无开关（§0.9） | 预算能力交付即生效 |

### 4.2 数据流

```text
【设置预算】用户：「本月餐饮预算 1500」
   → （意图识别归既有链路）
   → upsert_budget(BudgetSpec(scope="category", category_id=餐饮, period="month", limit_minor=150000))
        → goal_repository 计划面：建 / 更新 goal（domain="budget"）
        → 返回 BudgetSpec(goal_id=...)

【检查预算】后台自治周期（plan step）
   → list_budgets(user_id, period="month")
   → for spec in budgets:
         consumed = PLA-006 summary(period).by_category[spec.category_id]（或 expense_minor for scope=total）
         check_budget(...) → BudgetCheck(consumed, remaining, ratio, breached)
   → 超支 / 接近上限 → 触发理由写入 plan 观察面
        → 既有 PlanObserver → PlanRevisionPolicy → 重规划
        → 或交 PLA-013 生成预警

【前台】只读：不写 goal、不改预算
```

## 5. Implementation Plan

1. **领域视图**：`services/ledger/budget.py`——`BudgetSpec` / `list_budgets` / `upsert_budget` / `archive_budget`。
2. **投影映射**：定义 goal ↔ `BudgetSpec` 的字段映射表（goal 的 `title` / `domain` / `horizon` / 目标指标字段如何承载 `limit_minor` / `period` / `scope`）——**不得加列**，用既有字段的组合承载；映射表写入 Detail 冻结。
3. **检查逻辑**：`BudgetCheck` + `check_budget` / `check_all_budgets`（消耗取 PLA-006）。
4. **plan step 注册**：在 Planning 的 step 类型注册表增 `budget_check`（只读消费面），由 `scheduler` 调度。
5. **失败理由扩展**：`goal_contract.py` 增预算类理由（与既有 `FailureKind` 风格一致）。
6. **前台只读校验**：确认前台 Run 路径无预算写入（静态 + 打桩断言）。
7. **测试**（§7），Focused → Module → Fast。
8. **口径一致性验证**：构造「预算 1500、已花 1400」场景，确认 `check_budget.consumed_minor == summary.expense_minor`（逐分）。
