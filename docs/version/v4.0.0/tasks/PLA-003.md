## 2. Background

### 2.1 现行策略与记账直接冲突

`docs/version/v1.0.0/v4/privacy-governance.md` 现行目标策略（§1.1）：

| 级别 | 内容示例 | 目标策略 |
|---|---|---|
| L2 敏感 | 身份证号、详细住址门牌、**财务数据** | **不保存**：Extractor 输出后 Policy 新增 R9 直接丢弃并 trace 记 `privacy_drop` |

同时 §3「实施边界」注明：分级（R9）与 200 条写入策略**均未实现**。

**结论**：在不重裁这条策略的前提下落地账本表，等于**明知违规建表**。因此本任务必须在 PLA-004（账本落表）之前完成策略裁决（架构 §10.7「治理先行」）。

### 2.2 三处配套缺口

| # | 缺口 | 现状 |
|---|---|---|
| G2 | 无数据导出 / 删除（被遗忘权） | 全库无相应 API |
| G3 | 无记录级溯源 | 无 `source` / `source_ref` 约定 |
| — | 明细进 Prompt 无硬约束 | 现状记忆是「注入 content + type」；账目若沿用会把金额写进 prompt 快照 |

### 2.3 在 V4.0 中的位置

- **前置关系**：本任务是 PLA-004 的**策略前提**（§2.3 风险点 2）。
- **为后续留点**：账本域（PLA-004）及后续生活域通过**领域注册点**把自身的导出 / 删除 handler 挂进治理服务——本任务只交付机制与注册点，账本域的注册由 PLA-005 完成（治理 handler 需要账本写面，故随仓储落地，避免循环依赖）。
- **Preserve 边界**：记忆域的 R1~R8 与敏感分级 R9 **零改动**；本次重裁只作用于**新增的账本域**与治理服务。

## 3. Scope

### 3.1 In Scope

1. **策略重裁文档改写**（`docs/version/v1.0.0/v4/privacy-governance.md`）：
   - §1.1 分级表：财务数据由 **L2「不保存」→ L1「受控保存」**，条件为「本地存储 + 用户可控 + 可导出 / 删除 + **明细永不进 Prompt**」；
   - 新增一节「账本类数据的 Prompt 边界」：明细不进上下文，仅**聚合结果**（合计 / 分布 / 计数）可进；
   - 在文档头部登记**改写性质**：本文件属「策略结论更新」，非「史实改写」——这是 V4.0 **唯一允许修改历史文档**的例外（架构 §4.7）。
   - **同步登记至 `docs/current-system-architecture-baseline.md`**（§7 配置 / §6 数据架构处增治理策略）。
2. **治理服务**（`services/governance/`）：
   - `registry.py`——**领域注册点**：`register_domain(name, export_handler, delete_handler, provenance_reader)`；代码静态注册（沿 `ToolRegistry` 模式，不做热插拔）。
   - `export.py`——`export_user_data(user_id, format="json"|"csv") -> ExportBundle`：汇集各注册领域的用户数据；**只读**。
   - `delete.py`——`delete_user_data(user_id) -> DeletionReport`：逐领域调用删除 handler；**必须经各域仓储单一写面**，禁止直接 SQL 清表；返回逐域计数（供审计与用户确认）。
   - `provenance.py`——`record_provenance(domain, record_id, source, source_ref)` + `resolve_provenance(...)`：记录级来源登记与回溯。
   - `models.py`——`ExportBundle` / `DeletionReport` / `ProvenanceRef` 值对象（`frozen`，零 IO）。
3. **出口 API**（`api/v1/governance.py`）：
   - `GET  /life/export`（返回导出包；CSV 用 `StreamingResponse`）
   - `DELETE /life/data`（需显式确认参数；返回 `DeletionReport`）
   - 路由注册进 `api/v1/router.py`；`api` 层**零 `repositories` / langchain 依赖**（聚合落 services，对齐 V3.0 遗留 L3 的「不扩大」承诺）。
4. **用户身份解析**：复用既有身份机制，**不得信任客户端传入的 `user_id`**；导出 / 删除只作用于解析出的当前用户。
5. **Prompt 边界护栏**：`services/governance/prompt_guard.py`——提供 `assert_no_financial_detail(text)` 供账本相关链路在写入 prompt 前校验（PLA-007 / PLA-011 / PLA-013 调用）；本任务只交付护栏函数与其测试。

### 3.2 Out of Scope（明确禁止扩张）

- **不做密钥管理服务**：加密沿用既有 `.env` 机制，本任务不引入 KMS / 信封加密。
- **不做合规认证 / 等保 / 审计报告导出**。
- **不改 V4 记忆的 R1~R8 与敏感分级 R9**（Preserve）；记忆域的 `privacy_drop` 行为零改动。
- **不做数据脱敏展示层**（归 PLA-016 前端）。
- **不做数据保留期 / 归档 / 冷表**（账本无过期语义，架构 §4.5）。
- **不做鉴权体系**（裁决 0.7）；导出 / 删除只保证「作用于自己」。
- **不新增任何功能开关**（§0.9）：导出 / 删除端点**直接提供**。
- **不注册账本域**（本任务只交付注册点；账本域注册归 PLA-005）。

## 4. Technical Design Requirements

### 4.1 接口契约

```python
@dataclass(frozen=True, slots=True)
class DomainHandlers:
    name: str
    export: Callable[[str], Mapping[str, Any]]       # user_id -> 该域数据
    delete: Callable[[str], int]                      # user_id -> 删除行数
    provenance: Callable[[str, str], ProvenanceRef | None] | None = None


def register_domain(handlers: DomainHandlers) -> None: ...
def registered_domains() -> tuple[str, ...]: ...


@dataclass(frozen=True, slots=True)
class ExportBundle:
    user_id: str
    generated_at: datetime
    domains: Mapping[str, Mapping[str, Any]]          # domain -> payload
    format: str


@dataclass(frozen=True, slots=True)
class DeletionReport:
    user_id: str
    deleted_at: datetime
    per_domain: Mapping[str, int]                     # domain -> 删除行数
    total: int
    failed_domains: tuple[str, ...]


def export_user_data(user_id: str, *, fmt: Literal["json", "csv"] = "json",
                     now: datetime | None = None) -> ExportBundle: ...

def delete_user_data(user_id: str, *, now: datetime | None = None) -> DeletionReport: ...


@dataclass(frozen=True, slots=True)
class ProvenanceRef:
    domain: str
    record_id: str
    source: str          # "conversation" | "action" | "manual" | "world_event" | ...
    source_ref: str      # 原始消息 id / 行动 id / 录入标记


def record_provenance(ref: ProvenanceRef, *, now: datetime | None = None) -> None: ...
def resolve_provenance(domain: str, record_id: str) -> ProvenanceRef | None: ...
```

**Prompt 护栏**：

```python
def assert_no_financial_detail(text: str) -> str:
    """检测文本是否含金额形态（数字+币种/元/块 等）；命中则抛 FinancialDetailInPrompt。
    调用点：账本相关链路在把内容拼进 prompt 之前。"""
```

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | 财务数据 **L2 → L1**，条件是「本地 + 用户可控 + 可导出删除 + 不进 Prompt」 | 记账的必要性 > 原策略的保守默认；但必须以「不进 Prompt」这条硬约束换取放开保存 |
| D2 | **账目明细永不进 Prompt**，仅聚合结果可进 | 直接回应 `docs/household-inventory-review.md` 证伪的失败模式（LLM 会编造数字）；同时是最强的泄露面收敛手段 |
| D3 | 治理服务采用**领域注册点**，账本域注册归 PLA-005 | 治理先于账本落地，但导出 / 删除要覆盖账本——用注册点解耦，避免循环依赖 |
| D4 | 删除**必须经各域仓储单一写面**，禁止直接 SQL 清表 | 单一写面纪律（架构 §10.5）；直接清表会留下孤儿引用与绕过审计 |
| D5 | 删除返回**逐域计数 + 失败域清单**，不静默吞错 | 删除是用户权利，必须可验证；部分失败要显式暴露而非「看起来成功了」 |
| D6 | 导出为**只读**，且不写审计以外的任何状态 | 导出不应改变系统状态；保持可重复执行（幂等） |
| D7 | 溯源在**账本域自持字段**（`source` / `source_ref`），治理服务只提供统一读取面 | 避免为溯源单独建表（零新表承诺，架构 §10.8） |
| D8 | 无开关（裁决 9） | 用户权利面不应「可关闭」——要么提供，要么不提供 |

### 4.3 数据流

```text
导出：GET /life/export
   → 身份解析（不信任客户端 user_id）
   → export_user_data(user_id)
        → 遍历 registered_domains() → 各域 export handler
        → 组装 ExportBundle → JSON / CSV 流式返回

删除：DELETE /life/data(confirm=true)
   → 身份解析
   → delete_user_data(user_id)
        → 逐域 delete handler（各走自己仓储单一写面）
        → DeletionReport（含 failed_domains）
        → 审计记录（行数与失败域，不含数据内容）

溯源：账本条目写入时 → record_provenance(ProvenanceRef(...))
      查询时 → resolve_provenance(domain, record_id)
```

### 4.4 依赖

- 允许依赖：`repositories`（各域删除 handler 内部使用）、`core.settings`、`core.db`。
- **禁止**依赖：`app.chains`、`app.prompts`（护栏只做字符串判定，不组装 prompt）、`app.channels.*`。
- `api/v1/governance.py` **禁止** import `app.repositories` / `langchain`。
