## 2. Background

### 2.1 为什么聚合是「零幻觉」的关键环节

`docs/household-inventory-review.md` 记录了一次真实故障：库存里有 6 个鸡蛋，角色却说「没了，刚才那枚刚好用完」；还凭空出现了不存在的番茄汤。报告结论是——

> 「即使给了『以清单为准』的引导语，LLM 仍编造。说明需要**系统侧强制**，而非只依赖提示。」

把「鸡蛋」换成「钱」，这就是记账上线后的故障模式：**LLM 编造「你这个月花了 3000」（实际 2000）**。因此：

- 聚合必须是**纯 SQL**，数字不经过任何模型；
- 下游（日结 / 周报 / 预警）只能消费本任务的输出，不得自行生成数字。

### 2.2 现状

账目此前不存在（PLA-004 才有表）。系统内既有的聚合能力（`services/development/aggregate.py`、`services/observability/metrics_aggregator.py`）分别服务于**角色成长**与**系统指标**，与用户财务数据无关，**不可复用**。

### 2.3 在 V4.0 中的位置

- PLA-011（日结 / 周报）、PLA-012（预算）、PLA-013（超支预警）、PLA-014（洞察）、PLA-015（查询 API）**全部依赖本任务**；
- 是 `tasks.md` §4.2 交付顺序第 4 步的核心产出。

## 3. Scope

### 3.1 In Scope

1. **期间定义**（必须先冻结，否则聚合不可对账）：

   | 概念 | 定义 |
   |---|---|
   | 自然月 | 按**本地时区**（既有世界时间系统的时区设定）的 `[当月1日 00:00:00, 次月1日 00:00:00)` |
   | 自然周 | 周一 00:00 起（与 `daily_plans` 的周口径一致） |
   | 自定义区间 | `[since, until)` 左闭右开 |
   | 归属时间 | **恒用 `occurred_at`**（补记场景下 ≠ `created_at`） |

2. **聚合服务**（`services/ledger/query.py`）：

   ```python
   def summary(user_id: str, *, period: Period, group_by: GroupBy | None = None,
               now: datetime | None = None) -> LedgerSummary: ...
   def trend(user_id: str, *, periods: Sequence[Period], now=None) -> list[LedgerSummary]: ...
   def top_categories(user_id: str, *, period: Period, limit: int = 5, now=None) -> list[CategoryTotal]: ...
   def list_entries(user_id: str, *, period: Period | None = None, category_id=None,
                    account_id=None, direction=None, limit=None, offset=None) -> list[LedgerEntryView]: ...
   ```

3. **`LedgerSummary` 值对象**（`frozen`）：

   | 字段 | 语义 |
   |---|---|
   | `period` | 期间（含起止与本地时区标记） |
   | `expense_minor` / `income_minor` | 分方向合计（冲正**双向计入**后的净额） |
   | `net_minor` | `income_minor - expense_minor` |
   | `transfer_minor` | 转账合计（**不计入消费净额**） |
   | `by_category` | 类目分布（`category_id` → 净额；「未归类」聚合为 `None` 键） |
   | `by_account` | 账户分布 |
   | `entry_count` | 有效条目数（冲正对相抵后的计数口径须冻结） |
   | `reversal_count` | 期间内冲正条数（供审计与用户可见性） |
   | `compared_to_previous` | 与上一等长期间的对比（合计差值 / 百分比） |

4. **仓储聚合读面**（`repositories/ledger_repository.py` 扩展）：`sum_by_direction` / `sum_by_category` / `sum_by_account` / `count_entries` / `sum_range`——全部为 SQL 聚合，**只读**。
5. **出口格式化**：`format_minor(minor: int, currency: str) -> str`（如 `"32.50"`），供 API / 模板共用（避免各层各写一份格式化）。

### 3.2 Out of Scope（明确禁止扩张）

- **不做可视化 / 图表**（前端归 PLA-016）。
- **不做预测 / 预算推算**（预算归 PLA-012）；本任务只回答「已经花了多少」，不回答「会花多少」。
- **不做 LLM 摘要 / 自然语言解读**（文案渲染归 PLA-011，且用模板）。
- **不做任意 SQL / 查询 DSL**；不暴露 `group_by` 之外的自由维度。
- **不做导出**（归 PLA-003 治理面）。
- **不做缓存 / 物化视图 / 快照表**（零新表承诺，架构 §10.8）；实时聚合。
- **不新增任何功能开关**（§0.9）。
- 不改账本表结构与写面（PLA-004 / PLA-005 冻结）。

## 4. Technical Design Requirements

### 4.1 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | 聚合**全部下压到 SQL**，Python 侧只做装配 | 数据量增长后 Python 聚合会成为瓶颈；且 SQL 聚合是「数字来源单一」的最强保证 |
| D2 | **冲正双向计入**：原条目与冲正条目都参与求和，净额自然相抵 | 不做「排除已冲正条目」的特殊逻辑——那会让「曾经记错」这一事实从报表里消失，且需要额外查询 |
| D3 | `transfer`（转账）**不计入消费净额**，单独列示 | 转账不是消费；计入会让「花了多少」虚高 |
| D4 | 「未归类」以 `category_id IS NULL` 聚合为一个显式分桶 | 让「有多少笔没归类」可见，驱动用户补类目（也便于 PLA-008 评估归一率） |
| D5 | 期间**左闭右开** `[since, until)` | 避免相邻期间边界重复计数；月末 / 年末无需特判 |
| D6 | 期间按 `occurred_at` 且**按本地时区**切分 | 用户感知的「这个月」是本地月；UTC 切分会导致月初/月末错位 |
| D7 | 金额内部整数分，**出口才格式化** | 精度纪律（PLA-004 裁决 D1）；格式化统一走 `format_minor`，避免各层各写 |
| D8 | `compared_to_previous` 用**等长期间**而非「上一自然月」 | 自定义区间也能对比；自然月场景下二者等价 |
| D9 | 聚合服务**零 LLM、零写入** | 架构 §10.3（金额零 LLM）；零写入保证可被日结 / 预警 / API 反复调用 |
| D10 | 不缓存 | 首版数据量小；缓存会引入失效语义与「数字不一致」风险。**如需优化，先测量再决策**（不预先加开关，§0.9） |

### 4.2 数据流

```text
summary(user_id, period=本月, group_by=category)
   → 解析期间（本地时区 → UTC 边界）
   → ledger_repository.sum_by_direction(user_id, since, until)
   → ledger_repository.sum_by_category(user_id, since, until)
   → ledger_repository.sum_by_account(user_id, since, until)
   → ledger_repository.count_entries(...)
   → （可选）上一等长期间同法
   → 装配 LedgerSummary（整数分）
   ↓
消费方：
   PLA-011 日结模板       → format_minor(...)（数字只来自此处）
   PLA-012 预算检查       → expense_minor vs 预算
   PLA-013 超支预警       → by_category / expense_minor vs 阈值
   PLA-014 消费洞察       → 特征投影（不含金额明细入记忆）
   PLA-015 查询 API       → 直接序列化
```

- **禁止**依赖：`app.chains`（**零 LLM**）、`app.prompts`、`app.application.*`、`app.channels.*`。

## 5. Implementation Plan

1. **冻结期间与计数口径**（写进 `LedgerSummary` docstring）：自然月 / 自然周 / 自定义区间的边界规则、`entry_count` 在「原条目 + 冲正」下的计数方式（推荐：有效条目数 = 非冲正行数 − 被冲正行数）。
2. **仓储聚合方法**：`ledger_repository.py` 增 5 个只读聚合方法（`func.sum` / `func.count` + `group_by`）。
3. **聚合服务**：新增 `services/ledger/query.py`（四个公开函数 + `Period` / `GroupBy` / `CategoryTotal` / `LedgerEntryView` 值对象）。
4. **格式化工具**：`format_minor` 落 `services/ledger/format.py`（供 PLA-011 / PLA-013 / PLA-015 共用）。
5. **测试**（§7），Focused → Module → Fast；**逐分一致**用例是硬项。
6. **性能基线记录**（只记录不优化）：造 10k 条数据测 `summary` 耗时，写入 Detail 的观察记录。

## 8. Acceptance Criteria

| # | 判据 | 验证方式 |
|---|---|---|
| AC1 | **精确性**：手工计算与聚合结果逐分一致（含冲正 / 跨月 / 同日多笔 / 补记） | `test_summary_matches_manual_computation` 等 |
