## 2. Background

### 2.1 为什么预警必须晚于节律

`tasks.md` §2.3 风险点 5 与 §4.2 交付顺序都把预警排在日结之后，原因有二：

1. **复用依赖**：预警的投递出口、免打扰遵守、幂等键机制都由 PLA-011 建立——预警不重造投递，只复用。
2. **可信度依赖**：如果用户还没见过一次「正确的日结」，突然收到「你超支了」，第一反应是怀疑数字。**先让他看到日结准确，预警才有说服力。**

### 2.2 为什么预警也必须零 LLM

架构 §4.6 的「零幻觉」设计对预警同样适用：

> LLM 编造「鸡蛋没了」（实际 6 个）↔ LLM 编造「你这个月超支 500」（实际没超）

且预警比日结更敏感：**误报会让用户对整个账本失去信任**。因此告警文案必须模板渲染，数字只来自 PLA-006 聚合 / PLA-012 预算检查。

### 2.3 在 V4.0 中的位置

交付顺序第 6 步的收口；是 Phase 4（主动性与洞察）的最后一块功能（PLA-014 为 P2 可延后）。

## 3. Scope

### 3.1 In Scope

1. **告警类型与阈值判定**（`services/ledger/alert.py`）：

   | 类型 | 判定依据 | 触发条件（阈值在 Detail 冻结） |
   |---|---|---|
   | 类目月超支 | `BudgetCheck(scope="category", period="month")` | `consumed > limit` |
   | 总额月超支 | `BudgetCheck(scope="total", period="month")` | `consumed > limit` |
   | 类目接近上限 | 同上 | `ratio ≥ near_limit_ratio`（如 0.9）且未超 |
   | 日消费异常 | PLA-006 当日 `expense_minor` vs 近 N 日均值 | 超过均值 M 倍（如 3 倍）且绝对值大于下限（避免小额误报） |
   | 无预算但月支出突增 | PLA-006 本月 `expense_minor` vs 上月 | 增幅超 P%（如 50%）且绝对额超下限 |

   ```python
   @dataclass(frozen=True, slots=True)
   class AlertDraft:
       kind: str                  # "budget_over" | "budget_near" | "daily_spike" | "monthly_surge"
       scope_ref: str             # 预算 goal_id 或 类目 group_key（用于幂等键）
       title: str
       body: str                  # 模板渲染，数字来自聚合
       dedupe_key: str
       severity: str              # 首版单级："notice"
       observed: Mapping[str, int]  # 结构化观测值（金额，整数分）


   def evaluate_alerts(user_id: str, *, now: datetime) -> list[AlertDraft]: ...
   def should_alert(draft: AlertDraft, *, now: datetime) -> bool: ...
   def deliver_alert(draft: AlertDraft, *, now: datetime) -> SendResult: ...
   ```

2. **幂等去重**：`dedupe_key = f"ledger_alert:{kind}:{scope_ref}:{period_start.isoformat()}"`——**同预算 / 同类目 + 同周期只报一次**；落既有 `proactive_actions.dedupe_key`。
3. **触发注册**：在 `trigger_registry` 注册账本预警触发源（沿既有注册模式，**代码静态注册**）；由后台自治周期（PLA-018 统一后的 Agent Runtime 轨道）评估。
4. **投递**：复用 PLA-011 建立的出口链路（既有 `proactive_delivery` / Outbound Gateway）；遵守既有 quiet hours / cooldown / 每日上限。
5. **空/异常数据保护**：期间零条目、预算缺失、上月无数据 → **不触发**（`no_data` 不当作超支）。

### 3.2 Out of Scope（明确禁止扩张）

- **不改 `trigger_registry` 机制与 trigger 评估数学**（`services/autonomy*` 的既有判定）。
- **不新增通知渠道**（不复用飞书之外的通道；渠道扩展归 Channel Adapter）。
- **不做分级告警策略**（severity 首版只有 `notice` 单级；分级 + 升级机制属后续版本）。
- **不做预测式预警**（「按当前速度本月会花 3000」——属预测，架构 §11 未排期）。
- **不做 LLM 文案生成**（模板渲染；数字零 LLM）。
- **不做告警历史 / 告警中心**（无新表；`proactive_actions` 已提供基本轨迹）。
- **不做用户级告警开关 / 静音配置**（§0.9 禁止功能位；免打扰由既有 quiet hours 机制承担）。
- **不新增常驻循环**（挂既有维护步 / trigger）。
- **不新增表**（§10.8）；**不新增功能开关**（§0.9）。
- 不改账本域模块、预算模块、投递机制（PLA-006 / 011 / 012 冻结）。

## 4. Technical Design Requirements

### 4.1 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **同一预算 / 类目 + 同一周期只报一次** | 账目是流式产生的，「超支」状态会持续为真；不去重会变成持续骚扰。去重键含周期起点，跨周期自然重置 |
| D2 | **数字只来自 PLA-006 聚合与 PLA-012 预算检查**，不得自行求和 | 单一数字来源；避免「预警说超了、报表说没超」 |
| D3 | `alert.py` **不得 import 任何 LLM 组件** | 零幻觉硬约束（架构 §4.6）；用静态断言固定 |
| D4 | 复用 PLA-011 的**投递出口与免打扰机制**，不重造 | 架构 §2.3 第 4 条；两处独立实现会造成行为不一致 |
| D5 | **`no_data` 不视为超支**；零条目 / 缺预算 / 上月无数据 → 不触发 | 误报比漏报更伤信任；数据不足时选择沉默 |
| D6 | 日消费异常需**双条件**：相对倍数 + 绝对下限 | 只用倍数会让「昨天花 3 块今天花 10 块」触发（3 倍但无关紧要）；加绝对下限过滤小额噪音 |
| D7 | 首版**单级告警**，不做 severity 升级 | 收敛复杂度；分级需要「用户对级别的感知训练」，属成熟期能力 |
| D8 | 免打扰窗口内**只跳过不补发** | 与 PLA-011 同口径，避免补发洪峰 |
| D9 | 触发评估挂**既有后台周期**，不新增常驻循环 | 架构 §2.3 第 4 条 |
| D10 | 无开关（§0.9） | 预警交付即生效；阈值是参数，不是开关 |

### 4.2 数据流

```text
后台自治周期（PLA-018 统一后的 Agent Runtime 轨道）
   → trigger_registry 评估账本预警触发源
   → evaluate_alerts(user_id, now)
        读取 PLA-012 check_all_budgets → 预算类告警
        读取 PLA-006 summary（当日 / 当月 / 上月）→ 异常类告警
        → list[AlertDraft]（含 dedupe_key）
   → should_alert(draft, now)
        未到条件 / 已推送（dedupe_key 命中）/ 免打扰 → 跳过
   → deliver_alert(draft, now)
        → 既有 proactive_delivery → Outbound Gateway → ChannelAdapter.send
        → dedupe_key 落 proactive_actions
        → SendResult（失败不抛）
```

## 5. Implementation Plan

1. **模板**：`prompts/` 增各类告警模板（占位符只接受结构化金额）；生成 golden 快照。
2. **判定逻辑**：`services/ledger/alert.py`——`evaluate_alerts` / `should_alert` / `deliver_alert` + `AlertDraft`。
3. **阈值参数**：把 near-limit ratio / 倍数 / 百分比 / 绝对下限等阈值落 `ledger.py` 设置（**参数类，非开关**）；取值与默认在 Detail 冻结。
4. **触发注册**：`trigger_registry` 注册账本预警源（代码静态注册）。
5. **投递接线**：复用 PLA-011 的出口与 `dedupe_key` 落 `proactive_actions`。
6. **测试**（§7），Focused → Module → Fast。
7. **手工验证**：在真实链路制造一次「预算 100、支出 120」场景，确认只收到一次告警且数字准确。
