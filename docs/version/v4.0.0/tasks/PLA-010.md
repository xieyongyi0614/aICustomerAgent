## 2. Background

### 2.1 为什么「可改」是账本的生命线

账本是**事实记录**。一旦用户无法修改，错误就会被永久固化：

- 用户说错金额（「20」说成「200」）→ 无法纠正 → 用户不再信任账目；
- 系统抽取出错（把「两个人吃了200」抽成 200 而不是 100/人）→ 无法订正 → 用户放弃使用；
- 记错类目 → 聚合分布失真 → 「这个月餐饮多少」的答案失去意义。

因此**「可订正」不是锦上添花，是账本可信度的组成部分**。这也是架构把「PLA-010 必须先于 PLA-011 主动推送」列为风险点 5 的原因：先推送一个不能改的账本，等于把错误直接摆到用户面前。

### 2.2 为什么订正必须走「冲正」而不是 UPDATE

| 手段 | 问题 |
|---|---|
| 直接 `UPDATE amount_minor` | 破坏 append-only（PLA-004 裁决 D3）；「曾经记错」这一事实消失，无法审计 |
| 直接 `DELETE` 条目 | 历史凭空消失；与治理删除（PLA-003）的语义混淆 |
| **冲正 + 新增** | 保留完整轨迹：原条目 + 冲正条目（+ 新条目）。净额自然正确，审计链完整 |

### 2.3 现状

- PLA-005 已交付 `reverse_entry`（生成反向条目，原行不动）与幂等；
- PLA-009 已把记账接入 Tool 五段的**确认段**——本任务是确认段的**策略与交互实现**；
- 系统内既有的跨轮待处理机制：`scene_state.pending_action`（跨轮延续）+ `action_schedules`（定时）——本任务**复用**，不新建表。

## 3. Scope

### 3.1 In Scope

1. **澄清触发条件**（`services/ledger/confirmation.py::should_confirm(...)`）：

   | 条件 | 触发来源 | 澄清内容 |
   |---|---|---|
   | 金额缺失（`missing_fields` 含 `amount_value`） | PLA-007 | 「这笔记多少？」 |
   | 置信度 < `ledger_extraction_min_confidence` | PLA-007 | 「你是说花了 20 块吗？」（带候选值确认） |
   | 同一消息抽出多个可能金额 / 方向歧义 | PLA-007 / PLA-009 | 「是支出还是收入？」 |
   | 金额 ≥ `ledger_confirm_threshold_amount`（默认 100 元） | PLA-009 确认段 | 「确认记一笔 320 元的支出？」 |
   | 类目无法归一（兜底命中） | PLA-008 | 「这笔记到哪一类？」（给出 top-3 候选） |

   ```python
   @dataclass(frozen=True, slots=True)
   class ConfirmationRequest:
       reason: str                       # "missing_amount" | "low_confidence" | "amount_over_threshold" | "category_ambiguous" | "direction_ambiguous"
       question: str                     # 面向用户的问题文案（模板渲染）
       candidates: tuple[CandidateOption, ...]
       pending_key: str                  # 幂等键（见 D1）
       expires_at: datetime


   def should_confirm(candidate: LedgerCandidate, *, settings, now: datetime) -> ConfirmationRequest | None: ...
   ```

2. **待确认登记**（**零新表**，复用既有承载）：
   - 落 `scene_state.pending_action`（跨轮延续的既有机制）承载待确认项；
   - 超时用 `action_schedules` 承载（到期未确认即失效）；
   - `pending_key = hash(source_ref + reason)`（确定性，供去重）。
3. **对话层挂接**：
   - post_process **新步骤**：处理抽取候选 → 判断是否需确认 → 是则登记 + 生成澄清问句（模板渲染）→ 由既有回复链路产出；
   - **回话解析**：用户对澄清的回复**复用 PLA-007 的抽取链**（`extract_ledger`），不另建解析逻辑；
   - 澄清只针对**当前待确认项**，不引入通用多轮对话状态机。
4. **订正服务**（`services/ledger/correction.py`）：

   | 用户意图 | 实现 | 语义 |
   |---|---|---|
   | 修改金额 / 类目 / 时间 | **冲正原条目 + 新增条目** | 两条记录都在；净额正确 |
   | 撤销（删除） | **冲正原条目** | 原行保留；净额归零 |
   | 撤销冲正 | **对冲正条目再冲正** | 净额恢复为原值（口径在 Detail 冻结并一致实现） |

   ```python
   @dataclass(frozen=True, slots=True)
   class CorrectionOutcome:
       original_entry_id: str
       reversal_entry_id: str
       new_entry_id: str | None          # 修改场景才有
       net_effect_minor: int


   def revise_entry(entry_id: str, changes: Mapping[str, Any], *, reason: str,
                    idempotency_key: str) -> CorrectionOutcome: ...
   def cancel_entry(entry_id: str, *, reason: str, idempotency_key: str) -> CorrectionOutcome: ...
   ```
5. **幂等与审计**：确认 / 订正 / 冲正**全部落审计**；所有操作带 `idempotency_key`。
6. **超时语义**：超时未确认 → **不产生任何账目**（候选失效，仅留审计痕迹）。

### 3.2 Out of Scope（明确禁止扩张）

- **不做图形化订正 UI**（前端归 PLA-016；本任务的订正入口是对话与 PLA-015 的 API）。
- **不做批量导入 / 批量订正**（架构 Backlog）。
- **不改 `scene_state` / `pending_action` 机制本体**（只**复用**承载；不扩字段、不改语义）。
- **不做通用多轮对话状态机**：澄清只针对单次待确认项；不做「连续追问 3 轮补全所有字段」（首版超时即失效）。
- **不做确认优先级 / 批处理**（多笔待确认的排序策略，首版按时间 FIFO）。
- **不做订正的原因分类统计**（后续按需）。
- **不新增任何表**（零新表承诺，架构 §10.8）；**不新增功能开关**（§0.9）。
- 不改 PLA-005 `reverse_entry` 的既有语义（本任务在其上做编排）。

## 4. Technical Design Requirements

### 4.1 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **同一 `source_ref` 只澄清一次**（`pending_key` 去重） | 重复消息（飞书重投 / 用户连点）不能触发重复回问；一次记账最多问一次 |
| D2 | 超时未确认 → **不产生账目**，仅留审计 | 「默认记下」会让用户莫名其妙多出账目；账本宁可缺一条也不能错一条 |
| D3 | 订正 = **冲正 + 新增**（两条记录），不 UPDATE | append-only 纪律；保留「曾经记错」的事实，审计链完整 |
| D4 | 待确认登记**复用 `scene_state.pending_action` + `action_schedules`**，不建表 | 零新表承诺；这两个机制本就是「跨轮待处理」与「定时」的既有承载 |
| D5 | 回话解析**复用 PLA-007 抽取链** | 避免第二套自然语言解析逻辑；也让「澄清回答」与「首次表达」走同一套 schema 与证据校验 |
| D6 | 确认问句由**模板渲染**（`prompts/`），不用 LLM 现场编 | 问句要稳定可测（golden 快照）；且问句含**金额数字**——按架构 §4.6，数字只能来自结构化字段 |
| D7 | 澄清**只针对单次待确认项**，不做多轮补全 | 首版收敛复杂度；超时即失效比「追问三轮」体验更诚实 |
| D8 | 所有确认 / 订正 / 冲正操作**必须带 `idempotency_key`** | 与 PLA-005 的幂等面一致；重复指令不产生重复记录 |
| D9 | `ledger_confirm_threshold_amount` 是**阈值参数**（默认 100 元），不是开关 | 裁决 9：只用参数控制行为强度，不用开关控制功能存在 |

### 4.2 数据流

```text
【确认】
PLA-007 候选 → should_confirm(candidate, settings, now)
    None      → 直接交 PLA-009 入账
    Request   → post_process 步骤：
                   ① 以 pending_key 查重 → 已存在则跳过（D1）
                   ② 登记待确认（scene_state.pending_action）+ 到期（action_schedules）
                   ③ 模板渲染问句 → 交回复链路
用户回答 → extract_ledger(回答)                       ← 复用 PLA-007
   → 补齐字段 → 交 PLA-009 入账 → 清除待确认登记
超时（action_schedules 到期）→ 清除登记，不产生账目（D2）

【订正】
用户：「刚才那笔改成 50」
   → 意图检测（PLA-009）命中 revise
   → ledger.revise 能力 → correction.revise_entry(entry_id, changes, reason, key)
        → reverse_entry(原) + record_entry(新)         ← 均为新增行
        → CorrectionOutcome(net_effect_minor)
   → 目账净额正确；原行逐字节未变

【撤销】
用户：「刚才那笔记错了，撤掉」
   → correction.cancel_entry(entry_id, reason, key) → reverse_entry(原) → 净额归零
```

### 4.3 依赖

- 允许依赖：`app.services.ledger.*`（service / query / extraction 链的**调用面**）、`app.repositories`（scene_state / action_schedules 既有仓储）、`app.prompts`（模板）、`app.core.settings`。
- **禁止**依赖：`app.chains.answer_chain`（回复生成归既有链路）、`app.channels.<impl>`、`app.api`。
