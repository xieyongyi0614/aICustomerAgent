## 2. Background

### 2.1 现状：挂起一旦发生就无人收敛

| 事实 | 证据 |
|---|---|
| 澄清载体有 `due_at` 字段（`PLN-003` 写入） | `apps/backend/app/core/db/autonomy.py:165-182`（`due_at` 列）；`PLN-003` §4.1.1（`due_at = now + plan_clarify_timeout_hours`，`0` 时用哨兵 `now + plan_ttl_hours`） |
| 载体已有终态操作 | `apps/backend/app/repositories/trigger_registry_repository.py:224`（`complete` → `done`）、`:256`（`force_cancelled` → `cancelled`）、`:308`（`cancel`） |
| 维护步的既有写法（可对齐） | `apps/backend/app/application/life_loop.py:594`（`_run_maintenance`）；`:671-683`（`trigger_reconcile` 块：调 `recover_stale` `:673-677`，随后 `_record_maintenance_run("trigger_reconcile", ...)` `:678`） |
| 维护循环由 tick 驱动 | `life_loop.py:65`（`run_life_loop_worker`）、`:68`（`_tick`）、`:69`/`:78`（`run_life_loop_tick`）、`:83`/`:84`/`:103`（tick 内维护调度） |
| **审批超时是另一件事**（不得混入） | 基线 §8.6（`docs/current-system-architecture-baseline.md:503`）：「闸门 ON 且长期无人裁决 → 超时策略（永久等待 / 自动批准 / 自动驳回）为**待决策项**，当前未实现」 |
| 无答复重新提案的既有能力 | `PLN-002` §4.1.2（`_build_messages` 在 `clarification=None` 时逐字节等于基线）→ 「无答复继续」即等价于基线提案路径 |
| 轮次硬闸（防再次追问） | `PLN-001` §4.1.2（`round < plan_clarify_max_rounds`）——超时 `proceed` 时 `round` 已达上限，闸门自然挡住再次澄清 |

### 2.2 为什么必须做

1. **没有兜底，澄清就是新的「永久悬空」源**：审批闸的悬空风险已被记录为待决策项（基线 §8.6）；若澄清闸不同期交付兜底，等于**叠加**一个同类风险（`docs/agent-evolution-plan-2026-10.md` §3.5 H-P3，且 `PLN-004` 的 `SKIP_LEXICON` 明确把「随便」留给了超时来处理）。
2. **必须显式策略而非隐式行为**：`cancel`（保守：计划停住，等用户主动回来）与 `proceed`（激进：按最合理假定继续）对用户的影响完全不同——必须由配置显式表达，默认取保守（D2）。
3. **必须与维护框架的既有隔离语义一致**：`_run_maintenance` 是多个维护步的容器；澄清超时只是其中一个块，失败不得影响其它块（D4）。

### 2.3 在本版本中的位置

P1 收尾任务：与 `PLN-003`（载体）/ `PLN-004`（恢复）共同构成完整的挂起生命周期（登记 → 答复恢复 / 到期收敛）。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 超时裁决契约（`expire_due_clarifications`）

| 项 | 契约 |
|---|---|
| 签名 | `expire_due_clarifications(now: datetime \| None = None) -> dict`（返回 `{"scanned": int, "cancelled": int, "proceeded": int, "skipped": int}`） |
| 早退 | `plan_clarify_timeout_hours <= 0` → **立即返回全零且不查库**（AC1） |
| 扫描条件 | 行 `payload.kind == "plan_clarification"` ∧ `status ∈ ACTIVE_STATUSES`（`trigger_registry_repository.py:27`）∧ `due_at <= now` |
| 策略 `cancel`（默认） | 调 `cancel_pending(plan_id, reason="clarify_timeout")`（`PLN-003` §4.1.3）→ 行 `cancelled`；**计划保持 `validated`**（既不激活也不驳回）；trace `plan_clarify_timeout`（`action="cancel"`） |
| 策略 `proceed` | ① 调 `mark_answered(plan_id, answers={})`（→ 行 `done`，标明已收敛）；② 以 `clarification=None` 调用重新提案（`PLN-002`）→ 走 `PLN-001` 闸（`round` 已在上限 → `reason="round_exhausted"`，不会再次澄清）→ 按 `plan_require_approval` 决定 `validated → active` 或等审批；trace `plan_clarify_timeout`（`action="proceed"`） |
| 幂等 | 收敛后行进入终态（`done` / `cancelled`）→ 后续 tick 不满足 `status ∈ ACTIVE_STATUSES` → 不再处理 |
| 单次上限 | 单 tick 最多处理 `CLARIFY_TIMEOUT_BATCH_LIMIT = 50` 行（模块常量），超出留待下一 tick（防一次扫全库） |
| 失败语义 | 单行失败 → `logger.warning` + 跳过该行（继续处理其余行）；整体不抛 |
| 未到期 | `due_at > now` 的行**不触碰**（AC4） |

#### 4.1.2 维护块接线契约（`life_loop._run_maintenance`）

| 项 | 契约 |
|---|---|
| 位置 | `:594`（`_run_maintenance`）内新增独立块，对齐 `:671-683` 的既有形态（块内调用 + `_record_maintenance_run(...)` `:678`） |
| 记录名 | `"plan_clarify_timeout"` |
| 隔离 | 块内自身 try/except；异常只记该块失败，**不影响**其它维护步（AC5） |
| 触发频率 | 沿用既有维护循环节奏（不新增独立调度） |
| 零动作保证 | `timeout_hours <= 0` → 块内立即返回（不查库） |

#### 4.1.3 新设置字段（`app/core/settings/plan.py`，追加于 `:43` 之后）

| 字段 | 类型 | 默认 | 语义 | 校验 |
|---|---|---|---|---|
| `plan_clarify_timeout_hours` | `float` | `0` | 澄清挂起超时（小时）；`0` = **不启用**（挂起可永久等待，由用户主动回来答复） | `ge=0`、`le=168`（1 周上限） |
| `plan_clarify_timeout_action` | `str` | `"cancel"` | 到期策略：`cancel`（取消澄清、计划停住）/ `proceed`（无答复继续提案） | 仅接受 `{"cancel","proceed"}`；非法 → 回落 `cancel` + 启动期 warning（保守优先） |

> `validate_plan_config`（`:45-73`）新增交叉校验：`plan_clarify_timeout_hours > 0` 且 `plan_require_clarification is False` → 启动期 warning（写了一堆无用的超时配置）。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **`timeout_hours == 0` 即关闭且零动作** | 关闭态必须真正零开销（不查库）；也让「合入即零行为变化」成立（§4.1.1 早退） |
| D2 | **默认策略 `cancel`（保守）** | `proceed` 会让角色基于**未获确认的假定**继续规划——用户回来看到「已经按猜的做了」比「还在等你」更糟；默认必须偏保守（与 `MEV-001` D6 / `MEV-006` 的「非法回落禁用」同源） |
| D3 | **`proceed` 复用「无澄清提案」路径** | `PLN-002` §4.1.2 保证 `clarification=None` 时 prompt 与基线逐字节一致——即「按现状继续」无需新逻辑 |
| D4 | **挂既有维护步，且块级隔离** | 维护框架已有多块隔离语义（`_run_maintenance` `:594`）；新增常驻 worker 属架构增量且无必要 |
| D5 | **与审批超时严格分离** | 基线 §8.6（`:503`）已把审批超时登记为**待决策项**；本任务只解决澄清闸的悬空（§3.2 第 1 条） |
| D6 | **批次上限 50 行** | 防单 tick 扫全库；与 `_CLAIM_BATCH_LIMIT`（`job_worker.py:38`，默认 20）同源的成本护栏思想 |
| D7 | **`proceed` 也要收尾行（→ `done`）** | 否则行一直 `pending`，会在下一 tick 被重复处理（幂等破坏） |
| D8 | **单行失败跳过而非中止** | 一行脏数据不应让整批澄清永久悬空（记忆域式隔离） |
| D9 | **策略非法回落 `cancel`** | 与 `MEV-001` D6 一致：配置错误必须偏保守，不得产生未预期的自动推进 |
| D10 | **本任务零迁移** | 载体与字段已由 `PLN-003` 提供 |

### 4.3 数据流

```text
life_loop.run_life_loop_tick（:69 / :78）→ _run_maintenance（:594）
   ★ 新增块 "plan_clarify_timeout"（对齐 :671-683 形态）
       clarify.expire_due_clarifications(now)
         ① timeout_hours <= 0 → 返回全零（不查库，D1）
         ② 扫 payload.kind=="plan_clarification" ∧ status ∈ ACTIVE ∧ due_at <= now（≤ 50 行）
         ③ 按 action：
              cancel  → cancel_pending(plan_id) → 行 cancelled；计划保持 validated；trace
              proceed → mark_answered(plan_id) → 行 done；propose_plan(clarification=None)
                        → PLN-001 闸（round 已达上限 → round_exhausted，不再澄清）
                        → 按 plan_require_approval 决定 validated→active 或等审批；trace
         ④ 单行异常 → warning + 跳过；整块异常 → 记录该块失败（不影响其它维护步）
       _record_maintenance_run("plan_clarify_timeout", ...)（:678 既有形态）

红线：0 时零动作；默认保守；与审批超时解耦；幂等；零迁移
```
