## 2. Background

### 2.1 现状：检索链无 LLM 参与，排序完全依赖确定性打分

| 事实 | 证据 |
|---|---|
| 检索入口与权重全部自 settings 读取，无硬编码 | `apps/backend/app/services/memory/retriever.py:265-271`（`retrieve(user_id, query, character_id="asuna", top_k=None, trace=None) -> RankedMemories`）；权重读取 `:247-249`（semantic/structured/affinity）、`:252`（temporal boost）、`:309` / `:311`（penalty） |
| 打分构成：结构化分 = (recency + importance + salience) / 3；亲和分来自查询类型命中 | `:98`（`_recency`，`0.5 ** (days / memory_recency_half_life_days)` `:103`）、`:106`（`_structured_score`，`:110`）、`:113`（`_affinity_score`）、`:75-80`（`_detect_query_types` 消费 `memory_types.TYPE_AFFINITY_KEYWORDS`） |
| 候选池两路：结构路 `list_active` + 向量 ANN；向量缺失即降级 | `:349`（`_candidate_pool`，调用 `:352-354`）、`:334`（`_vector_recall`，调用 `:338-343`）；降级三值 `MODE_HYBRID="hybrid"` `:30` / `MODE_STRUCTURED="structured"` `:31` / `MODE_DEGRADED="degraded"` `:32` |
| 已有降级-不阻断先例（本任务必须沿用同一形态） | 向量路 try/except + warning `:344-346`；候选池 try/except `:355-357` |
| 命中即加固、并落 trace | `record_reinforce` 调用 `:322`；trace 调用 `:323-330`；`_trace` 定义 `:376-380`；步名 `STEP_NAME = "memory_retrieve_v2"` `:28` |
| 返回类型是 dataclass，字段固定 | `RankedMemory`（memory / semantic / structured / affinity / penalty / score / reason）`:55-63`；`RankedMemories`（items / mode）`:66-72`，`.memories()` `:71` |
| 检索链**无任何 LLM 调用**；lite profile 在记忆域已有先例（评估灰区兜底） | `apps/backend/app/services/memory/evaluator.py:47`（`_LLM_LITE_PROFILE_ID="lite"`）、`:79-81`（`_resolve_llm` → `get_llm("lite")`） |
| 结构化输出链有统一入口 | `apps/backend/app/chains/structured.py:66-68`（`build_structured_chain(messages, schema, llm=None)`）；参考链 `apps/backend/app/chains/extractor_chain.py:7` / `:30` |

### 2.2 为什么必须做

1. **词法/结构打分的召回精度上限是硬的**：`affinity` 依赖 `TYPE_AFFINITY_KEYWORDS` 的关键词命中（`:113` → `types.py:30-35`，当前仅 4 键），而 `semantic`（cosine）在 `embedding_model` 未配置时整条降级（`core/settings/memory.py:48` 默认空串）——此时排序只剩结构化分，与「查询意图」几乎无关。
2. **它是 M2/M3 的地基**：`MEV-006` / `MEV-007` 会显著增加条目量（情景 + 语义），若无重排，条目越多越容易「淹没」高相关记忆；`MEV-008` 的分层配额也需要一个可靠的排序依据。
3. **成本可控且必须可关**：一次 lite 调用 + 候选数阈值 + 失败回落，使「打开重排」成为纯收益型选择（`docs/agent-evolution-plan-2026-10.md` §2.5 R-M2 的缓解设计）。

### 2.3 在本版本中的位置

M1 第 1 个任务，`MEV-004`（可观测与离线门槛）依赖它产出「重排前后名次」数据；`MEV-008`（分层配额）依赖它提供稳定排序。它不改 schema、不改写面，是 M1 的最小前置。

## 3. Scope

### 3.1 In Scope

1. 新增链 `app/chains/memory_rerank_chain.py`：结构化输出「候选 id → 相关性分（0~1）」，经 `build_structured_chain` 构建，模型默认 `lite` profile。
2. 新增 prompt `app/prompts/memory_rerank.py`（对齐 `app/prompts/extractor.py` 先例的文件形态：模块级常量 prompt 文本 + schema 说明）。
3. `RankedMemory` 增 `rerank_score: float | None = None`；`RankedMemories` 增 `rerank_mode: str = "off"`（**带默认值**，保证既有构造调用不破）。
4. `retrieve()` 内挂接重排：在 `_filter_reasons` 应用（`:306`）与 penalty 计算（`:309` / `:311`）**之后**、`record_reinforce`（`:322`）与 trace（`:323-330`）**之前**。
5. 排序键分支：`off` → 按既有 `score` 降序（逐字节不变）；`lite` → 按 `rerank_score` 降序，`rerank_score is None` 的候选排在重排候选**之后**并按 `score` 降序（保序回落，**不丢条目**）。
6. 三个新设置字段（`app/core/settings/memory.py`）。
7. 失败与降级：LLM 超时/异常/解析失败 → `rerank_mode="off"` 语义 + `logger.warning` + trace，**不抛**。

### 3.2 Out of Scope（明确禁止扩张）

| # | 禁止项 | 理由 |

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 链契约（新增 `app/chains/memory_rerank_chain.py`）

| 符号 | 契约 |
|---|---|
| `MemoryRerankItem` | Pydantic：`id: str`（记忆 id，必须在候选集合内）、`score: float`（`ge=0.0, le=1.0`，相关性）、`reason: str = ""`（可选，仅调试用，不注入 prompt） |
| `MemoryRerankResult` | Pydantic：`items: list[MemoryRerankItem]` |
| `build_memory_rerank_chain(llm=None) -> Runnable` | 经 `app/chains/structured.py::build_structured_chain`（`:66-68`）构建；`llm` 缺省取 `core/llm_factory.get_llm("lite")`（`:37`） |
| `async rerank_memories(query: str, candidates: list[tuple[str, str]], llm=None) -> list[MemoryRerankItem]` | `candidates` = `(memory_id, content)`；返回**至多** len(candidates) 条；**未知 id 丢弃**；**缺项不补齐**（由调用方回落）；异常一律**向上抛给调用方**（由 `retriever` 统一捕获降级），**链内不吞异常** |
| 模块常量 | `RERANK_CONTENT_MAX_CHARS = 200`（单条内容截断，纯 prompt 防爆，**不是策略位**，故用模块常量而非设置） |

**prompt 契约**（`app/prompts/memory_rerank.py`）：system 段声明「按用户查询与记忆内容的相关性打分，0~1；只返回给定 id；不得新增 id」；user 段注入 `query` + 若干 `(id, content)` 行；**不得**注入记忆的 `salience` / `confidence` / `status` 等机制字段（对齐 D5 口径精神）。

#### 4.1.2 返回类型字段扩展

| 类型 | 新增字段 | 类型 | 缺省 | 语义 |
|---|---|---|---|---|
| `RankedMemory` | `rerank_score` | `float \| None` | `None` | 该候选的 LLM 相关性分；`off` 或未参与重排时为 `None` |
| `RankedMemories` | `rerank_mode` | `str` | `"off"` | `"off"` / `"lite"`；报告本次是否实际发生重排 |

> **兼容纪律**：两个字段**必须带默认值**；`RankedMemories` 的既有构造调用与 `.memories()`（`:71`）语义不变。既有消费方（`services/conversation/context.py:253`、`services/planning/context.py:608`）**零改动**。

#### 4.1.3 挂接点与排序契约（`app/services/memory/retriever.py`）

| 项 | 契约 |
|---|---|
| 挂接位置 | `_filter_reasons` 应用 `:306` 与 penalty `:309` / `:311` **之后**；`record_reinforce` `:322` 与 trace `:323-330` **之前**（保证 trace 记录的是最终名次） |
| 参与集合 | 按既有 `score` 降序取前 `memory_rerank_top_k` 条（默认 20，与 `memory_vector_recall_k`（`:62`，默认 20）同量级）；**其余候选不参与** |
| 触发下限 | 参与候选数 `< memory_rerank_min_candidates`（默认 3）→ **不发起 LLM 调用**，`rerank_mode="off"` |
| `off` 排序 | 按 `score` 降序（**与基线逐字节一致**） |
| `lite` 排序 | 参与候选按 `rerank_score` 降序；未参与 / `rerank_score is None` 的候选整体排在**其后**，内部按 `score` 降序 |
| 同分稳定性 | 同 `rerank_score`（或同 `score`）时按 `memory.id` 升序，保证**确定性**（可测） |
| 加固与 trace | `record_reinforce` 与 trace 的**触发集合与前次相同**（仍按最终次序取前 `top_k`），不因重排新增/减少加固次数 |
| 失败语义 | 链异常 / 超时 / 解析失败 → 结果等价于 `off`（全部 `rerank_score=None`）、`rerank_mode="off"`、`logger.warning` + trace 落一条降级记录；**函数不抛** |

#### 4.1.4 新设置字段（`app/core/settings/memory.py`，类 `MemorySettings` `:8`）

| 字段 | 类型 | 默认 | 语义 | 校验 |
|---|---|---|---|---|
| `memory_rerank_mode` | `str` | `"off"` | `off`（不重排）/ `lite`（lite profile 重排） | 仅接受 `{"off","lite"}`；非法值 → **回落 `off` + 启动期 warning**（不回落到 `lite`，避免误开成本） |
| `memory_rerank_top_k` | `int` | `20` | 参与重排的候选数上限 | `ge=1`、`le=memory_candidate_pool_limit`（`:25`） |
| `memory_rerank_min_candidates` | `int` | `3` | 触发重排的最小候选数 | `ge=1`；`> memory_rerank_top_k` 时视为不触发（`off`） |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **重排不改写 `score`**，只新增 `rerank_score` 与排序键分支 | `score` 是 M1 其他任务（`MEV-004` 名次对比、`MEV-008` 配额基线）的对照量；改写会让「重排前」不可复现 |
| D2 | **只对 top-N 重排，未参与者排在重排结果之后** | 全量重排会随条目增长线性抬升 token 成本（R-M2）；尾部候选在结构分意义下本就低相关，保序回落即可 |
| D3 | **未知 id 丢弃 + 缺项回落 `score`**，而非「让 LLM 补齐」 | 缺项补齐等于让模型**发明**一条相关性判断；丢弃未知 id 是 fail-closed（对齐仓库「未知类型 fail-closed」惯例） |
| D4 | **不给 `mode` 加值**，重排状态走新字段 `rerank_mode` | `mode` 承载召回路径语义，被降级判定消费（`:282` / `:286` / `:294`）；混入重排会污染既有语义 |
| D5 | **`memory_rerank_mode` 取值类而非布尔**（不叫 `memory_rerank_enabled`） | V4.0.0 裁决 9 禁止 `*_enabled`；取值类还能承载未来第三种模式而无需改字段类型 |
| D6 | **非法 mode 值回落 `off`**（而不是回落 `lite`） | 配置错误必须偏保守：默认关，误配不得产生未预期的 LLM 成本 |
| D7 | **链内不吞异常，由 `retriever` 统一降级** | 与既有降级先例一致（`:344-346` / `:355-357`）：降级点集中在一处，便于 trace 与测试 |
| D8 | **模型档位用 `lite`** | 与记忆域既有 LLM 用法同档（`evaluator.py:47` / `:79-81`）；重排是「判断相关性」，非生成，lite 足够 |
| D9 | **同分按 `memory.id` 升序** | 检索结果必须**确定性**（既有排序已确定）；随机 tie-break 会让测试不可复现 |
| D10 | **加固集合不因重排改变** | `record_reinforce`（`:322`）是 salience 增长的唯一来源，改变触发集合等于间接收改生命周期数学（属 M2/既有 Preserve 面） |

### 4.3 数据流

```text
对话前台 services/conversation/context.py:253  ｜  规划后台 services/planning/context.py:608
   └─ 同一入口 memory_retriever.retrieve(user_id, query, character_id, top_k, trace)   ← 签名不变
        ▼
   retriever.py::retrieve（:265）
     ① 结构路候选池 _candidate_pool（:349） ② 向量路 _vector_recall（:334，可降级）
     ③ 去 hypothetical（:280 / :292） ④ penalty（:309 / :311） ⑤ 冷却过滤（:306）
        ▼ ★ MEV-001 新增挂接点（⑤ 之后、record_reinforce 之前）
     _maybe_rerank(query, ranked, settings)
       ├─ memory_rerank_mode != "lite"                        → 直接返回 rerank_mode="off"（零行为变化）
       ├─ 候选数 < memory_rerank_min_candidates                → 同上（不发起调用）
       └─ 取前 memory_rerank_top_k → chains/memory_rerank_chain.py::rerank_memories(...)
            ├─ 成功 → 有效 id 映射 rerank_score；未知 id 丢弃
            └─ 异常/超时 → warning + trace 降级记录 → 等价 off（不抛）
        ▼
   排序：off 按 score ｜ lite 按 rerank_score（无分者随后按 score）
        ▼
   record_reinforce（:322）+ trace（:323-330）→ RankedMemories(items, mode, rerank_mode)

降级红线：任何新增分支异常一律回落 off 语义，绝不阻断对话 / 规划（对齐 :344-346 先例）
```
