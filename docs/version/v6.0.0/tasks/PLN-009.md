### 2.2 为什么必须做

1. **「能力已实现但无人能用」是当前最大的产品落差**：`plan_require_approval`（`apps/backend/app/core/settings/plan.py:29`）默认关闭的原因之一是「没有 UI 就无法批」；没有界面的闸门等于强制永久关闭（基线 §8.6 `:503` 已记录「长期无人裁决 → 目标停在 `validated`」）。
2. **它必须与澄清共用一页**：用户视角里「角色要我问你两件事」与「角色要你确认一份计划」是同一类待办；`PLN-006` 已建 `/plan` 与卡片形态，本任务只加一个区块（D1）。
3. **必须诚实呈现「无人裁决会怎样」**：超时策略未实现（待决策项），所以 UI **不得**承诺「稍后自动批准/驳回」（D3），否则等于用文案掩盖未实现的能力。

### 2.3 在本版本中的位置

P2 第 4 个任务（P 线终点）：与 `PLN-006` 共同构成移动端「计划待办中心」。完成后 P 线（澄清 + 审批）在前后端闭合。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 数据层（`features/plan/data/`）

| 符号 | 契约 |
|---|---|
| `PlanApprovalRepository.listPending()` | `GET /plans/pending` → `List<PlanApprovalData>`（`planId` / `goalId` / `goalDescription` / `version` / `createdAt` / `stepsSummary[]`） |
| `PlanApprovalRepository.approve(planId)` | `POST /plans/{planId}/approve` → `{planId, outcome}`（`outcome` 取值对齐既有 `PlanApprovalOut`，`:44`） |
| `PlanApprovalRepository.reject(planId, reason)` | `POST /plans/{planId}/reject`，body `{reason: string}`（可空；长度上限沿用 `REJECTION_REASON_MAX_CHARS`，`approval.py:34`） |
| 错误映射 | 404 → 「该计划已不存在」；409 → 「该计划已不在待批状态」（两者都触发刷新）；401 → 走既有全局登录处理 |
| 数据类 | `PlanApprovalData` / `PlanStepSummaryData`（`index` / `description`） |

#### 4.1.2 `PendingPlanOut` 只读字段追加（**唯一允许的后端改动**）

| 项 | 契约 |
|---|---|
| 条件 | 仅当既有 `PendingPlanOut`（`plans.py:27`）**未含**步骤摘要与目标描述时追加 |
| 追加字段 | `steps_summary: list[StepSummaryOut]`（`{index: int, description: str}`，`description` 截断至 `PLAN_STEP_DESC_MAX_CHARS = 80`）；`goal_description: str`（若未含） |
| 兼容性 | **只新增字段**；既有字段名 / 类型 / 语义零改动；不新增端点、不改状态码语义 |
| 纪律 | `steps_summary` 不含 `params` / `tool_id` / `criteria` 等机制字段（用户只需知道「要做什么」，D6） |
| 读面实现 | 由服务层提供摘要派生（`goal_repository.get_plan` `:456` → `sub_goals` → 截断），**不新增仓储函数**（如需，须带默认值且不改既有签名） |

#### 4.1.3 展示层契约（`features/plan/presentation/`）

| 组件 | 契约 |
|---|---|
| `PlanApprovalCard` | `AppCard` 承载：标题 = 目标描述；副标题 = 版本与生成时间；中部 = 步骤摘要列表（`1. …`）；底部 = 「批准」（主按钮）+「驳回」（次按钮） |
| 批准交互 | 点击 → `ConfirmDialog` 二次确认（文案说明「批准后角色会开始执行该计划」）→ 成功后刷新 + `SnackBar` |
| 驳回交互 | 点击 → 理由输入对话框（可空，上限 `REJECTION_REASON_MAX_CHARS`）→ `ConfirmDialog` 确认 → 成功后刷新 |
| 页面整合 | `/plan` 页两区块：**待澄清**（`PLN-006` 卡片）+ **待审批**（本任务）；各自空态；整页无数据 → 单一 `EmptyState` |
| 角标 | 首页入口角标 = 待澄清数 + 待审批数 |
| **禁止文案** | 不得出现「稍后自动批准 / 自动驳回 / 超时会自动处理」等承诺（D3） |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **与澄清共用 `/plan` 与入口**，不新增 Tab / 路由 | 用户视角两者都是「角色等你的事」；复用 `PLN-006` 骨架成本最低（也避免 Tab 膨胀） |
| D2 | **只允许「向后兼容新增只读字段」这一处后端改动** | 审批不看步骤等于盲批；但改既有三端点的语义/字段属契约破坏。新增只读字段是唯一同时满足「可用」与「不破坏」的折中 |
| D3 | **不显示超时承诺** | 审批超时是未实现 + 待决策项（基线 §8.6 `:503`）；文案承诺会让用户等待一个不会发生的动作（诚实性硬约束） |
| D4 | **批准/驳回都需二次确认** | 批准会触发**计划开始执行**（不可逆的动作序列），驳回会使计划作废——两者都属高影响操作 |
| D5 | **驳回理由可空但保留输入框** | 既有 `RejectPlanRequest \| None`（`plans.py:75-80`）与 `DEFAULT_REJECTION_REASON`（`approval.py:33`）已支持空理由；提供输入框可提升归因质量 |
| D6 | **步骤摘要只给 `index` + `description`** | 用户只需知道「要做什么」；`params` / `tool_id` / `criteria` 是机制（D5 口径精神） |
| D7 | **409 / 404 一律刷新** | 两者都是「本地状态过期」，刷新是唯一正确响应（与 `PLN-006` D6 的错误处理一致） |
| D8 | **不在审批卡片里放澄清入口** | 两类待办的「已答位置」不同（审批走端点、澄清可走端点或对话）；混放会让用户误以为点选项就算批准 |

### 4.3 数据流

```text
首页入口（角标 = 澄清数 + 审批数）→ /plan（PLN-006 提供路由）
   ▼
/plan 页
   ├─ 待澄清区块（PLN-006 卡片，零改动）
   └─ 待审批区块（本任务）
        repo.listPending() → GET /plans/pending（plans.py:51，既有）
             → 200 [PlanApprovalData]（含 steps_summary）
        PlanApprovalCard × N
          ├─ 批准 → ConfirmDialog → POST /plans/{id}/approve（:69）→ 刷新
          └─ 驳回 → 理由输入 → ConfirmDialog → POST /plans/{id}/reject（:75）→ 刷新
       404 → 「该计划已不存在」+ 刷新；409 → 「已不在待批状态」+ 刷新

后端（唯一改动）：若 PendingPlanOut 缺 steps_summary / goal_description → 向后兼容新增只读字段
红线：不实现超时 / 不触达 / 不新路由 / 不改既有端点语义 / 不显示超时承诺
```

## 7. Testing Requirements

### 7.1 Focused（移动端 `plan_approval_test.dart`）

| 用例名 | 断言 |
|---|---|
| `repository requests pending plans endpoint` | `listPending()` → `GET /plans/pending`，解析出 `planId` / `goalDescription` / `stepsSummary` |
| `repository approves plan` | `approve(id)` → `POST /plans/{id}/approve` |
| `repository rejects plan with reason` | `reject(id, "时间不合适")` → `POST /plans/{id}/reject` 且 body 含 `reason` |
| `repository maps 404 and 409 distinctly` | 404 → 「该计划已不存在」；409 → 「该计划已不在待批状态」 |
| `approval card renders goal and step summary` | 渲染目标描述与按 `index` 排序的步骤摘要 |
| `approval card hides mechanism fields` | 卡片不出现 `tool_id` / `params` / `criteria` 文案（D6） |
| `approve asks for confirmation before posting` | 点击批准 → 出现 `ConfirmDialog`；取消 → **不发请求**；确认 → 发请求 |
| `reject collects reason then confirms` | 点击驳回 → 理由对话框 → 确认 → 请求 body 含理由；取消 → 不发请求 |
| `reject reason length is capped` | 超长理由被截断到 `REJECTION_REASON_MAX_CHARS` |
| `success refreshes both sections` | 审批成功后重新拉取审批列表与澄清列表（各 +1 次调用） |
| `page renders two sections with own empty states` | 有澄清无审批 → 审批区块显示自身空态且澄清区块正常（反之亦然） |
| `badge counts both kinds` | 2 条澄清 + 1 条审批 → 角标 3 |
| `no_timeout_promise_copy` | 页面文案不含「自动批准」/「自动驳回」/「超时自动」（D3） |
