## 2. Background

### 2.1 现状：澄清的痕迹散落在 trace 里，且与计划版本无关联

| 事实 | 证据 |
|---|---|
| 三条澄清 trace 由前三任务分别落盘 | `PLN-001` §4.1.2（`clarify_decision`）、`PLN-004` §4.1.3（`plan_clarify_resume`）、`PLN-005` §4.1.1（`plan_clarify_timeout`）——**字段各自定义**，无统一 schema |
| 计划已有版本链字段 | `apps/backend/app/models/goal.py:331`（`GoalPlanRecord`）、`:340-351`（字段含 `version` / `revision_of` / `context_digest` / `evidence_refs`）；`apps/backend/app/repositories/goal_repository.py:462`（`list_plans`）、`:473`（`get_latest_plan`）、`:478`（`count_plans`）、`:554`（`count_plan_versions`） |
| 修订链的既有写面（**不是 goal_repository**） | `apps/backend/app/services/planning/observer.py:453`（`_record_advance`）、`:485`（`record_plan_advance`）、`:515`（`record_plan_revision`）、`:562`（`project_plan_revision`）；`decision_records` 写面在 `app/repositories/decision_repository.py` |
| **`decision_records` 的 kind 有 CHECK（新增 kind 需迁移）** | `PLN-008` 的约束来源：`PLN-003` §4.2 D7 / `PLN-007` §4.2 D6（「不新增 `decision_records` kind」的一致性纪律） |
| 既有只读调试面（**不新增端点**） | `apps/backend/app/api/v1/debug/plans.py`（6 个只读端点）；`apps/backend/app/api/v1/debug/observability.py:32` / `:43` / `:51`（trace 读法）；`apps/backend/app/services/observability/trace_query.py`（仓储级读面） |
| 原子任务子目标结构（差异比对的基础） | `models/goal.py:203`（`SubGoalSpec`）、`:216-234`（字段 `index` / `description` / `capability` / `criteria` / `depends_on` / …）；`validate_sub_goals`（`:294`） |
| 澄清前后的计划都是「同一 `goal_id` 下的多个 `version`」 | `apps/backend/app/services/goal/planning.py:404`（`plan_goal`）、`:391`（`activate_plan`）；`goal_plans` 表对同一目标可有多版本（`version` 字段 + `list_plans`） |

### 2.2 为什么必须做

1. **没有归因就不知道澄清值不值得保留**：澄清闸是「多一轮交互换更准的计划」的交易；没有「答复前后计划差异」的观测量，就无法判断它是提高了质量还是只增加了往返（`docs/agent-evolution-plan-2026-10.md` §3.2 G-P6）。
2. **必须复用既有版本链而不是新造审计表**：`revision_of`（`models/goal.py:340-351`）已存在，`record_plan_revision`（`observer.py:515`）已有修订链投影；新增审计表会引入第二份真相（R-M3）。
3. **必须零新增 kind / 零新增端点**：`decision_records` 的 kind 有 CHECK（新增需迁移）；调试面端点已足够读 trace 与 plans（`debug/plans.py` 6 端点 + `debug/observability.py` trace）——本任务只**统一 schema 与补链**。

### 2.3 在本版本中的位置

P2 第 3 个任务（P2 后端收尾）：把 `PLN-001~005` 产生的痕迹整理成可查询、可对照的审计面。`PLN-009`（移动端审批 UI）在其后，为 P 线终点。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 trace schema 统一契约

| 项 | 契约 |
|---|---|
| 命名空间 | 三条事件的 `event` 名统一以 `clarify` 语义前缀（`clarify_decision` / `plan_clarify_resume` / `plan_clarify_timeout` **保持不变**——改名字会破坏 `PLN-001/004/005` 已落数据与既有断言） |
| 统一键集（冻结） | `plan_id` / `goal_id` / `round` / `stage`（`decision` \| `resume` \| `timeout`）/ `outcome`（`accepted` \| `declined` \| `resumed` \| `cancelled` \| `proceeded` \| `stale`）/ `questions_count` / `source`（`chat` \| `structured` \| `timeout`） |
| 键集纪律 | 三条事件**共同拥有**上述 7 键；事件特有的补充键（如 `reason`）单独允许，但**不得**缺失统一键 |
| 落点 | 仍走既有 `runtime_traces`（`PLN-001` / `PLN-004` / `PLN-005` 已接线）；本任务只**补齐缺失键**与统一取值 |
| 不写 `loop_runs.steps` | 键集断言冻结（`tasks/README.md` §4 第 3 条） |

#### 4.1.2 `revision_of` 链契约

| 项 | 契约 |
|---|---|
| 写入时机 | 澄清触发的**重新提案**落库时（`PLN-004` 的 `resume_from_answers` 与 `PLN-005` 的 `proceed` 路径），把新计划的 `revision_of` 设为**前一版计划 id** |
| 取值来源 | `goal_repository.get_latest_plan(goal_id)`（`:473`）取当前版本 id（在插入新版本前读取） |
| 无前版时 | `revision_of = None`（首次提案，行为与基线一致） |
| 与基线路径的关系 | **非澄清**路径（`plan_goal` 的常规重规划）的 `revision_of` 语义**不变**（既有行为零改动） |
| 可遍历性 | 版本链可由 `list_plans(goal_id)`（`:462`）+ `revision_of` 反查重建；`count_plan_versions`（`:554`）可用于计数核验 |

#### 4.1.3 归因派生契约（纯函数）

| 函数 | 契约 |
|---|---|
| `sub_goals_diff(before: list[dict], after: list[dict]) -> dict` | 输入为两版 `sub_goals`（`SubGoalSpec` 的序列化）；输出 `{"added": int, "removed": int, "changed": int, "unchanged": int, "churn": float, "added_capabilities": list[str]}`；**确定性**（按 `index` 对齐；同 `index` 且关键字段相同 → `unchanged`） |
| `churn` 定义 | `(added + removed + changed) / max(len(before), len(after), 1)`，保留 4 位小数（与 `MEV-004` 的分数精度纪律一致） |
| `added_capabilities` | 新版本中出现而旧版本没有的 `capability` 集合（升序）——直接反映「澄清补齐了什么能力」 |
| 纯函数纪律 | 不查库、不调 LLM、无随机、无时间依赖；同输入同输出（可单测） |
| 使用方 | 调试面与离线评估（未来）；本任务只交付函数与用例 |

#### 4.1.4 只读查询面契约

| 项 | 契约 |
|---|---|
| 复用 | `apps/backend/app/api/v1/debug/plans.py`（既有 6 只读端点）与 `apps/backend/app/api/v1/debug/observability.py`（trace 读法 `:32` / `:43` / `:51`） |
| 必要补齐 | 若 `debug/plans.py` 的计划响应未含 `revision_of` / `version`，则**补齐只读字段**（纯新增字段，不改既有字段）；若已含则零改动 |
| 不新增端点 | 见 §3.2 第 3 条 |
| 鉴权 | 调试面既有 `require_user` 与 `debug_surface_gate` 语义不变（ADR-17） |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **事件名保持 `PLN-001/004/005` 已定的三个**，只统一键集 | 改名会破坏已落 trace 数据的可读性与既有断言；统一键集即可达到可比对目的 |
| D2 | **不新增 `decision_records` kind / 不新增表** | kind 有 CHECK（需迁移）；`revision_of` 链 + trace 已能完整回答「澄清是否改变了计划」（R-M3：一份真相） |
| D3 | **`revision_of` 只在澄清路径补齐** | 非澄清路径的版本语义属既有行为（`observer.py` 修订投影）；混改会造成既有修订链语义漂移 |
| D4 | **归因做「客观差异」不做「质量打分」** | 客观差异是纯函数、可复现；质量打分需要 Judge（属评估域，且会引入 LLM 成本） |
| D5 | **复用既有 debug 面，不新增端点** | 调试面治理成本高（ADR-17）；且 trace 与 plans 都已有读法 |
| D6 | **`churn` 用 4 位小数** | 与 `MEV-004` 的分数精度纪律一致（避免浮点噪声进响应/日志） |
| D7 | **`source` 字段区分三条恢复路径** | 让「对话轮次（chat）/ 结构化端点（structured）/ 超时（timeout）」三类来源可分别统计，这是评估澄清 UX 的基础 |
| D8 | **本任务零设置** | 归因是派生逻辑，无可调项 |

### 4.3 数据流

```text
【产生】PLN-001 判定 / PLN-004 恢复 / PLN-005 超时 → 三条 trace（补齐统一 7 键）
【落链】澄清触发的重新提案
   ├─ 读 get_latest_plan(goal_id)（:473）→ 前版 id
   ├─ 插入新计划版本（version + 1），revision_of = 前版 id
   └─ 非澄清路径不变（D3）

【只读】debug 面（既有）
   GET /debug/plans/...（6 端点）→ 计划含 version / revision_of
   GET /debug/turns/{turn_id}/trace → clarify 三事件的统一键集
   ▼
【派生】sub_goals_diff(before, after)（纯函数）→ {added, removed, changed, unchanged, churn, added_capabilities}

红线：不新增 kind / 表 / 端点 / 迁移；事件名不改；只读面既有语义不变
```
