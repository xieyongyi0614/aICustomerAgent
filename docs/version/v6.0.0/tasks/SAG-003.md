## 2. Background

### 2.1 现状：异步执行底座已现成，但**没有任何派发与回投机制**

| 事实 | 证据 |
|---|---|
| 通用后台任务表（含唯一幂等键） | `apps/backend/app/core/db/autonomy.py:138`（`BackgroundJobRow`）、`:139`（表名）、`:141-151`（列含 `job_type` / `payload` / `status` / `attempts` / `run_at` / **`idempotency_key`(unique)** / `last_error`） |
| 通用 worker 循环 | `apps/backend/app/application/worker_loop.py:21-29`（`run_worker_loop(name, tick, interval, max_backoff_seconds=..., offload=False, max_consecutive_failures=None, on_circuit_open=None)`） |

| 跨域可靠投递（回投可复用） | `app/application/outbox_consumer.py`（Outbox 消费者）；事件总线 `app/application/agent_runtime/events.py`（进程内同步，**只落 Trace**，非跨进程可靠投递） |

| 并发原语现状（**不可复用**） | `asyncio.gather` 全库仅 4 处：`services/briefing/compose.py:130`、`application/observability.py:290` / `:296`、`application/chat_pipeline.py:543` |
| S-C 形态的工具面（最小验证落点） | `app/services/tool/registry.py`（注册期七项校验 + 单例）、`app/services/tool/executor.py`（五段：权限/确认/校验/归一/健康）；既有「条件/无条件注册」先例：`channel_feishu`、`external_api`（基线 §3.5） |
| 既有「后台 + 异步结果」先例 | 规划步骤执行（`life_loop._execute_plan_step` `:418`）、工具确认恢复（`action_engine._resume_confirmed_record` `:838`）——均**同步收敛**，可作为「收敛语义」的对照 |

### 2.2 为什么必须做

1. **没有派发与回投，`SAG-001` / `SAG-002` 只是「登记表」**：身份与血缘若不接上实际执行，就无法验证它们是否够用（`docs/agent-evolution-plan-2026-10.md` §4.4 G-S6）。
2. **收敛语义必须先定义再实现**：超时 / 失败 / 部分成功若不定死，「子 Agent 没回来」会被各种临时逻辑各自解释（父上下文等多久？失败算不算父失败？一半成功如何合并？），这是 subAgent 最容易变成技术债的地方（D2/D3）。
3. **`S-C` 最小验证是风险最低的路径**：它不改红线（`docs/agent-evolution-plan-2026-10.md` §4.5「落地建议顺序」）、复用既有 Tool 五段治理，能在「独立 prompt + 独立上下文 + 异步执行 + 结果回投」四要素上先验证是否够用（D1）。

### 2.3 在本版本中的位置

S 线第 3 个任务：**收口任务**。它是「是否值得升级到 S-A」的决策依据（D6），也是 `SAG-004` 文档的输入。

## 3. Scope

### 3.1 In Scope

1. `app/application/agent_runtime/dispatch.py`：`dispatch_subagent(...)`（写 job）+ `collect_returns(...)`（回投读取与合并）。
2. 复用 `background_jobs` + `worker_loop` + `register_job_type`（**零新表**）。
3. **收敛语义**（冻结）：超时 / 失败 / 部分成功（§4.1.3）。
4. 回投通道（二选一，由裁决：既有事件总线 **或** Outbox 可靠投递；§4.2 D4）。
5. **S-C 最小验证**：新增一个 Agent-as-Tool 工具实现 + 注册（§4.1.4）。
6. 新增设置（参数类）：`subagent_dispatch_timeout_seconds`、`subagent_dispatch_max_inflight`。
7. 新增用例（§7.1 / §7.2）。

### 3.2 Out of Scope（明确禁止扩张）

| # | 禁止项 | 理由 |
|---|---|---|
| 1 | **不做并行调度 / DAG / 拓扑执行** | 并发原语现状不可复用（§2.1）；并行属独立议题，且与「单管线」纪律张力最大 |
| 2 | **不新增表 / 不新增 Run 状态值** | 复用 `background_jobs`；状态语义归既有 Run 生命周期 |
| 3 | **不做「子 Agent 结果自动写入业务域」** | 结果只回投到父上下文（父决定怎么用）；自动写入会绕过各域的写面纪律（D5） |
| 4 | **不做外部 Agent 框架** | RL-2（`SAG-000` 预期维持禁止） |
| 5 | **不做多角色（`character_id` 多实例）** | 属 S-B 落点，需 `SAG-000` 另裁 |
| 6 | **不改既有前台/自治链路** | 未启用时行为逐字节一致（D6/AC4） |
| 7 | **不升级到 S-A（新 run_kind + 独立 Run 的完整委派）** | 属本任务**验证通过后**的后续决策（D1/D7）；本任务只做 S-C 最小验证 |
| 8 | **不做「子 Agent 之间互相委派」** | 多层委派的调度策略未设计（`SAG-002` §3.2 第 6 条） |

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 派发契约（`dispatch.py`）

| 符号 | 契约 |
|---|---|
| `dispatch_subagent(agent_name, user_id, *, payload, parent_run_id, idempotency_key, timeout_seconds=None) -> str` | ① 校验身份存在（`SAG-001` 注册表）；② 校验 `parent_run_id` 存在且同用户（`SAG-002` D3 同源）；③ 经既有 job 入队（`register_job_type` 注册的 `subagent_dispatch` 类型），`idempotency_key` 由调用方给出（建议 `f"subagent:{parent_run_id}:{agent_name}:{payload_hash}"`）；④ 返回 job id |
| 入队实现 | 复用 `job_worker` 既有入队路径（`run_job_tick` `:71` 的调度 + `_claim` `:100` 的 `FOR UPDATE SKIP LOCKED` `:111`）；**不新增表、不新增 worker 进程** |
| 并发上限 | 单用户同时在飞派发数 ≤ `subagent_dispatch_max_inflight`（默认 1）；超限 → **拒绝派发**（返回错误，不排队） |
| 幂等 | 同一 `idempotency_key` 重复派发 → 返回既有 job（不重复执行，`BackgroundJobRow.idempotency_key` unique `:141-151`） |
| 失败语义 | 入队失败 → 显式抛错（派发是主动行为，静默失败不可接受——与 `PLN-005` D7 同源） |

#### 4.1.2 回投契约

| 项 | 契约 |
|---|---|
| 结果载荷 | `{job_id, agent_name, parent_run_id, status, outcome, summary, produced_at, error?}`；`summary` 为**子 Agent 产出的文本摘要**（长度上限常量 `SUBAGENT_SUMMARY_MAX_CHARS = 2000`） |
| 回投通道（二选一，由 `SAG-000` 裁决；D4） | A：**既有事件总线**（`agent_runtime/events.py`，进程内，零持久化，只落 Trace）；B：**Outbox 可靠投递**（`outbox_consumer.py`，跨进程可靠） |
| 父上下文读取 | `collect_returns(parent_run_id) -> list[dict]`：返回该父 Run 已到达的结果（按 `produced_at` 升序，确定性）；**不阻塞等待**（由父在下一阶段读取） |
| 不自动写入业务域 | 结果只回投到父 Run 的可见面（D5） |

#### 4.1.3 收敛语义（★ 冻结，本任务核心交付）

| 场景 | 契约 |
|---|---|
| **成功** | job `done` + 回投一条 `status="ok"` |
| **失败**（handler 抛错且重试耗尽） | job `failed` + 回投一条 `status="error"`（含 `error` 摘要）；**父 Run 不因此失败**（父自行决定） |
| **超时** | 超过 `subagent_dispatch_timeout_seconds`（默认 120）仍在 `running` → 由派发器收敛为 `status="timeout"` 回投；job 由既有僵尸回收（`job_worker._recover_zombies` `:183`）处理 |
| **部分成功**（一个父 Run 派发多个子任务） | `collect_returns` 返回已到达结果集合 + `pending_count`；父侧判定「是否可继续」-**不由派发器决定**（D3） |
| **未到达** | 父上下文拿到 `pending_count > 0`（不阻塞、不抛错） |

#### 4.1.4 S-C 最小验证契约（Agent-as-Tool）

| 项 | 契约 |
|---|---|
| 工具 | 新增一个工具（如 `builtin.agent.research`，最终命名由裁决/实现冻结），走既有 `ToolRegistry` 注册期七项校验与 `executor` 五段（权限/确认/校验/归一/健康） |
| 行为 | 工具内部：取身份（`SAG-001`）→ 开子 Run（`SAG-002` 的 `parent_run_id`）→ 执行 → 同步返回摘要（**S-C 天然同步**，异步派发仅在需要跨轮时使用） |
| 验证四要素 | ① **独立 prompt**（由 `prompt_scope` 解析，与主角色不同）；② **独立上下文**（开新 Session/Run，隔离，`docs/agent-evolution-plan-2026-10.md` §4.1 的唯一隔离姿势）；③ **异步执行**（经 `background_jobs` 路径可跑通至少一次）；④ **结果回投**（父 Run 经 `collect_returns` 可读到） |
| 结论产出 | 四要素是否**够用**的明确结论（够用 → 评估升级 S-A 是否有额外收益；不够用 → 指出缺少什么） |
| 落点纪律 | 工具注册走既有 `ToolRegistry`（代码注册非热插拔）；**不得**在 `services/planning/` 加模块 |

#### 4.1.5 新设置字段

| 字段 | 类型 | 默认 | 语义 | 校验 |
|---|---|---|---|---|
| `subagent_dispatch_timeout_seconds` | `int` | `120` | 单次派发超时（用于收敛语义） | `ge=10`、`le=3600` |
| `subagent_dispatch_max_inflight` | `int` | `1` | 单用户同时在飞派发上限 | `ge=1`、`le=10` |

> 命名按领域语义，**不带版本前缀**；均为参数类，**无 `*_enabled`**（`tasks.md` §0.4）。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **先做 S-C 最小验证，不直接做 S-A** | S-C 不改红线、复用既有 Tool 治理五段，是风险最低的验证路径（`docs/agent-evolution-plan-2026-10.md` §4.5「落地建议顺序」） |
| D2 | **收敛语义必须显式定义（成功 / 失败 / 超时 / 部分成功 / 未到达）** | 这是 G-S6 的原始缺口；不定死会让各处临时逻辑各自解释（§2.2 第 2 条） |
| D3 | **「是否继续」由父决定，派发器不做策略** | 派发器是基础设施（对齐「能力是手脚不是逻辑」，基线 §10 ADR-10 精神）；策略归调用方 |
| D4 | **回投通道二选一，由裁决决定** | 事件总线零持久化（只落 Trace）适合同进程；Outbox 适合跨进程可靠投递。二者成本与可靠性差异大，必须显式选一个 |
| D5 | **结果不自动写入业务域** | 各域有唯一写面纪律（基线 ADR-9）；自动写入会绕过域治理 |
| D6 | **未启用时既有链路逐字节一致** | 与 M / P 线全部能力同源的零回归纪律 |
| D7 | **本任务不放开 S-A** | 升级属验证后的独立决策；混做会让「最小验证」失去意义 |
| D8 | **超时由派发器收敛，job 回收交既有僵尸回收** | 避免自造第二套清理机制（`job_worker._recover_zombies` `:183` 已存在） |
| D9 | **在飞上限默认 1** | 成本与可解释性优先（首版不做并发）；上限提升由实测决定 |
| D10 | **零新表** | `background_jobs` 已具备幂等/重试/僵尸回收/死信全部要素（§2.1） |

### 4.3 数据流

```text
【派发】调用方（工具 / 父 Run 阶段）
   dispatch_subagent(agent_name, user_id, payload, parent_run_id, idempotency_key)
     ① 身份存在？（SAG-001）② parent 同用户？（SAG-002 D3）③ 在飞数 ≤ max_inflight？
     ④ 入队 background_jobs（job_type="subagent_dispatch"，idempotency_key unique）
        └─ 幂等：同 key → 返回既有 job，不重复执行
   ▼
【执行】既有 worker_loop（:21）→ run_job_tick（job_worker.py:71）→ _claim（:100，SKIP LOCKED :111）
     子 Run：open_run(parent_run_id=..., delegation_kind="agent_tool"|"task_delegate")（controller.py:38）
     handler 执行（身份 → prompt_scope → 独立 Session/Context）
   ▼
【收敛】成功 → done + 回投 ok ｜ 重试耗尽 → failed + error ｜ 超时 → 派发器收敛 timeout
     僵尸回收交既有 _recover_zombies（job_worker.py:183）
   ▼
【回投】通道 A：事件总线（events.py，只落 Trace）｜ 通道 B：Outbox（outbox_consumer.py，可靠）
   collect_returns(parent_run_id) → [results...] + pending_count（父自行决策，D3）

【S-C 最小验证】工具 builtin.agent.* 走 ToolRegistry + executor 五段 → 四要素端到端跑通
红线：零新表；不改既有链路；不自动写业务域；不做并行；不放开 S-A
```
