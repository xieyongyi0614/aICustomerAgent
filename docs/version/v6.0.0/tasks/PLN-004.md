## 2. Background

### 2.1 现状：项目里唯一的「提问 → 等答复 → 恢复」在工具授权域，且语义不同

| 事实 | 证据 |
|---|---|
| 零 LLM 检出器的既有范式（词表 + 问句守卫） | `apps/backend/app/services/tool/confirmation.py:642`（`ConfirmationIntentDetector`）、`:645`（`detect(content, pending) -> tuple[str,str] \| None`）、`:654`（`_detect`）、`:670`（`_confirmation_verb`）、`:684`（`_is_question_inquiry`）、`:694`（`_most_recent`）；词表来自角色资产 `app/character/asuna/tool.py`（import `:27-31`） |
| 确认闸的接线方式（前台后处理内、动作规划之前） | `apps/backend/app/application/post_process.py:564`（`_run_confirmation_round(ctx) -> bool`）；由 `run_action_planning`（`:504`）在 `:517` 调用；内部再调 `action_engine.run_confirmation_round`（`:581`） |
| 后处理步骤注册表 | `:881-895`（`STEP_HANDLERS`，13 个步骤）；`run_post_process`（`:901`）按表顺序执行；`schedule_post_process`（`:908-924`）为调度入口 |
| 步骤函数的既有形态（同步按用户、含 trace） | `run_goal_review`（`:104`）、`run_summary`（`:138`）、`run_memory_extract`（`:150`）、`run_action_planning`（`:504`） |
| 澄清的载体与读面（`PLN-003`） | `PLN-003` §4.1.3（`get_pending` / `list_pending` / `mark_answered` / `cancel_pending`）、§4.1.1（`trigger_key = plan_clarify:{plan_id}`） |
| 答复归一与重新提案（`PLN-002`） | `PLN-002` §4.1.3（归一为 `{round, qa[]}`）、§4.1.2（`_build_messages` 注入）、D8（重新提案复用 `propose_plan`） |
| 轮次硬闸（`PLN-001`） | `PLN-001` §4.1.2（`round < plan_clarify_max_rounds`）+ `plan_clarify_max_rounds` 默认 1 |
| 计划与目标仓储 | `apps/backend/app/repositories/goal_repository.py`：`get_plan`(`:456`)、`get_goal`(`:150`)、`list_active_plans`(`:512`) |

### 2.2 为什么必须做

1. **没有检出器，答复就永远是「普通聊天」**：`PLN-003` 只能把载荷存下来；用户答「选第二个」时，若无前置守卫就检测，会把任何含「第二个」的普通对话都当成答复——**误判比漏判更伤体验**（`docs/agent-evolution-plan-2026-10.md` §3.5 H-P2）。
2. **走前台对话轮次是「零客户端改动」的唯一路径（R1）**：结构化端点（R2）需要客户端 plans 页（`PLN-006`/`PLN-007`）；而对话轮次复用既有链路，立刻可用（§3.3.5 的取舍）。
3. **必须与工具确认严格区分**：两者都是「用户答复 → 恢复」，但一个恢复的是**动作授权**、一个恢复的是**规划输入**；混用会导致「答澄清却执行了动作」（D2）。

### 2.3 在本版本中的位置

P1 第 4 个任务：闭合「提问 → 答复 → 继续」链路。`PLN-005`（超时兜底）与 `PLN-006`（客户端卡片）在其后。

## 3. Scope

### 3.1 In Scope

1. `clarification.py` 新增 `PlanClarificationIntentDetector`（零 LLM）与 `resume_from_answers(...)`。
2. 检出前置守卫：**存在该用户 pending 澄清行** + 轮次未超上限。
3. 答复匹配三路：选项 `label` 子串 / 序号（`1` / `第 1 个` 等）/ 自由文本（`allow_free_text` 的问题）。
4. `post_process.py` 新增步骤 `run_plan_clarification` 并注册进 `STEP_HANDLERS`（§4.1.3）。
5. 恢复流程：归一 → `mark_answered` → 重新提案（`PLN-002`）→ `PLN-001` 闸（`round+1`）。
6. 新增用例（§7.1 / §7.2）。

### 3.2 Out of Scope（明确禁止扩张）

| # | 禁止项 | 理由 |
|---|---|---|
| 1 | **不调用 LLM 做意图识别** | 与工具确认同源纪律（`ConfirmationIntentDetector` 是零 LLM）；LLM 检出会作用于**每一轮对话**，成本与误判都不可接受（D1） |
| 2 | **不做 NLP / 分词 / 模糊匹配库** | 新增依赖；且答复格式受控（选项 label + 序号），确定性规则足够 |
| 3 | **不新增 REST 端点** | 结构化端点属 `PLN-007`；本任务走对话轮次（R1） |
| 4 | **不改 `_run_confirmation_round`（`:564`）与工具确认语义** | 两者语义不同（授权 vs 规划输入）；混改会让「答复澄清」触发动作执行（D2） |
| 5 | **不做移动端 / Web UI** | 属 `PLN-006` / `PLN-007`；本任务声称「零客户端改动」 |
| 6 | **不实现超时与自动决策** | 属 `PLN-005` |
| 7 | **不在本轮内自动激活计划** | 是否激活由 `PLN-001` 闸 + `plan_require_approval` 决定；本任务只重新提案 |

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 检出器契约（`PlanClarificationIntentDetector`）

| 项 | 契约 |
|---|---|
| 入口 | `detect(self, content: str, pending: list[dict], *, max_rounds_reached: bool) -> dict \| None` |
| **前置守卫（硬）** | ① `pending` 非空（存在该用户的 pending 澄清行）；② `max_rounds_reached is False`。任一不满足 → 立即返回 `None`（**零副作用**） |
| 问句守卫 | 复用既有范式（对齐 `confirmation.py:684` 的 `_is_question_inquiry`）：内容是**疑问句**且不含任何选项词 → 视为「反问/追问」，不当作答复（返回 `None`） |
| 匹配路 A：选项 label 子串 | 对每个问题，若内容包含某选项的 `label`（归一后大小写不敏感子串）→ 该问题的答复为该选项 |
| 匹配路 B：序号 | 内容含「第 N 个」/ 纯数字 / 「第N项」等序号表达（词表常量 `_ORDINAL_LEXICON`）→ 按**该问题的 `options` 顺序**取第 N 项（越界则忽略） |
| 匹配路 C：自由文本 | 问题 `allow_free_text=True` 且 A/B 均未命中 → 整段内容作为该问题的自由文本答复（截断由 `PLN-002` 的 `plan_clarify_answer_max_chars` 负责） |
| 多问题 | 逐问题独立匹配；**全部问题都未命中** → 返回 `None`（不视为答复）；部分命中 → 返回已命中的（未命中项由 `PLN-002` 归一函数跳过） |
| 返回 | `{"plan_id": str, **answers}` 形态：`{"q1": {"value": ...}}` / `{"q2": {"free_text": ...}}`（与 `PLN-002` §4.1.3 的输入结构一致） |
| 多条 pending | 取 `created_at` **最新**一条（对齐 `confirmation.py:694` 的 `_most_recent` 思路） |
| 零副作用 | `detect` 是**纯函数**：不写库、不调 LLM、不落 trace |

#### 4.1.2 恢复流程契约（`resume_from_answers`）

| 步骤 | 契约 |
|---|---|
| ① 归一 | 调 `PLN-002` §4.1.3 的归一函数（答复 + `ClarificationPayload` → `{round, qa[]}`）；`qa` 为空 → **中止**（不 `mark_answered`，行保持 pending，避免「误收尾丢答复」） |
| ② 收尾 | `mark_answered(plan_id, answers=...)`（`PLN-003` §4.1.3）→ 行转 `done` |
| ③ 重新提案 | 取 `goal`（`goal_repository.get_goal` `:150`）→ `propose_plan(goal, ..., clarification=归一结果)`（`PLN-002`）→ `PLN-001` 判定闸（`round+1`） |
| ④ 落库与激活 | 与 `plan_goal` 既有分支一致：命中澄清 → 停 `validated` 并登记新 pending（`PLN-003`）；否则按 `plan_require_approval` 决定 `validated → active` 或等审批 |
| 幂等 | ② 之后该 `plan_id` 无 pending → 同一答复文本再次出现时 `detect` 因守卫①返回 `None`（**天然幂等**） |
| 失败语义 | 任一环节异常 → `logger.warning` + trace + **不阻断本轮对话**（记忆域式降级纪律延伸到规划辅助链路）；② 已成功的收尾**不回滚**（避免重复答复） |
| 与对话的关系 | 本步骤**不产出回复文本**（回复仍由既有 answer 链生成）；仅影响计划状态 |

#### 4.1.3 后处理步骤接线契约

| 项 | 契约 |
|---|---|
| 新步骤名 | `run_plan_clarification` |
| 位置 | 注册进 `STEP_HANDLERS`（`:881-895`），**排在 `run_action_planning`（`:504`）之前**（理由：同轮若既有澄清答复又有动作意图，先收澄清，避免「澄清还没落地就按旧计划执行动作」） |
| 步骤形态 | 与既有步骤同构：同步函数、接收 `PostProcessContext`、内部自行 try/except 降级 |
| 早退 | 无 pending 澄清行 → **立即返回**（零开销；保证绝大多数对话轮次不受影响） |
| trace | 经既有 trace 通道记录 `plan_clarify_resume`（`plan_id` / `round` / `matched` / `outcome`） |
| 不写 `loop_runs.steps` 新键 | 键集断言冻结（`tasks/README.md` §4 第 3 条） |

#### 4.1.4 词表与常量（`clarification.py` 模块常量）

| 常量 | 内容（实现期冻结具体词条） |
|---|---|
| `CLARIFY_SELECT_ORDINAL_LEXICON` | 序号表达（`第N个` / `第N项` / `选项N` / 纯数字 1~5） |
| `CLARIFY_SKIP_LEXICON` | 「随便 / 你决定 / 不重要」→ 视为**不回答**（保持 pending，交由 `PLN-005` 超时兜底；不当作自由文本） |
| `CLARIFY_QUESTION_GUARD_LEXICON` | 疑问句守卫词（「吗 / 呢 / 为什么 / 怎么」等），命中且无选项词 → 不检出的既有范式 |

> **落点说明**：若后续需与角色资产侧文案统一（对齐 `app/character/asuna/tool.py` 的既有存放方式），可在不改行为的前提下迁移；本 Detail 实现期确认。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **零 LLM 检出** | 与 `ConfirmationIntentDetector`（`confirmation.py:642`）同源纪律：检出发生在**每一轮对话**，LLM 化会让成本与误判双双不可控 |
| D2 | **与工具确认完全分离**（独立检出器、独立后处理步骤） | 两者恢复的语义不同（规划输入 vs 执行授权）；混用会造成「答了澄清却执行动作」（§2.2 第 3 条） |
| D3 | **前置守卫（有 pending 才检出）** | 误判是主要风险（H-P2）；守卫把检出范围限制在「确实在等答复」的极少数轮次 |
| D4 | **问句守卫 + 跳过词表** | 「你在说什么？」不应被当作答复；「随便」不应被当作自由文本（否则会把无意义内容注入 prompt） |
| D5 | **归一为空则中止，不收尾** | 宁可保持 pending（能被后续轮次或超时处理），也不要「收尾了但没答复」导致澄清信息永久丢失 |
| D6 | **步骤排在动作规划之前** | 同轮「答复 + 动作意图」并存时，先让计划信息补齐，避免基于旧计划执行动作 |
| D7 | **异常不阻断、已收尾不回滚** | 对话轮次的可用性优先；回滚会造成「同一答复重复触发」 |
| D8 | **不产出回复文本** | 回复由既有 answer 链负责；本步骤只改计划状态，避免两处生成回复 |
| D9 | **多条 pending 取最新** | 与确认闸 `_most_recent`（`:694`）一致；理论上 `PLN-003` 已保证同计划至多一条（D4），多计划并存时取最新最合理 |
| D10 | **本轮不自动激活** | 激活权在 `PLN-001` 闸与 `plan_require_approval`；本任务只重新提案，不越过闸门 |

### 4.3 数据流

```text
【用户回复一句消息】→ 既有 chat_pipeline → 既有 post_process（STEP_HANDLERS :881-895）
   ★ 新增步骤 run_plan_clarification（排在 run_action_planning :504 之前）
       ① pending = clarification.list_pending(user_id)（PLN-003）
          空 → 立即返回（零开销，绝大多数轮次）
       ② max_rounds_reached = (pending.round >= plan_clarify_max_rounds)
       ③ PlanClarificationIntentDetector.detect(content, pending, max_rounds_reached)
          ├─ None（守卫未过 / 问句 / 跳过词 / 全未命中）→ 返回（不改任何状态）
          └─ answers → resume_from_answers(...)
       ④ 归一（PLN-002 §4.1.3）→ qa 为空 → 中止（保持 pending，D5）
       ⑤ mark_answered（PLN-003）→ 行 done（幂等：后续同文本无 pending → 不触发）
       ⑥ propose_plan(..., clarification=归一结果) → PLN-001 判定闸（round+1）
            ├─ 再需澄清 → 停 validated + 登记新 pending（PLN-003）
            └─ 不需 → 按 plan_require_approval 决定 validated→active 或等审批
       ⑦ trace：plan_clarify_resume（不写 loop_runs.steps 新键）

红线：零 LLM；有 pending 才检出；与工具确认分离；异常不阻断；不产出回复文本
```

## 8. Acceptance Criteria

| AC# | 判据 | 验证方式 |
|---|---|---|
| AC1 | 无 pending / 轮次超限 → **零检出** | `test_no_pending_means_no_detection` + `test_rounds_exhausted_means_no_detection` |
| AC2 | 三路匹配（label / 序号 / 自由文本）均可用且受 `allow_free_text` 约束 | 3 条匹配用例 |

| AC5 | 归一为空则中止且不收尾（不丢答复） | `test_resume_aborts_when_normalized_qa_empty` |
| AC6 | 幂等：同一答复只触发一次 | `test_resume_is_idempotent_per_answer` |
| AC7 | 异常不阻断本轮对话 | `test_resume_failure_does_not_break_turn` |
| AC8 | 步骤排在动作规划之前；无 pending 零开销 | `test_step_runs_before_action_planning` + `test_step_early_returns_without_pending` |
| AC9 | 与工具确认彻底分离（无 import、语义不变） | `test_no_tool_confirmation_import` + `test_confirmation_round_untouched` |
| AC10 | `loop_runs.steps` 键集不变；零客户端改动；零迁移 | 3 条静态用例 |
