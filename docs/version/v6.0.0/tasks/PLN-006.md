## 2. Background

### 2.1 现状：移动端没有任何「计划」概念，且澄清只能靠打字

| 事实 | 证据 |
|---|---|
| 移动端 features 目录（**无 plan**） | `apps/mobile/lib/features/`：`album` / `briefing` / `car` / `chat` / `home` / `ledger` / `life` / `memory` / `profile` |
| 路由集中声明 | `apps/mobile/lib/app/router/app_router.dart:158`（`final appRouter = GoRouter(...)`）、`:92`（`ShellTab` enum）、`:163`（`ShellRoute`）、`:169-249`（`GoRoute` 列表） |
| 可复用的设计系统组件（**不得自造**） | `apps/mobile/lib/design_system/components/cards.dart:15`（`AppCard`）、`confirm_dialog.dart:35`（`ConfirmDialog`）、`chips.dart:16`（`ModeChip`）、`states/states.dart:38`（`EmptyState`）、`:75`（`ErrorState`）、`:18`（`LoadingState`）；列表页范例 `features/album/presentation/album_page.dart` / `features/ledger/presentation/ledger_page.dart` |
| 既有「待办类」交互范例（可借鉴） | 账本待确认：`apps/mobile/lib/features/chat/presentation/chat_ledger_page.dart`、`ledger_auto_page.dart`（对应后端 `GET /ledger/pending` + `POST .../confirm` / `/ignore`） |
| 澄清载体（`PLN-003`）与端点（`PLN-007`） | `PLN-003` §4.1.3（`list_pending` / `mark_answered`）；`PLN-007`（`GET /plans/clarifications/pending` + `POST /plans/{plan_id}/clarify`） |
| 答复解析与恢复（`PLN-004`） | `PLN-004` §4.1.1（`{"q1": {"value": ...}}` / `{"q2": {"free_text": ...}}`）、§4.1.2（`resume_from_answers`） |
| 端上零映射纪律 | `apps/mobile/lib/features/memory/presentation/memory_page.dart`（分组/标签/来源中文名**全部服务端下发**；V5.0.0 `API-007` §4.1.2 同源） |
| 设计系统是 UI 唯一真源 | `AGENTS.md`（「任何 UI / 样式 / 设计稿 / Flutter 主题工作先读 `.agents/skills/zhaoxi-design-system/`；其优先级**高于** `design/` 下的设计稿与原型」） |

### 2.2 为什么必须做

1. **R1（对话轮次）解决了「能不能答」，没解决「好不好答」**：`PLN-004` 的检出器让用户能用自然语言答，但选项式回答（点一下）在移动端是更自然、更不易误判的交互（`docs/agent-evolution-plan-2026-10.md` §3.3.5 的 R2）。
2. **它是澄清闸唯一可见的产品面**：`PLN-001~005` 全部是后端行为；没有客户端入口，用户只能「等角色问」——而挂起后若用户没意识到，就会一路走到 `PLN-005` 的超时（默认策略是保守 `cancel`，等于白问一次）。
3. **组件与路由基建齐备，成本可控**：`AppCard` / `ModeChip` / `EmptyState` / `ConfirmDialog` 已存在；路由是集中声明（`:158`）；只需加一个 feature 与一个 route（D3）。

### 2.3 在本版本中的位置

P2 第 1 个任务（客户端产品面）：与 `PLN-007`（结构化端点 + Web 页）同批，把后端澄清能力变成可点选的 UI。`PLN-009`（审批 UI）在其后用同一 `features/plan/` 承载。

## 3. Scope

### 3.1 In Scope

1. 新增 `apps/mobile/lib/features/plan/`：`domain/`（模型）、`data/`（repository）、`presentation/`（页面 + 卡片 widget）。
2. 路由：新增 `GoRoute(path: '/plan', ...)`（`app_router.dart:169-249` 的既有列表内追加），并决定 Tab 归属（`ShellTab` `:92`，见 §4.2 D3）。
3. 入口：首页（`features/home`）或「我的」（`features/profile`）展示「待澄清」入口；存在 pending 时显示数量角标。
4. 卡片交互：逐问题渲染 options（chips）/ 自由文本输入 / 提交 / 错误与空态。
5. 提交后刷新（列表 + 入口角标）。
6. 测试：widget 测试 + repository 单元测试。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 数据层（`features/plan/data/`）

| 符号 | 契约 |
|---|---|
| `PlanClarificationRepository.listPending()` | `GET /plans/clarifications/pending` → `PlanClarificationData`（`planId` / `goalId` / `round` / `createdAt` / `questions[]`） |
| `PlanClarificationRepository.submit(planId, answers)` | `POST /plans/{planId}/clarify`，body 为 `{answers: {q1: {value}}, q2: {freeText}}`（与 `PLN-004` §4.1.1 结构一致）→ 返回 `{planId, outcome}`（`outcome ∈ clarified \| activated \| pending_approval`） |
| 数据类 | `PlanClarificationData` / `PlanQuestionData`（`id` / `question` / `options[]` / `allowFreeText`）/ `PlanOptionData`（`value` / `label`） |
| 错误映射 | 404 → 「这条问题已不再需要回答」（并刷新列表）；409 → 「已被回答或已取消」（刷新）；422 → 「答复不合法」（保留用户输入）；沿用既有 `AuthCodeException` 风格的统一错误映射（对齐 `features/profile` 的既有做法） |

#### 4.1.2 展示层（`features/plan/presentation/`）

| 组件 / 页面 | 契约 |
|---|---|
| `PlanClarificationPage` | 四态：loading（`LoadingState`）/ error（`ErrorState` + 重试）/ empty（`EmptyState`：「现在没有需要确认的计划」）/ content（`PlanClarificationCard` 列表） |
| `PlanClarificationCard` | 用 `AppCard` 承载；标题为计划的目标描述（服务端下发）；逐问题渲染：问题文案 + 选项 `ModeChip`（单选）/ 自由文本 `TextField`（当 `allowFreeText`）；底部「提交」按钮（`press_scale` 既有交互） |
| 选项交互 | 单选（每问题一个答案）；点击已选 chip 可取消选择；`allowFreeText` 为真且未选任何选项 → 使用输入框内容 |
| 提交按钮启用条件 | 至少一个问题有答案（选项或非空自由文本）；否则 disabled |
| 提交后 | 成功后刷新列表（角标同步）；失败按 §4.1.1 错误映射处理（不清空用户输入） |
| 文案 | 全部中文；**不得自创风格**（沿用设计系统 `principles.md` §5.3 的语气）；后端下发的 `label` 原样展示 |

#### 4.1.3 入口与路由契约

| 项 | 契约 |
|---|---|
| 路由 | `GoRoute(path: '/plan', builder: ...)` 追加进 `app_router.dart` 既有 `GoRoute` 列表（`:169-249`）；`redirect`（`:161`）链不受影响 |
| Tab 归属 | **不新增 Tab**（`ShellTab` `:92` 与 `app_tab_bar` 已冻结为 5 Tab，见 `MEV-013`/V5 决策）→ 入口走**已有页面内的卡片/行**（D3） |
| 入口位置 | 首页（`features/home`）顶部「待确认」卡片；存在 pending 时显示数量角标；点击 → `context.push('/plan')` |
| 空态 | 无 pending 时首页不显示该卡片（避免长期占位）；`/plan` 直达时显示 `EmptyState` |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **客户端走结构化端点（R2），与 `PLN-004`（R1）并存** | R1 保证「不装新版本也能答」；R2 提供更优交互。两者复用同一 `resume_from_answers` 与 `mark_answered`，语义一致（不会出现两套状态） |
| D2 | **新增独立 feature `features/plan/`** | 仓库纪律禁止 `features/*` 互相 import；计划澄清是独立领域，不能塞进 `chat` 或 `memory` |
| D3 | **不新增 Tab，改用「首页卡片 + 直达路由」** | Tab 数量是 IA 决策（V5 已定 5 Tab）；澄清是**低频临时**状态，不配得一个常驻 Tab（也避免空态长期占位） |
| D4 | **只用既有设计系统组件** | 设计系统是 UI 唯一真源；自造组件会破坏 token 一致性与 golden 基线 |
| D5 | **端上零映射、零排序** | `label` 与 `options` 顺序由服务端决定（对齐记忆页既有纪律）；端上猜测会与服务端答案语义不一致（`value` 才是程序标识） |
| D6 | **错误不清空用户输入** | 404/409 的刷新会重建卡片；422/网络错误必须保留已填内容，否则用户要重填（体验硬伤） |
| D7 | **不做本地草稿持久化** | 单页短交互；持久化引入一致性议题，收益低（§3.2 第 7 条） |
| D8 | **依赖修正为 `PLN-007`** | 客户端需要结构化端点；registry 记为依赖 `PLN-004` 是按「对话轮次」路线写的，与 R2 落地后的实际依赖不符——本 Detail 显式登记该修正 |

### 4.3 数据流

```text
首页（features/home）→ 有 pending → 「待确认」卡片（角标 N）→ context.push('/plan')
   ▼
PlanClarificationPage → repo.listPending() → GET /plans/clarifications/pending（PLN-007）
   ▼
PlanClarificationCard × N（AppCard）
   逐问题：问题文案（服务端） + ModeChip 选项（服务端 label）｜TextField（allowFreeText）
   提交 → repo.submit(planId, {q1:{value}, q2:{freeText}})
        → POST /plans/{planId}/clarify（PLN-007）
        → 后端 resume_from_answers（PLN-004）→ mark_answered（PLN-003）→ 重新提案（PLN-002/PLN-001）
   ▼
成功 → 刷新列表 + 角标；失败（404/409）→ 提示 + 刷新；422/网络 → 提示 + 保留输入

红线：后端零改动；不做审批 UI；只用设计系统组件；端上零映射
```

### 4.4 依赖与边界

| 类别 | 内容 |
|---|---|
| 允许依赖 | 本 feature 内 `data/` / `domain/` / `presentation/`；`core/network`（Dio 客户端）；`design_system/**`（只读消费）；`app/router/app_router.dart`（追加 1 条路由）；`features/home`（仅新增入口卡片） |
| 禁止依赖 | 其他 `features/*` 的 presentation（仓库纪律）；`apps/backend/**`（零改动）；设计系统组件源码（不得修改） |
| Preserve 断言 | 既有 5 个 Tab 与 `app_tab_bar` 行为不变；既有路由（`:169-249`）与其参数不变；`redirect`（`:161`）逻辑不变；既有页面零回归 |
| 被依赖契约 | `PLN-009`（审批 UI）将在同一 `features/plan/` 内扩展（复用页面骨架与卡片形态） |
| 待定项 | ① 入口最终位置（首页卡片 vs 「我的」行）——**不阻塞**（默认首页卡片，可按视觉评审调整）；② 是否需要在提交后自动跳回首页——**不阻塞**；③ 多计划并存时的卡片排序（按 `createdAt` 升序 / 降序）——**不阻塞**，默认升序（先出现的先答） |

## 7. Testing Requirements

### 7.1 Focused（`apps/mobile/test/features/plan_page_test.dart`）

| 用例名 | 断言 |
|---|---|
| `repository requests pending endpoint` | `listPending()` → 请求 `GET /plans/clarifications/pending`，解析出 `planId` / `questions` |
| `repository submits structured answers` | `submit(planId, {...})` → `POST /plans/{planId}/clarify`，body 为 `{answers: {q1:{value}, q2:{freeText}}}` |
| `repository maps 404 and 409 distinctly` | 404 → 「不再需要回答」文案；409 → 「已被回答或已取消」文案 |
| `card renders options from server order` | 三个选项按服务端顺序渲染；端上未做排序（D5） |
| `card allows single selection and deselection` | 点选项选中；再点取消；不出现多选冲突状态 |
| `card shows free text field only when allowed` | `allowFreeText=true` → 显示输入框；`false` → 不显示 |
| `submit disabled until at least one answer` | 无任何答案 → 按钮 disabled；填一个 → enabled |
| `page shows empty state when no pending` | 空列表 → `EmptyState` 可见，无错误态 |
| `page shows error state with retry` | 请求失败 → `ErrorState` + 重试按钮可用 |
| `submit success refreshes list` | 提交成功 → 重新调用 `listPending`（计数 +1） |
| `submit 422 keeps user input` | 422 → 提示可见且输入内容仍在（D6） |
| `submit 404 refreshes and informs` | 404 → 提示 + 触发刷新 |
| `home entry hidden when no pending` | 无 pending → 首页无该卡片 |
| `home entry badge shows pending count` | 2 条 pending → 角标显示 2；点击跳转 `/plan` |
