### 2.2 为什么必须做

1. **R1（对话轮次）无法被「点选」**：`PLN-004` 让用户能打字答复；结构化端点让答复变成**受控的 `value` 集合**，既提升体验（`PLN-006` 卡片依赖它），也彻底消除「检出误判」（端点不经过自然语言解析）。
2. **它是 `PLN-006` / `PLN-009` 的共同基础**：移动端卡片与审批 UI 都需要「列出待办 + 提交裁决」的端点语义（澄清与审批共用同一 `/plans` 前缀与守卫风格）。
3. **Web 端缺口必须补**：基线 §3.6 记录「计划审批无前端/移动端入口」，`MEV-013` 只补了记忆面板——本任务让**计划域**在 Web 可核验（含澄清与审批），是「可观测」纪律的一部分。

### 2.3 在本版本中的位置

P2 第 2 个任务：后端出口 + Web 视图。`PLN-006`（移动端）与 `PLN-009`（审批 UI）在其上落地。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 端点契约

| 端点 | 鉴权 | 语义 |
|---|---|---|
| `GET /api/v1/plans/clarifications/pending` | `Depends(require_user)` | 返回当前用户**待澄清**列表（`list_pending(user_id)` `PLN-003` §4.1.3）；`limit` 缺省 `CLARIFY_PENDING_LIMIT = 20`（模块常量）、`ge=1`、`le=50`；空 → 200 + `items: []` |
| `POST /api/v1/plans/{plan_id}/clarify` | `Depends(require_user)` | body：`{answers: {<question_id>: {"value": str} \| {"freeText": str}}}`；调 `resume_from_answers(user_id, plan_id, answers)`（`PLN-004` §4.1.2）；返回 `{plan_id, outcome, round}` |

| `outcome` 取值（冻结） | 含义 |
|---|---|
| `clarified` | 已收答复并重新提案，**新计划仍需澄清**（新 pending 已登记） |
| `activated` | 已收答复并重新提案，计划已 `active` |
| `pending_approval` | 已收答复并重新提案，计划停在 `validated` 等审批（`plan_require_approval=True`） |
| `stale` | 提交时该计划**已无可答澄清**（幂等重放情形）→ 端点映射 **409** |

#### 4.1.2 模型（`plans.py` 追加，不改 `:27-44` 既有四个）

| 模型 | 字段 |
|---|---|
| `ClarificationOptionOut` | `value` / `label` |
| `ClarificationQuestionOut` | `id` / `question` / `options[]` / `allow_free_text` |
| `PendingClarificationOut` | `plan_id` / `goal_id` / `round` / `created_at` / `questions[]` |
| `PendingClarificationsOut` | `generated_at` / `total` / `items[]` |
| `ClarifyAnswerIn` | `value: str \| None` / `free_text: str \| None`（**二者恰一**，`@model_validator` 校验） |
| `ClarifyAnswersIn` | `answers: dict[str, ClarifyAnswerIn]`（`min_length=1`） |
| `ClarifyPlanOut` | `plan_id` / `outcome` / `round` |

> **不暴露机制字段**：响应不得含 `id`（trigger_registry 行 id）/ `priority` / `attempt_count` / `last_error` 等载体内部字段。

#### 4.1.3 状态码契约

| 场景 | 码 | 语义 |
|---|---|---|
| 成功 | 200 | `GET` 列表 / `POST` 已收答复 |
| 无令牌 / 无效 | 401 | `require_user` |
| 计划属于他人 | 403 | 「不得读写他人数据」（沿用 `memory.py:27` 文案风格） |
| 计划不存在 | 404 | 对齐既有 `NOT_FOUND_DETAIL`（`plans.py:23`） |
| 提交时已无待澄清（含重复提交） | 409 | `outcome == "stale"`；对齐既有 `NOT_PENDING_DETAIL`（`:24`）风格 |
| 答复非法（字段缺失 / 二者都填 / 未知 `question_id` / 超出问题数） | 422 | FastAPI 校验 + 服务层校验 |

#### 4.1.4 Web 视图契约（`apps/frontend/src/features/plans/`）

| 项 | 契约 |
|---|---|
| 文件 | `PlansView.tsx`（页面）+ `PlanClarificationCard.tsx`（澄清卡片）+ `PlanApprovalRow.tsx`（审批待办只读行） |
| API 层 | `apps/frontend/src/api/rest.ts` 追加 `fetchPendingClarifications()` / `submitClarification(planId, answers)` / `fetchPendingPlans()`（后者复用既有审批端点 `GET /plans/pending`） |
| 类型 | `apps/frontend/src/types/backend/plans.ts` |
| 挂载 | 在 `components/shell/workbench` 的既有视图切换中追加一个入口（**不引入路由库**） |
| 交互 | 澄清卡片：选项（radio/按钮）+ 自由文本 + 提交；成功后刷新；失败显示错误；审批行：只读展示（动作归 `PLN-009`） |
| 样式 | 沿用既有 Tailwind 变量与 `components/ui`（不新造设计 token） |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **澄清走 `POST .../clarify`（结构化），与 `PLN-004` 的对话检出并存** | 两条恢复路径共享同一 `resume_from_answers`，状态只有一处（`PLN-003` 行）→ 不存在「两套真相」 |
| D2 | **端点只调 service，不碰仓储** | API 层铁律（§3.2 第 3 条）；也让后续替换载体（如未来专用表）不动端点 |
| D3 | **`outcome` 显式枚举而非布尔** | 客户端需要区分「还要再问」「已激活」「等审批」三种后续行为（`PLN-006` 的角标与刷新策略依赖它） |
| D4 | **重复提交映射 409 而非 200** | `stale` 是「你的答复没用了」的事实，客户端需要刷新列表而不是静默成功（`PLN-006` §4.1.1 的错误映射与之对齐） |
| D5 | **Web 不引入路由库** | 前端是调试控制台，靠 `App.tsx:16` 的 hash 切换；引入 router 属架构变更且无收益 |
| D6 | **不重复实现审批端点** | 既有三端点已验收；本任务只**读**审批待办 |
| D7 | **不暴露载体内部字段** | 载体（`trigger_registry`）是内部机制；对外只暴露「计划 + 问题 + 选项」语义 |
| D8 | **`limit` 上限 50** | 澄清是低频状态；上限护栏与记忆搜索（`MEV-011`）同源 |

### 4.3 数据流

```text
【移动端 PLN-006 / Web PlansView】
   GET /plans/clarifications/pending → require_user（auth.py:116）
        → services/goal/clarification.list_pending(user_id)（PLN-003）
        → 200 {generated_at, total, items[{plan_id, goal_id, round, created_at, questions[]}]}
   POST /plans/{plan_id}/clarify  body {answers:{q1:{value}, q2:{freeText}}}
        → 服务层校验（question_id ∈ 载荷、二者恰一）→ 422 或继续
        → clarification.resume_from_answers(user_id, plan_id, answers)（PLN-004）
              归一 → mark_answered（行 done）→ propose_plan（PLN-002）→ PLN-001 闸（round+1）
        → 200 {plan_id, outcome ∈ clarified|activated|pending_approval} ｜ 409 stale

【Web 只读审批】GET /plans/pending（既有 :51）→ 只读列表（动作归 PLN-009）

红线：API 层零仓储依赖；既有三端点零改动；不引入前端路由库；不暴露载体字段
```

### 4.4 依赖与边界

| 类别 | 内容 |
|---|---|
| 允许依赖 | `app/api/v1/{auth,schemas}.py`、`app/services/goal/clarification.py`（唯一服务入口）、`app/core/settings/plan.py`（只读） |
| 禁止依赖 | `app.repositories.*`（API 层铁律）；`app.application.*`；`app.services.planning/**`（包断言）；`langchain` |
