## 2. Background

### 2.1 现状：读面只能「全量 + 四分组」，没有任何定位手段

| 事实 | 证据 |
|---|---|
| 端点只有 `limit` 一个参数 | `apps/backend/app/api/v1/memory.py:51`（`@memory_router.get("/items", response_model=MemoryItemsOut)`）、`:52-55`（`def list_items(limit: int = Query(default=200, ge=1, le=200), user_id: str = Depends(require_user))`） |
| 读面入口只有全量列表 | `apps/backend/app/services/memory/product_view.py:296`（`list_product_memories(user_id, limit=200) -> ProductMemoryList`）、`:134`（`ProductMemoryList`）、`:113`（`ProductMemoryItem`）、`:127`（`ProductMemoryGroup`） |
| 分组与来源映射是**冻结表**（不可改） | `:39`（`GROUP_ORDER`）、`:41-46`（`GROUP_LABELS`）、`:48-58`（`TYPE_TO_GROUP`，9 键）、`:60-68`（`TYPE_LABELS`）、`:70-82`（`SOURCE_LABELS`，11 键）、`:143`（`group_for`，未映射抛 `UnknownMemoryTypeError`） |
| 仓储只有两种 active 查询，均无时间/层维度 | `apps/backend/app/repositories/memory_repository.py:85`（`list_active(user_id, character_id, limit=20)`）、`:128`（`list_active_by_types(user_id, character_id, types, limit=200)`） |
| 信封响应模型 | `apps/backend/app/api/v1/schemas.py:529-534`（`MemoryItemsOut`：`generated_at` / `total` / `added_this_week` / `groups` / `degraded`）、`:523-526`（`MemoryGroupOut`）、`:508-520`（`MemoryProductItemOut`） |
| 会被影响的既有断言（**不可静默改**） | `apps/backend/tests/v50/test_memory_product_view.py:86`（`test_group_table_is_frozen`）、`:100`（`test_group_order_and_labels_are_frozen`）、`:118`（`test_groups_always_four_in_order_even_when_empty`）、`:140`（`test_total_matches_group_sum`）；`apps/backend/tests/v50/test_memory_api.py:72`（`test_list_items_returns_grouped_envelope`）、`:88`（`test_list_items_does_not_leak_mechanism_fields`） |
| 检索器有副作用，**不得**用于只读搜索 | `apps/backend/app/services/memory/retriever.py:322`（`record_reinforce`）、`:323-330`（trace） |

### 2.2 为什么必须做

1. **记忆可见性目前是「有出口但不可用」**：用户记忆一旦过百（`docs/agent-evolution-plan-2026-10.md` §2.2 G-M7），四分组列表只能滚动查找——「记忆可见」这条设计原则在产品层面打了折扣。
2. **它是 M2 与 M3 结构的必要出口**：`MEV-005` 引入 `layer`、`MEV-009/010` 引入关系后，用户（与调试面）需要能**按层/按类型**看，否则这些结构只对开发者可见。
3. **必须复用既有只读路径而不是走检索器**：检索器会 `record_reinforce`（`:322`）并落 trace（`:323-330`）——搜索是**浏览行为**，若让它改变 salience，会污染记忆生命周期（本任务最关键的纪律）。

### 2.3 在本版本中的位置

M3 第 3 个任务；为 `MEV-013`（Web/移动端搜索入口）提供冻结的 API 契约。它不改任何写面与机制。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 端点参数（`GET /api/v1/memory/items`）

| 参数 | 类型 | 缺省 | 语义 | 校验 |
|---|---|---|---|---|
| `limit` | `int \| None` | `None` | 条数上限。**无筛选/q 时**：`None` → 200（基线语义，`le=200`）；**有筛选/q 时**：`None` → `memory_search_limit_default`，显式值须 `≤ memory_search_limit_max` | `ge=1`；越上限 → **422** |
| `q` | `str \| None` | `None` | 关键词。归一化后对 `content` 做**子串**匹配（含中文）；空白串视为 `None` | 长度 `≤ 100`；超长 → **422** |
| `type` | `str \| None` | `None` | 按存储类型筛选；必须 ∈ `STORAGE_MEMORY_TYPES`（9 值） | 非法 → **422**（fail-closed） |
| `layer` | `str \| None` | `None` | 按层筛选；必须 ∈ `MEMORY_LAYERS`（`MEV-005` §4.1.3，2 值） | 非法 → **422** |
| `since` / `until` | `str \| None` | `None` | 按 `created_at` 的闭开区间（ISO 8601 日期或日期时间）；`since > until` → **422** | 格式非法 → **422** |

**响应**：仍为 `MemoryItemsOut`（四分组信封），新增 2 顶层字段（§4.1.3）。身份仍经 `Depends(require_user)`（`apps/backend/app/api/v1/auth.py:116`）。

#### 4.1.2 筛选与搜索语义（`product_view.search_product_memories`）

| 项 | 契约 |
|---|---|
| 入口 | `search_product_memories(user_id, *, q=None, memory_type=None, layer=None, since=None, until=None, limit=None) -> ProductMemoryList` |
| 取数 | `memory_repository.list_active_filtered(user_id, character_id=CHARACTER_ID, types=[memory_type] if memory_type else None, layer=layer, since=since, until=until, limit=<取数上限>)` |
| **基线等价** | 无筛选且 `q is None` → **调用既有 `list_product_memories`**（同一条代码路径），保证既有字段逐项一致 |
| `q` 匹配 | 对 `content` 做归一化（`strip` + 连续空白折叠）后**大小写不敏感子串**匹配；不做分词、不做同义扩展、不做语义近似（D2） |
| 组合语义 | 多条件为**交集**；空结果 → 四组俱在且 `items: []`（对齐 `:118` 的既有纪律） |
| 排序 | 组内按 `last_updated` **降序**；同值按 `id` 升序（确定性）；**不改**既有基线路径的组内次序 |
| 分组 | 仍用 `group_for`（`:143`）+ `GROUP_ORDER`（`:39`）；**不改映射表** |
| 计数 | `total` = 本次筛选后**实际返回**的条数（与 `Σ len(items)` 同口径，对齐 `:140`）；`matched_total` = 满足条件的**全量**条数（在 `limit` 截断前统计，供「还有 N 条」提示） |
| 副作用 | **零**：不调 `retrieve`、不 `record_reinforce`、不落检索 trace、不改 `last_accessed_at` |
| 降级 | 仓储异常 → 与既有列表路径同策略（不新增吞异常点）；派生异常按既有 `degraded` 语义（`:134` 信封字段）处理 |

#### 4.1.3 信封新字段（`schemas.py:529-534`）

| 字段 | 类型 | 缺省 | 语义 |
|---|---|---|---|
| `filtered` | `bool` | `False` | 本次是否应用了任一筛选/搜索条件 |
| `matched_total` | `int` | `total` | 条件命中的全量条数（未筛选时 == `total`） |

> **兼容纪律**：只**新增**字段，不删除/改名既有 5 个字段（`generated_at` / `total` / `added_this_week` / `groups` / `degraded`）；`test_list_items_returns_grouped_envelope`（`:72`）与 `test_list_items_does_not_leak_mechanism_fields`（`:88`）须保持不变并通过。

#### 4.1.4 新设置字段（`app/core/settings/memory.py`）

| 字段 | 类型 | 默认 | 语义 | 校验 |
|---|---|---|---|---|
| `memory_search_limit_default` | `int` | `20` | 有筛选/q 且未显式给 `limit` 时的条数 | `ge=1`、`le=memory_search_limit_max` |
| `memory_search_limit_max` | `int` | `50` | 有筛选/q 时的条数上限 | `ge=1`、`le=200`（不超过既有基线上限） |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **无参路径完全复用既有函数** | 「无参逐项一致」是最硬的可验证判据；分支越多风险越大 |
| D2 | **搜索用词法子串，不接检索器** | 检索器有 `record_reinforce`（`:322`）与 trace（`:323-330`）副作用——搜索不得改变记忆的生命周期（§2.2 第 3 条） |
| D3 | **`type` / `layer` 非法即 422** | 与 `group_for`（`:143`）的「未映射抛错」纪律一致（fail-closed）；静默忽略会让用户以为筛选生效 |
| D4 | **四分组契约不变，用 `filtered` / `matched_total` 表达筛选态** | 保留既有契约（`:86` / `:100` / `:118` 冻结用例）同时提供筛选反馈，避免破坏客户端既有渲染 |
| D5 | **`total` 保持「返回条数」语义，全量另用 `matched_total`** | `total == Σ len(items)` 是既有硬约束（`:140`）；改 `total` 语义会破坏它 |
| D6 | **`limit` 语义随「是否有条件」切换默认值** | 无参保持基线 200；有条件时收紧到 20/50，防止「搜索即全量」 |
| D7 | **不做分页游标** | 记忆域 active 上限 200，游标收益低而一致性成本高 |
| D8 | **筛选在 SQL 层完成**（新只读函数），不在 Python 侧全量过滤 | 避免把 200 条读进内存再筛（性能）；与既有 `list_active_by_types`（`:128`）同风格 |
| D9 | **组内排序只在有条件时生效** | 无参必须与基线一致（含次序） |

### 4.3 数据流

```text
客户端（MEV-013 的搜索框）
   ▼ Authorization: Bearer <token> → require_user（auth.py:116）→ user_id
api/v1/memory.py::list_items（:52）
   ├─ 参数校验（type ∈ STORAGE_MEMORY_TYPES / layer ∈ MEMORY_LAYERS / since ≤ until / limit 上限）→ 422
   ├─ 无任何条件 → product_view.list_product_memories(user_id, limit)（:296，既有路径，逐项一致）
   └─ 有条件     → product_view.search_product_memories(...)
            ▼
        memory_repository.list_active_filtered(...)（★ 新增只读）
            ▼
        分组（group_for :143 + GROUP_ORDER :39，映射表不改）
        组内按 last_updated desc / id asc 排序
        计数：total（返回）/ matched_total（命中全量，截断前）
            ▼
        MemoryItemsOut（+ filtered / matched_total）→ JSON

零副作用红线：不调 retriever.retrieve、不 record_reinforce、不落检索 trace、不改 last_accessed_at
```
