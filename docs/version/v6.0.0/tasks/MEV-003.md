## 2. Background

### 2.1 现状：两张表都只覆盖了一部分类型

| 事实 | 证据 |
|---|---|
| 规范类型 7 项 | `apps/backend/app/services/memory/types.py:9-17`（`V2_MEMORY_TYPES`：user_preference / user_fact / experience / relationship_fact / commitment / milestone_event / behavior_pattern） |
| 遗留类型 2 项 + 映射 | `:19`（`LEGACY_MEMORY_TYPES`：important_event / relationship_event）、`:21-24`（`LEGACY_TYPE_ALIASES`：`important_event→experience`、`relationship_event→relationship_fact`）、`:26`（`STORAGE_MEMORY_TYPES` = 9 值）、`:28`（`DEFAULT_MEMORY_TYPE="user_fact"`）、`:44`（`normalize_type`）、`:53`（`storage_type`） |
| **亲和词表只有 4 键** | `:30-35`（`TYPE_AFFINITY_KEYWORDS`）：仅 `user_preference` / `user_fact` / `experience` / `relationship_fact`——**缺** `commitment` / `milestone_event` / `behavior_pattern` |
| 亲和词表是 `affinity` 分量的唯一来源 | `apps/backend/app/services/memory/retriever.py:75-80`（`_detect_query_types`）、`:113`（`_affinity_score`）；权重 `core/settings/memory.py:58`（`memory_weight_affinity` 默认 0.20） |
| **中文标签表只有 4 键** | `apps/backend/app/prompts/builder.py:35-40`（`MEMORY_TYPE_LABELS`）：`user_preference→偏好`、`user_fact→事实`、`important_event→事件`、`relationship_event→关系事件` |
| 标签的兜底路径会把原始枚举写进 prompt | `apps/backend/app/prompts/builder.py:443`（`MEMORY_TYPE_LABELS.get(m.type, m.type)`）→ `commitment` 等 5 个类型在 prompt 里以英文枚举出现 |
| 存储层确实允许这 9 值 | `apps/backend/app/core/db/memory.py:61-66`（`CheckConstraint ck_memories_type`，名 `:65`） |
| 另一处标签表（Insight，非本任务） | `apps/backend/app/prompts/builder.py:42-46`（`INSIGHT_TYPE_LABELS`） |

### 2.2 为什么必须做

1. **`affinity` 是 0.20 权重的确定性分量，但其覆盖面只有 4/7**：对 `commitment`（承诺）/ `milestone_event`（里程碑）/ `behavior_pattern`（习惯）三类记忆，`_detect_query_types`（`:75-80`）**永远无法命中**，等于这三类在打分上被系统性歧视——而它们恰恰是「角色是否记得约定 / 纪念日 / 用户习惯」最需要被召回的类型。
2. **prompt 里出现英文枚举是可见的质量缺陷**：`builder.py:443` 的兜底把 `commitment` 原样写进 system 段（`builder.py:441-453`），既破坏中文一致性，也让模型难以利用该信息。
3. **修复成本极低、风险接近零**：只改两张静态表的键集合，**不引入任何新分支、不改打分数学、不新增设置**——是本版本性价比最高的一项。

### 2.3 在本版本中的位置

M1 第 3 个任务，为 `MEV-004`（可观测与门槛）提供「扩表后 affinity 生效」的对照基础；也是 `MEV-008`（分层配额）的前置质量项——配额只有在打分能区分类型时才有意义。

## 3. Scope

### 3.1 In Scope

1. `TYPE_AFFINITY_KEYWORDS` 补齐至 **7 个规范类型的全覆盖**（逐类型给基础词 + 同义词）。
2. `MEMORY_TYPE_LABELS` 补齐至 **9 个存储类型的全覆盖**（7 规范 + 2 遗留）。
3. `builder.py` 未知类型的兜底路径补 `logger.warning`（保留原值回落，**不抛异常**）。
4. 新增「键集 == 类型集」的**枚举断言用例**（防止未来新增类型时再次漏表）。
5. 词表与标签表的**键顺序与类型常量顺序对齐**（可读性 + 便于 diff 审查）。

### 3.2 Out of Scope（明确禁止扩张）

| # | 禁止项 | 理由 |
|---|---|---|
| 1 | **不改任何打分数学**（`_recency` `:98` / `_structured_score` `:106` / `_affinity_score` `:113`） | 本任务是**数据扩容**，不是算法调整；改数学会让 `MEV-001` 的「重排前后名次」与 M2 配额失去基准 |
| 2 | **不改 `V2_MEMORY_TYPES` / `STORAGE_MEMORY_TYPES` / `LEGACY_TYPE_ALIASES` 的值与数量** | 类型体系是存储层 CHECK（`core/db/memory.py:61-66`）的镜像；改值等于改 schema（需迁移），超出本任务 |
| 3 | **不引入外部词表 / 分词库 / 同义词包** | 新增依赖违反最小依赖纪律，且词表规模属人工维护资产（与仓库「静态资产」惯例一致） |
| 4 | **不做关键词权重分级**（如「强/弱关键词」） | 会引入新的打分参数与调参面（R-M1），且当前 `_affinity_score` 只做命中计数 |
| 5 | **不改 `_detect_query_types` 的判定方式**（仍是子串命中） | 改判定属算法变更（第 1 条同理） |
| 6 | **不改 `INSIGHT_TYPE_LABELS`（`:42-46`）** | Insight 类型体系属反思域，与本任务无关 |
| 7 | **不改记忆段 prompt 结构**（`builder.py:441-453`） | 只补标签表 + warning；段落结构、预算（`:301`）与格式（`:443`）不变 |
| 8 | **不新增 `*_enabled` 开关 / 迁移 / 表** | `tasks.md` §0.2 / §0.4；纯静态数据 |

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 词表契约（`app/services/memory/types.py`）

| 项 | 契约 |
|---|---|
| `TYPE_AFFINITY_KEYWORDS` | `dict[str, tuple[str, ...]]`；**键集合必须等于 `V2_MEMORY_TYPES`（7 项）**；值为非空元组，元素均为非空字符串、无重复 |
| 键的取值 | 仅**规范类型**（7 项）。遗留类型不单独建键——它们经 `normalize_type`（`:44`）/ `storage_type`（`:53`）归一后落到规范类型 |
| 覆盖要求（冻结值域，具体词条由实现冻结） | `user_preference`（保留既有 + 同义词）、`user_fact`（保留既有 + 同义词）、`experience`（保留既有 + 同义词）、`relationship_fact`（保留既有 + 同义词）、**新增** `commitment`、**新增** `milestone_event`、**新增** `behavior_pattern` |
| 既有词条 | **不得删除**（既有条目已被线上行为与测试依赖；只做「新增键 + 补同义词」） |
| 判定语义（不变） | 命中 = `keyword in query`（子串），命中一个类型即记 1 次命中（沿用 `retriever.py:75-80`） |

#### 4.1.2 标签表契约（`app/prompts/builder.py`）

| 项 | 契约 |
|---|---|
| `MEMORY_TYPE_LABELS` | `dict[str, str]`；**键集合必须 ⊇ `STORAGE_MEMORY_TYPES`（9 项）**（7 规范 + 2 遗留） |
| 遗留类型的标签 | `important_event→事件`、`relationship_event→关系事件`（**保留既有措辞**，不改） |
| 规范类型的标签 | 6 项为**新增**（`experience` / `relationship_fact` / `commitment` / `milestone_event` / `behavior_pattern` 及 `user_fact` 视既有表定）；措辞须与移动端记忆页既有中文口径一致（`apps/mobile/lib/features/memory` 由服务端下发标签，**不得**与端上文案冲突） |
| 兜底路径 | `builder.py:443` 保持 `.get(m.type, m.type)`，但**新增**：当 `m.type not in MEMORY_TYPE_LABELS` 时 `logger.warning("unknown memory type for label: %s", m.type)`；**不抛异常**（prompt 装配不得因数据异常失败——记忆域降级纪律） |
| 标签唯一性 | 9 个标签两两不同（避免用户/模型混淆「事件」与「关系事件」类同义重复） |

#### 4.1.3 顺序契约

`TYPE_AFFINITY_KEYWORDS` 与 `MEMORY_TYPE_LABELS` 的键顺序**按类型常量顺序**排列（`V2_MEMORY_TYPES` 在前，`LEGACY_MEMORY_TYPES` 在后），便于 diff 与人工审查。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **词表键 = 7 规范类型（不含遗留）**，标签键 = 9 存储类型 | 两条路的使用点不同：词表消费方（`retriever.py:75-80`）处理的是**归一后**的类型；标签消费方（`builder.py:443`）直接读库内 `m.type`（CHECK 允许 9 值），故必须分别覆盖 |
| D2 | **只增不删既有词条** | 既有词条是当前线上召回行为的组成部分；删除会造成不可预期的召回退化，且无法在本任务的判据里体现 |
| D3 | **未知类型 warning + 回落原值（不抛）** | prompt 装配失败会导致整轮对话不可用；记忆域既有纪律是「异常只降级不阻断」（`docs/agent-evolution-plan-2026-10.md` §2.5 R-M4） |
| D4 | **新增「键集 == 类型集」枚举断言** | 本任务暴露的本质问题是「新类型入库时漏更新静态表」；只有断言才能防止再次发生（与既有 `API-007` 的「映射表覆盖全部 9 值、无兜底分支」纪律同源） |
| D5 | **不引入关键词权重分级** | 会新增调参面与设置项，违反 R-M1 预算纪律与「只增词表」的最小改动原则 |
| D6 | **标签措辞以「服务端唯一真源」为准** | 移动端记忆页的分组/标签中文名**全部服务端下发、端上零映射**（`apps/mobile/lib/features/memory/presentation/memory_page.dart` 既有纪律）；本任务新增的标签会被该表复用，故必须一次定准，避免端上出现两套说法 |
| D7 | **本任务零设置** | 词表与标签是静态资产，不存在「需要灰度」的语义；设开关反而制造「部分开启」的不可解释状态 |

### 4.3 数据流

```text
【写入侧（零改动）】ingest/evaluator/lifecycle → memories.type ∈ 9 值（ck_memories_type core/db/memory.py:61-66）

【读侧-召回】retriever.py:75-80 _detect_query_types(query)
   └─ 查 TYPE_AFFINITY_KEYWORDS（★ 本任务扩至 7 键）→ 命中类型集合

【读侧-注入】prompts/builder.py:441-453 记忆段装配
   └─ :443 MEMORY_TYPE_LABELS.get(m.type, m.type)（★ 本任务扩至 9 键）
        └─ 未命中 → logger.warning + 回落原值（不抛）

【零改动声明】打分公式、过滤、加固、trace、会话预算、DB 结构、迁移链 —— 全部不动
```
