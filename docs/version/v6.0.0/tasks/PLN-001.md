## 2. Background

### 2.1 现状：规划是「一次提案即定稿」，没有信息补齐环节

| 事实 | 证据 |
|---|---|
| 规划主路径：`plan_goal` 一次提案后即决定激活 | `apps/backend/app/services/goal/planning.py:404`（`plan_goal(goal_id: str, trigger: str, world_facts: dict \| None = None) -> dict`）；`:497-498`（`if not settings.plan_require_approval: activate_plan(...)`）；`:391`（`activate_plan(goal_id, plan_id)`） |

### 2.2 为什么必须做

1. **计划质量问题的主要来源是「信息不足」而非「模型不够强」**：目标描述常缺关键约束（时间窗 / 预算 / 场所），而当前链路只能猜——猜错后的代价是「计划被驳回」或「执行出无意义动作」（`docs/agent-evolution-plan-2026-10.md` §3.2 G-P1）。
2. **它是三层闸门的第一层，缺了它后面的两层都不完整**：审批闸（计划级许可）与工具确认（执行授权）都已落地，唯独缺「信息补齐」。三层语义不同、不可合并（§3.3.1）。
3. **必须与既有审批闸同构**：停靠复用 `validated`（`approval.py:24` 已把 `validated` 定义为「待批」），这样「澄清 → 审批」天然串联且**零新增状态值**（D1/D2）。

### 2.3 在本版本中的位置

P1 第 1 个任务（P 线地基）：定义澄清的**判定契约与载荷结构**，后续 `PLN-002`（上下文与 prompt 槽位）、`PLN-003`（停靠载体）、`PLN-004`（恢复）、`PLN-005`（超时）全部依赖它。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 澄清载荷结构（`app/services/goal/clarification.py`）

| 结构 | 字段 | 契约 |
|---|---|---|
| `ClarificationOption` | `value: str` / `label: str` | `value` 稳定标识（写入答复时使用）；`label` 中文文案（展示用）；两者均非空、长度 ≤ 40 |
| `ClarificationQuestion` | `id: str` / `question: str` / `options: list[ClarificationOption]` / `allow_free_text: bool` | `id` 稳定（`q1` / `q2`…，同一轮内唯一）；`question` ≤ 120 字；`options` 允许为空**仅当** `allow_free_text=True` |
| `ClarificationPayload` | `round: int`（1-based）/ `questions: list[ClarificationQuestion]` / `plan_id: str \| None` | 载荷随计划落库；`plan_id` 在持久化后回填（`PLN-003`） |
| `ClarificationDecision` | `needed: bool` / `payload: ClarificationPayload \| None` / `reason: str` | `reason` 取值冻结：`off` / `accepted` / `round_exhausted` / `too_many_questions` / `weak_options` / `empty` / `error` |

#### 4.1.2 判定闸契约（`evaluate_clarification`）

| 条件（全部满足才澄清） | 不满足时的 `reason` |
|---|---|
| `plan_require_clarification is True` | `off` |
| 提案的 `clarification` 非 `None` 且 `questions` 非空 | `empty` |
| `round < plan_clarify_max_rounds`（`round` = 「已完成的澄清轮次」） | `round_exhausted` |
| `len(questions) <= plan_clarify_max_questions` | `too_many_questions` |
| 每个问题：`len(options) >= plan_clarify_option_min` **或** `allow_free_text is True` | `weak_options` |
| 问题 `id` 在同轮内唯一且非空 | `error`（校验失败按异常路径处理） |

| 项 | 契约 |
|---|---|
| 触发失败（模型未给澄清） | `needed=False`、`reason="empty"` → 按现状继续（**不激活变更**） |
| 异常 | 任何校验/装配异常 → `needed=False`、`reason="error"`、`logger.warning` + trace，**不抛** |
| 轮次计数来源 | 由 `PLN-003` 的停靠载体提供（本任务以形参 `round` 接收，默认 `0`） |
| trace | 经既有 `runtime_traces` 记录 `clarify_decision`（`reason` / `round` / `questions_count`）；**不写 `loop_runs.steps` 新键** |

#### 4.1.3 `plan_goal()` 插入点契约

| 项 | 契约 |
|---|---|
| 位置 | `propose_plan`（`:350`）返回之后、`if not settings.plan_require_approval: activate_plan(...)`（`:497-498`）**之前** |
| 命中澄清时 | 计划落库为 `validated`（沿用既有落库路径）→ 返回 `{"status": "needs_clarification", "plan_id": ..., "clarification": <payload>}`；**不调用 `activate_plan`**、**不写 `rejection_reason`** |
| 未命中时 | 走既有分支（`validated → active` 或停在 `validated` 等审批）——**逐字节不变** |
| 返回值兼容 | `plan_goal` 既返回 `dict`；新增 `status` 取值 `"needs_clarification"` 是**新增枚举**（既有消费者需容忍未知 `status`——由 §7.1 断言覆盖）。**若既有消费者对 `status` 做了穷举断言，须按契约扩展显式登记** |
| `PlanningProposal` 扩展 | 新增字段**必须带默认值** `None`，既有构造调用（含测试）零改动 |

#### 4.1.4 新设置字段（`app/core/settings/plan.py`，追加于 `:43` 之后，**不改既有字段**）

| 字段 | 类型 | 默认 | 语义 | 校验 |
|---|---|---|---|---|
| `plan_require_clarification` | `bool` | `False` | 策略位：是否启用澄清闸（命名对齐 `plan_require_approval` 先例） | — |
| `plan_clarify_max_rounds` | `int` | `1` | 单一目标允许的澄清轮次上限（**防无限追问**） | `ge=0`、`le=3`；`0` = 等价关闭 |
| `plan_clarify_max_questions` | `int` | `3` | 单轮问题数上限 | `ge=1`、`le=5` |
| `plan_clarify_option_min` | `int` | `2` | 单问题最少选项数（低于此且非自由文本 → 判 `weak_options`） | `ge=1`、`le=5` |

> `validate_plan_config`（`:45-73`）须增加交叉校验：`plan_require_clarification=True` 且 `plan_clarify_max_rounds==0` → 启动期 warning（不阻断）。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **判定与持久化解耦**：本任务只**返回**载荷，不落库 | 让判定可纯函数化单测；停靠载体（`PLN-003`）成为独立可替换件 |
| D2 | **不新增状态值**，命中澄清时计划仍落 `validated` | `validated` 是既有停靠态（`approval.py:24` 已定义为待批），`list_active_plans` 只认 `active` → 「停住即不执行」是既有语义，零迁移 |
| D3 | **`plan_require_clarification` 命名对齐既有审批策略位**（不叫 `plan_clarify_enabled`） | V4.0.0 裁决 9 禁 `*_enabled`；同域两个策略位命名必须一致 |
| D4 | **四道上限闸（轮次 / 问题数 / 选项强度 / 非空）** | 澄清的最大风险是「无限追问」（§3.5 H-P1）；四闸都必须在**判定时**拒绝，而不是靠 prompt 自觉 |
| D5 | **异常一律回落「不澄清」** | 规划链路是后台 job，抛异常会让目标卡在执行外；回落即「按现状提案」，与基线等价 |
| D6 | **trace 走 `runtime_traces`，不碰 `loop_runs.steps`** | `steps` 键集被 `test_agent_loop_core.py` 断言冻结；新增键会让该断言转红且无法静默修正 |
| D7 | **`PlanningProposal.clarification` 带默认 `None`** | 既有构造点（含测试 fixture）零改动 |
| D8 | **`status="needs_clarification"` 为新增枚举**，需显式登记 | 既有消费者若穷举 `status` 会受影响——必须在实现期扫描并显式扩展（不得静默改断言） |
| D9 | **澄清发生在审批之前** | 信息补齐应先于许可裁决（§3.3.1 三层顺序）；两者串联而非并行 |
| D10 | **`plan_clarify_max_rounds=0` 等价关闭** | 配置语义一致性（上限为 0 即不可能澄清），避免「开着但不生效」的困惑态 |

### 4.3 数据流

```text
goal_planning.plan_goal（:404）
   ① 前置闸（既有）→ propose_plan（:350）→ PlanningProposal（+ clarification?）
   ② ★ PLN-001 澄清判定闸
        evaluate_clarification(proposal, goal, round, settings)
          ├─ 四闸通过 → needed=True → 落库 validated → 返回 {"status":"needs_clarification", "clarification": payload}
          │                                  ✗ 不调 activate_plan（:391 / :497-498）
          └─ 不通过   → needed=False（reason 记录）→ 走既有分支（validated→active 或等审批）
   ③ trace：runtime_traces 记 clarify_decision（不写 loop_runs.steps 新键）

停靠与恢复：载荷持久化 = PLN-003；答复检出 = PLN-004；超时 = PLN-005
红线：off 时逐字节一致；异常回落；不新增状态值；不新增 steps 键
```
