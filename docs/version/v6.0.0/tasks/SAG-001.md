## 2. Background

### 2.1 现状：运行时有「阶段序列」但没有「Agent 身份」

| 事实 | 证据 |
|---|---|
| 唯一的 Agent 契约是运行时内核接口，**不含身份字段** | `apps/backend/app/application/agent_runtime/contracts.py:233`（`AgentRuntime` Protocol `@runtime_checkable` `:232`）、`:236-238`（唯一方法 `async def run(self, input: RuntimeInput, context: SessionContext) -> RunResult`）——**无** `name` / `role` / `tools` |
| Profile 是「Run-Kind → 阶段序列 + 预算档」，**不是 Agent 身份** | `apps/backend/app/application/agent_runtime/profiles.py:17`（`ProfileSpec`）、`:25-30`（字段 `run_kind` / `budget_tier` / `stages` / `llm_capable` / `critical` / `optional_stages`）、`:33`（`_PROFILE_TABLE`）、`:34` / `:51` / `:70`（三个既有 Profile） |
| **无运行时注册 API** | `profiles.py:80`（`get_profile`）、`:87`（`snapshot_profile`）——全文仅此两个读函数，无 `register_profile` |
| 模型档位可分流，但 **prompt 与主体解耦** | `apps/backend/app/application/agent_runtime/llm_gateway.py:89-95`（`acquire(user_id, capability, run=None, now=None, account=True) -> Grant`）、`:53-57`（`Grant` 字段仅 `granted` / `degraded` / `reason`）；`app/core/llm_factory.py:37`（`get_llm(profile_id)`）、`:74`（`set_llm`） |
| 阶段实现是**静态注册**的 | `apps/backend/app/application/agent_runtime/loop.py:215`（`STAGE_RUNNERS`）、`:221`（`register_stage_runner`，重复注册 fail-closed）、`:154`（`resolve_stages`）、`:389-391`（`_run_stages`，线性驱动） |
| Run 生命周期入口（身份需在此被消费） | `apps/backend/app/application/agent_runtime/controller.py:38-46`（`open_run(user_id, run_kind, trigger_type, reason, now=None, *, session_id=None) -> RunContext`）、`:57-66`（写 `loop_runs`）、`:137`（`close_run`） |
| 数据面已就绪（异步派发无需新建基建） | `apps/backend/app/core/db/autonomy.py:138`（`BackgroundJobRow`）、`:141-151`（含 `idempotency_key` unique）；`app/application/worker_loop.py:21-29`（`run_worker_loop`）；`app/services/memory/job_worker.py:41` / `:46`（`register_job_type` / `register_tick_hook`） |
| 缺口（规划稿已登记） | `docs/agent-evolution-plan-2026-10.md` §4.4 G-S1（无 Agent 身份/注册抽象）与 G-S2（无主体 → prompt 绑定） |

### 2.2 为什么必须做

1. **没有身份，子 Agent 只是「另一个函数」**：同一进程内并行两个「研究者」，若不能区分它们的 system prompt、工具作用域与预算，就无法保证行为与成本可控（`docs/agent-evolution-plan-2026-10.md` §4.4 G-S1/G-S2）。
2. **它是 `SAG-002` / `SAG-003` 的前置**：血缘（父/子 Run）需要「子是谁」；派发器需要「按身份取 prompt 与工具面」。
3. **必须与既有 Profile 机制同构而非平行**：基线 ADR-7（`docs/current-system-architecture-baseline.md:545`）要求「不另开阶段序列」——身份抽象必须**建立在 Profile 之上**（D2），而不是造第二套编排。

### 2.3 在本版本中的位置

S 线第 1 个任务：**仅在 `SAG-000` 裁决放开后**才有意义与合规性。落点形态由裁决选定（S-A 需运行时注册；S-C 只需在既有 Tool 注册面绑定身份）。

## 4. Technical Design Requirements

### 4.1 契约

> **前置声明**：下列契约是**候选形态**，最终形态取决于 `SAG-000` 的落点裁决（S-A 运行时注册 / S-B 按角色多实例 / S-C Agent-as-Tool）。本 Detail 在裁决前**不冻结**实现细节，只冻结「必须存在的 5 个身份要素」与「默认路径零回归」两条。

#### 4.1.1 `BaseAgent` 身份契约（5 要素，冻结）

| 要素 | 类型 | 语义 |
|---|---|---|
| `name` | `str` | 身份标识（唯一；点分命名空间，对齐 Tool 的命名惯例） |
| `role` | `str` | 角色短描述（用于观测与调试展示，**不参与 LLM 输入**） |
| `prompt_scope` | `str` | system prompt 作用域标识（用于解析 prompt 模板；**不得**是 prompt 全文） |
| `tool_scope` | `tuple[str, ...]` | 该身份允许的工具 id 白名单（fail-closed：不在白名单内即不可用） |
| `budget_tier` | `str` | 预算档（取值沿用既有 `main` / `light`，`llm_gateway.py:29-42`） |

#### 4.1.2 注册与解析契约

| 符号 | 契约 |
|---|---|
| 注册表 | 需提供按 `name` 查询的能力；**注册方式**（源码级 vs 运行时）由 `SAG-000` 裁决——若为源码级，则落 `agents.py` 模块常量（对齐 `profiles.py:33` 的 `_PROFILE_TABLE` 形态） |
| 重复注册 | **fail-closed**（抛错），对齐 `loop.py:221`（`register_stage_runner` 的既有纪律） |
| `resolve_prompt_scope(subject)` | 解析「主体 → prompt 作用域」；**未注册主体 → 返回基线默认作用域**（保证既有链路零行为变化） |
| 工具作用域判定 | 与既有 `ToolRegistry.resolve`（`app/services/tool/registry.py`）协同：`tool_scope` 是**收窄**而非替代（既有权限/确认/校验/归一/健康五段不变） |
| 与 Profile 的关系 | 一个 `BaseAgent` **映射到**一个既有形态的 Profile（或复用既有 Profile + 参数化 stages）；**不得**声明独立阶段序列（D2） |

#### 4.1.3 连线契约

| 项 | 契约 |
|---|---|
| 模型选择 | 仍经 `llm_gateway.acquire`（`:89`）与 `get_llm`（`:37`）；`budget_tier` 只作为输入之一 |
| prompt 选择 | **新增**绑定层：由 `prompt_scope` 决定 prompt 模板来源；既有调用方（未传身份）走默认作用域 |
| Run 打开 | 身份信息经 `open_run`（`:38`）的既有形参或新增**带默认值**的形参传递（不得改既有必填参数语义） |
| 观测 | 身份应可在 trace 中识别（便于 `SAG-002` 的参与树）；**不写 `loop_runs.steps` 新键**（键集断言冻结） |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **红线只在 `SAG-000` 放开**；本任务不触碰 | 实现者不得自行解禁（`SAG-000` D1） |
| D2 | **身份建立在 Profile 之上，不另开阶段序列** | 基线 ADR-7（`:545`）：Run Profile 唯一声明；平行编排会立即违反 RL-3/RL-4 |
| D3 | **默认路径（无身份）必须逐字节等于基线** | 既有前台/自治链路不能因新抽象而变化；这也是本任务最重要的回归判据 |
| D4 | **注册重复即 fail-closed** | 对齐 `loop.py:221` 的既有纪律：静默覆盖会让「哪个身份在跑」不可判定 |
| D5 | **`prompt_scope` 是标识不是内容** | 把 prompt 全文放注册表会让配置与代码混淆，且无法做版本管理 |
| D6 | **`tool_scope` 只收窄不扩权** | 子 Agent 不得获得比主链路更宽的工具面（安全底线） |
| D7 | **预算档沿用 `main` / `light`** | 与 `llm_gateway` 既有 tier 取值一致，不引入新档位（避免成本模型分叉） |
| D8 | **不写 `loop_runs.steps` 新键** | 键集被 `test_agent_loop_core.py` 断言冻结 |

### 4.3 数据流

```text
【裁决后】SAG-000 选定落点（S-A / S-B / S-C）
   ▼
SAG-001 交付
   BaseAgent（name / role / prompt_scope / tool_scope / budget_tier） + 注册表（fail-closed）
   resolve_prompt_scope(subject)  ← 未注册 → 基线默认作用域（D3）
        ▼
   Run 打开（controller.open_run :38，带默认值形参）→ 取身份
        ├─ prompt：由 prompt_scope 解析模板（新增绑定层）
        ├─ 模型：llm_gateway.acquire（:89）→ get_llm（:37）（既有逻辑不变）
        └─ 工具：tool_scope 与既有 ToolRegistry 五段协同（只收窄，D6）
   ▼
   trace 可识别身份（不写 loop_runs.steps 新键，D8）

红线：不改既有 3 Profile / 不新增阶段本体 / 不改 llm_gateway 裁决 / 默认路径零回归
```

| AC# | 判据 | 验证方式 |
