## 2. Background

### 2.1 现状：`trigger_registry` 是既有的「待办/待答」载体，但 `trigger_type` 有 CHECK 白名单

| 事实 | 证据 |
|---|---|
| 载体表结构（列齐备，`payload` 为 JSON、`trigger_key` 唯一） | `apps/backend/app/core/db/autonomy.py:162`（`TriggerRegistryRow`）、`:163`（`__tablename__`）、`:165-182`（列：`id` / `user_id` / `character_id` / `trigger_type` / `trigger_key`(**unique**) / `status` / `due_at` / `priority` / `cooldown_until` / `attempt_count` / `payload`(JSON) / `last_error` / `created_at` / `updated_at`） |
| **`trigger_type` 是 3 值 CHECK 白名单** | `:185-188`（`ck_trigger_registry_type`：`conversation_inactivity` / `scheduled_followup` / `action_due`）→ **新增值需迁移**，故本任务必须复用既有值 |
| `status` 是 5 值 CHECK | `:189-192`（`pending` / `due` / `fired` / `done` / `cancelled`）；索引 `:193` / `:194` |
| **既有先例正是「复用 trigger_type + payload.kind 区分」** | `apps/backend/app/services/tool/confirmation.py:53`（`CONFIRMATION_TRIGGER_TYPE = "action_due"`）、`:50`（`CONFIRMATION_ROW_KIND = "tool_confirmation"`）；登记 `:281-289`（`trigger_registry_repository.register(...)`） |
| 载体仓储函数齐备 | `apps/backend/app/repositories/trigger_registry_repository.py`：`get`(`:35`)、`list_recent`(`:44`)、`register`(`:54`)、`complete`(`:224`)、`force_cancelled`(`:256`)、`cancel`(`:308`)、`fail_for_retry`(`:272`)、`has_due`(`:326`，**含 `exclude_payload_kinds` 参数**)；常量 `ACTIVE_STATUSES`(`:27`) / `TERMINAL_STATUSES`(`:28`) |
| 既有消费路径（必须先排除） | `claim_due_followups`(`:171`)；`has_due(..., include_types, exclude_payload_kinds)`(`:326`)；确认闸的 `expire_due`（`confirmation.py:385`）扫行 `_scan_rows`(`:395`)；`trigger_reconcile` 维护步（`application/life_loop.py:594` 的 `_run_maintenance` 内 `:671-683`，调 `recover_stale` `:673-677`） |
| 计划停靠态与激活语义 | `apps/backend/app/models/goal.py:29`（`GoalPlanStatus` 5 值，**不得新增**）；`apps/backend/app/services/goal/approval.py:24`（`STATUS_PENDING = "validated"`）；`docs/current-system-architecture-baseline.md` §8.6（`list_active_plans` 只认 `active` → 「停住即不执行」） |
| 审批闸「不撤旧 active」的既有语义 | 基线 §8.6「闸门 ON 时新计划停在 `validated` 且**不撤下**旧 `active` 计划」 |

### 2.2 为什么必须做

1. **没有持久化载体，跨请求的「等待答复」无法成立**：`PLN-001` 只返回载荷；若进程重启或用户下一轮在另一请求里答复，载荷就丢了（`docs/agent-evolution-plan-2026-10.md` §3.3.2）。
2. **复用 `trigger_registry` 是本项目唯一能做到零迁移的路径**：`trigger_type` 的 CHECK 是 3 值白名单（`:185-188`），新增值必须迁移；而「复用 `action_due` + `payload.kind`」正是确认闸已验证过的先例（`confirmation.py:50` / `:53`）。
3. **最大风险是「被别的消费路径抢走」**：`action_due` 是动作重试触发器的类型，自治理/动作链路会认领 `due` 行。若不把这些消费点逐一排除，澄清行会被当作动作触发执行——**这是本任务的核心纪律**（D3）。

### 2.3 在本版本中的位置

P1 第 3 个任务：把 `PLN-001` 的载荷落地成可跨请求恢复的行；`PLN-004`（恢复）与 `PLN-005`（超时）都以本任务的行与 `trigger_key` 为操作对象。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 行契约（`trigger_registry`）

| 列 | 值 | 说明 |
|---|---|---|
| `trigger_type` | `"action_due"` | **复用既有白名单值**（`:185-188`；先例 `confirmation.py:53`） |
| `trigger_key` | `f"plan_clarify:{plan_id}"` | **unique**（`:165-182`）→ 同一计划只能有一条行（幂等基础） |
| `user_id` / `character_id` | 计划所属用户 / 角色 | 读取隔离依据 |
| `status` | `"pending"` | 登记态；答复后 `complete`（`:224`）→ `done`；超时/被取代 `force_cancelled`（`:256`）→ `cancelled` |
| `payload` | 见 §4.1.2 | JSON；`kind` 是本任务的身份标识 |
| `due_at` | `now + plan_clarify_timeout_hours`（`PLN-005`） | `timeout==0`（未启用超时）→ 哨兵 `now + plan_ttl_hours`（`core/settings/plan.py:35`，默认 168）以避免 NULL 语义；**实现期须确认 `due_at` 可空性** |
| `priority` | 沿用仓储默认（`PRIORITY_BY_TYPE`，`trigger_registry_repository.py:22`） | 不特殊化 |

#### 4.1.2 载荷结构（`payload`）

| 字段 | 契约 |
|---|---|
| `kind` | **恒为** `"plan_clarification"`（`PLAN_CLARIFICATION_ROW_KIND`，模块常量） |
| `plan_id` / `goal_id` | 关联标识（恢复与超时需要） |
| `round` | 本澄清轮次（1-based） |
| `questions` | `ClarificationPayload.questions` 的序列化（`{id, question, options[{value,label}], allow_free_text}`） |
| `created_at` | ISO 8601（超时判定与展示排序） |
| **禁止** | 不得写入模型原文、不得写入机制字段（`salience` 等）、不得写入 prompt 全文 |

#### 4.1.3 服务面契约（`app/services/goal/clarification.py`）

| 函数 | 契约 |
|---|---|
| `register_pending(user_id, goal_id, plan_id, payload, *, due_at, character_id="asuna", now=None) -> bool` | 委托 `trigger_registry_repository.register`（`:54`）；**登记前**先 `cancel_pending` 同计划旧行（保证「同计划至多一条 pending」）；返回是否新建 |
| `get_pending(plan_id) -> dict \| None` | 经 `trigger_registry_repository.get(f"plan_clarify:{plan_id}")`（`:35`）；校验 `payload.kind` 与 `status ∈ ACTIVE_STATUSES`（`:27`），否则 `None` |
| `list_pending(user_id) -> list[dict]` | 经 `list_recent(user_id)`（`:44`）过滤 `kind` 与状态；**按 `created_at` 升序**（确定性） |
| `mark_answered(plan_id, *, answers: dict) -> bool` | 委托 `complete`（`:224`）→ `done`；**不在此处触发重新提案**（属 `PLN-004`） |
| `cancel_pending(plan_id, *, reason: str) -> bool` | 委托 `force_cancelled`（`:256`）或 `cancel`（`:308`）；用于超时与「被新轮次取代」 |
| 写面纪律 | 全部写操作经 `trigger_registry_repository`；**不得**直接 ORM 写 |

#### 4.1.4 排除点契约（★ 本任务核心纪律）

| 排除点 | 契约 |
|---|---|
| `has_due(..., exclude_payload_kinds=...)`（`trigger_registry_repository.py:326`） | **所有**调用点必须把 `"plan_clarification"` 加入 `exclude_payload_kinds` |
| `claim_due_followups(user_id, ...)`（`:171`） | 其内部/调用侧对 `payload.kind` 的筛选必须排除 `plan_clarification`（若该函数不支持 kind 过滤，则在其调用点先过滤或在函数内最小改动加入排除） |
| 确认闸扫描（`confirmation.py:395` 的 `_scan_rows` → `:617`） | 确认闸按自有 `kind`（`tool_confirmation` `:50`）筛选，理论上天然隔离；**实现首步必须核对**，若为「按 trigger_type 扫描」则须补 kind 过滤 |
| 自治/生活循环消费 | `application/life_loop.py` 与 `application/autonomy_engine.py` 中所有 `action_due` 相关读点 |
| `trigger_reconcile` 维护步（`life_loop.py:673-677`，`recover_stale`） | `recover_stale`（`:368`）按超时回收 running 行；**排除点**须确认澄清行不会被 `fail_for_retry` 误改（若会，则加 kind 排除） |
| 登记要求 | 实现首步**静态扫描**以上全部调用点，形成「排除点清单」并逐一覆盖；清单进 Task 实现说明 |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **复用 `action_due` + `payload.kind`**，不新增 `trigger_type` | `ck_trigger_registry_type`（`:185-188`）是 3 值 CHECK；新增值需迁移，与「`PLN-001~005` 零迁移」的既定方案冲突（`docs/agent-evolution-plan-2026-10.md` §3.3.2 A 方案） |
| D2 | **计划停靠 `validated`，不新增状态值** | `validated` 是既有停靠态（`approval.py:24`），且 `list_active_plans` 只认 `active` → 「停住即不执行」零成本 |
| D3 | **排除点必须全覆盖，且逐点登记** | 澄清行与动作重试行同 `trigger_type`；任何漏掉的消费点都会把「等用户答复」变成「执行动作」——这是最有破坏力的失效模式 |
| D4 | **同一计划至多一条 pending** | 幂等键 `plan_clarify:{plan_id}`（unique）；换轮次时先取消旧行，避免多行竞争答复 |
| D5 | **`due_at` 必须有值（不依赖 NULL）** | 仓储与消费路径未对 NULL 做特殊语义；用哨兵（`plan_ttl_hours`）表达「不超时」比 NULL 更稳 |
| D6 | **登记失败不阻断规划** | 载体是辅助设施：登记失败 → `logger.warning` + trace + 按「未澄清」继续（回落到与基线等价的提案路径）；不因附属设施让目标卡死 |
| D7 | **不新增仓储函数** | `trigger_registry_repository` 已有 `register` / `get` / `list_recent` / `complete` / `cancel` / `force_cancelled`；新增函数会扩大该模块的契约面 |
| D8 | **读取按 `user_id` 隔离** | `list_recent(user_id)`（`:44`）已带用户维度；`get_pending` 按 `trigger_key` 取行后**必须**校验 `user_id`（越权防护） |
| D9 | **不复用确认闸的 `resolve` 语义** | 确认闸的 resolve 会改工具授权状态；澄清是「收答复」，不是「批准」。两者共享表但语义独立（D6 的失效模式同源） |
| D10 | **本任务零设置** | `due_at` 由 `PLN-005` 的参数决定；其余无需可调项 |

### 4.3 数据流

```text
goal_planning.plan_goal（:404）+ PLN-001 判定闸命中
   ▼
clarification.register_pending(user_id, goal_id, plan_id, payload, due_at)
   ① cancel_pending(plan_id)（同计划旧行 → cancelled，保「至多一条」）
   ② trigger_registry_repository.register(
          trigger_type="action_due",                       ← 复用白名单值（D1）
          trigger_key=f"plan_clarify:{plan_id}",           ← unique（幂等）
          payload={"kind":"plan_clarification", plan_id, goal_id, round, questions, created_at},
          due_at=now+timeout 或 哨兵 now+plan_ttl_hours, status="pending")
   └─ 失败 → warning + trace，按「未澄清」继续（D6，不阻断）
   ▼
计划状态：validated（停靠，不激活；不撤旧 active）

【读取】get_pending(plan_id) / list_pending(user_id)（PLN-004 / PLN-006 消费）
【结束】mark_answered → complete（done） ｜ cancel_pending → force_cancelled/cancel（cancelled）

★ 排除点：has_due(exclude_payload_kinds) / claim_due_followups / 确认闸扫描 / autonomy / recover_stale
   必须全部排除 "plan_clarification"（D3，实现首步逐点登记）
```
