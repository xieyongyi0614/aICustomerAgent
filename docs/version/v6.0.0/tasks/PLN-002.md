## 2. Background

### 2.1 现状：上下文与 prompt 都没有「用户答复」这一维

| 事实 | 证据 |
|---|---|
| 规划上下文装配入口与字段收口 | `apps/backend/app/services/planning/context.py:277`（`PlanContextAssembler.assemble`）、`:297`（`_build_context`）、字段清单收口于 `:310-327`；六源：Goal / World / Context / Memory / Reflection / ToolSurface |
| prompt 装配只有目标、开发约束、世界事实、证据 | `apps/backend/app/services/goal/planning.py:274-280`（`_build_messages(goal, overlay, world_facts, settings, evidence_refs=())`）；字段：`goal{description,layer,domain,priority}` `:297-302`、`development_constraints` `:303-310`、`world_facts` `:311`、`evidence_refs`/`evidence_note` `:313-316` |
| 提案只走一条路径 | `:350-355`（`propose_plan`）→ `:329`（`_ask_llm_with_retry`） |
| **`services/planning/` 有包模块枚举断言** | `apps/backend/tests/v25/test_plan002_static_scan.py:189-207`（逐条枚举既有 14 个模块路径）→ **本任务只允许修改既有文件，不得新增模块** |
| 规划包对 `goal_repository` 的调用受白名单约束 | `apps/backend/app/services/planning/goal_contract.py:197`（`PLANNING_GOAL_REPOSITORY_ALLOWED_CALLS`） |
| 澄清载荷结构（由 `PLN-001` 定义） | `PLN-001` §4.1.1（`ClarificationPayload{round, questions[], plan_id}` / `ClarificationQuestion{id, question, options[], allow_free_text}` / `ClarificationOption{value, label}`） |

### 2.2 为什么必须做

1. **没有答复槽位，澄清就退化为「重问」**：若第二轮提案的 prompt 与第一轮完全相同（`_build_messages` 无答复输入），模型会给出同样的计划或继续提问——澄清的收益归零（`docs/agent-evolution-plan-2026-10.md` §3.3.4）。
2. **必须避免给 `services/planning/` 加依赖**：该包有模块枚举断言与调用白名单双重约束；把「读 `trigger_registry`」放进该包会同时触碰两条约束——故设计为**载荷由 goal 域读出后作为参数传入**（纯数据装配）。
3. **prompt 预算纪律**：答复是用户输入，必须截断并有上限，否则一条长答复会把 `world_facts` / `evidence` 挤出上下文（R-P1 相关）。

### 2.3 在本版本中的位置

P1 第 2 个任务：把 `PLN-001` 的判定结果变成**模型可用的输入**；`PLN-003`（停靠载体）与 `PLN-004`（恢复）在其后。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 `PlanContext` 扩展（`app/services/planning/context.py`）

| 项 | 契约 |
|---|---|
| 新字段 | `clarification: dict \| None = None`（**纯数据**，不持有 repository 引用） |
| 结构 | `{"round": int, "qa": [{"question": str, "answer": str, "source": "option" \| "free_text"}]}`——**已归一为问答对**，planning 包不需要理解 `ClarificationPayload` 的类型 |
| `assemble` 形参 | `assemble(..., clarification: dict \| None = None)`（**带默认值** → 既有调用点零改动） |
| 字段收口 | `_build_context`（`:297`）把 `clarification` 并入返回 dict（字段集 `:310-327`）；`clarification is None` 时**不写入该键**（保证无澄清时上下文逐字节不变） |
| digest | 既有 `context_digest` 语义不变；澄清参与 digest 时须**确定**（键序固定） |

#### 4.1.2 prompt 注入契约（`services/goal/planning.py`）

| 项 | 契约 |
|---|---|
| `_build_messages` 形参 | 增可选 `clarification: dict \| None = None`（默认 `None` → 既有调用零改动） |
| 注入位置 | 在 `goal`（`:297-302`）之后、`development_constraints`（`:303-310`）之前，新增一段 `clarified_answers`（**仅当** `clarification` 非空且 `round >= 1`） |
| 段内容（冻结格式） | 每行 `- {question} → {answer}`（`answer` 为 option 的**中文 label** 或自由文本；**不暴露 option.value**） |
| 段标题 | 「用户已澄清以下问题（请基于这些答复重新规划，不要重复提问）」 |
| 二次提防重问 | 段内显式声明「不要重复提问」；并保留 `PLN-001` 的轮次上限作为硬保险（prompt 只是软约束） |
| 无澄清时 | 不注入任何新段 → prompt 与基线**逐字节一致** |
| 答复清洗 | 去首尾空白、连续空白折叠、`\n` 归一为空格；单条答复截断至 `plan_clarify_answer_max_chars`（默认 200）；空答复 → 该行不注入（并计一次 warning） |
| 段总长上限 | `CLARIFY_BLOCK_MAX_CHARS = 1200`（模块常量）：超出则按 `qa` 顺序截断并追加「（其余答复已省略）」（防 prompt 膨胀） |

#### 4.1.3 载荷归一契约（由 goal 域执行的转换）

| 输入 | 输出（`clarification` dict） |
|---|---|
| `ClarificationPayload{round, questions[]}` + 用户答复（`{"q1": {"value": "..."} \| {"free_text": "..."}}`） | `{"round": int, "qa": [{"question": <问题文案>, "answer": <label 或自由文本>, "source": "option"\|"free_text"}]}` |
| 找不到答复的问题 | **该问题不进入 `qa`**（不注入「未回答」噪音）；若 `qa` 为空 → 整个 `clarification` 视为 `None` |
| `option.value` 映射 | 通过 `ClarificationPayload` 里的 `options` 反查 `label`；反查失败 → 用 `value` 原样（并计一次 warning） |

#### 4.1.4 新设置字段（`app/core/settings/plan.py`）

| 字段 | 类型 | 默认 | 语义 | 校验 |
|---|---|---|---|---|
| `plan_clarify_answer_max_chars` | `int` | `200` | 单条答复注入上限（字符） | `ge=20`、`le=1000` |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **只改既有文件，不新增 `planning/` 模块** | 包枚举断言（`:189-207`）会转红；改既有 `context.py` 是唯一合规落点（§3.2 第 1 条） |
| D2 | **载荷以「已归一 dict」传入 planning 包** | 让 planning 包保持**纯数据装配**：不新增 repository 依赖（避开 `goal_contract.py:197` 白名单议题），也让上下文可单测（纯输入输出） |
| D3 | **`clarification is None` 时不写入键** | 「无澄清时上下文与 prompt 逐字节不变」是最硬的零回归判据；写入 `None` 会让 digest 与 prompt 都变化 |
| D4 | **注入中文 label 而非 `option.value`** | 模型看到的是人类语义；`value` 是程序标识（`expense` 之类），注入它既无信息量又可能诱导英文输出 |
| D5 | **不注入 `plan_id` 等内部标识** | 模型无需知道内部 id；注入无收益且扩大 prompt 面积 |
| D6 | **段总长硬上限 + 单条上限** | 答复是用户可控输入；双上限保证 prompt 预算不被单轮答复挤占（R-P1） |
| D7 | **找不到答复的问题不注入** | 注入「未回答」会让模型误以为用户弃答；部分回答时只给已答部分更准确 |
| D8 | **重新提案复用 `propose_plan`** | 避免第二套 prompt 装配路径（也保证 `PLN-001` 的判定闸能再次生效） |

### 4.3 数据流

```text
【恢复触发（PLN-004 之后）】用户答复 → goal 域归一（§4.1.3）→ clarification dict
   ▼
goal_planning.propose_plan（:350）→ _build_messages（:274-280, +clarification）
   ├─ clarification is None → 段不注入（prompt 逐字节不变）
   └─ 非空 → 注入 clarified_answers 段（label / 自由文本，截断 + 上限）
   ▼ _ask_llm_with_retry（:329）→ PlanningProposal
   ▼ PLN-001 判定闸（round+1）→ 若再次澄清则停，否则落 validated / active

【上下文侧】PlanContextAssembler.assemble（:277, +clarification）→ _build_context（:297）字段集（:310-327）
   └─ clarification is None → 不写键（上下文逐字节不变）

红线：不新增 planning 模块；不新增仓储依赖；无澄清时 prompt/上下文逐字节一致；答复截断
```
