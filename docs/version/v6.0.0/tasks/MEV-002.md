## 2. Background

### 2.1 现状：单 query、单路召回

| 事实 | 证据 |
|---|---|
| 检索签名固定为单 query | `apps/backend/app/services/memory/retriever.py:265-271`（`retrieve(user_id, query, character_id="asuna", top_k=None, trace=None)`） |
| 候选池与向量召回各一次 | `:349`（`_candidate_pool`，`list_active` 调用 `:352-354`）；`:334`（`_vector_recall`，调用 `:338-343`）；`embedding` 路失败即降级（`:344-346`） |
| 分量计算是逐候选确定性函数 | `:98`（`_recency`）、`:106`（`_structured_score`）、`:113`（`_affinity_score`）、`:75-80`（`_detect_query_types`） |
| 过滤在打分前 | hypothetical 剔除 `:280` / `:292`；冷却过滤应用 `:306`；penalty `:309` / `:311` |
| 向量客户端可缺省 | `apps/backend/app/core/settings/memory.py:48`（`embedding_model` 默认空串）→ 向量路降级为纯结构化（`:282` / `:286` / `:294`） |
| 检索是**唯一**入口，被对话与规划共用 | `apps/backend/app/services/conversation/context.py:253`；`apps/backend/app/services/planning/context.py:608` |
| 记忆域已有「lite + 失败回落」先例可对齐 | `apps/backend/app/services/memory/evaluator.py:47` / `:79-81` |

### 2.2 为什么必须做

1. **单 query 是召回率的结构性瓶颈**：用户口语化输入（「上次那个面试怎么样来着」）与记忆正文（「参加了 XX 公司面试」）之间存在表达鸿沟，而结构化分只依赖 `TYPE_AFFINITY_KEYWORDS`（`types.py:30-35`，当前 4 键）与 recency/importance/salience，**没有任何语义扩展能力**；cosine 在 `embedding_model` 未配置时整条不可用。
2. **与 `MEV-001` 互补而非重叠**：重排（`MEV-001`）是「在已有候选里选得更准」，改写是「让候选池里真的有那条」——召回缺失时重排无解（`MEV-001` §3.2 第 3 条已明确不做「重排后再检索」）。
3. **成本可被两个旋钮约束**：`memory_query_rewrite_max_queries` 限上限、一次 LLM 调用批量出多条，且 `off` 时零调用（`docs/agent-evolution-plan-2026-10.md` §2.5 R-M2）。

### 2.3 在本版本中的位置

M1 第 2 个任务；与 `MEV-001` 共同构成「召回 → 排序」双端增强。`MEV-004` 需要能区分「改写命中」对最终结果的影响，故本任务必须在 trace 中留痕（§4.1.4）。

## 3. Scope

### 3.1 In Scope

1. 新增链 `app/chains/memory_query_rewrite_chain.py`：一次调用产出 0~N 条改写 query。
2. 新增 prompt `app/prompts/memory_query_rewrite.py`。
3. `retriever.py` 增**多路召回 + 归并**：仅在 `memory_query_rewrite_mode="lite"` **且**改写返回非空时启用；否则走**既有单路代码原样**。
4. 归并契约（§4.1.3）：按 memory id 去重、分量取最大、惩罚取最大、`reason` 记录命中 query 序号。
5. 两个新设置字段。
6. trace 留痕：`rewrite_mode` / `queries_count` / 每条的 `matched_queries`（供 `MEV-004` 消费）。
7. 失败与降级：改写调用异常/超时/解析失败 → 单路回落 + warning + trace，**不抛**。

### 3.2 Out of Scope（明确禁止扩张）

| # | 禁止项 | 理由 |
|---|---|---|
| 1 | **不扩展 `retrieve()` 签名**（不加 `recent_context` 等参数） | 签名是既有两个消费方（`conversation/context.py:253`、`planning/context.py:608`）的冻结契约；加参会扩大回归面，而「最近上下文注入」属会话侧增强，另有归属 |
| 2 | **不做本地同义词词典 / 规则式改写** | 与「词表扩容」职责重叠（`MEV-003` 管 `TYPE_AFFINITY_KEYWORDS`）；两处改写会导致「谁生效」不可判定 |
| 3 | **不做多轮检索循环 / 迭代改写** | R-M2 的直接放大项；改写一次、检索 N 次封顶 |
| 4 | **不改 `_recency` / `_structured_score` / `_affinity_score` 的数学** | 属既有确定性打分（`:98` / `:106` / `:113`）；改数学会让 `MEV-001` 的「重排前后名次」与 M2 配额失去基准 |
| 5 | **不改 `mode` 三值语义**（`hybrid` / `structured` / `degraded` 仍表示召回**路径**） | 被多处降级判定与断言消费（`:30-32` / `:282` / `:286` / `:294`）；改写状态走新字段 `rewrite_mode` |
| 6 | **不改 `prompts/builder.py` 与会话注入预算语义** | `:441-453` 记忆段装配、`:301` 总预算、`conversation/context.py:40` 检索段选取均属会话侧既有语义 |

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 链契约（新增 `app/chains/memory_query_rewrite_chain.py`）

| 符号 | 契约 |
|---|---|
| `QueryRewriteResult` | Pydantic：`queries: list[str]`（**不含**原 query） |
| `build_query_rewrite_chain(llm=None) -> Runnable` | 经 `app/chains/structured.py::build_structured_chain`（`:66-68`）构建；`llm` 缺省 `get_llm("lite")`（`core/llm_factory.py:37`） |
| `async rewrite_queries(user_input: str, llm=None) -> list[str]` | 返回**已清洗**的改写列表：① 逐条 `strip()`；② 剔除空串；③ 剔除与 `user_input` 归一化后相同者；④ 归一化后去重（保留首次出现序）；⑤ 单条长度 > `QUERY_MAX_CHARS = 120` → **丢弃**（不截断，避免半句误导检索）+ warning；⑥ 截断到 `memory_query_rewrite_max_queries`；⑦ 任何异常 → 返回 `[]`（由调用方回落单路），**不向上抛** |
| 模块常量 | `QUERY_MAX_CHARS = 120`、`REWRITE_PROMPT_VERSION = 1` |
| 归一化函数 | `_normalize(text) -> str`：`strip` + 连续空白折叠为单空格 + ASCII 大小写折叠（用于「同原文」与去重判定，**不改写文本本身**） |

#### 4.1.2 挂接点与启用条件（`app/services/memory/retriever.py`）

| 项 | 契约 |
|---|---|
| 挂接位置 | `retrieve()`（`:265`）进入召回**之前**：`settings` 读取后（`:273` 一带）解析 query 集合 |
| 启用条件（全部满足） | ① `memory_query_rewrite_mode == "lite"`；② `rewrite_queries()` 返回**非空**；③ 最终 query 集合条数 > 1 |
| 未启用时 | **完整走既有单路代码路径**（不进入多路分支），保证逐字节一致 |
| 单路/多路的差异边界 | 多路分支只在「召回 + 分量计算」段生效；**过滤（`:280` / `:292` / `:306`）、惩罚（`:309` / `:311`）、加固（`:322`）、trace（`:323-330`）在多路下仍**统一执行一次**（对归并后的集合） |
| 时间词加成 | `_detect_query_types` / 时间词判断在多路下取「**任一 query 命中即为真**」（更宽松召回），并在 trace 中记录命中 query 序号 |
| 失败语义 | 改写调用异常 → 回落单路、`rewrite_mode=="off"`、warning + trace 降级记录 |

#### 4.1.3 归并契约（多路专属）

| 项 | 契约 |
|---|---|
| 归并键 | `memory.id`（同一记忆在多个 query 下命中 → **只出现一次**） |
| 分量归并 | `semantic` / `structured` / `affinity` 各取参与命中 query 中的**最大值** |
| 惩罚归并 | `penalty` 取**最大值**（最保守，不因某 query 无惩罚而免除） |
| `score` 重算 | 用与基线**同一公式与同一 settings 权重**（`memory_weight_semantic/structured/affinity` `core/settings/memory.py:56-58` + temporal boost `:63`）对归并后分量重算，保证与「单 query 命中同分量」时可比 |
| `reason` 契约 | 记录**命中的 query 序号集合**（`q0` = 原 query，`q1...` = 改写序），形如 `"semantic+q0,q1"`；用于 `MEV-004` 归因 |
| 确定性 | 归并后排序键与基线一致（同分按既有 tie-break），**不得**依赖 dict 插入序 |

#### 4.1.4 trace 契约（新增只读字段）

| 字段 | 位置 | 契约 |
|---|---|---|
| `rewrite_mode` | 检索步（`STEP_NAME="memory_retrieve_v2"` `:28`）的 extra | `"off"` / `"lite"`（**实际发生**语义：改写返回空即为 `off`） |
| `queries_count` | 同上 | 本次实际检索的 query 条数（`off` 时恒为 1） |
| `matched_queries` | 同上，逐条命中项 | 命中 query 序号集合（§4.1.3 `reason`） |

> **纪律**：trace 只**新增** extra 键，不新增事件类型、不改 `loop_runs.steps` 键集、不改既有键语义（`tasks/README.md` §4）。

#### 4.1.5 新设置字段（`app/core/settings/memory.py`，类 `MemorySettings` `:8`）

| 字段 | 类型 | 默认 | 语义 | 校验 |
|---|---|---|---|---|
| `memory_query_rewrite_mode` | `str` | `"off"` | `off`（不改写）/ `lite`（lite profile 改写） | 仅接受 `{"off","lite"}`；非法值回落 `off` + 启动期 warning（同 `MEV-001` D6 保守原则） |
| `memory_query_rewrite_max_queries` | `int` | `2` | **新增**改写 query 数上限（总 query 数 ≤ `1 + 该值`） | `ge=1`、`le=3`（成本护栏：3 条已是上限） |

> **不新增**：不使用 `memory_recent_context_messages`（`:18`）——本任务不注入最近上下文（§3.2 第 1 条）。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **不改 `retrieve()` 签名** | 两个消费方（`conversation/context.py:253`、`planning/context.py:608`）零改动是本任务的零回归基础；`MEV-001` 亦以签名不变为前提 |
| D2 | **改写只在「有增益」时启用**（返回空/单条 → 走既有单路代码） | 「逐字节一致」是最硬的可验证判据；多路分支只要被进入就存在归并顺序风险，故把入口条件收紧到「确实多条」 |
| D3 | **归并取分量最大值**（而非平均/加权求和） | 最大值语义 = 「该记忆在最有利的表达下被召回的证据强度」，可解释、可测、不引入新权重（R-M1 预算纪律：不新增调参面） |
| D4 | **惩罚取最大值（保守）** | 若取最小值，被拒/矛盾记忆会因「某条 query 无惩罚」而绕过冷却机制（`:306` / `:309` / `:311`），等于削弱既有治理 |
| D5 | **单条超长直接丢弃而非截断** | 截断产生半句（「…面试怎么」），在半句上算 affinity/vector 相似度会引入噪声评分；丢弃 + warning 更安全 |
| D6 | **改写失败的降级点放在 `retrieve()`**（链内不抛） | 与 `MEV-001` D7 同构：降级集中一处，便于 trace 与测试 |
| D7 | **trace 只加 extra 键，不新增事件类型** | 新增事件类型需登记 `EXPECTED_EVENT_TYPES`（fail-closed），属不必要的契约扩张 |
| D8 | **`reason` 记录 query 序号** | `MEV-004` 需要区分「因改写而召回」的条目，否则重排/改写的收益不可归因（`docs/agent-evolution-plan-2026-10.md` §2.3 M1.4） |
| D9 | **总 query 数硬上限 3** | 每次 query 都要跑一次候选池查询（`:349`）与一次 ANN（`:334`）；3 条已是成本与召回的平衡点（R-M2） |
| D10 | **不改时间词语义**，多路下取「任一命中」 | 时间词加成（`memory_temporal_recency_boost` `:63`）只在查询含时间词时生效；多路下若按「全部命中」则改写反而**降低**加成概率，与改写意图相反 |

### 4.3 数据流

```text
services/conversation/context.py:253  ｜  services/planning/context.py:608（两处签名零改动）
   ▼
retriever.py::retrieve（:265）
   ① 读 settings（:273）→ 解析 query 集合（★ MEV-002 新增）
        ├─ mode != "lite"                    → queries = [query]，走既有单路
        └─ mode == "lite" → chains/memory_query_rewrite_chain.py::rewrite_queries(query)
              ├─ 返回空 / 异常                → 回落单路 + warning + trace(rewrite_mode="off")
              └─ 返回 N 条                    → queries = [query] + N（≤ 3）
   ② 逐 query 召回（仅多路时循环）
        结构路 _candidate_pool（:349）  向量路 _vector_recall（:334，可降级）
        逐候选分量：_recency（:98）/ _structured_score（:106）/ _affinity_score（:113）
   ③ 归并（仅多路）：按 memory.id 去重；semantic/structured/affinity 取 max；penalty 取 max；
                    reason 记命中 query 序号（q0,q1…）；score 用同一公式重算
   ④ 统一过滤：hypothetical（:280 / :292）→ 冷却（:306）→ penalty（:309 / :311）
   ⑤ 交给 MEV-001 的 _maybe_rerank 挂接点 → 排序 → record_reinforce（:322）+ trace（:323-330）

降级红线：改写异常 → 单路；向量路异常 → 结构化（既有）；任何分支异常 → 不抛不阻断
```
