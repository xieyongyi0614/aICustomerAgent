# REL-003 Task Detail — Relationship Patterns 接入（Integration）

> 上游：[../tasks.md](../tasks.md) REL-003 ｜ [../../architecture/domain-boundaries.md](../../../architecture/domain-boundaries.md) §1 ｜ 依赖：REL-001, P3 DEV-003（已交付）

## Task 目标

让 Development 产出的关系模式在关系域产生行为意义：读取源 Insight scope=relationship 的 active pattern 类调制行，经 strength 门槛过滤后 ①注入 Context 关系段扩展（「你们之间的关系模式」行）、②作为 AutonomyPolicy 的参考输入进入 PolicySnapshot。**只读调制**——不写任何数值、不改 V8.5 闸门结构、不产生新 Pattern。不接入则「关系模式」只是 development_state 里的死数据，P3 产出的闭环缺最后一块消费面。

## 背景 / 为什么需要

P3 交付的编译链（代码事实）：reflector 产出 Insight（scope 由 LLM 自报，`scope='relationship'` 是合法枚举且 DB CHECK 支持，`app/core/db.py` ck_insights_scope）→ `notify_insight_created_listeners` → `development_compile` job → `policy.compile_insight` 按 **type** 分派（不看 scope）→ `development_state` 行（kind=pattern 的 key 现为 `goal.user_care.weight` / `autonomy.time_preference`）→ `read_overlay` 装配消费。

两个缺口：

1. **「关系模式」无身份**：pattern 行不区分源 Insight 的 scope——一个 scope=relationship 的 pattern Insight 与 scope=user 的一律编译进同一组槽位，关系域无法回答「我的关系模式是什么」。
2. **关系域零消费**：Development 的消费面只有 BehaviorEngine / answer max_tokens / goal_service（DEV-003），关系行为（stage 表达、自主闸门）对「用户在深夜更愿意向我倾诉」这类关系模式毫无感知。

本 Task 的裁决口径（README 核对记录 6）：**关系模式（relationship pattern）≡ active 且 kind='pattern' 且 source_insight.scope='relationship' 的 development_state 行**——不在 development_state 加 scope 列（不动 P3 表结构），经 `source_insight_id` join insights 过滤（依赖矩阵合法方向：Relationship 只读 Development，Development 行的溯源字段已全审计）。

## 设计方案

1. **读取与过滤**（Relationship 域内新模块，Development 域零改动）：
   ```python
   read_relationship_patterns(user_id) -> list[RelationshipPattern]
   # 1. list_active_modulations(user_id) 取全部 active 行
   # 2. 过滤 kind='pattern'
   # 3. 按 source_insight_id 批量 join insights → 保留 scope='relationship'
   # 4. strength >= v2_relationship_pattern_min_strength 门槛（Pattern 噪声防线）
   # 5. 每行产出 RelationshipPattern{key, value, strength, statement=源 insight.statement, source_insight_id}
   # 6. 异常 → 空列表（fail-safe，对齐 read_overlay 先例）
   ```
   `RelationshipPattern` 模型追加在 `app/models/development.py`（与 DevelopmentOverlay 同文件，值对象归属清晰）。读取函数带独立 Flag 检查（双闸之一）。
2. **Context 关系段扩展**：`build_relationship_pattern_section` 渲染「【关系模式】· {statement 截断}」行（每条 ≤`v2_relationship_pattern_budget_chars`/max_items，默认总预算 120 字符、至多 2 条，strength 降序取头部）。位置：关系切片之后、共同经历段（REL-002）之前——关系数值语义 → 关系模式语义 → 共同经历叙事，同一关系域扩展区三段并列、预算各自独立。空列表 → 段不出现（golden 零漂移）。内容用源 Insight statement（这是「模式」的人话表达），不暴露 key/数值。
3. **AutonomyPolicy 参考**：`PolicySnapshot.relationship_patterns` 装入 pattern key 元组（Flag 双闸）。**本 Phase 消费边界 = 参考注入 + 可观测**：
   - 不改 R1~R5 任何规则、阈值、解锁条件（Non-Scope「不改 v8.5 闸门结构」；domain-boundaries「数值数学不动」）。
   - autonomy 决策 trace 记录 `relationship_patterns` keys——「参考」的落点是闸门输入可见化，供 P5 Life Loop 设计消费策略时已有数据与灰度观测（tasks.md 被依赖：Phase 5 关系闸门已有）。
   - 与 P3 口径一致（Phase 3 核对记录 4：`autonomy.time_preference` 只编译落库不接线）——本 Task 把「接线」同样限制为参考注入，任何阈值/规则调制属 P5 需求，Phase 4 不设计。
4. **双闸 Flag**：注入生效需 `v2_relationship_evolved_enabled AND v2_development_enabled` 同时 ON（tasks.md Feature Flag 口径）。任一 OFF → `read_relationship_patterns` 恒空、PolicySnapshot 字段恒空、段不渲染——全部回 v1/P3 既有行为。
5. **trace**：context_builder 内 `trace.record("relationship_pattern", ms, "ok", selected=[{key, strength, source_insight_id}], reasons=[below_threshold/scope_excluded/over_limit/in])`（对齐 context_insight 逐条落选先例）。

## 数据模型 / 状态变化

- 零新表、零迁移、零写路径。`RelationshipPattern`（models/development.py 追加的只读值对象）+ `ConversationState.relationship_patterns` 字段 + `PolicySnapshot.relationship_patterns` 可选字段 + 3 个 settings。

## 核心处理流程

```text
装配期（context_builder.build，双闸 ON）:
  read_relationship_patterns(user_id)
    → list_active_modulations → kind=pattern → join insights(scope=relationship)
    → strength ≥ 0.6 过滤 → strength 降序 top-2
  → ConversationState.relationship_patterns
  → prompts/builder 渲染【关系模式】段（空则不出现）
  → trace: relationship_pattern

闸门期（autonomy_engine 组装 PolicySnapshot，双闸 ON）:
  read_relationship_patterns → keys 元组 → PolicySnapshot.relationship_patterns
  → 决策 trace 附带（不改任何规则行为）
```

## 与 Memory / Reflection / Development 的关系

- **Reflection**：模式的源头是经反思验证的 Insight（scope=relationship）——本 Task 只消费编译结果，不读原始记忆（domain-boundaries 依赖矩阵脚注：Development 读 Memory 仅限经 Insight 验证者；Relationship 同样不直读原始记忆调制行为）。
- **Development**：纯只读消费（合法方向：Relationship → Development ✓）。不在 development_state 加列、不改编译器、不改仲裁——「关系模式」的判定发生在消费侧 join，P3 全部资产语义不变。
- **Memory**：无直接交互（模式注入不经记忆检索；REL-001/REL-002 已覆盖记忆侧关系内容）。

## 异常与边界情况

- insights 行缺失（source_insight_id 悬空，理论不发生：changes 审计含 insight_id 必填）→ 该行按 scope 不明丢弃 + trace reason（保守不过注入）。
- 读取失败/超时 → 空列表（fail-safe），trace 记 error，Context 与闸门均无注入。
- strength 全部低于门槛 → 空段（不是降低门槛）。
- 双闸 OFF 且 DB 有数据 → 一律不读不渲染（冻结）。
- pattern 行与用户当前关系状态矛盾（如冲突期注入亲密模式行）→ 不做状态仲裁——模式是慢变量表达，数值语义由关系切片段与冲突指令行（既有 CONFLICT_DIRECTIVES）承载，两者并存不冲突。

## 测试要求

- Unit：join 过滤（scope=user 的 pattern 行被排除）；strength 门槛与降序 top-N；insight 悬空丢弃；双闸任一 OFF → 空。
- Integration：①端到端——注入 scope=relationship 的 pattern Insight → 编译落库 → Context 出现【关系模式】段 + trace 含 source_insight_id；PolicySnapshot 携带 keys 且决策 trace 可见、R1~R5 行为与无注入时逐字节一致；②Flag 矩阵——`v2_relationship_evolved_enabled` 与 `v2_development_enabled` 各 OFF 一侧 → 无注入且 golden 不变（四组合全覆盖）。
- Regression：V8.5 checklist（闸门结构零改动证明：autonomy 全量测试原样通过）；golden prompt 快照（Flag OFF / 无数据两态）。

## 验收标准

- 给定 strength≥阈值的 relationship Pattern，当装配，那么 Context 关系段扩展可见【关系模式】行且 trace 可溯源 insight_id。
- 给定任一 Flag OFF，那么无注入且 golden 不变。
- 给定闸门运行，那么 PolicySnapshot 携带 patterns 时 R1~R5 判定结果与不携带时逐字节一致（参考不改变行为）。

## Implementation Constraints

- 只读调制：不写数值、不写 development_state/insights 任何行、不改 v8.5 闸门结构与 R 规则、不产生新 Pattern。
- Development 域零改动（过滤在消费侧；加 scope 列属 P3 表结构变更，超出本 Phase，见 README 核对记录 6）。
- Autonomy 消费仅到「PolicySnapshot 字段 + trace」为止，任何阈值调制、R 规则改动属 Phase 5。
- LLM Usage = NONE。
- 不提前设计 Phase 5 的关系闸门调制策略与 Phase 6 Goal 层级化消费。
