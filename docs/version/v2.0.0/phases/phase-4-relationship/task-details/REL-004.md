# REL-004 Task Detail — 叙事里程碑与关系评估（Integration / Evaluation）

> 上游：[../tasks.md](../tasks.md) REL-004 ｜ [../../architecture/evaluation.md](../../../architecture/evaluation.md) §1 ｜ 依赖：REL-002, P2 REF-004（已交付）

## Task 目标

两件事：

1. **叙事里程碑**：高置信 relationship 类 Insight 达到白名单叙事里程碑条件 → milestone 落账本（走 V8.5 里程碑仓储通道，零 bonus）→ 经 REL-001 通道转写为 `milestone_event` 记忆。数值里程碑判定逻辑一字不动，叙事里程碑**只增不改**，白名单 + 频控防泛滥。
2. **关系域评估闭环**：Evaluation 新增 relationship 一致性规则（账本重放对账 + 真相源审计）+ 离线场景集 + 运维级重放工具——REL-001 真相源统一（E-REL-01）与本 Task 里程碑合规（E-REL-04）由此才能验收。

V8.5 数值里程碑（12 项 spec）表达的是可判定的数值事实（first_conflict、stage_partner…）；「第一次一起熬夜赶工」这类叙事里程碑只能从反思产物的关系认知中判定——这是 Insight 驱动的唯一入口。

## 背景 / 为什么需要

代码现状（缺口）：

- 里程碑只有 12 项数值 spec（`relationship_milestone.py` MILESTONES L81-169），`detect` 谓词全部基于信号/状态，无法表达叙事性「第一次」。
- `relationship_milestones` 表（迁移 0019）有 UniqueConstraint(user_id, milestone_key, period_key) 的幂等地基，但**无来源溯源列**——数值里程碑来源自明（spec 清单），叙事里程碑必须记录「哪个 Insight、按什么白名单规则触发」，否则 E-REL-04「可溯源 Insight」无法审计。
- 评估域 relationship 维已有 4 条数值护栏规则（`evaluation_rules/relationship.py`：jump/ledger 对账/限速/信号记账），但**真相源审计**（叙事事实必须有账本来源）与**里程碑合规**（白名单/溯源）无规则覆盖；`scripts/` 无 relationship 重放工具（regression-checklist 执行步骤 1「evolve() 重放字节级对比（replay 工具）」当前无工具可跑）。
- REF-004 产出的 scope=relationship Insight 已可进入 Context（`v2_reflection_context_scopes_json` 默认含 relationship），但其「关系认知」没有任何向关系状态沉淀的通道——反思与关系域之间断链。

## 设计方案

1. **叙事里程碑判定**（全规则，LLM Usage = NONE）：
   - **白名单**：`v2_relationship_narrative_whitelist_json`，形如 `{"narrative:all_nighter": {"title": "第一次一起熬夜赶工", "keywords": ["熬夜", "一起"], "all": true}}`——key 即 milestone_key（`narrative:` 前缀与 12 项数值 spec key 空间隔离），keywords 全命中（all=true）/任一命中（all=false）作用于 Insight statement，纯子串匹配（对齐 DEV-002 `_keyword_matches` 确定性先例）。
   - **触发链**（镜像 development_compile）：`reflector._persist` commit 后 `notify_insight_created_listeners` → `relationship_narrative.on_insight_created(user_id, created)` 过滤 `scope='relationship'` 且 `confidence ≥ v2_relationship_narrative_min_confidence(0.75)` → enqueue job `relationship_narrative_milestone`（幂等键 `relationship_narrative:{insight_id}`——「同 Insight 只触发一次」在入队层即保证）→ job handler：重读 Insight（须仍 active，对齐 `compile_insight_by_id` 的 skip_inactive 语义）→ 白名单匹配 → 频控 → 落账本 → trace。
   - **频控**：①`create_milestone` 唯一约束兜底（同 milestone_key 重复 → 返回 None，天然「触发两次只落一条」——叙事里程碑 period_key 取 `""` 与数值 first_* 同为终身一次）；②单日上限 `v2_relationship_narrative_daily_cap`（当日已落叙事里程碑数 ≥ cap → skip，防 Insight 灌水刷里程碑）；③同周期触发异常 → 跳过 + trace，不阻塞反思链（listener 异常已被 lifecycle 吞掉，job 内异常走 worker 退避重试）。
2. **落账本（V8.5 通道）**：`create_milestone(user_id, milestone_key, title, period_key="", applied_bonus=None, unlocks=(), meta={...})`。**零 bonus、零 unlocks**——叙事里程碑不进 state、不碰限速、不解锁闸门资产（数值里程碑判定与 bonus cap 逻辑零改动；「只增不改」）。meta 载荷：`{"source": "insight", "insight_id": ..., "matched_rule": ..., "matched_at": ...}`——E-REL-04「可溯源 Insight」的落点。
3. **转写**：里程碑行落库后不做主动调用——REL-001 的 post_process 里程碑扫描（`fetch_recent_relationship_milestones` → `ingest_from_relationship_milestone`）在下轮 post_process 自动转写为 `milestone_event` 记忆（source_ref 回指里程碑行；ingest 侧从 meta 提取 insight_id 进 source_ref_extra）。链路闭环：Insight →（job）→ 里程碑行 →（REL-001 摄取）→ 叙事记忆 →（REL-002 投影）→ Context。
4. **评估规则**（追加 2 条， subjects=("turn","proactive_action","offline_batch")，ctx.relationship 为 None 静默跳过）：
   - `NarrativeFactProvenanceRule` → `RELATIONSHIP_NARRATIVE_ORPHAN`（CRITICAL）：审计窗口内 type∈{relationship_fact, milestone_event} 的 memories 行 source_ref.table 必须 ∈ {relationship_events, relationship_milestones}——E-REL-01 真相源审计的规则化。
   - `NarrativeMilestoneProvenanceRule` → `RELATIONSHIP_MILESTONE_UNPROVENANCED`（CRITICAL）：milestone_key 带 `narrative:` 前缀的行必须 meta.source='insight' 且 insight_id 可解析为存在行，且 key 在白名单内——白名单外私造/溯源缺失即违例。
   - 账本重放对账规则侧：既有 `LEDGER_RECONCILIATION`（状态=Σimpact+comfort 漂移）保留；离线重放由工具承担（下条）。
5. **重放工具** `scripts/replay_relationship.py`（对齐 `replay_development.py`：默认只读校验）：
   - 读账本全量行 → `relationship_evolution.replay(state0, events)` 前向重建 → 与当前 `relationship_state`（及最近快照锚点，复用 debug rollback 的重建路径逻辑 `app/api/v1/debug.py:449-507`）比对，输出逐维偏差报告。
   - 快照锚点漂移属预期（comfort drift 逐段施加 vs 一次性结算的口径差）——报告分「可解释偏差/不可解释偏差」两栏，不可解释非空即 fail。数值零改动证明（E-REL-03）= 不可解释偏差为空。
   - 无 `--rebuild` 模式：关系状态由账本+漂移公式决定，不存在「重建写回」需求（与 Development 审计行修复场景不同），工具恒只读。
6. **离线场景集** `relationship_evaluation.py`（复刻 development/evaluation.py 结构）：
   - 场景：`provenance_complete`（里程碑达成→账本行+记忆互溯）/ `conflict_resolution_narrative`（冲突解决→叙事转写、delta 只在账本）/ `pattern_ablation`（有/无 Pattern 的关系段对比）/ `milestone_flood`（白名单外 Insight 不触发、同日超 cap 不落）。
   - `GATE_THRESHOLDS`：E-REL-01 真相源审计 1.0 / E-REL-02 共同经历对账 1.0 / E-REL-04 叙事里程碑合规 1.0（E-REL-03 字节级由重放工具在 Regression Gate 承担，不入场景集）。
   - `run_scenarios(session_factory, now=None)`（0 LLM，注入式 runner，对齐 reflection/development 先例）；`build_db_report()` → `{narrative_milestones, provenance_rate, orphan_narrative_facts, milestones_total}`；`offline_evaluator._aggregate` 追加 `relationship` 小节。

- `relationship_milestones` 加 nullable `meta JSON` 列（迁移 0027，本 Phase 唯一 alembic 迁移）：NULL 默认 → 12 项数值里程碑行与既有读写路径零影响；check/索引零改动。账本语义不变（行仍由唯一写点产生、bonus 路径不变）。

- 状态机：里程碑只增（HARD，沿既有唯一约束；无 update/delete 路径）；Insight 只读。
- 新 settings：3 项（见上表）。

## 核心处理流程

```text
反思链（P2）:
  reflector._persist commit → notify_insight_created_listeners
    → relationship_narrative.on_insight_created
      scope=relationship ∧ confidence≥0.75 → enqueue job（幂等键 relationship_narrative:{insight_id})

后台（job_worker，Flag ON）:
  handler: 重读 Insight（须 active）→ 白名单关键词匹配
    → 频控（同 key 唯一约束 + 当日 cap）
    → create_milestone(key='narrative:*', bonus=0, unlocks=(), meta={insight_id, matched_rule})
    → trace relationship_milestone（insight_id/判定依据）

下一轮 post_process（REL-001 通道）:
  fetch_recent_relationship_milestones → ingest_from_relationship_milestone
    → milestone_event 候选（source_ref→里程碑行）→ 转正 → REL-002 投影/Context 可见

评估:
  在线：2 条新规则（真相源审计/里程碑溯源）
  离线：relationship_evaluation.run_scenarios → Gate；scripts/replay_relationship.py → E-REL-03
```

## 与 Memory / Reflection / Development 的关系

- **Reflection**：触发源与溯源终点。Insight 是唯一输入（scope=relationship、高置信、active）；里程碑 meta.insight_id 使「这条叙事里程碑从哪来」永远可答；Insight 被 supersede/invalidated **不回滚**已落里程碑（只增 HARD——里程碑记录的是当时达成的经历事实，非行为参数；与 Development 回退语义刻意不同，README 核对记录 7 登记）。
- **Memory**：转写产物经 REL-001 通道成为 `milestone_event` 记忆，参与检索与投影；本 Task 不直写 memories。
- **Development**：无直接交互。若未来关系模式与叙事里程碑出现语义重叠，由白名单内容管理（设计期避让），不建运行时联动。

## 异常与边界情况

- Insight 在入队后被 supersede/invalidated → handler 重读非 active → skip + trace（不落里程碑）。
- 白名单 JSON 配置损坏 → 启动校验告警（对齐 `validate_rel_config` 模式）+ handler 空白名单跳过。
- 落账本成功但转写失败 → 里程碑行已在（账本真相成立），记忆下轮重扫补齐（REL-001 幂等）——两段之间允许短暂不一致，E-REL-01 审计以「最终一致 + 追踪窗口」口径执行。
- 频控计数与落库并发竞争 → 唯一约束兜底（返回 None 不抛），最坏情况当日多落 1 条（cap 是软防线，唯一约束是硬防线）。
- 重放工具遇账本行 impact 为 0 的 system 审计行 → 照常参与重放（impact=0 前向应用无影响），不特判。
- 触发异常一律不阻塞反思链（listener 吞异常 + job 重试/死信 + last_error 留痕）。

## 测试要求

- Unit：白名单匹配（all/any 两模式、大小写、白名单外不触发）；频控（同 key 幂等返回 None、当日 cap）；meta 载荷结构；confidence 阈值边界（0.74/0.75）。
- Integration：①端到端——scope=relationship 高置信 Insight → job → 里程碑行（meta 可溯源）→ post_process 转写 → milestone_event 记忆 source_ref 回指 → timeline 互溯；②触发两次同叙事 → 只落一条（唯一约束路径）；③非 active Insight → skip；④无 bonus 证明——落里程碑前后 relationship_state 六维逐字节不变。
- Eval Gate：`relationship_evaluation.run_scenarios` 四场景 + `compute_metrics` gate_passed + 报告归档 `tests/eval/reports/rel-{date}.json`；IssueCode 34→36 收口断言。
- Regression：**V8.5 regression-checklist 全量重跑**（硬门）：`evolve()` 字节级（`test_relationship_replay.py` + 限速/迟滞/12 里程碑判定）、Flag OFF golden、`create_milestone` 既有调用方（process_milestones）零改动证明（既有 v8.5 测试原样通过）。
- 工具：重放工具对既有账本 fixture 输出「不可解释偏差为空」。

## 验收标准

- 给定数值回归，当 evolve() 执行，那么输出与 v1 字节级一致（重放工具不可解释偏差为空）。
- 给定叙事里程碑触发两次，那么只落一条且 meta 可溯源同一 Insight。
- 给定白名单外或低置信的 relationship Insight，当触发链执行，那么不落任何里程碑。
- 给定任一叙事事实，当审计，那么数值归账本、叙事归记忆、里程碑有 meta 溯源（E-REL-01 100%）。

## Implementation Constraints

- 数值里程碑判定逻辑不动；叙事里程碑只增不改（不 update/delete，不进数值，不解锁）；V8.5 数学（D1/D2/D3/D5、限速、迟滞）零改动——`create_milestone` 仅追加默认 None 的 meta 尾参。
- 触发全规则（关键词白名单），LLM Usage = NONE；不引入新的 LLM 判定点。
- 里程碑写入只经 `relationship_milestone_repository.create_milestone` 唯一写点；记忆转写只经 REL-001 ingest 通道。
- 评估只产报告不写业务状态（V7.5 铁律）；重放工具恒只读。
- 不提前设计 Phase 5（关系闸门对解锁/模式的消费）与 Phase 6；`unlocks` 恒空是刻意的（解锁资产扩展属 Phase 5 需求）。
