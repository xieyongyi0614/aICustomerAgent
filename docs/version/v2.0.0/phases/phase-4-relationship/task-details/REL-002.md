# REL-002 Task Detail — Shared Experience 投影（Core / Projection）

> 上游：[../tasks.md](../tasks.md) REL-002 ｜ [../../architecture/domain-boundaries.md](../../../architecture/domain-boundaries.md) §2 ｜ 依赖：REL-001

## Task 目标

让「共同经历」可查询、可注入 Context：把 Memory（experience / relationship_fact）+ relationship_events + 完结 world_events（双人参与项）投影为时间序的共同经历列表，并作为 Context 新段注入（Freshness 选材、预算内）。这是关系从「数值 Current State」变「历史叙事」的核心缺口——v1 知道关系数值多高，但说不出「我们一起经历过什么」。

## 背景 / 为什么需要

现状盘点（代码事实）：

- 关系切片（`app/prompts/builder.py` `build_relationship_section` L137-181，预算 150 字符）只有：stage 标签/描述 + 三维档位词 + 紧张度 + 条件 extras（冲突指令、neglect 注记、**一个**最近 memory_worthy 里程碑标题 L172-173）。没有任何「经历列表」表达。
- 关系数值事件全量躺在 `relationship_events`（含 impact 六列），里程碑在 `relationship_milestones`，叙事事实在 memories——三处数据从未被拼成「我们一起的经历」视图。
- E-REL-02 要求共同经历随真实交互增长、无凭空条目——只有从真实源数据投影（可对账、可重算）才能满足，任何「生成式总结」都不行。

投影是**只读视图**（domain-boundaries §2：Shared Experience = Projection（Relationship 域），对 Memory + relationship_events 的视图），零写路径、同数据同结果、可随时重算。

## 设计方案

1. **投影服务** `relationship_shared.collect_shared_experiences(user_id, character_id="asuna", now=None) -> list[SharedExperience]`，三源查询后归并排序：
   - **账本事件**：`relationship_events` 中 `source IN ('conversation','system')` 且 `type != 'none'`（type=none 是冲突结算/neglect 的无因审计行，非经历；conversation 行是真实互动，system 的 reconciled 结算行是冲突解决经历）。title = cause 截断，occurred_at = created_at。
   - **叙事记忆**：memories 中 `type IN ('experience','relationship_fact')`、active、visibility 非 hypothetical。experience 全部天然双人（与角色对话产生），按 `v2_relationship_shared_min_salience` 过滤噪声；relationship_fact 无门槛（REL-001 保证其为账本转写）。
   - **world_events**：经 `worlds.user_id` 关联，`status='completed'` 且 `source='user_mention'` 且 `importance != 'low'`。双人参与判定口径见 README 核对记录 3（world_events 无 participants 字段，source=user_mention 是唯一用户在场信号）。
   - **去重**：relationship_fact 记忆的 `source_ref={table:'relationship_events', id}` 与账本行同指一事 → 合并为一条（occurred_at 取账本行，title 优先记忆 content——账本给结构、记忆给叙事）；milestone_event 记忆不在本投影范围（最近里程碑已有关系切片行承载，且 tasks.md Inputs 未列 milestones，不扩范围）。
   - **排序**：occurred_at 升序（验收口径「按时间序返回」）；每条带 salience 供注入选材。
2. **幂等与对账**：同数据同投影（纯函数式读）；`source_ref` 携带 `(kind, table, id)` 三元组使每条经历可对回唯一源行——E-REL-02「对账一致 100%」的落点：测试逐条断言 `count(投影) == count(源行去重后)` 且无投影独有条目。
3. **性能**：三查询均走既有索引（relationship_events idx user_id+created_at 0007；memories idx_memories_user 0001 + type 过滤在用户行集内；world_events 经 worlds.user_id 单行定位）。上限保护：events 查询 limit 100（倒序取最近的）、memories 沿用 pool limit 口径。查询慢时启用 `v2_relationship_shared_cache_ttl_seconds`（0=关）；`Data Changes: 可选 SQL 视图（0~1）` 取 **0**——服务投影可重算、可测试，视图维护成本不值（登记于 README 核对记录 4）。
4. **Context 注入**（复刻 REF-007 模式）：
   - context_builder Flag 门控（`v2_relationship_evolved_enabled`）：读失败/空 → 空列表（fail-safe 降级，不抛）。
   - 选材：投影升序列表按 **Freshness 取最新 `v2_relationship_shared_limit`（3）条**，渲染仍按时间序（叙事连贯）；预算 `v2_relationship_shared_budget_chars`（200 字符）内贪心装入，超预算条目落选并记 reason。
   - 渲染：`build_shared_experience_section` 产出「【共同经历】· X · Y · Z」单行风格（对齐关系段行式），置于关系切片之后、World 切片之前；列表为空 → 段整体不出现（Flag OFF 与空数据 golden 零漂移同一机制）。
   - 该段是 context-architecture §1 分层中 P1 关系切片的扩展子段（README 核对记录 5 登记文档对齐口径），预算独立、不占 800 检索类合并预算（它是结构化投影而非检索召回）。
5. **trace**：`trace.record("relationship_shared", ms, "ok", budget, used, selected=[source_refs], reasons=[逐条])`；外层 `context_assemble_v2` 步骤附带 shared_budget/shared_used（对齐 insight_budget 先例 L184-186）。

## 数据模型 / 状态变化

- 零新表、零迁移、零写路径（投影可重算）。唯一持久面：`ConversationState` 新字段（轮级，不落库）+ 4 个 settings。
- `SharedExperience`：`entry_id:str`（源行 id 或 memory id）、`kind: Literal["relationship_event","experience","world_event"]`、`title:str`（≤60 字符截断）、`occurred_at:datetime`、`source_ref:dict`、`salience:float`。

## 核心处理流程

```text
装配期（context_builder.build，Flag ON）:
  collect_shared_experiences(user_id)
    ├─ relationship_events（conversation/system，type≠none）──┐
    ├─ memories(experience/relationship_fact, active)  ──────┼─ source_ref 去重合并
    └─ world_events(completed, user_mention, 非low) ─────────┘
  → occurred_at 升序投影 → Freshness 取最新 3 条 → 200 字符预算贪心装入
  → ConversationState.shared_experiences
  → prompts/builder 渲染【共同经历】段（空则不出现）
  → trace: relationship_shared（budget/used/selected/reasons）
```

## 与 Memory / Reflection / Development 的关系

- **Memory**：投影读取 memory 域两类型行（experience/relationship_fact），只读不写、不触发 reinforce 缓冲（对齐「读路径零直写」——投影不记 last_accessed，避免写放大）。
- **Reflection**：无直接消费。relationship 类 Insight 不进投影（Insight 是认知不是经历；其叙事化出口是 REL-004 里程碑 → 里程碑记忆 —— 里程碑不在本投影 Inputs，保持任务边界）。
- **Development**：无直接消费。关系模式注入是 REL-003 独立交付（模式行渲染在关系段扩展处，与共同经历段相邻但数据源正交）。

## 异常与边界情况

- 任一源查询异常 → 该源按空处理 + trace error（不抛错；三源部分可用仍出段）。
- 全空（新用户/Flag OFF）→ 段不出现，golden 不变。
- 账本行与记忆行时间不一致（转写延迟）→ occurred_at 取账本行（账本是事件时序权威）。
- 世界事件极多（长期运行）→ 查询 limit 100 倒序 + importance 过滤兜底。
- 双人参与判定误差（user_mention 未必真双人）→ 判定口径登记在案（README 核对记录 3），宁可漏选不可错选；投影对账不受影响（源行级一致）。

## 测试要求

- Unit：三源各自过滤口径（type=none 排除、hypothetical 排除、superseded 排除）；source_ref 去重合并（同事件账本行+记忆行 → 1 条）；升序稳定排序；空数据 → 空列表。
- Integration：①端到端——构造 3 次共同事件（1 账本事件 + 1 转写记忆 + 1 world_event）→ 投影按时间序返回且与源对账一致 → Context 段可见 → trace 落 `relationship_shared`；②Flag OFF → 无该段且 prompt 快照与 v1 golden 一致；③读失败降级 → 段缺席无异常。
- Performance：投影查询 P95 < 50ms（对齐 context 检索目标）；三查询计划走索引。
- Regression：V8 World checklist（world_events 只读不写）；golden prompt 快照（Flag OFF 与空数据两态）。

## 验收标准

- 给定 3 次共同事件，当投影，那么按时间序返回且与源数据对账一致（逐条 source_ref 可回指）。
- 给定 Flag OFF，那么 Context 无该段且 golden 不变。
- 给定任一投影条目，当查询 source_ref，那么可定位唯一源行（无凭空条目）。
- 给定投影查询异常，那么段缺席且当轮回答不受影响。

## Implementation Constraints

- 只读投影：零写路径（不写任何表、不触发记忆 reinforce/last_accessed）、零新表（SQL 视图取 0）、不改 World 域模型与数据。
- 注入经 context_builder + prompts/builder 装配（禁止绕过 Context Architect 直改 prompt）；预算独立 settings，不动 12000 总预算与 800 检索类预算结构。
- LLM Usage = NONE（投影/排序/截断全规则）。
- 不提前设计 Phase 5 关系闸门对共同经历的消费（tasks.md 被依赖声明只承诺「数据可用」）。
