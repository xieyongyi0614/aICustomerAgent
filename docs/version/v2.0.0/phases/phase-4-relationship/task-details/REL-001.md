# REL-001 Task Detail — 关系事实真相源统一（Core / 转写通道）

> 上游：[../tasks.md](../tasks.md) REL-001 ｜ [../../architecture/domain-boundaries.md](../../../architecture/domain-boundaries.md) §4 ｜ 依赖：P1 MEM-002, MEM-005（已交付）

## Task 目标

消除关系事实双真相源：**数值与增量归 `relationship_events` 账本（唯一数值真相），叙事事实归 Memory `relationship_fact` / `milestone_event` 类型记忆（唯一叙事真相），账本行与记忆行经 `source_ref` 互相溯源**。具体交付三件事：

1. 转写通道收口——关闭 v1 直写旁路，里程碑纳入 P1 ingest 转写（事件通道 Phase 1 已建成）；
2. v1 遗留 `relationship_event` 类型记忆迁移脚本（dry-run + 幂等重跑 + 双读校验）；
3. 关系叙事查询在 Relationship 域内收敛的审计可答性（配合 REL-002 投影 + debug timeline 关联）。

不消除双真相源，任何一边变更都会产生「角色又记错关系」体验（v1 审计问题 4），且后续 Shared Experience / 叙事里程碑全部建立在无法对账的地基上。

## 背景 / 为什么需要

v1 审计确认的债务：同一份关系事实存在两条独立的记忆写路径，且互相成环——

- **v1 直写旁路**（仍在运行、不受任何 v2 Flag 门控）：`app/services/relationship_memory.py` `to_memory_candidates`（模板确定性渲染，24h 内存去重）→ `deliver_candidates`（L134-153）→ **直接 `memory_repository.create_memory(memory_type="relationship_event", source="ai_inferred")`**，调用点 `app/services/state_service.py:379-383`（`_run_relationship_subsystems` 内）。
- **v2 摄取通道**（Phase 1 已建成）：`app/services/memory2/ingest.py:241` `ingest_from_relationship_event`（`SOURCE_RELATIONSHIP="relationship_events"`，`proposed_type="relationship_event"`，转正归一化为 `relationship_fact`），接线在 `app/application/post_process.py:216-220`，受 `v2_memory_enabled` 门控。

两条通道内容口径不同（模板渲染 vs cause 原文）、类型不同（`relationship_event` vs `relationship_fact`）、幂等机制不同（进程内 24h 去重 vs `(source_table, source_id)` 唯一约束）。更糟的是 `relationship_event` 类型记忆被关系域反向消费：`state_service._replay_relationship_memories`（L476-530）筛 `memory.type == "relationship_event"` 的记忆做关系数值回放补记（source=memory_replay 写回账本）——形成「账本→记忆→账本」的写环。v2 裁决（domain-boundaries §4）：Relationship 永不直写 memories，转写一律走 Ingest。

## 设计方案

1. **总闸与旁路关停**：`v2_relationship_evolved_enabled` 默认 False。ON 时 `state_service._run_relationship_subsystems` 的记忆投递段（L379-383）整段跳过——v1 模板旁路不再产生新记忆；事件叙事由既有 `ingest_from_relationship_event` 承接（覆盖面是超集：v1 只投递六类筛选事件，v2 摄取全部账本行），里程碑叙事由新增通道承接。OFF 时不做任何读取/分支行为变化（冻结，不是清空）。启用前置：Enablement 串行链中位于 `v2_development_enabled` 之后（dependency-graph §1）。
2. **里程碑转写通道**（事件通道 Phase 1 已交付，本 Task 补齐里程碑半边）：
   - `ingest_from_relationship_milestone`：content = 里程碑 title（数值里程碑为 spec title，叙事里程碑为白名单 title）；`proposed_type="milestone_event"`；`source_kind="user_derived"`；幂等键 `(source_table="relationship_milestones", source_id=milestone.id)`；`source_ref={"table": "relationship_milestones", "id": milestone.id, "milestone_key": ..., "period_key": ...}`；salience 常量映射：memory_worthy 数值里程碑 0.90（对齐 v1 `relationship_memory` importance 口径）、叙事里程碑 0.85、其余 0.70。
   - **只读里程碑行，不读 relationship_state 数值**（对齐 ingest.py:242 的域边界 docstring 约定）；**不写账本、不碰数值**。
   - 接线在 post_process `_run_memory_ingest_v2` 事件循环之后，同款异常隔离（摄取失败仅 log，事件留待下轮重扫——tasks.md Error/Failure 口径）。
3. **v1 遗留记忆迁移脚本** `scripts/migrate_relationship_memory_types.py`：
   - 映射：`memories.type='relationship_event'` → `'relationship_fact'`（存储层 `ck_memories_type` 9 值已含两者，迁移 0024；类型列 UPDATE 不动 content/source/created_at，检索语义由既有别名保证不变）。
   - 默认 **dry-run**：输出报告（待迁移行数、per-user 分布、创建时间分布、`_replay_relationship_memories` 源影响预估——见设计 4）；`--apply` 执行；分批 UPDATE（每批 500，对齐 decay_batch 习惯）。
   - **幂等重跑**：条件 `WHERE type='relationship_event'`，重跑命中 0 行即 no-op。
   - **双读校验窗口**：`--apply` 后脚本输出校验清单——迁移行按 `LEGACY_TYPE_ALIASES` 双类型检索对比（`memory_service.retrieve` 与 `memory2.retriever.retrieve` 各跑同 query 集合，对比命中集合），供灰度评审留档。不做自动双写（避免再造双真相源）。
   - v1 旧行无 `source_ref`：**不回填伪造溯源**——迁移报告单列「无 source_ref 行数」，审计口径登记为「v1 时代产物，溯源到 v1 模板通道而非账本行」；只有 v2 通道新产行才承诺与账本互溯。这是「给定任一重要关系事件可互相溯源」验收的边界：v2 起点之后的行 100% 可溯，存量行在迁移报告中显式声明。
4. **memory_replay 回放路径的处置（登记项）**：`_replay_relationship_memories`（L476-530）筛 `type=='relationship_event'` 的记忆在闲置 ≥24h 时补记 weak 折扣事件（`rel_replay_discount=0.5`）回账本。本 Task **不改该函数**（属 v1 数值路径输入源，Non-Scope「不改 V8.5 数学」覆盖）。Flag ON + 迁移执行后，该筛选自然命中 0 行 → memory_replay 事件归零。这是叙事/数值解耦的**预期结果**（v2 下叙事事实不再驱动数值；账本即真相），在迁移 dry-run 报告中显式输出受影响行数供评审；若评审要求保留回放行为，属架构裁决（扩筛选类型需防与 v2 行双计），另行处理，本 Task 不做。
5. **查询路径收敛**：Relationship 域内收敛 = ①REL-002 投影服务成为「共同经历/叙事事实」的统一读入口；②本 Task 在 `/debug/relationship/timeline` 每行附 `narrative_memory_ids`（source_ref JSON 反查），使「账本行→记忆行」「记忆行→账本行（source_ref）」双向可答；③对话检索侧不变（`retriever` 亲和别名已把两类型归一到 relationship_fact 语义）。审计四问可答：存在哪（memories.type + source_ref.table:id）、为什么存在（memory_ingest trace + 里程碑/事件行）、数值在哪（relationship_events.impact 列）、叙事在哪（memories.content）。

## 数据模型 / 状态变化

- **零新表、零 alembic 迁移**（本 Task）。memories 新增行：type ∈ {`relationship_fact`, `milestone_event`}（两类型均已在 7 类枚举 + ck 约束内）。
- `relationship_milestones` 行保持只读消费（本 Task 不写里程碑表——写入属 REL-004）。
- 候选流：`memory_candidates` 行（source_table=relationship_milestones）→ evaluator → 转正，全部沿 MEM-002/003 既有状态机（MEM-005 TRANSITIONS，无新增）。
- 新增 settings：`v2_relationship_evolved_enabled`（唯一本 Task Flag）。

## 核心处理流程

```text
Flag OFF（现状）:
  账本变更 → v1 relationship_memory.deliver_candidates 直写 memories(type=relationship_event)   [现状不变]
  账本变更 → post_process v2 通道（v2_memory_enabled 时）→ relationship_fact 候选                [现状不变]

Flag ON:
  账本变更(commit_relationship_update) → v1 直写段跳过
  relationship_events 行 ──post_process──> ingest_from_relationship_event ──> relationship_fact 候选
  relationship_milestones 行 ──post_process──> ingest_from_relationship_milestone ──> milestone_event 候选
  候选 → evaluator 转正（source_ref 回指账本行）→ 检索/投影可召回
  /debug/relationship/timeline 每行 ← source_ref 反查 → narrative_memory_ids（互相溯源）

存量（运维，一次性）:
  scripts/migrate_relationship_memory_types.py [--apply] : relationship_event → relationship_fact（幂等）
```

## 与 Memory / Reflection / Development 的关系

- **Memory（写方向）**：Relationship 域经 P1 Ingest 通道转写（合法跨域写入路径之一，dependency-graph §5）；Relationship 自身零直写 memories。Memory 仍不读关系数值（domain-boundaries §1）。
- **Memory（读方向）**：REL-002 投影读 memories（experience/relationship_fact）+ 账本 + world_events，是「查询收敛」的载体；本 Task 交付其前提（类型统一 + 溯源可查）。
- **Reflection**：无直接交互。relationship 类 Insight 是 REL-004 的触发源，其落库产生的里程碑行经本通道转写——反思产物进入叙事记忆的路径因此可归因。
- **Development**：无直接交互。development patterns 只读消费（REL-003），不经本通道。

## 异常与边界情况

- 里程碑摄取失败 → log + 下轮重扫（幂等键兜底），不阻塞 post_process 其余步骤。
- 里程碑行被删除/账本行不存在（理论不发生：里程碑只增 HARD）→ 转写照常（source_ref 悬空可被 E-REL-01 审计捕获）。
- v1 旁路关停后 24h 内存去重失效问题不存在——v2 幂等在 DB 层（唯一约束），跨进程/重启安全。
- 迁移执行中并发写入：分批 UPDATE 只动 type 列，与候选转正写入无行交集（候选转正只产 relationship_fact/milestone_event，不产 relationship_event）；仍要求停写窗口执行（运维约束，脚本头注明）。
- Flag ON 但 `v2_memory_enabled` OFF：转写通道不运行（ingest 在 run_memory_extract 门内）。Enablement 串行链保证不出现该组合；settings 校验器（对齐 `validate_rel_config` L517-533 模式）加一条启动告警。
- 迁移脚本误跑 Flag OFF 环境：不检查 Flag（纯存量规整，不影响行为——类型在读取层同义）；dry-run 报告提示当前 Flag 状态。

## 测试要求

- Unit：`ingest_from_relationship_milestone` 幂等（同 milestone 二次摄取 0 新候选）、salience 映射、source_ref 结构；Flag ON 时 state_service 记忆投递段跳过、其余子系统（冲突/里程碑/快照）照常。
- Integration：①端到端转写——构造账本事件+里程碑 → post_process → 候选 → 转正 → `memory_attribution` 可答「存在哪/为什么存在」；②迁移——构造存量 relationship_event 行 → dry-run 报告 → apply → 重跑 0 行 → 双读检索对比一致；③debug timeline 关联——账本行带出 narrative_memory_ids。
- Regression：**Flag OFF 全量 golden**（state_service 路径逐字节）；V8.5 regression-checklist 重跑（数值零改动证明，含 `test_relationship_replay.py` 既有重放确定性测试）。
- 性能：摄取循环增量 ≤50 事件/轮（既有 limit）+ ≤10 里程碑/轮；迁移脚本 1 万行 < 60s（分批）。

## 验收标准

- 给定任一重要关系事件（Flag ON 后产生），当查询审计，那么账本行与记忆行可互相溯源且数值归账本、叙事归记忆。
- 给定 v1 旧类型（relationship_event）记忆，当执行迁移，那么检索语义不变（双读对比一致）且重跑幂等。
- 给定 Flag OFF，那么关系行为与 v1 逐字节一致（golden 断言）。
- 给定里程碑达成，当 post_process 扫描，那么产生 milestone_event 类型候选且幂等。

## Implementation Constraints

- 账本仍是数值唯一真相；Relationship 域禁止直写 memories（唯一合法路径 = ingest）；不改 V8.5 数学（D1/D2/D3/D5、限速、迟滞、12 项数值里程碑判定、`_replay_relationship_memories` 函数体）。
- 迁移脚本只动 `memories.type` 列，不回填伪造 source_ref，不做自动双写。
- LLM Usage = NONE（全程规则与 SQL）。
- `relationship_memory.py` 模块保留不删（Flag OFF 回退面 + 历史可读性）；删除属 3.0 清理决策。
- 不提前实现 REL-002 投影与 REL-004 叙事里程碑（本 Task 只保证通道与审计就绪）。
