# AUT-003 Task Detail — 观察与调整（Core / Observation · Progress · Adjustment）

> 上游：[../tasks.md](../tasks.md) AUT-003 ｜ [../../../architecture/character-runtime.md](../../../architecture/character-runtime.md) §2.2 生活时刻 / §3 闭环表 ｜ [../../../architecture/domain-boundaries.md](../../../architecture/domain-boundaries.md) §1 Goal 行 ｜ 依赖：AUT-002、LIFE-002

## Task 目标

让 Sub-Goal 执行**被观察、被调整、会失败**——补上 §十四 Observation→Adjustment 缺口的后半段：没有本 Task，规划（AUT-002）是一次性的，Goal 只能「存在」不能「追求」。

具体交付四件事（调整规则全确定性，本 Task 0 LLM）：

1. **判据观察**：Life Loop 周期内检查 active plan 当前 Sub-Goal 的完成判据（输入 = 编排投影的 Action 结果 + World/状态事实，见 GAP-AUT-02 裁决）；
2. **推进与失败计数**：判据达成 → Sub-Goal done 并推进下一序（0 LLM）；未达成 → 连续失败计数，达阈值 → Sub-Goal failed；
3. **调整规则**（顺序 / 拆分 / 放弃，纯规则）：按观察结果调整计划——拆分类调整走 AUT-002 重规划通道（唯一 LLM 通道），本 Task 只做裁决与触发；
4. **失败与周期封顶**：goal 级失败语义（Sub-Goal 连续失败达阈值 → goal failed + failure_reason，禁止无限重试）；单 goal 最长执行周期封顶（超期 → failed）；
5. **Sub-Goal 执行接线**：周期内把当前 Sub-Goal 变成一次 Action 尝试（规则构建 ActionIntent → V9 既有闸门），为观察提供被观察对象。

## 背景 / 为什么需要

AUT-002 产出的 plan 入库后如果无人看，就是一张废纸：完成判据永远不会被检查，Sub-Goal 永远 pending，goal 永远 active——「追求」退化为「挂着」。tasks.md Problem 原文：无观察调整则规划是一次性的。

为什么观察必须是纯规则且判据必须可自动判定：

- **成本铁律**：character-runtime.md §2.2「生活时刻每一环默认纯规则，LLM 只在 Decision 命中且预算允许时发生」——判据检查每周期都跑，用 LLM 判定等于 `while true: call LLM()`（§二十二明禁）；
- **可解释**：E-AUT-02 要求「判据达成自动推进」「为什么推进/为什么失败」可答——白名单谓词的判定过程是确定性 trace，LLM 判定不可重放；
- **防无限重试**：失败计数与阈值是预算硬顶（P6 Capability Map 五项之一）——没有它，一次判据永远不达成的 Sub-Goal 会让角色永远执行同一动作（消息风暴的行动版）。

## 设计方案

1. **观察输入 = 编排投影**（GAP-AUT-02 裁决落地）：Goal 域判定函数不查询 Action/World 表——`evaluate_criteria(criteria, facts)` 是纯函数，`facts` 由 Life Loop 的 goal_advance 步骤采集后传入：

   ```text
   facts = {
     action_results:  action_repository.list_records(user_id, 窗口=v2_autonomy_observation_window_minutes)
                      按 capability 过滤（观察窗 = 修复 LIFE-004 最终一致的时序容忍）
     world_facts:     world_engine.collect_facts(user_id)   （编排域采集，矩阵 ✓）
     state_facts:     state_service.load_states 投影（tension/intimacy/mood）
     memory_facts:    list_top_salience 计数（salient_memory_count 指标）
   }
   ```

   facts 采集一次、判据求值 N 次（active plan 全 Sub-Goal 共用一份快照，同周期判定幂等）。

2. **判据求值（白名单谓词语义）**——与 AUT-002 校验闸共用 `app/models/goal.py` 常量，每谓词一个确定性求值器：

   ```text
   action_succeeded   {capability, within_minutes}   → 窗口内该 capability 存在 succeeded 记录
   field_equals       {source: world|state|memory, path, value}   → 投影事实路径等值
   threshold_reached  {source, path, op(≥|≤), value}              → 越限判定
   all_of / any_of    {children}                       → 组合（一层，校验闸已拒深层嵌套）
   ```

   判据异常（事实源缺失/路径不存在）→ 该 Sub-Goal 本轮 skip+trace（tasks.md Error/Failure：判据异常跳过不计数——计数只对「判定为未达成」生效，异常是第三态）。

3. **推进与失败计数**：

   ```text
   判定 done  → sub_goal.status=done → 下一序 pending→in_progress（无下一序 → goal 完成，
                走 AUT-004 完成语义：completed + experience 转写入队）
   判定未达成 → sub_goal.attempt_count+=1（本次执行尝试若失败/被 V9 闸门拒绝同计）
                连续失败 ≥ v2_autonomy_subgoal_failure_threshold(3) → sub_goal failed
                → 调整规则裁决（设计 4）
   幂等：attempt_count 按事件幂等——同周期内同 Sub-Goal 只计一次（步骤级去重键
         sub_goal_key + cycle；重复执行周期不双计）
   ```

4. **调整规则（纯规则三分支，全 trace）**：

   ```text
   顺序（park/skip）  当前 Sub-Goal failed 且存在可并行的后续 Sub-Goal
                     → 跳到下一可执行步（被跳过的 failed 步留痕，树内标记）
   拆分（重规划）      failed 且无并行步 / 连续多步失败
                     → enqueue AUT-002 重规划（trigger=goal_blocked|goal_replan；
                        failed goal 仅一次重规划资格前置校验；degraded → 不入队只 trace）
   放弃（goal failed） 全部 Sub-Goal 终态且未完成 / 重规划资格已用尽
                     → goal failed + failure_reason（subgoal_threshold_exceeded 等）
   ```

5. **单 goal 最长执行周期封顶**：plan 的 active 起始时刻（goal_plans.updated_at，status 变 active 时）为周期起点，`now - 起点 > v2_autonomy_goal_max_active_hours(168h)` → goal failed（failure_reason=exec_period_exceeded），不再重试（与 Sub-Goal 阈值同语义：封顶后唯一出路是 AUT-004 abandonment 或用户显式干预）。周期起点无新列：active 迁移时 updated_at 即起点（AUT-002 落库时写入）。

6. **Sub-Goal 执行接线与工作发现扩展**：

   ```text
   goal_advance 步骤内序：观察 → 调整 → 执行尝试
   执行尝试（规则构建，0 LLM）：
     当前 in_progress Sub-Goal 且距上次尝试 ≥ v2_autonomy_subgoal_execute_cooldown_minutes
       → ActionIntent(action_type=sub_goal.capability, params=sub_goal.params,
                      dedupe_key=f"goal:{goal_id}:{plan_version}:{sub_goal.index}")
       → run_action_planning(user_id, intent, source="autonomy")   （V9 全闸门原样生效）
       → V9 拒绝（duplicate/quota 等）≠ 执行失败——不计失败数，trace reason（防闸门误伤计数）
   工作发现第四来源：has_goal_work(user) = 存在 active plan 且（当前 Sub-Goal 非终态）
     → 并入 _collect_work_users；LIFE-003 Idle 判定的「无到期 goal」口径同步扩展
     （到期 goal 的 P6 语义 = Sub-Goal 执行窗到期，due 驱动兜底不变）
   ```

   执行尝试的前置克制：静音时段跳过 user-facing 能力（send_notification）的尝试（编排层规则判定，不入 AutonomyPolicy——该纯函数保持零改动，红线继承）。

## 数据模型 / 状态变化

- `goal_plans.sub_goals[]`：status pending→in_progress→done|failed；attempt_count/last_observed_at/failure_note 随观察更新（JSON 原子更新，version 不变——进度是状态不是版本，重规划才升版本）。
- `character_goals`：status 新增 **failed** 终态（本 Task 引入；abandoned/suspended 由 AUT-004 引入，本 Task 的转换表不开放非法出口）；failure_reason 首次启用（exec_period_exceeded / subgoal_threshold_exceeded / replan_exhausted 枚举字面量）。
- goal 状态机本 Task 视角：`active → completed | failed`；failed 后仅允许一次重规划（重规划成功 → 回 active，资格用尽 → 终态）。completed 的 experience 转写：入队 memory ingest 任务（复用 P1 通道），**Goal 域不直写 memories**。
- 零新表零新列（全部落在 AUT-001/002 已建结构内）；新增 settings 4 项。

## 核心处理流程

```text
Flag OFF: goal_advance 步骤不存在；_collect_work_users 维持三来源；零行为差异

Flag ON（周期内 goal_advance，0 LLM）:
  ├─ 前置门控：v2_autonomy_advanced_enabled ∧ 有 active plan → 否则 skip(reason)
  ├─ facts 采集（编排投影：action 窗口/world/state/memory）
  ├─ 封顶检查：执行周期超限 → goal failed(reason=exec_period_exceeded) → 结束
  ├─ 判据求值（当前 in_progress Sub-Goal）：
  │    [达成] → done → 推进下一序 | 全完成 → completed（+experience 转写入队）
  │    [未达成] → attempt_count+1 → 达阈值 → sub_goal failed → 调整三分支
  │    [异常] → skip+trace（不计数）
  ├─ 调整裁决：顺序/拆分(触发 AUT-002 重规划)/放弃(goal failed)
  └─ 执行尝试：当前步 cooldown 到期 → ActionIntent → V9 闸门 → action_records（下周期被观察）
```

## 行为决策流程

P6 特别关注的闭环在本 Task 的落点（全链可解释、可追踪、可回溯）：

```text
角色状态 ──(AUT-002 供给/规划)──▶ 目标生成 ──▶ 意图评估 ──▶ 行为选择
                                                    │
        ┌───────────────────────────────────────────┘
        ▼
   执行（ActionIntent → V9 闸门 → action_records + outbox）
        ▼
   反馈分析（本 Task：判据求值 → done/failed/异常 三态 + 失败计数）
        ▼
   状态更新（sub_goal 推进 / goal failed / 调整裁决留痕）
        ▼
   影响未来（推进改变下一步执行；失败改变计划；封顶改变 goal 生命周期）
```

每一步的「为什么」落 goal_observation trace：判据内容、facts 快照摘要、判定结果、计数变化、调整分支与理由——「为什么推进/为什么失败」（E-AUT-02）可答。

## 与 Memory / Reflection / Development / Relationship / Life Loop 的关系

- **Memory**：读显著度计数（判据指标）；goal completed 时 experience 转写经 P1 ingest 通道入 Candidate（**不直写**——dependency-graph §5 红线）；Memory 不感知 goal 状态。
- **Reflection**：无直接交互（goal 完成的经验若要成为 Insight，走 Memory→Evidence 窗口→REF 既有链，Goal 不越级）。
- **Development**：无直接交互（Dev 调制已在 select/供给层生效；观察判据不读调制参数）。
- **Relationship**：判据的关系类指标读关系状态投影（编排传入，只读）；本 Task 零关系数值写入。
- **Life Loop**：goal_advance 是核心消费点——观察/调整/执行三段全部发生在周期内（0 LLM，不占 LIFE-003 周期预算）；重规划经 background_jobs 异步出周期；工作发现扩展第四来源使 Idle 判定与 P6 语义一致。

## 异常与边界情况

- **判据异常**（事实源缺失/路径不存在/类型不符）：该步本轮 skip+trace，不计数（第三态语义）；连续异常 ≥ 阈值 → 视同连续失败（tasks.md：连续异常 goal 转 failed 不无限重试——异常与失败在 goal 级合流，Sub-Goal 级异常不计）。
- **V9 闸门拒绝**：不计失败（闸门拒绝是「此刻不可执行」非「尝试失败」）；dedupe_key 含 plan_version + sub_goal.index，重规划后自然换键不撞旧闸。
- **执行与观察的时序**：本周期执行的行动最坏下周期才可见（outbox 同事务，但观察窗与执行窗错位）——判据窗口 `v2_autonomy_observation_window_minutes` 覆盖跨周期回看；对超窗判据（如「一天内不重复」类）由 field_equals/threshold 指标天然表达，不依赖执行窗。
- **重规划与观察并发**：重规划 job 运行期间 active plan 可能切换版本——观察每周期从 `list_active_plans` 现读，版本切换后旧进度随旧版本归档（新版从 pending 起步，attempt 归零；重规划成本已在 AUT-002 计数内）。
- **completed 的 experience 转写失败**：入队失败仅 trace（goal 已 completed，转写是旁路收益非完成前提）。
- **多 goal 并存**：同用户多个 active plan 的观察/执行在同一 goal_advance 内按 plan 创建序串行（每 goal 独立判定，互不阻塞）；执行尝试受 V9 全局闸门约束，不会因多 goal 放大行动量。
- **封顶与 abandonment 的边界**：exec_period 封顶 → failed（本 Task）；abandoned 是 AUT-004 对「长期无进展但未达失败阈值」goal 的裁决——两者不重叠（failed 优先，abandoned 只作用于仍 active 的 goal）。

## 测试要求

- Unit：判据谓词逐类型真值表（含组合/异常三态）；失败计数幂等（同周期重复不双计）；调整三分支裁决表；封顶现算（起点=active 迁移时刻）；转换表守卫（非法转换拒绝）。
- Integration：①达成推进全链（执行→outbox→下周期观察→done→推进，0 LLM 断言）；②连续失败达阈值 → goal failed + failure_reason + 不再重试（E-AUT-02）；③拆分 → 重规划 job 入队（degraded 时只 trace 不入队）；④completed → experience Candidate 落库（经 Ingest 通道断言）；⑤工作发现第四来源 + Idle 语义。
- FailureInjection：判据事实源持续异常 → goal failed 不无限重试；outbox 延迟 → 窗口容忍不误判。
- Regression：V6/V7 checklist（执行接线不触碰 AutonomyPolicy/V9 引擎本体）+ Flag OFF golden + P1~P5 Eval Gate。

## 验收标准

- 给定判据达成，当周期检查，那么自动推进不调 LLM（goal_advance 全程 0 LLM 调用记录——E-AUT-02 前半）。
- 给定 Sub-Goal 连续失败达阈值，那么 goal 转 failed 且记录 failure_reason，不再重试（后续周期 goal_advance 对该 goal 零动作——E-AUT-02 后半）。
- 给定单 goal 执行超 `v2_autonomy_goal_max_active_hours`，那么 failed（reason=exec_period_exceeded）。
- 给定 completed goal，那么 experience 候选经 P1 Ingest 落库且 Goal 域无 memories 直写（依赖矩阵断言）。
- 「为什么推进/为什么失败」对任意一次周期检查均可由 goal_observation trace 回答（判据/结果/计数三要素齐备）。

## Implementation Constraints

- **红线**：AutonomyPolicy 纯函数与 Action/World 引擎本体零改动（继承 P5 红线；执行接线是 ActionIntent 构建方，`run_action_planning` 原样调用）；`goal_service.select` 的 v1 语义零改动（v1 调用点补「layer NULL 过滤」属本 Task 唯一既有行修改，见冲突登记 GAP-AUT-04）。
- **域边界**：Goal 域判定函数纯函数化（facts 由编排投影传入，Goal 不查 action/world 表——GAP-AUT-02）；写面仅 goal/goal_plans；Memory 经 Ingest 通道。
- **0 LLM**：观察/调整/执行接线全确定性；LLM 仅可能经 AUT-002 重规划 job 发生（异步、受其 attempt 封顶与本 Task degraded 门控）。
- 调整规则不新增 LLM 通道：拆分=AUT-002 重规划触发，顺序/放弃=纯规则（tasks.md Non-Scope：常规调整纯规则）。
- 失败计数与封顶全部 settings 化；禁止硬编码阈值。

## 冲突登记（评审决策材料）

### GAP-AUT-04：v1 select 消费点的层级过滤

**问题**：`goal_repository.list_active`（v1 主路径）不过滤层级字段——AUT-001/002 落库的层级 goal 会混入 `goal_service.select` 的轮内动机集合，v1 select 对层级 goal 的行为未定义（tier 表无对应 type 时 KeyError 风险：层级 goal 的 type 取值若沿用 v1 4 类则不会 KeyError 但语义被误选）。
**裁决**：v1 `select()` 本体零改动（golden），本 Task 在既有调用点（chat_pipeline `_select_goal` / autonomy_engine `_snapshot_for`）入参侧过滤 `layer IS NOT NULL` 的行——轮内动机仍由 v1 4 类承担，层级 goal 的行动表达走本 Task 的 Sub-Goal 执行通道（主动消息动机不变，P6 不扩 PROACTIVE_INTENTION_MAP——登记为 3.0 演进项）。改动是消费侧一行过滤 + 测试，非行为语义变更。
**备选**：若评审认为层级 goal 也应驱动 proactive 消息，需改 AutonomyPolicy（红线破除）+ PROACTIVE_INTENTION_MAP 扩展——超出本 Phase 范围，不予采纳。
