# AUT-001 Task Detail — Goal 层级与存储扩展（Foundation）

> 上游：[../tasks.md](../tasks.md) AUT-001 ｜ [../../../architecture/domain-boundaries.md](../../../architecture/domain-boundaries.md) §1 Goal 行 ｜ [../../../architecture/character-runtime.md](../../../architecture/character-runtime.md) §4 不变量 ｜ 依赖：无（可提前开发；启用依赖 P5）

## Task 目标

给 Goal 域补上层级与分类的**存储基座**，让「目标」从 v1 的扁平 4 类规则列表升级为可表达长期追求的两维模型：

```text
维度一（时间 layer）：short_term / long_term
维度二（域 domain）：personal / relationship / world
```

具体交付三件事：

1. `character_goals` 表扩 4 列：`parent_goal_id`（挂树）/ `layer` / `domain` / `failure_reason`（失败语义留痕，AUT-003/004 消费）；
2. 新表 `goal_plans`（迁移 0031）：Planning 产物（Sub-Goal 树 + 每步完成判据）的版本化存储，本 Task 只建表与服务壳，写入方是 AUT-002；
3. `goal_service` 层级查询扩展（list_tree / list_children / 按 layer+domain 过滤）与层级 goal 创建 API（供 AUT-002 供给装配与剧情测试调用的纯存储入口，0 LLM、无运行时行为）。

**本 Task 无任何运行时行为变化**（tasks.md Runtime Flow: 无；LLM Usage: NONE）——它是纯 DDL + 服务壳，Flag 只定义不接线。

## 背景 / 为什么需要

v1 Goal（V6 实现）是扁平 4 类（user_care/relationship/conversation/scene）规则列表：`goal_service._decide_creation` 从 turn 信号确定性产出 4 条固定描述目标，`select()` 按 tier 排序选动机——**目标没有父子、没有时间跨度、没有域归属**。这带来两个结构性缺口：

- **无层级则无法表达长期追求**：「守护用户的身心状态」这类 persistent 目标只能被完成/过期/取消，不能被拆解为跨会话推进的执行计划——角色「有目标」但不会「追求」（Phase 6 README 的问题陈述）；
- **无 domain 则 Personal Goal 无从 Development 供给**：tasks.md Problem 原文——Phase 3 已产出 Belief/Pattern 慢变量（`development_state`），但 v1 goal 的 4 类 type 里没有 personal 位，Development 的产出无处落地为「角色因经历而立的目标」。

v2 裁决（domain-boundaries.md §1 Goal 行）：Goal 域职责 = 目标层级、优先级、生命周期，数据真相源 `goals + goal_plans`（实现中即 `character_goals` 表，见冲突登记 GAP-AUT-03），依赖只向下（Dev/Rel/Memory 只读），不能写 Scene/World、不被 Memory 反向写。本 Task 把这个域的存储面一次建齐，供 AUT-002~004 消费。

## 设计方案

1. **两维分类进列不进枚举墙**：`layer`/`domain` 是可空 String + CHECK 约束（`layer IN ('short_term','long_term') OR layer IS NULL`；`domain IN ('personal','relationship','world') OR domain IS NULL`）。旧行两列为 NULL = 「走 v1 路径」的判据（验收硬条件），Pydantic 层 `GoalLayer/GoalDomain` 用 `str | None` 承接。**不迁移旧 goal 为层级**（tasks.md Non-Scope）：v1 persistent 三种子目标保持 layer/domain NULL，语义不变。

2. **goal 层级树 = goal 行；Sub-Goal 树 = goal_plans 行**——两个层级两种载体，职责不重叠：
   ```text
   goal 行（character_goals）        目标级层级：long_term 追求 ← short_term 子目标
                                    生命周期/优先级/仲裁的单位（AUT-004 以行为单位裁决）
   goal_plans 行                     执行计划：Planning 产出的 Sub-Goal 树（JSON 内嵌）
                                    每个 Sub-Goal = {序, 描述, capability, params, 完成判据, 状态}
                                    随重规划整树重生成（版本化），不升格为 goal 行
   ```
   裁决理由：Sub-Goal 无独立生命周期（随 plan 版本重生成），升格为表行会制造 v1 审计「概念债」式的双账本；`parent_goal_id` 只表达 goal↔goal 的归属（如 short_term「本周完成读书笔记」挂 long_term「成为更博学的人」）。**本 Phase 内 supply 创建的层级 goal 默认顶层（parent NULL）**，挂树入口作为 API 能力交付、创建侧是否用由 AUT-002 供给规则决定。

3. **goal_plans 表结构**（写入方 AUT-002，本 Task 建表+服务壳）：
   ```text
   goal_plans
     id / goal_id（软引用 character_goals.id，无硬 FK，与库内既有风格一致）
     version int          -- 每 goal 内自增；重规划产生新版本，旧版留痕
     status               -- draft → validated → active | rejected（AUT-002 状态机）
     sub_goals JSON       -- [{index, description, capability, params, criteria, status,
                          --   attempt_count, last_observed_at, failure_note}]（AUT-003 推进）
     rejection_reason     -- 校验闸拒绝原因（可执行性/预算封顶），status=rejected 时非空
     created_at / updated_at
     唯一：(goal_id, version)；索引：(goal_id, status)
   ```
   判据 `criteria` 的**形式化白名单**（判据可自动判定的落地，AUT-002 校验闸与 AUT-003 观察共用同一定义，放 `app/models/goal.py` 常量）：`action_succeeded`（capability 行动成功回执）/ `field_equals`（固定事实路径等值）/ `threshold_reached`（固定指标越限，指标白名单：tension/intimacy/mood/salient_memory_count/reminder_created 等）/ `all_of`/`any_of`（组合，一层）。自由文本判据不在白名单 = 不可判定 = 校验闸拒绝。

4. **LIFE-002 缺口裁决（time-based 到期）**：LIFE-002 曾登记「goal 到期是 turn 基准，time-based 到期属 P6 AUT-001 存储扩展」。本 Task 裁决：**不新增 due_at 列**（tasks.md Data Changes 固定 4 列，不加列）。层级 goal 的时间性表达为：long_term 恒 `horizon=persistent`（跨会话存续，v1 过期规则天然不触及——`_expire_due_goals` 只扫 `horizon=current`）；short_term 用 `expires_at_turn` 既有列（NULL=不过期）。「单 goal 最长执行周期封顶」（P6 预算硬顶之一）不依赖 due_at，由 AUT-003 以 plan active 起始时刻现算（见 AUT-003 设计 4）。若真实回归暴露需要绝对时间到期，登记为后续存储扩展项，不在本 Phase 提前。

5. **层级查询服务**（`goal_service` 薄封装 + repository 实现，全部只读）：
   ```text
   list_children(goal_id)                     直接子 goal（parent_goal_id 索引）
   list_tree(user_id, root_goal_id)           以根为起点的子树（含各节点状态）
   list_layered_active(user_id, layer=None, domain=None)   层级 active goal（layer/domain 过滤）
   list_active_plans(user_id)                 活跃 plan 联查（status=active 的最新版本）
   ```
   降级口径对齐 `load_active`（查询异常 → 空集 + exception log，动机层不因 Goal 域故障而崩）。

6. **创建 API 与向后兼容分界**：`create_hierarchical_goal(user_id, layer, domain, description, priority, parent_id=None, source="policy")` 是层级 goal 唯一合法创建入口——内部强制 `layer/domain` 非空、`horizon=persistent`（long_term）或显式（short_term）、不触碰 v1 `_decide_creation` 路径。v1 路径与层级路径以「layer/domain 是否为 NULL」为唯一分界判据，任何消费点（AUT-003 观察、AUT-004 仲裁）先按此分流。

## 数据模型 / 状态变化

- `character_goals`：+4 可空列（旧行自然 NULL）；`parent_goal_id` 建索引；(layer, domain) 建部分索引（仅非 NULL 行）——供 AUT-004 同域冲突分组扫描。
- 新表 `goal_plans`：见设计 3。本 Task 零写入。
- goal 状态机**本 Task 不动**：status 仍 4 值（active/completed/expired/cancelled）；suspended/failed/abandoned 由 AUT-004（仲裁与放弃）与 AUT-003（failed）引入状态机扩展，`failure_reason` 列本 Task 只预留（AUT-003 写入失败原因）。
- 新增 settings：`v2_autonomy_advanced_enabled`（default=False，仅定义）。
- 零业务域表写入、零运行时读面变化——迁移后所有既有查询返回与迁移前逐字节一致。

## 核心处理流程

```text

迁移 0031:
  upgrade: ALTER character_goals +4 列 + 索引；CREATE goal_plans

```

## 行为决策流程

本 Task 无行为决策（0 LLM、0 运行时分支）。唯一的「决策」是创建 API 内的合法性守卫（确定性规则，非运行时行为）：

```text
create_hierarchical_goal 调用
  ├─ layer ∉ {short_term, long_term} 或 domain ∉ {personal, relationship, world}
  │     → 拒绝（ValueError，不落库）
  ├─ parent_id 给定但父行不存在 / 父行 layer=NULL（v1 行不可作父）
  │     → 拒绝（层级树只允许挂在层级 goal 下）
  ├─ long_term 强制 horizon=persistent；short_term 允许 persistent 或显式 expires_at_turn
  └─ 通过 → 落库（source 固定 "policy"，created_turn=0）→ 返回 GoalRecord
```

## 与 Memory / Reflection / Development / Relationship / Life Loop 的关系

- **Memory**：零交互（依赖矩阵 Goal→Memory 允许读，但本 Task 无读取点）；「不被 Memory 反向写」铁律不新增违反面。
- **Reflection**：零交互（Insight 供给 goal 的接线属 AUT-002 供给装配的登记缺口，见 GAP-AUT-01）。
- **Development**：零交互本 Task——`development_state` 供给 Personal Goal 的运行时接线归 AUT-002（同 GAP-AUT-01）；domain=personal 的存储位是这一供给的前提。
- **Relationship**：零交互（domain=relationship 的存储位供 AUT-002 读 REL-003 patterns 后落地）。
- **Life Loop**：零接线本 Task——LIFE-002 的 goal_check 补扫与 `_expire_due_goals` 对 NULL 层级行行为不变（`horizon=current` 过滤天然绕开 persistent 层级 goal）；AUT-003 才把层级 goal 接入周期。

## 异常与边界情况

- **迁移幂等与往返**：upgrade 可重入（IF NOT EXISTS 口径）；downgrade 在有 goal_plans 数据时仍干净 drop（表为 P6 专属，降级即放弃 P6 数据，无 v1 数据损失）。
- **旧行 layer/domain NULL 的所有查询路径**：`list_active`（v1 主路径）不过滤层级字段——旧行与新层级 goal 都可能出现在 v1 select 的入参里。裁决：`list_active` 保持原样（不过滤），v1 `select()` 对层级 goal 行为未定义的风险由消费方分流规避——AUT-003/004 各自只取自己语义的集合（v1 select 调用点在 AUT-003 接线时改为「v1 4 类 + layer NULL」过滤，登记到 AUT-003 设计）；本 Task 不改 `select()`（改了就动 v1 golden）。
- **孤儿父子**：`create_hierarchical_goal` 守卫父行存在性；运行期父 goal 被置终态后子 goal 的语义（级联 suspended？）归 AUT-004 仲裁器裁决，本 Task 只保证不留悬空 parent_goal_id（无删除 API，天然无孤儿）。
- **sub_goals JSON 形状漂移**：goal_plans 由 AUT-002 写入，本 Task 的服务壳提供 `SubGoalSpec` Pydantic 校验入口（`validate_sub_goals`），非法形状在写入侧拒绝而非读取侧容错。
- **并发创建**：创建 API 无唯一键约束（同描述可并存，去重是供给规则的职责——AUT-002 幂等键拦截）；层级查询只读无并发问题。

- Regression：V6 goal checklist（每 Task 合入硬门）；P1~P5 全量 Flag OFF golden。

## 验收标准

- 给定 v1 旧 goal 行，当升级后运行，那么行为与 v1 一致（层级字段空走旧路径，review/select/list_active 输出逐字节一致）。
- 给定层级查询（list_children/list_tree），那么父子关系正确（含深层挂树、跨用户隔离）。
- 给定 downgrade，那么 `character_goals` 回到 12 列、`goal_plans` 消失、v1 零影响。
- 给定迁移后空跑全量回归，那么 2079 既有用例全绿（零行为漂移的机器证明）。

## 冲突登记（评审决策材料）

### GAP-AUT-03：表名口径

### GAP-AUT-01：层级 goal 供给链缺失（跨 AUT-001/002，主登记在 AUT-002）

tasks.md 未包含「层级 goal 由谁创建」的运行时接线：AUT-001 只做存储，AUT-002 的 Runtime Flow 以「目标创建」为输入，AUT-004 以「目标集合变更」为输入——**创建本体无 Task 承接**。Phase 6 README §核心能力 1 定义了三类来源（personal 源自 Belief/Pattern、relationship 源自 Relationship Patterns、world 源自 World 事件），但实现侧若无创建路径，Phase 6 交付的是「有层级存储、有规划、有观察，但生产环境永远没有层级 goal」的死存储——验收剧情只能靠测试侧直建 goal。调整建议（不改架构、不新增 Task）：创建接线作为 AUT-002 Runtime Flow 第一环「目标创建」的实体化交付（纯规则供给装配器，0 LLM），详见 AUT-002 设计 1 与其 GAP-AUT-01。本 Task 为其预留 `create_hierarchical_goal` 唯一入口。
