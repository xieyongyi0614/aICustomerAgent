# AUT-002 Task Detail — Planning 执行器（Core）

> 上游：[../tasks.md](../tasks.md) AUT-002 ｜ [../../../architecture/llm-orchestration.md](../../../architecture/llm-orchestration.md) §1 Goal Planning 行 ｜ [../../../architecture/character-runtime.md](../../../architecture/character-runtime.md) §3 闭环表 Goal→Action 行 ｜ 依赖：AUT-001、P5 LIFE-002

## Task 目标

把「目标 → 可执行计划」这一步做成**受闸的 LLM 规划管线**：给定一个层级 goal，产出 Sub-Goal 树（每步有可自动判定的完成判据、能力对齐的执行面），且 100% 过可执行性校验才入库——任务书 §十四明令禁止「LLM 随便生成任务然后无限执行」。

具体交付四件事：

1. **供给装配器**（目标创建的实体化，GAP-AUT-01 的收口落点，纯规则 0 LLM）：三类来源信号 → 层级 goal 候选 → 经 AUT-001 `create_hierarchical_goal` 落库 → 触发规划；
2. **Planning Prompt 组装**：goal + 能力清单 + World/Development 约束（编排投影传参，见设计 3）；
3. **Planning LLM 执行器**（main 档结构化输出，后台 job）：产出 PlanningProposal → 校验闸 → 入库 `goal_plans`；
4. **预算硬顶**：Sub-Goal 深度 ≤2、数量 ≤5/树、Planning LLM ≤3 次/goal 生命周期（第 4 次请求前置拒绝并 trace）、失败重试 1 次后放弃规划。

规划**不直接执行任何 Action**（tasks.md Non-Scope）——产出的是计划，执行归 AUT-003 的周期接线。

## 背景 / 为什么需要

P6 前系统里「目标」只被两种方式处置：v1 规则创建（`_decide_creation` 4 条固定描述）与轮内选择（`select()`）。没有任何机制把一个目标**拆解成可推进的步骤**——这是「角色有目标但不会追求」的直接原因，也是 §十四 Observation→Adjustment 缺口的前半段：没有 plan，观察就没有对象。

为什么必须过校验闸而不能信任 LLM 规划：

- **能力不对齐 = 必然失败循环**：LLM 天然倾向产出「多陪陪用户」这类无执行面的步骤；系统能执行的动作面只有 V9 能力注册表的 9 类 Action（`ACTION_TYPES`）加 autonomy 分支的 create_reminder 模板（`PROACTIVE_ACTION_MAP`：check_in→create_reminder）。步骤若引用不存在的能力，执行期才会失败，然后无限重试——正是 §十四禁止的形态；
- **判据不可判定 = 观察退化为人肉**：AUT-003 的观察是 0 LLM 规则判定（预算铁律），判据必须是白名单形式化谓词；自由文本判据让「为什么推进/为什么失败」永远不可答；
- **无预算封顶 = 成本无底洞**：反思的教训已写入 llm-orchestration.md（Goal Planning 低频、每 goal ≤3 次/生命周期）——规划是 main 档调用，必须用计数硬顶而不是「尽量少调」。

## 设计方案

1. **供给装配器（GAP-AUT-01 收口）——目标创建的实体化**：tasks.md AUT-002 Runtime Flow 第一环就是「目标创建」，但注册表无 Task 承接创建本体（详见 GAP-AUT-01 登记）。裁决：**供给装配器并入本 Task**，作为规划触发链的最前端，纯规则 0 LLM：

   ```text
   来源一 personal：read_overlay(goal_weights/care_topics/habit_candidates 非空
              且 strength ≥ v2_autonomy_supply_personal_min_strength)
            → 候选：long_term personal goal（描述 = 调制摘要模板，settings JSON 可配）
   来源二 relationship：read_relationship_patterns 中 active 且 min_strength 达阈值
            → 候选：long_term relationship goal（描述 = pattern 模板）
   来源三 world：list_top_salience 记忆中 source=world_event 的 experience，
            近 N 天未被同类 goal 覆盖
            → 候选：short_term world goal（描述 = 事件摘要截断 ≤40 字符）
   幂等：候选去重键 (domain, description) 活跃唯一——已存在同键 active goal 则跳过
   频控：v2_autonomy_supply_interval_minutes（默认 720min）每用户节流
   ```

   创建经 `create_hierarchical_goal`（AUT-001 唯一入口）后**立即 enqueue 规划 job**——创建与规划在同一条 Runtime Flow 里首尾相接。0 LLM：goal 描述用规则模板（非生成）。

2. **规划触发器三类**（tasks.md Runtime Flow：创建/受阻/重规划）：

   ```text
   goal_created     供给装配器创建后（设计 1）
   goal_blocked     AUT-003 观察：当前 Sub-Goal 连续失败达阈值 / 判据不可判定（trace 上报）
   goal_replan      AUT-003 调整规则裁决「需重规划」（拆分类调整的唯一 LLM 通道）
                    且 failed 后仅允许一次重规划（AUT-003 状态机约束，此处前置校验）
   ```

   入队统一走 background_jobs（幂等键见下），**禁止前台调用**（llm-orchestration.md：Planning 时机=后台；main.py lifespan 注册 handler）。受阻/重规划触发由 Life Loop 周期内（AUT-003 步骤）发起——payload 携带 World 事实投影（见设计 3），规划 job 本体不读 World。

3. **Planning 输入组装与域边界投影（GAP-AUT-02 落点）**：依赖矩阵 Goal→World 为 ✗（Goal→Action 同）——规划输入的「World/Development 约束」按来源分流：

   ```text
   Development 约束   job 内直读 read_overlay（Goal→Dev ✓，读调制参数）
   World 约束         入队方（Life Loop 周期步骤）调用 world_engine.collect_facts
                      后塞进 job payload（编排域投影传参，LifeLoop→一切 ✓）
                      job 内零 World 查询——payload 即全部世界事实
   能力清单           注册表静态快照（capability 名 + 参数要求摘要）进 prompt
   goal 本体          job 内经 goal_repository 读（本域 ✓）
   ```

   Prompt 结构（结构化输出 `PlanningProposal`：`[{index, description(≤40字符，对齐 GOAL_DESCRIPTION_MAX_LENGTH), capability, params, criteria(白名单谓词), depends_on}]`）要求：每步必须 capability ∈ 能力清单；判据必须白名单形式化；树深 ≤2（顶层 Sub-Goal + 一层子步）；全树 ≤5 步。

4. **校验闸（Plan Validation，双段）**——LLM 输出先过闸再入库，**拒绝不是异常而是正常产出**（trace 原因，goal 留待规则通道或重规划预算）：

   ```text
   前置闸（调用 LLM 之前，0 成本拒绝）：
     ├─ 规划尝试计数：goal_plans 行数（该 goal_id 全版本） ≥ v2_autonomy_planning_max_attempts(3)
     │     → 拒绝（E-AUT-01 验收第 4 次请求被拒的落点），不调 LLM，trace reason=attempt_cap
     ├─ failed goal 二次重规划拦截（AUT-003 状态机「failed 后仅一次重规划」的前置复检）
     └─ goal 已有 active plan 且触发源非受阻/重规划 → skip（幂等）
   结构闸（LLM 输出之后）：
     ├─ capability 对齐：每步 capability ∈ ACTION_TYPES ∪ autonomy 模板；参数过 registry 元数据校验
     ├─ 判据可判定：criteria ∈ 白名单且 params 形状合法（SubGoalSpec.validate_sub_goals）
     ├─ 深度 ≤2 / 数量 ≤5（settings 封顶）
     └─ depends_on 无环、无前向引用
   [通过] → goal_plans 落库（version=max+1, status=validated）→ 置 active（旧 active 版本置
            superseded 留痕，登记为状态机补充）→ trace goal_planning(validated)
   [拒绝] → goal_plans 落库（status=rejected, rejection_reason）→ trace goal_planning(rejected)
            → 不静默降级执行（tasks.md Error/Failure 原文）；goal 无 plan 期间 AUT-003
              观察按「无计划」路径记账，执行面留空
   ```

5. **LLM 执行与失败语义**（对齐 reflector 模式）：main 档（`v2_autonomy_planning_llm_profile`，空回退默认 profile，`_resolve_llm` 同构）；结构化链 `build_structured_chain`；解析/调用失败**重试 1 次**（tasks.md LLM Usage 口径），再失败 → 放弃本次规划（trace reason=llm_failed + job done 不重排——重规划由下次触发器自然发起，避免 job 级无限重试叠加 LLM 级重试）。重试消耗 attempt 计数吗？**不消耗**：attempt 计数以「成功产出入库的规划版本 + 被拒请求」计——重试是同一次请求的内部恢复。裁决依据：E-AUT-01 门槛是「LLM ≤3 次/goal」按**规划请求**计（每请求至多 1 次成功调用 + 1 次重试），验收断言按 goal_plans 行数核对，口径自洽。

6. **周期接线（Life Loop）**：`goal_supply` 步骤（设计 1）插入管线，前置条件链：`v2_autonomy_advanced_enabled ∧ v2_life_loop_enabled ∧ budget≠degraded ∧ 节流未到` → 否则 skip（skip_reason：flag_disabled / quota_circuit_open / throttled / no_candidates）。步骤产出：created 数 + enqueued job 数，全记账。**本 Task 不动 decision 步骤**（Sub-Goal 执行接线是 AUT-003）。

## 数据模型 / 状态变化

- 写 `goal_plans`（AUT-001 建表）：version 递增、status draft→validated→active|rejected（+superseded 版本归档，登记）；rejection_reason 留痕。
- 写 `character_goals`：经 `create_hierarchical_goal` 新增层级 goal 行（layer/domain 非空、horizon=persistent|显式）。
- 写 `background_jobs`：`goal_planning` job（幂等键 `goal_planning:{goal_id}:{trigger}:{version_hint}`，重复事件天然拦截）。
- goal 行 attempt 语义：**无新列**——计数 = `SELECT COUNT(*) FROM goal_plans WHERE goal_id=:gid`（(goal_id, status) 索引覆盖）。
- 新增 settings：见代码位置表。零 Memory/State/Relationship/Development/World 表写入（全部只读消费）。

## 核心处理流程

```text
Flag OFF: goal_supply 步骤不存在（管线与 v2_life_loop_enabled 现状逐字节一致）；
          goal_planning job 无注册方（入队点全在 Flag ON 分支内）

Flag ON（周期内，0 LLM）:
  goal_supply 步骤
    ├─ 前置门控（Flag/预算/节流）→ 不满足 skip(reason)
    ├─ 三来源规则候选（设计 1）→ 去重 → create_hierarchical_goal
    └─ enqueue goal_planning(payload={goal_id, trigger=goal_created, world_facts 投影})

后台（job worker，LLM 唯一发生点）:
  run_planning_job
    ├─ 前置闸（attempt 计数/重规划资格/幂等）→ 拒绝则 trace + done（不调 LLM）
    ├─ 组装输入（goal + payload 世界事实 + Development overlay + 能力清单）
    ├─ LLM 结构化规划（main 档；失败重试 1 次 → 放弃 trace）
    ├─ 结构闸（能力对齐/判据白名单/深度数量封顶/依赖无环）
    └─ [通过→validated→active（旧版 superseded）| 拒绝→rejected+reason] → goal_planning trace
```

## 行为决策流程

规划触发与入库的决策全链（可解释性要求：「为什么这么拆」可答）：

```text
供给决策（纯规则）:
  调制参数强度 / pattern 强度 / salient 世界经验  ──阈值──▶ 候选 ──去重──▶ 创建
  每一步落 goal_supply 步骤记账（候选来源、命中键、跳过原因）

规划决策（LLM 一次调用 + 双段闸）:
  输入 = goal 描述 + 域约束（Dev 调制 / World 投影）+ 能力清单 + 判据白名单说明
  输出 = Sub-Goal 树提案
  闸门 = 前置闸（预算/资格，拒绝不调 LLM）→ 结构闸（可执行性）
  产物 = active plan（执行对象）| rejected（trace 原因，无副作用执行）
```

「意图评估 / 行为选择」两层保留在既有引擎：规划产物不改变 AutonomyPolicy 八步裁决与 `goal_service.select` 的轮内动机——本 Task 交付的是**计划**，把计划变成行动的决策在 AUT-003 周期规则里（且规划不直接执行任何 Action，tasks.md Non-Scope）。

## 与 Memory / Reflection / Development / Relationship / Life Loop 的关系

- **Memory**：供给来源三读 `list_top_salience`（world_event 源 experience）；**Goal 不写 Memory**（规划产物入 goal_plans，完成后的 experience 转写是 AUT-003/004 完成语义的事，且走 Ingest 通道不直写）。
- **Reflection**：无直接交互——供给来源一的 strength 来自 Development 慢变量（Insight 的下游），Goal 域不读 Insight 本体（经 Development 一跳，守「Development ← Reflection 单向」不被绕过）。
- **Development**：只读 `read_overlay`（调制参数进 Planning prompt + personal 供给阈值）；**Development 不感知 Goal**（Goal 是 Dev 的下游消费方，零回调）。
- **Relationship**：只读 `read_relationship_patterns`（供给来源二）；关系数值写入零触碰。
- **Life Loop**：`goal_supply` 是新增周期步骤（本 Task 交付，纯规则）；规划本体以 background_job 形态运行（不占周期 LLM 预算——LIFE-003 的 `_cycle_llm_budget_exhausted` 统计的是周期内 LLM capable 步骤，goal_supply 是 0 LLM 步骤）；日配额 degraded 时供给与入队双停。

## 异常与边界情况

- **LLM 失败**：重试 1 次后放弃本次规划，trace llm_failed；goal 留在无 plan 态（不是 failed——失败语义是 AUT-003 观察的产出，规划失败只意味着「暂无计划」）。
- **校验拒绝**：正常分支（status=rejected + reason 留痕）；同一 goal 被拒后再次触发规划仍消耗 attempt 计数（防「被拒-重触发」抖动绕过封顶），3 次耗尽后前置闸拒绝。
- **payload 世界事实过期**：job 执行时距入队可能跨多个周期——World 事实仅作规划参考约束（不作为判据数据源，判据在执行期由 AUT-003 重新采集），过期无害；trace 记录入队时刻。
- **供给候选与 v1 目标撞描述**：层级 goal 与 v1 goal 是不同行（layer/domain 分流），同描述并存合法（判定域不同）；幂等去重只在层级 goal 集合内生效。
- **job 重复投递**：幂等键拦截；即使重复执行，`version=max+1` 会产生两个版本——防御：handler 内先查同 goal 未终态 draft/validated 行存在则直接复用（同版本幂等，tasks.md Idempotency 口径）。
- **旧版本 plan 残留引用**：superseded 归档后 AUT-003 只认 max active version；查询接口 `list_active_plans` 单点收敛，无悬空消费。
- **Flag 热切换**：无——供给步骤与 job 注册随 lifespan；运行中切 Flag 需重启（P1~P5 同口径）。
- **配额降级窗口**：degraded → 供给 skip + 已入队 job 照常消费（规划是低频 main 档，1 次调用在日预算内；若熔断期间积压多 goal，handler 侧无配额再检查——登记：规划 job 不做二次熔断，日配额由 LIFE-003 全局口径覆盖，超出属可接受一次性成本，评审材料）。

## 测试要求

- Unit：三来源候选规则真值表（阈值边界/去重键）；校验闸双段（前置拒绝对话零 LLM 断言 + 结构闸逐条拒绝原因）；attempt 计数（第 4 次请求 trace reason=attempt_cap）；判据白名单（自由文本/未知 capability/超深/超数逐例拒绝）；版本幂等（同 goal 重复入队单版本）。
- Integration：①创建→规划→validated 入库全链（fake LLM 固定输出）；②rejected 路径留痕且无执行副作用；③Flag OFF 管线不变（goal_supply 步骤不存在，其余步骤逐字节）；④degraded → skip 记账。
- FailureInjection：LLM 解析失败×2 → 放弃 trace；LLM 返回超数/超深/未知能力 plan → rejected。
- Regression：V6 goal checklist + V7 autonomy checklist（规划不触碰触发/预算既有面）+ Flag OFF golden。

## 验收标准

- 给定规划产物，那么 100% 通过可执行性校验且判据可自动判定（入库行 100% validated；rejected 行均有 reason——E-AUT-01 前半）。
- 给定同一 goal 第 4 次规划请求，那么被拒绝并 trace（reason=attempt_cap，LLM 零调用——E-AUT-01 后半）。
- 给定规划 LLM 全部失败，那么重试 1 次后放弃、trace 可答「为什么没规划」，goal 不误入 failed。
- 给定 Flag OFF，那么周期管线与现状逐字节一致（goal_supply 不存在、无 job 注册）。
- 「为什么这么拆」对任一 validated plan 均可由 goal_planning trace（输入约束/原始提案/校验结果）回答。

## Implementation Constraints

- **红线**：AutonomyPolicy 纯函数与 Action/World 引擎本体零改动（继承 P5 红线口径）；规划产物不直接执行任何 Action（tasks.md Non-Scope）——本 Task 无 `run_action_planning` 调用点。
- **禁止前台**：规划 LLM 只能发生在 background job；supply 步骤 0 LLM。
- **域边界**：Goal 只写本域表（character_goals/goal_plans）+ background_jobs（MEM-009 公共底座）；World 事实必须由编排方投影进 payload（GAP-AUT-02 裁决），job 内禁止 world/action 查询；Development/Relationship/Memory 只读。
- 判据白名单常量与 `SubGoalSpec` 定义集中在 `app/models/goal.py`（AUT-001 已建位），校验闸与 AUT-003 观察共用同一套定义——禁止两处各写一份谓词逻辑。
- 预算硬顶全部 settings 化且前置闸先行（能在调 LLM 前拒绝的绝不调后拒绝）。
- 不实现观察/调整/失败计数（AUT-003）、仲裁与状态机扩展（AUT-004）——本 Task 的 goal 写面仅限「创建行」与「goal_plans 版本流转」。

## 冲突登记（评审决策材料）

### GAP-AUT-01：层级 goal 供给链缺失（主登记）

**问题**：tasks.md 五个 Task 中无人承接「层级 goal 由谁创建」——AUT-001 只做存储（创建 API 是存储层自然延伸），AUT-002 Runtime Flow 以「目标创建」为输入，AUT-004 以「目标集合变更」为输入；README §核心能力 1 定义了三类来源但无实现归属。
**分析**：这不是设计遗漏而是归并空间问题——创建与规划在同一条 Runtime Flow（创建后必须立即规划，分离到其他 Task 会制造跨 Task 事务边界）；AUT-002 是唯一以「目标」为输入产出的 Core Task。
**建议**（本 Detail 采用，不新增 Task、不改架构）：供给装配器并入 AUT-002，作为 Runtime Flow 第一环实体化；纯规则模板产出描述（0 LLM），创建走 AUT-001 唯一入口。备选方案（若评审不采纳）：创建接线归 AUT-004 的「目标集合变更」入口——代价是 AUT-004 承担非仲裁职责且 M2 前无法端到端联调。**风险声明**：若两者皆不采纳，P6 验收剧情只能测试侧直建 goal，生产路径层级 goal 永不产生，Phase 6 完成标准第 1 条（跨 3+ 会话剧情）在生产配置下不可达。

### GAP-AUT-02：World 事实进规划输入的依赖矩阵冲突

**问题**：tasks.md AUT-002 Inputs 含「World/Development 约束」，但 domain-boundaries §3 矩阵 Goal→World ✗（Goal→Action 同）。
**裁决**：World 约束以**编排投影**进输入——Life Loop 周期步骤（编排域，可调用一切）在入队前采集 `world_engine.collect_facts` 塞入 job payload；规划 job 内零 World 查询。这与 LIFE-002 的 perception→decision 传参模式同构，不修改矩阵。AUT-003 的观察输入沿用同一裁决（其 Detail 引用本条）。

### 裁决登记：plan 状态机补充

tasks.md AUT-002 状态机 `draft→validated→active|rejected` 覆盖单版本生命周期；重规划新版本 active 时旧 active 版本需归档——引入 `superseded` 作为归档迁移（仅由「新版本激活」触发，可从 active 迁出）。属状态机补充而非变更，登记备评审。
