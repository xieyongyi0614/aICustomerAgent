# DEV-006 Task Detail — 成长闭环验证

> 上游：[../tasks.md](../tasks.md) DEV-006 ｜ [evaluation.md](../evaluation.md) E-DEV-04 ｜ [../../dependency-graph.md](../../../dependency-graph.md) §4 数据流 ｜ [../../architecture/character-runtime.md](../../../architecture/character-runtime.md) §3 ｜ 依赖：DEV-003, P2 REF-006, P1 MEM-010

## Task 目标

**验证性 Task（不新增代码能力，产出为场景集与报告）**：证明 §十完整闭环成立——Insight→调制→重复行为→新经历→再反思→调制演进。即角色真的在成长，而非「每次请求动态改参数」；校验 P1+P2+P3 全链归因完整，且任一环节 Flag 中断时闭环在该环节停止、无越级影响。

## 背景 / 为什么需要

tasks.md Problem 原文：调制若不反馈为新经历，Development 就退化成「每次请求动态修改参数」（任务书 §十明令防止）。该风险只有跨 Phase 才能暴露：DEV-003 的单轮接线测试无法证明「调制结果改变对话行为 → 行为经 P1 Ingest 变 Candidate → 新证据进 REF-002 窗口 → 第二次反思强化/修正 Insight → 调制演进」这条链真实闭合。dependency-graph §4 指明闭环落点 `BP → 新对话 → C`——Dev 不自证，必须以长周期离线模拟显式验证。

## 设计方案

1. **三周期剧情模拟**（全部走既有链路，离线确定性 stub——ScriptedLLM 按 REF-006 tests 模式注入，不做 monkeypatch）：
   - 周期 1：注入「连续加班」压力类证据（多源 Candidate：对话/WorldEvent）→ MEM-003 转正 → REF-002 聚窗 → REF-004 产出 `pattern` 类 Insight（如「用户近期持续高压」）→ DEV-002 编译 → `goal.user_care.weight`/care_topics 调制生效（`development_compile` trace）。
   - 周期 2：角色行为因调制而变化（care 提示行入 prompt、user_care 目标提升——以 prompt 快照与 goal_selection trace 断言）→ 这些「新对话」经 P1 摄取为 Candidate 并转正 → 成为新证据。
   - 周期 3：新证据进证据窗 → 第二次反思产出**强化或修正**的 Insight（strength/confidence 变化）→ 重编译 → 调制演进（幅度变化在 changes 时间序可见）。
2. **归因链审计**（复用 DEV-005 归因检查器）：对每个周期断言 `memory→evidence_links→insight→development_changes→development_apply（prompt 快照）` 五环齐备且 id 链连续；调制幅度变化必须可归因到「新证据 → 新 Insight」而非无中生有（E-DEV-04 闭环归因完整率）。
3. **Flag 中断矩阵**：全链 Flag ON 执行主线；变体场景分别关闭 `v2_memory_enabled` / `v2_reflection_enabled` / `v2_development_enabled` 之一，断言闭环在对应环节停止且下游零变化（无越级影响——如 Development OFF 时即使 Insight 产出也不得有任何调制/行为参数变化）。
4. **负向演进变体**：周期 3 前注入用户反驳（「其实我最近不累了」）→ REF-005 失效 → DEV-004 回退 → 调制回到基线 → 后续对话不再体现该调制（闭环可逆性）。
5. **报告**：`compute_metrics` 扩 E-DEV-04 = 「闭环归因完整率 + 各 Flag 变体停止正确性」，门槛「闭环成立且无越级影响」（布尔 + 归因率 1.0）；报告落 `tests/eval/reports/`，长期场景集入 offline_evaluator 可重复执行。

## 数据模型 / 接口变化

- 无。新增物 = 场景集（tests/eval）+ 场景 runner（development/evaluation.py 内）+ 报告文件。

## 核心处理流程

```text
剧情注入（周期 1 证据）→ 多周期模拟（P1 摄取 → P2 反思 → P3 编译调制 → 行为变化 → 新对话）
  → 每周期归因链审计（五环 id 链）
  → Flag 中断矩阵变体（三开关逐一关闭）
  → 负向演进变体（反驳→回退）
  → E-DEV-04 报告
```

## 模块关系

- 横切质量平面：只读调用 P1/P2/P3 服务；是 REF-006（反思质量）与 DEV-005（Development 一致性）两个场景框架的串联验收，不新增域能力。
- 报告是 Phase 3 Milestone M4 的最后一项验收输入（Eval Gate 汇总后申请开启 `v2_development_enabled`）。

## 异常与边界情况

- 场景失败 → 按环节归因（memory/reflection/dev）输出定位报告，而非笼统 fail（tasks.md Error/Failure 口径）。
- 剧情模拟成本 → 离线批量 + 确定性 stub + 采样 Judge（零真实 LLM 依赖，可重复执行；真实模型验证属 regression-checklist 人工环节）。
- 第二次反思可能产出与第一次同 statement 的强化 Insight（REF-004 supersede 通道替代旧行）或同主题新结论——两种合法演进形态在报告中分别记数。
- 周期内 Insight 未达反思门槛 → 场景设计保证门槛满足（Evidence 组 ≥3 条/跨度合规），否则报告标记 `gate_blocked` 并定位。

## 测试要求

- 即测试本身：场景集确定性（同输入同报告）；三周期归因链逐环断言；Flag 中断矩阵 4 组合；负向演进变体。
- 回归：全程在 Flag ON 影子环境执行，不污染在线数据（独立 session_factory）；P1/P2 既有 Eval Gate 复跑不回退。

## 验收标准

- 给定「连续加班」剧情，当三周期模拟，那么第二次反思产出强化/修正的 Insight 且调制幅度变化可归因到新证据。
- 给定中断任一环节 Flag，那么闭环在该环节停止且无越级影响。
- 给定全链归因审计，那么五环 id 链完整率 100%（E-DEV-04）。

## Implementation Constraints

- 不新增代码能力（验证性 Task）；不修改 P1/P2/P3 任何业务模块；全程 Flag ON 影子环境；不涉及 Phase 4~6 消费方（Relationship Patterns 接入属 REL-003，Goal 层级化属 P6——本 Task 的 goal 调制仅限 DEV-002 已定义的 `goal.user_care.weight` 槽位）。
