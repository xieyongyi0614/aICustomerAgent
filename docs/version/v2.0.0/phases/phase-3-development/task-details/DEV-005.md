## 设计方案

1. **trace payload 规范**（测试断言锁定，模式同 test_ref006）：
   - `development_state`（DEV-001）：`key/kind/op(write|arbitrate|retire)/strength/source_insight_id/status`。
   - `development_compile`（DEV-002）：`insight_id/type/rules_hit/proposals(key+value+strength)/arbitration(win|lose|no_op)/reason(no_rule|skip_inactive)`。
   - `development_apply`（DEV-003）：逐 key `key/before/after/source_insight_id`（读侧叠加前后值）。
   - `development_rollback`（DEV-004）：`insight_id/affected_keys/rollback_target/replay_rounds`。
2. **归因端点**（`development/attribution.py`）：`development_state_attribution(state_id)` 返回 state 行 + 全部 changes（时间序）+ `source_insight_id` → `insight_attribution`（REF-006 端点）嵌套引用，构成 memory→evidence→insight→changes→apply 完整链；changes.insight_id 悬空（理论不可能，insights 审计不删）标 `insight_purged` 不中断。
3. **development 规则集**（4 规则，全部纯函数、逐条异常隔离、slice 缺席跳过）：
   - `DEVELOPMENT_CHANGE_UNATTRIBUTED`（CRITICAL）：changes 行 insight_id 缺失或悬空 → E-DEV-01 归因完整率兜底闸。
   - `DEVELOPMENT_CONCURRENT_ACTIVE`（CRITICAL）：同 (user,key) 两条 active → E-DEV-03 并存生效闸。
   - `DEVELOPMENT_OVER_CAP`（WARNING）：调制幅度 > strength × 预设封顶（按 value 与 settings 复算） → E-DEV-02 封顶闸。
   - `DEVELOPMENT_STALE_ACTIVE`（WARNING）：active state 行的 source insight 已 superseded/invalidated → 回退滞后检测（DEV-004 死信时的可视化信号）。
4. **离线场景集**（`development/evaluation.py`，注入式 runner：session_factory + ScriptedLLM 由 tests/eval 运行器注入，离线零真实 LLM）：
   - `compile_idempotent`（E-DEV-01）：同 Insight 重编译逐字节一致 + changes 100% 可溯。
   - `cap_saturation`（E-DEV-02）：10 条强化 Insight → 幅度仍封顶 + before/after trace 可见；Judge 抽样（复用 `evaluation_judge_chain`，threshold 0.9，失败记 skipped 重跑）。
   - `contradiction_arbitration`（E-DEV-03）：矛盾对只一个 active。
   - `rebuttal_rollback`（E-DEV-03）：反驳 → 回退基线 + verify_replay 与在线一致。
   - `compute_metrics` 输出 GATE_THRESHOLDS（全部 1.0）对照的 E-DEV-01~03 报告。
5. **build_db_report**：states/changes 计数、归因率、并存 active 数、stale 数；Flag OFF 返回空 dict；挂入 offline_evaluator `development` 小节。

## 数据模型 / 接口变化

- 无业务表变化；`IssueCode` +4、`DEFAULT_SEVERITY` +4、`EvaluationContext` +`development` 可选切片、debug API +2 端点、RULES 汇编 +1 模块。
- 只读旁路：规则/归因/报告不写任何业务状态（V7.5 铁律）。

## 核心处理流程

```text
在线：各 DEV 环节事件 → trace 步骤（payload 规范）→ 规则阶段读 DevelopmentSlice → issue
离线：场景注入 → 交互模拟（确定性 stub）→ compute_metrics → E-DEV-01~03 报告
      + offline_evaluator development 小节（build_db_report 只读统计）
```

## 模块关系

- 横切质量平面：只读 Development/Reflection/Memory 产物；与 V7.5 引擎、V7.8 trace 体系、REF-006 同构不互依。
- 是 DEV-006 闭环验证的方法论底座（E-DEV-04 复用本 Task 的场景 runner 与归因链检查器）。

## 异常与边界情况

- Judge 失败/超时 → 该场景记 skipped，可重跑（E-DEV-02-JUDGE 不阻塞其余指标）。
- 规则单条异常 → 隔离为该条失败，不拖垮整轮评估（evaluation_rules 既有行为）。
- Flag OFF → DevelopmentSlice=None、规则全跳过、build_db_report 空——评估面不产生任何假阳性。
- trace 写失败 → 沿 `TurnTraceSession.record` 既有吞异常语义（不阻塞业务）。

## 测试要求

- Unit：4 规则表驱动（命中/跳过/边界值——封顶复算、悬空 id）；payload 序列化。
- Integration：端到端 trace 完整性（compile→apply→rollback 步骤齐且字段全）；debug 端点 200/404/悬空分支；offline_evaluator development 小节挂载。
- 评估自证：E-DEV-01~03 场景集全过（Gate 报告为证）；Flag OFF 全场景空跑。
- 回归：V7.5 checklist（evaluation 扩展项）；`ISSUE_CODE_COUNT` 收口。

## 验收标准

- 给定全部 development_changes，当评估，那么 100% 可追溯 insight_id。
- 给定矛盾场景集，当离线评估，那么无并存生效（E-DEV-03=1.0）。
- 给定任一 active 调制，当查询 debug API，那么可回溯 state→changes→insight→evidence 完整链。

## Implementation Constraints

- 只读旁路；不新建存储（runtime_traces/evaluation_reports 复用）；规则集注册表式扩展不线性堆积（evaluation.md 裁决）；不提前实现 E-DEV-04（DEV-006）。
