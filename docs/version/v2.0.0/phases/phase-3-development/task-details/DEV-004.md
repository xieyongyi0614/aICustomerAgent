# DEV-004 Task Detail — 回退与重放

> 上游：[../tasks.md](../tasks.md) DEV-004 ｜ [../architecture.md](../architecture.md) §3 规则要点 ｜ [data-flow.md](../../../architecture/data-flow.md) §2.3 ｜ 依赖：DEV-002, P2 REF-005

## Task 目标

Insight 失效后调制**自动回退**（被反驳的认知不得永久影响行为）；全量调制历史**可重放**（删 changes 后按 Insight 时间序重编译，重放=在线）。补齐任务书 §十七「矛盾处理」在 Development 侧的闭环：REF-005 让 Insight 终止，本 Task 让它的行为后果同步终止且全程可审计。

## 背景 / 为什么需要

REF-005 交付时预留了订阅点：`reflection/lifecycle.py` L210 `register_invalidation_listener`，`invalidate_insight`/`supersede_insight`/`_persist` supersede 半边迁移成功后才广播（参数：user_id + 变更摘要列表 `[{insight_id, status, invalidated_reason|superseded_by}]`）。P2 无消费方零行为。若 Development 不订阅：用户反驳「其实我最近不累」后，`user持续工作压力` 派生的行为调制仍生效——不可反驳的认知永久污染行为（R6 回收通道在行为侧断链）。同时 E-DEV-03 要求「重放工具输出与在线一致」，审计不可验证则灰度期无法自证。

## 设计方案

1. **订阅与回退触发**：`main.py` lifespan（`v2_development_enabled` 门控）注册监听器 → 回调内对每个 changed 条目 enqueue `development_rollback` job（payload={insight_id, status}）。回调内不执行重算（监听器异常被 REF-005 尽力而为吞掉——重算必须走 job 的重试通道才能满足「不静默丢失」）。
2. **按 key 回退**（`audit.py` `rollback_for_insight(user_id, insight_id, status)`）：
   - 定位受影响 key：`development_state` 中 `source_insight_id == insight_id` 且 status=active 的行（superseded 事件同样处理——双保险，见幂等）。
   - 对每个 key：**重放该 key 的调制历史**——取该用户全部 active Insight 按 `created_at` 时间序逐条 `compile_insight`（DEV-002 纯函数），筛选产出该 key 提案者，重跑仲裁 → 得到「次优胜者」或「无调制」。
   - 有继任者 → `upsert_modulation`（新 active + 旧行 superseded + changes `reason=rolled_back`、`insight_id`=触发失效的 id——E-DEV-01 归因不变）；无继任者 → `retire_modulation`（active→retired，changes after=NULL）。
   - superseded 事件的常规路径是 DEV-002 创建事件先仲裁出胜者（本 Task 无操作）；失效事件与编译事件竞态时以本重放结果为准（重新收敛，结果一致）。
3. **幂等**：重复事件 → 重放结果与当前态一致 → 条件 UPDATE no-op、不产生新 changes 行（「重复事件不重复回退」）；幂等键 `dev_rollback:{insight_id}:{status}` 拦截重复入队。
4. **重放工具**（`audit.py` `verify_replay(user_id) -> report` / 脚本 `scripts/replay_development.py`）：单事务内「删（逻辑上清空）该用户 changes 后按 Insight 时间序全量重编译」→ 重建 state+changes → 与在线态比对（state 逐 key、changes 归因率）→ **事务回滚**（默认校验模式：原始审计行零改动，输出比对报告；tasks.md Non-Scope「重放不改原始审计行」）。`--rebuild` 显式模式才 commit 重建（运维决策入口，仅用于审计行损坏修复）。此口径调和 data-flow §2.3「重放=删 changes 后重编译」与 Non-Scope 的表面张力（见 README 核对记录 7）。
5. **Failure**：回放异常 → job 退避重试，达上限死信 failed+last_error+告警日志；**当前态保留不静默清空**（tasks.md Error/Failure 原文口径）。

## 核心处理流程

```text
REF-005 迁移成功 → notify_invalidation_listeners（invalidated|superseded）
  → 编排层监听器 enqueue dev_rollback:{insight_id}:{status}
  → job worker 认领 → rollback_for_insight：
      定位受影响 key → 该 key 调制历史按 Insight 时间序重放 → 仲裁
      → [有次优 → upsert(rolled_back) | 无 → retire]
      → development_rollback trace（受影响 key/回退目标/重放轮数）
重放工具（离线）：单事务重编译 → 比对在线态 → 回滚事务出报告（--rebuild 才落库）
```

## 模块关系

- Development → Reflection：只读 insights + 事件订阅（编排层注册，依赖单向）。
- Development 域内：audit.py 复用 policy.py 纯函数与 aggregate.py 写服务，不复制仲裁逻辑（回退=重放=同一套编译+仲裁代码，这是「重放=在线」的结构保障）。
- 行为域：零接触（回退后的参数变化经 DEV-003 的读取在下一轮自然生效，无需行为域感知）。

## 异常与边界情况

- 失效 Insight 从未产生调制（编译空提案/规则未命中）→ 定位 0 key，job done（trace `no_affected_keys`）。
- 受影响 key 的次优胜者随后也被失效 → 各事件独立回退 job，最终态收敛一致（重放确定性保证）。
- 重放期间新 Insight 并发编译同 key → per-user 写锁串行化，两者都基于「active Insight 集合」收敛到同一结果。
- 监听器回调在 post_process 同步上下文内执行 → 只 enqueue（毫秒级），不做 DB 重算，不阻塞记忆评估步骤。
- `--rebuild` 模式与在线服务并发 → 文档声明仅停写窗口执行（运维约束，写入脚本 argparse help）。

## 测试要求

- Unit：rollback_for_insight（有次优/无次优/无受影响 key）；重放幂等（重复事件行数不变）；仲裁收敛（回退后再编译结果一致）。
- Integration：端到端「反驳→回退」——注入压力类记忆 → 反思产出 Insight（ScriptedLLM）→ 编译生效 → `observe_negation` 失效 → 回退 job → `read_overlay` 下一轮为 None/次优 + `development_rollback` trace + changes 可溯；重放工具报告与在线态 100% 一致、原始审计行零改动。
- FailureInjection：回放中途 DB 断连 → job 重试后收敛；死信路径 last_error 完整。
- 回归：Flag OFF 时监听器不注册、P1/P2 测试全绿。

## 验收标准

- 给定用户反驳 Insight，当失效事件到达，那么行为参数回到失效前基线（或次优调制）且 `read_overlay` 下一轮不再包含被反驳认知的贡献。
- 给定重放工具，当执行校验，那么输出与在线一致（state 逐 key 相等、changes 归因率 100%）且原始审计行未变。
- 给定同一失效事件重复投递，那么回退不重复执行（changes 计数不变）。

## Implementation Constraints

- 重放不改原始审计行（默认校验模式事务回滚；`--rebuild` 仅运维显式触发）；不产生新 Insight；只写本域两表；0 LLM；不直接改 Memory/Reflection（只消费其事件与只读行）。
