# DEV-001 Task Detail — Development Aggregate 存储

> 上游：[../tasks.md](../tasks.md) DEV-001 ｜ [../architecture.md](../architecture.md) §1 ｜ 依赖：无（可并行；schema 风格对齐 REF-001 评审）

## Task 目标

建立 Development 域持久化基座：`development_state` / `development_changes` 两张新表（Alembic 0026，up/down 完整）、`core/db.py` ORM、`app/models/development.py` 域模型、`services/development/aggregate.py` 读写服务（状态机 + 单事务写 + 审计）。本 Task 不接任何消费方、不做编译——完成后 P3 其余 Task 才有落笔处。

## 背景 / 为什么需要

Belief/Preference/Pattern 是角色「因经历而变」的唯一载体。v1~P2 交付面上没有任何「认知→长期演化」存储：`insights`（0025，REF-001）只承载反思产物，`memories` 只承载经历；无独立存储则 Development 与 Memory/Reflection 混为一谈，违反任务书 §十七「三个系统不得混为一谈」红线。Domain 分类（[domain-boundaries.md](../../../architecture/domain-boundaries.md) §1）裁决 Development 为独立 Domain：真相源 = `development_state` + `development_changes`，慢变量、全审计、变更必须可重放。

## 设计方案

1. **0026 迁移**（字段以 [../architecture.md](../architecture.md) §1 为准，补全隔离/审计列，模式同 REF-001 Detail 的「补全不改语义」处理）：
   - `development_state`：`id`（`dev:{uuid4().hex}`）、`user_id`、`character_id`（server_default="asuna"）、`kind`（CHECK ∈ belief|preference|pattern）、`key`（调制槽位名，如 `response_style.length`；命名空间约定见 DEV-002 Detail §key 设计）、`value`（JSON，调制参数载荷）、`strength`（Float 0~1，CHECK 0≤strength≤1）、`source_insight_id`（String，无外键——insights 为审计表永不物理删除，无悬空风险）、`status`（CHECK ∈ active|superseded|retired，server_default="active"）、`created_at`、`updated_at`。
   - `development_changes`：`id`（`devc:{uuid4().hex}`）、`development_state_id`、`before`（JSON，可 NULL=新建）、`after`（JSON，可 NULL=撤除）、`insight_id`（String NOT NULL——E-DEV-01「100% 可溯 insight_id」的存储侧保障；DEV-004 回退行填触发失效的 insight_id）、`reason`（Text：compiled|arbitrated|rolled_back|replayed）、`created_at`。
   - 索引：`idx_development_state_user_status(user_id, status)`、`idx_development_state_user_kind(user_id, kind, status)`、`idx_development_changes_state(development_state_id)`、`idx_development_changes_insight(insight_id)`。
   - **active 唯一性**：同一 `(user_id, key)` 至多一条 active——服务层在 per-user 写锁（`post_process.get_user_write_lock` 同款协议）内以条件 UPDATE 保证；另建部分唯一索引 `uq_development_state_active_key ON (user_id, key) WHERE status='active'`（PG 生产 + SQLite≥3.8 测试均支持）兜底。此项在实施前评审确认（见 README 核对记录 5）。
   - downgrade：先删索引再删两表；v1/P1/P2 表零触碰。
2. **`app/models/development.py`**：`DevelopmentStatus`/`DevelopmentKind` Literal 与 StrEnum、`DevelopmentState`/`DevelopmentChange` BaseModel、`ModulationTarget` Literal（response_style|behavior|goal|autonomy——key 命名空间的类型化表达）。`retired` 语义：该 key 的调制被撤除且无继任者（源 Insight 失效无次优）；`superseded` 语义：同 key 出现新的 active 行，旧行留痕。两者均终态、不复活（非法转换拒绝）。
3. **`services/development/aggregate.py`**（对齐 REF-001 lifecycle 风格，模块 docstring 写明状态机与幂等口径）：
   - `transition(status, event)`：合法事件 `arbitrate`（active→superseded，同 key 新王登基）、`retire`（active→retired，撤除无继任）、`write`（无状态行→active 新建）。superseded/retired 收到任何事件拒绝。
   - `upsert_modulation(user_id, kind, key, value, strength, source_insight_id, trace)`：单事务「读同 key active → 仲裁（比较器入参注入，比较器本体属 DEV-002 策略；本 Task 默认 strength 降序、created_at 破平）→ 新建 active + 旧行 superseded + changes 行（before=旧 value，after=新 value，insight_id）→ commit」。旧王落败即写 changes 留痕。
   - `retire_modulation(user_id, key, insight_id, reason, trace)`：单事务 active→retired + changes（after=NULL）。
   - `list_active_modulations(user_id) -> list[DevelopmentState]`：active 只读查询（key ASC），DEV-003 叠加层读取入口。
   - `get_state_history(development_state_id) -> list[DevelopmentChange]`：changes 按时间序（DEV-004 重放与归因复用）。
   - 全部写路径 trace 步骤名 `development_state`（写入 TRACE_STEP_NAMES 属 DEV-005；本 Task trace 参数按 None 安全缺省，写法对齐 `reflection/lifecycle._trace`）。

## 核心处理流程

`alembic upgrade head`（0026）→ ORM/模型/服务可用 → `v2_development_enabled` 存在且 default=false → v1/P1/P2 全部服务与测试无感知（无任何 import 交叉）。

## 模块关系

- 被 DEV-002（编译写入方）、DEV-004（回退/重放写入方）、DEV-003（`list_active_modulations` 读取方）依赖；本 Task 不感知任何上游/下游。
- 与 `reflection/lifecycle.py` 同构但不 import（复刻 REF-001 的裁决：Reflection 不 import memory2，Development 亦不 import reflection）。

## 异常与边界情况

- 迁移在无 pgvector 之外的老 Postgres 上：本表无向量依赖，无特殊处理；SQLite 兜底库直跑（JSON 列 SQLite 方言兼容，0022/0025 已验证该路径）。
- `value` JSON 载荷本 Task 不做 schema 校验（编译器 DEV-002 产出即合法；校验属编译器测试面）。
- 同 key 并发仲裁：服务层条件 UPDATE + 部分唯一索引双保险；索引冲突时事务回滚并抛出，调用方重试（本 Task 内无并发调用方，协议供 DEV-002 使用）。
- downgrade 前存在数据：直接 drop（v2 灰度前表恒空；灰度后 downgrade 属运维决策，不在本 Task 范围）。

## 测试要求

- Unit：状态机全路径（write/arbitrate/retire + 三种非法转换拒绝）；upsert 仲裁比较器（胜/负/破平）；changes 行 before/after/insight_id 完整性；终态不复活。
- Integration：0026 up→down→up 往返逐表逐列断言；`(user_id,key)` active 唯一（并发 upsert 双写只有一胜）；downgrade 对 v1/P1/P2 表零影响。
- 回归：v1 全量 pytest 零差异（新表对既有代码不可见）。

## 验收标准

- 给定任何变更，当 `upsert_modulation`/`retire_modulation` 写入，那么 changes 行含 before/after 且 insight_id 可定位到 insights 行。
- 给定 downgrade，那么两表删除、v1/P1/P2 零影响、全量测试通过。
- 给定 settings，当加载，那么 `v2_development_enabled` 存在且 default=false。

## Implementation Constraints

- 纯 DDL + 存储服务；不做编译（DEV-002）、不接消费方（DEV-003）、不写 trace 步骤名进 TRACE_STEP_NAMES（DEV-005）。
- 不 import memory2/reflection/行为域任何模块；`kind` 沿用 insights 的枚举字面量，不做跨域校验查询。
- 不添加代码注释；命名表达意图（AGENTS.md 全局约定）；docstring 仅写在模块头（沿 0025/lifecycle 惯例）。
