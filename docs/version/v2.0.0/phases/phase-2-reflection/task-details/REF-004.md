# REF-004 Task Detail — 反思执行器（Core / Reflector）

> 上游：[../tasks.md](../tasks.md) REF-004 ｜ [../architecture.md](../architecture.md) §3 ｜ [../../../architecture/risk.md](../../../architecture/risk.md) R6 ｜ 依赖：REF-002, REF-003

## Task 目标

实现 `reflection/reflector.py`：消费 queued 反思任务，取证据组 → LLM 结构化推理（Reasoning Engine 调用点）→ confidence 代码校准（LLM 自报值不采用）→ 三闸复检 → 单事务写 `insights + evidence_links + reflection_runs`。核心裁决：**LLM 只产候选，代码决定终值**——把「结论生成」与「入库判定」彻底分离（任务书 §二十红线：防 AI 自嗨）。

## 背景 / 为什么需要

LLM 从零星证据跳到强结论、直写真相 = 幻觉 Insight 永久污染行为（risk.md R6）。防线不是「相信 LLM 的自我评估」，而是结构性隔离：LLM 输出只是**提案**（statement + 引用 + 自报置信度），入库的每一项——confidence 终值、引用完整性、类型与范围——全部由代码按证据强度折算与复检；不合规提案丢弃并留痕。这是 P2 全部 Eval Gate（E-REF-01/02）的技术承载。

## 设计方案

1. **认领与幂等**：
   - `run_queued_reflections(now, trace)`：扫描 `reflection_runs.status='queued'`，逐条认领——条件 UPDATE `status: queued→running`（WHERE status='queued'），影响行数 1 才执行；执行完回写 done/failed。单进程下天然防并发重复。
   - 同 run 重复执行不产第二条 insight：`insights.run_id` 判重（执行前查该 run_id 是否已产 Insight，已产则直接标 done）。
   - 与 `background_jobs` 的关系：run 行是操作状态机（queued→running→done|failed），job 行是持久化意图（幂等键 + 日桶额度审计）。执行函数 `execute_run(run_id)` 不感知 job；MEM-009 已交付（c39cb6e），消费侧以 `register_job_type("reflection_run", handler)` 注册进 job_worker（协议兼容，见冲突记录第 1 条）。
2. **取证据组**：按 run 的 user_id/character_id 调 REF-002 重新聚合（同数据同分组），取通过门槛的窗口；入队到执行之间证据可能变化（记忆被 forget/supersede）→ 重聚合后窗口不合格 → run 记 `done`、outcome=`evidence_gone`、0 Insight、0 LLM（先于 LLM 拦截）。
3. **Prompt 结构**（architecture §3，`app/prompts/reflection.py`）：
   - 输入：窗口成员（每条含 content 截断至 `v2_reflection_evidence_content_chars`、created_at、source、weight；成员按 weight 降序取 top `v2_reflection_evidence_max_members`，超限截断——architecture §5 token 上限）+ 类型约束说明（belief/preference/pattern 定义与「结论不得超出证据可支撑范围」）+ scope 选项 + **反例字段强制**（每条候选必须填 counter_evidence：「证据不支持什么」，无反例写「无」，缺字段即不合规）。
   - 输出 schema `ReflectionProposal`：`insights: list[InsightDraft(statement, type, scope, evidence_ids: list[str], counter_evidence: str, self_confidence: float)]`。
4. **confidence 代码校准**（LLM 的 self_confidence 仅记入 trace 作对照，不参与终值）：
   ```text
   final = clamp(coherence × count_factor(distinct_source_refs), 0, 0.95)
   count_factor: 3→0.65, 4→0.75, 5→0.85, ≥6→0.95   （settings JSON 曲线，可校准）
   若成员含 source=ai_inferred → final = min(final, v2_reflection_ai_inferred_cap)
   ```
   - 单调性保证：成员数与 coherence 越高 → final 越高或不降（tasks.md 验收「confidence 与证据强度单调一致」的测试锚点）。
5. **三闸复检（代码，逐条 draft）**——任一不过即丢弃该 draft + trace 拒绝原因：
   - 引用完整性：`evidence_ids` 非空、每条都在**本次实际提供给 LLM 的成员集合**内（防幻觉引用/防篡改证据——FailureInjection 验收点）、数量 ≥ `v2_reflection_min_evidence`；
   - 形态合规：statement 非空且 ≤ 长度上限、`counter_evidence` 字段存在、`type/scope` 合法枚举；
   - 置信门槛：`final >= v2_reflection_min_confidence`（默认 0.6），否则丢弃（低置信不入库，architecture §2 V 闸）。
6. **LLM 调用纪律**（tasks.md LLM Usage 行逐条落地）：main 档（`v2_reflection_llm_profile` 空 → default profile）；≤1 次成功调用/任务；解析失败重试 **1** 次；重试仍失败 → run 记 `failed`（error=llm_failed）不产 Insight，**不产 Insight 即不写 insights/evidence_links**；禁止任何前台路径调用本模块。
7. **落库（单事务，data-flow §2.3）**：一个事务内完成——INSERT insights（按 final 降序取 top `v2_reflection_max_insights_per_run` 条）、INSERT evidence_links（weight=成员 weight）、更新旧行：与任一新 Insight 同 scope+type 且 `same_topic(statement)` 的旧 active Insight 调 `lifecycle.supersede_insight(old, new)`（同事务执行，supersede 半边的调用点在 REF-004，服务与阈值归 REF-005）、UPDATE reflection_runs（status=done，outcome，insight_ids，evidence_summary 摘要）。DB 异常整体回滚（run 保持 running→由重试路径回收为 failed）。
8. **trace**（设计裁决）：有 trace 上下文（单元/集成测试、未来调用方传入）时记录 `reflection_run` 步骤（证据引用/原始输出摘要/折算过程/拒绝原因）；后台执行无 turn trace session → 明细落 `reflection_runs` 行（evidence_summary/outcome/insight_ids/error）+ `llm_call_records`（structured chain 自动记账）。任一 Insight 的完整回溯链 = run 行 + evidence_links → memories 原文，不依赖 runtime_traces（REF-006 验收按此口径）。

## 核心处理流程

```text
run_queued_reflections: 扫 queued → 条件 UPDATE 认领(running) → execute_run
execute_run: 重聚合证据组 → [无合格窗口 → done(evidence_gone), 0 LLM]
 → build_reflection_messages → build_structured_chain(main 档) → 解析
 → [失败 → 重试 1 次 → 仍失败 → failed(llm_failed), 不产 Insight]
 → 逐 draft: confidence 代码校准 → 三闸复检 → [通过 | 丢弃+原因]
 → 单事务: INSERT insights+evidence_links ∥ supersede 冲突旧 Insight ∥ UPDATE runs(done)
```

## 模块关系

- 只写本域三表（REF-001 提供的行级 API + 直接 ORM 写入）；**对 memories 零写入**（认知与记忆分层，README 明确禁止反思写 Memory，防自我强化）。
- 调用：REF-002（聚合）、`chains/structured.py`、`llm_factory`；由 job_worker 注册的 reflection handler 驱动（REF-003 注册）；supersede 服务（REF-005 语义）在本模块事务内被调用。
- 不接 Development/Goal/Context 消费方（REF-007 才做 Context 注入；P3 才做行为调制）。

## 异常与边界情况

- LLM 超时/异常 → 重试 1 次 → 仍失败 run=failed（不占当日额度判定中的「占额」状态，可被次日周期重新覆盖主题）。
- 输出不合规（缺反例/引用越界/超范围断言形态）→ 该 draft 丢弃 + trace；全部 draft 被拒 → done(outcome=rejected)，0 Insight 入库（run 完成≠必须产 Insight）。
- 证据组在等待期被清空（记忆 forget/supersede）→ done(evidence_gone)，0 LLM。
- LLM 幻觉注入（引用组外 memory_id / 伪造 id）→ 引用完整性复检拒绝（tasks.md FailureInjection 验收：被篡改证据必须降级或拒绝）。
- 单事务中途 DB 失败 → 回滚，run 停留 running → `run_queued_reflections` 对 running 超时（`v2_reflection_run_timeout_minutes`，默认 10）的行回收重置为 queued 重跑（幂等由 run_id 判重保证安全）。
- Flag OFF → `run_queued_reflections` 直接返回 0（任务不执行，tasks.md）。

## 测试要求

- Unit：confidence 折算表驱动（count_factor 曲线/ai_inferred cap/单调性：强证据组 ≥ 弱证据组）；三闸复检逐闸表驱动；认领条件 UPDATE 幂等。
- Integration：「5 次说累」场景端到端 → 1 条 Insight 且 100% 带 ≥3 条 evidence_links、confidence 落在折算区间（Prompt 回归集首条）；反例护栏（证据中混入反例记忆 → 结论降级或拒绝，evaluation.md P2 场景）。
- FailureInjection：幻觉注入（draft 引用组外 id → 拒绝）；LLM 500/超时 → 重试 1 次后 failed；DB 事务回滚后 run 可被回收重跑且无重复 Insight。
- LLM 用量断言：单 run 成功路径 llm_call_records 恰 1 条。

## 验收标准

- 给定合规证据组，当反思，那么产出 100% 带 ≥门槛数证据引用且 confidence 与证据强度单调一致（tasks.md 原文）。
- 给定被篡改证据（引用越界/伪造），那么该结论被拒绝或降级，不入库。
- 给定同一 run 重复执行两次，那么 insights 中该 run_id 仅一批行（幂等）。
- 给定 LLM 连续两次失败，那么 run=failed、无任何 insights 行、llm_call_records 记 2 次调用。

## Implementation Constraints

- LLM 无权决定 confidence 终值（自报值仅 trace 对照）；不写 Memory/State/Relationship/Development；不修改证据（evidence_links 只引用不改 memories）。
- ≤1 次成功调用/任务、重试 1 次、失败不产 Insight、禁止前台；Evidence 组 token 上限（top 显著度成员 + 内容截断）。
- 单事务写三表（data-flow §2.3）；supersede 只发生在同事务内对旧 active Insight 的转换，不做跨事务异步补偿。
- 不提前设计 P3 Development 编译逻辑；产出条数/长度上限全部 settings 化。
