## Task 目标

让「为什么形成这个 Reflection」可答、反思质量可测：统一 `reflection_*` trace 步骤 payload 规范；debug API 新增 Insight 归因查询；Evaluation 新增 reflection 规则集与 Judge 维度；离线误报率场景集（E-REF-01~04）落地。只读旁路，不新建存储。

## 设计方案

1. **payload 规范（MEM-008 schema 的 Reflection 扩展）**：`{step, user_id, run_id?, insight_id?, memory_id?, trigger?, decision?, reason?, stats?, llm_used?, ts}`——五步骤各自的必填字段：
   - `reflection_evidence`：stats（池/簇/门槛明细）、decision（组级 pass/skip）、reason；
   - `reflection_trigger`：trigger、decision（queued/skipped/quota）、reason；
   - `reflection_run`：run_id、decision（done/failed/evidence_gone/rejected）、llm_used、confidence 折算摘要；
   - `reflection_invalidate`：insight_id、memory_id（触发者）、decision、reason、匹配相似度；
   - `context_insight`：insight_id、decision（入选/落选）、reason（预算/置信）。
2. **后台 run 的可观测口径**（与 REF-004 设计 8 一致）：反思执行无 turn trace session，其「trace」事实源 = `reflection_runs` 行（evidence_summary/outcome/insight_ids/error）+ `llm_call_records`（链自动记账）+ evidence_links→memories 原文；runtime_traces 的 reflection_* 步骤仅在有 trace 上下文处记录（触发点/装配点）。本 Task 的归因端点把两个来源拼为完整回溯视图。
3. **debug 归因端点（只读）**：
   - `GET /debug/insights/{insight_id}/attribution` → `{insight, run(trigger/evidence_summary/outcome/llm_used), evidence: [{memory_id, weight, content 原文, created_at, source}], status_history 字段}`——验收「每条 evidence 可查原文」的落点；
   - `GET /debug/reflection-runs?user_id=&limit=` → run 列表（额度审计与 skipped 原因排查）。
4. **Evaluation 规则集**（`evaluation_rules/reflection.py`，纯函数、逐条异常隔离，subjects 含 `offline_batch`）：
   - `REFLECTION_NO_EVIDENCE_LINK`：active Insight 无任何 evidence_links → CRITICAL（无证据不出 Insight 的复核闸）；
   - `REFLECTION_STALE_INJECTED`：prompt_snapshots 的 insight 段出现 status≠active 的 Insight → CRITICAL（REF-007 即时退出的复核闸）；
   - `REFLECTION_CONFIDENCE_OVER_CALIBRATED`：confidence 高于按证据数折算上限 → WARNING（校准被绕过的信号）。
   - 输入切片：`EvaluationContext` 新增可选 `reflection` 切片（Insight 摘要 + 引用数 + prompt 段出现清单，构造器只读收集、缺失容错为 None——沿 context 收集器既有风格，不破坏 turn 评估既有行为）。
5. **Judge 维度**：`judge_reflection` 按 E-REF-01 的 Judge 口径评「结论不超证据范围/引用真实支撑结论」，输入 = statement + 全部 evidence 原文，输出复用既有 judgement 结构（issues + pass）；采样率沿 judge 采样机制，离线场景集内全量评。
6. **离线场景集（`reflection/evaluation.py`，可重复执行，幂等）**：按 evaluation.md P2 专属场景逐条构造 memories → 跑 REF-002/003/004/005 全链（LLM 用 fake/录制响应，离线零真实调用）→ 指标：
   - E-REF-01 引用率（100% 带 ≥门槛引用）+ Judge 通过率（≥0.9）；
   - E-REF-02 门槛有效性（压力聚合场景产出且带 ≥3 证据；孤立/噪声场景 0 产出）；
   - E-REF-03 误报率（噪声场景集 0 Insight 0 LLM，含「无证据月成本」场景：LLM 调用 = 0）；
   - E-REF-04 反驳失效有效性（澄清 → invalidated + 退出 Context + 钩子被调；误失效率 = 0）。
   - 报告为返回值/日志，不落新表（tasks.md Non-Scope）；offline_evaluator `_aggregate` 追加小节引用其结果。

## 核心处理流程

```text
链路事件（REF-002~005/007 打点） → payload 规范校验（测试期） → runtime_traces/runs 行/llm_call_records
debug: insight_id → run 行 + evidence_links join memories → 归因视图
离线: 场景构造 → 反思全链（fake LLM） → 指标计算 → 报告（E-REF-01~04）
在线: judge_reflection 采样 → issues → 与规则集 min 合并（沿既有 _merge 语义）
```

## 模块关系

- 横切质量平面（domain-boundaries：评估与观测是两套平面的统一收口），只读旁路、零业务写入。
- 依赖 REF-001~005 全部产物（trace 步骤/三表/事件钩子）；debug API 扩展沿用 MEM-008 已交付的归因端点模式（`memory2/attribution.py`，冲突记录第 5 条）。
- 被 Phase 2 Eval Gate（evaluation.md）与 regression-checklist 消费；为 P3 DEV-004 提供误报率基线。

## 异常与边界情况

- 单条规则/Judge 异常 → 逐条隔离跳过（沿 `run_rules` 既有容错）；Judge 失败 → 该场景记 skipped 并可重跑（tasks.md）。
- 历史数据无 reflection 步骤/无 run 行 → 归因视图标 `no_data`，不报错（沿 MEM-008 口径）。
- evidence_links 悬空（memory 被物理清）→ 归因视图该条标 `memory_purged`，不中断（REF-001 Non-Scope 的回收路径复核）。
- 场景集重复执行 → 幂等（每次独立构造、独立库状态，结果可复现）。
- Flag OFF → 在线旁路无 reflection 产物，规则集空转、离线报告 reflection 小节为空，不报错。

## 测试要求

- Unit：payload 规范字段校验（五步骤）；三条评估规则表驱动；`judge_reflection` 输入构造。
- Integration：端到端 trace 完整性（一次「触发→聚合→执行→失效」全链五步骤齐全且字段合规）；归因端点回溯（含悬空链接与 no_data 分支）。
- 离线场景集：E-REF-01~04 全量（即 tasks.md 验收的测试载体）。
- Regression：枚举/切片扩展后既有 7 维评估输出不变（Flag OFF golden）。

## 验收标准

- 给定噪声记忆场景集，当离线评估，那么误报率 0（0 Insight 0 LLM，tasks.md 原文）。
- 给定任一 Insight，当查 debug 归因端点，那么可回溯完整证据链（每条 evidence 可查原文，tasks.md 原文）。
- 给定「5 次说累」场景，那么 E-REF-01/02 指标达 evaluation.md 门槛（100% 引用、Judge ≥0.9）。
- 给定 Flag OFF 全量回归，那么既有评估维度与 trace 输出零变化。

## Implementation Constraints

- 误报率量化以本 Task 场景集为准；不提前设计 Development/Goal trace（P3+ 域）。
