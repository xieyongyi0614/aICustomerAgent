# REF-001 Task Detail — Insight 存储与生命周期（Foundation）

> 上游：[../tasks.md](../tasks.md) REF-001 ｜ [../architecture.md](../architecture.md) §1 ｜ 依赖：无（可与 P1 并行开发，启用依赖 P1）

## Task 目标

建立 Reflection 域全部存储基座：`insights` / `reflection_runs` / `evidence_links` 三张新表（alembic 迁移）+ Insight 生命周期状态机服务（active→superseded|invalidated，终态不复活，非法转换拒绝，幂等迁移 API）。纯存储层 Task，不接任何消费方、不做反思执行。

## 背景 / 为什么需要

Insight 是 P3 Development / P4 Relationship / P6 Goal 调制的**唯一合法上游**（domain-boundaries §1：Development 读 Memory 仅限「经 Reflection 验证的 Insight」）。无存储则整个认知链无落点；无生命周期则幻觉 Insight 无法回收（risk.md R6 的最后一道防线：`invalidated` 通道）。状态机设计直接复刻 Phase 1 已验证的 memory2 生命周期模式（守卫表 + 非法转换异常），保证两个域的行为语义一致、代码风格一致。

## 设计方案

1. **三表结构**（architecture.md §1 为基础，列补全见「数据模型」节）：
   - `insights`：Insight 主表，`status ∈ active|superseded|invalidated`；`type ∈ belief|preference|pattern`；`scope ∈ user|relationship|world`；`invalidated_reason` 必填约束用 CheckConstraint 表达（`status='invalidated'` 时非空）；`superseded_by` 为字符串引用（不建 FK，沿 `memories.superseded_by` 惯例）。
   - `reflection_runs`：反思任务运行记录，`status ∈ queued|running|done|skipped|failed`；`trigger ∈ scheduled|event`；`evidence_summary` JSONB 存组统计摘要（组数/成员数/跨度/门槛结果）。
   - `evidence_links`：`insight_id → memory_id` 引用 + weight，`UNIQUE(insight_id, memory_id)`；**不建外键**（memories 物理删除后按「链接悬空→过滤」处理，见 REF-006 验收口径）。
2. **状态机**（`reflection/lifecycle.py`）：
   ```text
   TRANSITIONS = {
       (ACTIVE, EVENT_SUPERSEDE): SUPERSEDED,
       (ACTIVE, EVENT_INVALIDATE): INVALIDATED,
   }
   ```
   - `superseded` / `invalidated` 为终态：转换表无出边，任何对终态行的事件由守卫拒绝（`IllegalTransitionError`）。
   - **幂等语义**（tasks.md：同状态重复迁移无操作）：`invalidate()` 对已 `invalidated` 行返回 no-op（不报错、不改行）；对 `superseded` 行发起 `invalidate` 属非法转换 → 拒绝（两终态互斥，防「先被更强结论替代、又被反驳复活」的语义混乱）。
3. **迁移 API**（服务层函数，全部单事务）：
   - `invalidate_insight(insight_id, reason, source) -> bool`：置 `status=invalidated`、`invalidated_at=now`、`invalidated_reason=reason`（必填校验在服务层再拦一次，DB 约束兜底）；`source ∈ user_clarification|new_evidence|judge` 记入 reason 前缀。原行不删除（审计保留，tasks.md Non-Scope）。
   - `supersede_insight(old_id, new_id, reason) -> bool`：置旧行 `status=superseded`、`superseded_by=new_id`；要求 new_id 行存在且 active。
   - 两个函数对状态不符/行不存在返回 False + trace，不抛业务异常到调用方。
4. **settings 新增**：`v2_reflection_enabled: bool = False`（本 Task 定义，后续 Task 消费）；`v2_reflection_min_confidence: float = 0.6`、`v2_reflection_min_evidence: int = 3`（阈值定义在 Foundation 一次到位，供 REF-002/004 消费，避免散落多次迁移）。

## 数据模型 / 接口变化

新表 3 张（迁移 0024，可 up/down 往返）：

```text
insights(id, user_id, character_id, statement Text, type, confidence Float,
         scope, status, run_id, created_at, updated_at,
         invalidated_at, invalidated_reason, superseded_by)
  CHECK status IN ('active','superseded','invalidated')
  CHECK type IN ('belief','preference','pattern')
  CHECK scope IN ('user','relationship','world')
  CHECK NOT (status='invalidated' AND invalidated_reason IS NULL)   -- 必填约束
  Index (user_id, status)；Index (user_id, scope, status)

reflection_runs(id, user_id, character_id, trigger, status, evidence_summary JSONB,
                outcome, llm_used Bool, insight_ids JSONB, error, created_at, updated_at)
  CHECK status IN ('queued','running','done','skipped','failed')
  CHECK trigger IN ('scheduled','event')
  Index (user_id, status)；Index (status, created_at)

evidence_links(id, insight_id, memory_id, weight Float, created_at)
  UNIQUE (insight_id, memory_id)；Index (memory_id)
```

> 与 architecture.md §1 的差异说明（补全，不改语义）：架构给出的 `reflection_runs(id, trigger, evidence_summary, outcome, llm_used, created_at)` 是最小示意列集。本 Detail 补 `user_id/character_id`（全库既有多用户隔离惯例，tasks.md REF-003 要求「每用户每日一条」必需）、`status`（tasks.md REF-003 状态机 `queued→running→done|skipped` 的落点）、`insight_ids/error/updated_at`（幂等与审计）。已登记至本目录 README 的冲突/口径记录第 4 条。

## 核心处理流程

```text
（本 Task 无运行时行为，全部为被调用接口）
invalidate_insight:
  查行 → [不存在→False | status=invalidated→no-op True | status=active
        → 单事务 UPDATE status/invalidated_at/invalidated_reason → True
        | status=superseded→IllegalTransition 拒绝→False]
supersede_insight:
  查两行 → [旧行 active 且新行 active → 单事务 UPDATE 旧行 superseded/superseded_by → True | 其余→False]
```

## 模块关系

- **只写本域三表**（domain-boundaries §1 Reflection 行）；不写 memories/State/Relationship，不读任何域。
- 不 import `memory2`（状态机为同构独立实现，防止跨域耦合；`same_topic` 等纯函数复用发生在 REF-002/004/005，不在本 Task）。
- 被依赖：REF-002（不直接依赖，但门槛阈值共享 settings）、REF-003（写 reflection_runs）、REF-004（写三表）、REF-005（迁移 API 唯一调用方）、REF-007（list_active_insights）。
- 消费方（P3/P4/P6）本 Task 一律不接。

## 异常与边界情况

- 非法转换（active→active 无此事件、superseded→invalidated、invalidated→superseded）→ `IllegalTransitionError` 被服务函数捕获转为 False + trace，不外泄。
- `invalidate` 未带 reason → 服务层直接拒绝（ValueError），DB CHECK 兜底。
- `supersede` 指向的新 insight 不存在或非 active → False（不产生悬挂引用）。
- 迁移往返：down 依次 drop 三表（逆序 evidence_links → reflection_runs → insights），v1 表零影响（三表均为新表，无扩列）。
- 同事务并发迁移（理论单进程不出现）：UPDATE 条件带 `status='active'`，影响行数 0 即视为 no-op，天然幂等。

## 测试要求

- Unit：状态机全路径表驱动（active→superseded / active→invalidated / 终态拒绝 / 终态幂等 no-op）；`invalidated_reason` 缺失被拒。
- Integration：迁移往返（upgrade→downgrade→upgrade 后三表结构一致、既有表数据逐行相等）；`list_active_insights` 过滤（status/confidence/scope）。
- Constraint：直接 SQL 插入 `status='invalidated'` 且无 reason → 违反 CHECK 报错。

## 验收标准

- 给定 active Insight 被反驳，当调用 `invalidate_insight`，那么状态变更、`invalidated_reason` 必填、原行不删除。
- 给定 downgrade，那么三表删除且 v1 零影响（v1 全量测试通过）。
- 给定已 superseded 的 Insight 再被请求 invalidate，那么拒绝且状态不变（终态互斥）。
- 给定同一 active Insight 重复调用两次 invalidate（同 reason），那么第二次为 no-op，`invalidated_at` 不变。
