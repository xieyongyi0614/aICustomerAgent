# REF-005 Task Detail — 反驳与失效通道（Integration）

> 上游：[../tasks.md](../tasks.md) REF-005 ｜ [../architecture.md](../architecture.md) §1 生命周期 ｜ [../../../architecture/domain-boundaries.md](../../../architecture/domain-boundaries.md) §3 ｜ 依赖：REF-001, REF-004

## Task 目标

让 Insight 可被推翻、可被替代：用户澄清类话语 → 匹配旧 Insight → `invalidated`（保守阈值，歧义不失效）；新反思结论与旧 Insight 冲突 → `superseded`（终态替代）；失效结果向下游广播（进程内事件钩子，P3 DEV-004 订阅）。不可反驳的认知会永久污染行为——本 Task 是 R6 的回收通道。

## 背景 / 为什么需要

REF-001 提供了状态机原语，REF-004 提供了「新结论替代旧结论」的入库事务，但「**用户说不对**」这条通道在 v1 是断裂的：v1 记忆冲突通道（extractor 产出 `action=invalidate` / `relation=negate` 候选 → `memory_conflict.resolve_candidate` 裁决「用户否定既有记忆」）只作用于 Memory，不作用于认知层。若无 Insight 失效通道，用户澄清后角色仍带着被推翻的「认知」对话——比记错事实更顽固。本 Task 复用记忆冲突通道的**信号与风格**，把裁决对象从 memories 换成 insights。

## 设计方案

1. **澄清通道（invalidated 半边）**：
   ```text
   用户话语 → extractor 产出 relation=negate 候选 → ingest 落候选 → evaluator 转正（Memory 侧 contradicts 并存不变）
   → post_process 订阅点发现 approve 且 source_ref.relation=="negate" → observe_negation(user_id, memory_id, content)
   → 查该 user 的 active Insights → 匹配（same_topic 相似度 ≥ invalidate_match_threshold）
   → [唯一高匹配 → invalidate_insight(reason="user_clarification:{memory_id}")
     | 多匹配 / 无匹配 / 低于阈值 → 忽略 + trace（保守不失效）]
   ```
   - 匹配严格性高于 Memory 侧：Reflection 认知是慢变量，误失效的代价大于漏失效（tasks.md Risk：误失效正确 Insight→保守阈值+误失效率指标），故阈值独立于 `memory_conflict_threshold` 且默认更严，并要求**唯一**高匹配（多匹配一律忽略）。
   - 匹配候选集 = 该 user 全部 active Insights（scope 不过滤——澄清话语不带 scope 标签，user/relationship/world 内的 statement 都可能被推翻；trace 记录命中 scope）。
2. **替代通道（superseded 半边）**：新反思结论与旧 Insight 同 scope+type 且 `same_topic(statement)` → REF-004 在入库事务内调 `supersede_insight(old, new, reason="superseded_by_new_reflection")`。本 Task 交付该策略的独立函数 `find_superseded_insights(new_insight, actives, settings) -> list[str]`（供 REF-004 调用与单测），阈值复用 `v2_reflection_invalidate_match_threshold` 同源参数（替代是「更强结论」，匹配要求与失效一致）。
3. **失效事件广播（DEV-004 订阅点）**：`reflection/lifecycle.py` 提供进程内钩子 `register_invalidation_listener(fn)`，`invalidate_insight`/`supersede_insight` 成功迁移后调用监听器（参数：user_id、变更 insight 摘要列表）。P2 无消费方——**不注册任何监听器即零行为**；P3 DEV-004 在编排层注册订阅（Reflection 不 import Development，依赖单向，domain-boundaries §3）。
4. **LLM Usage 裁决**：本 Task 全程 0 LLM——澄清识别复用 extractor 既有信号（tasks.md「复用 REF-004 通道内调用（不新增独立链）」的落地口径：不在 REF-005 内新增任何 LLM 链；REF-004 的链已由其自身额度约束）。
5. **trace**：`reflection_invalidate` 步骤记录：触发 memory_id、匹配过程（各候选 Insight 的相似度）、裁决结果（invalidated / ignored 多匹配 / ignored 低匹配）、触发者（user_clarification / new_reflection）。

## 数据模型 / 接口变化

- 无新表；仅 `insights.status / invalidated_reason / superseded_by` 列变更（tasks.md Data Changes 原文）。
- 新接口：
  ```text
  reflection/lifecycle.py（策略层新增）
    observe_negation(user_id, memory_id, content, trace) -> list[str]   # 返回被失效 insight_id
    find_superseded_insights(new_statement, new_scope, new_type, actives) -> list[str]
    register_invalidation_listener(fn) -> None                          # P3 DEV-004 订阅点
  ```

## 核心处理流程

```text
澄清: post_process evaluate 尾部 → 发现 negate 转正记忆 → observe_negation
      → active Insights 匹配 → [唯一高匹配 → invalidated(reason 必填) + 事件钩子 + trace
                               | 歧义/低匹配 → 忽略 + trace]
替代: REF-004 落库事务 → find_superseded_insights → supersede_insight(同事务) + 事件钩子
下游: 监听器注册表（P2 空注册，P3 DEV-004 接线）→ DEV 侧处理失效
```

## 模块关系

- 只写本域 insights 表；Memory 侧的 contradicts 并存、State/Relationship/Goal 零接触（tasks.md Non-Scope：只发事件）。
- 事件钩子是**回调注册**而非跨域 import：Reflection 不感知消费方，编排层负责注册（保持依赖单向）。
- 被 REF-007 间接依赖（invalidated 后退出 Context 的数据前提）；为 P3 DEV-004 提供订阅点。

## 异常与边界情况

- 模糊澄清（「其实最近还好吧」低相似度）→ 不失效任何 Insight（tasks.md 验收原文）。
- 一次澄清匹配多条 Insight → 全部忽略（保守；trace 记 match_count 供离线评估调阈值）。
- 同一话语重复触发（用户复述澄清）→ `invalidate_insight` 幂等 no-op（REF-001 语义），不二次迁移、事件钩子不重复触发（迁移成功才回调）。
- negate 信号被 evaluator 拒绝（未转正）→ 无 memory_id、无订阅事件——此时澄清内容不构成被确认的事实，Reflection 保守不动（失效只信任「已确认的澄清」，宁缺勿错）。
- 监听器抛异常 → 捕获记日志，不影响已完成的迁移（迁移是事实，通知是尽力而为）。
- 时序口径（登记于 README 冲突记录第 6 条）：澄清识别在 post_process（后台），当轮回答已用旧 Context 生成——invalidated 的生效点 = **下一轮 Context 装配起 0 出现**（REF-007 查询只取 active，天然保证）；「当轮退出」验收按此口径解释为「处理该澄清的轮次之后不再出现」，本轮已产出回答不回溯。

## 测试要求

- Unit：匹配阈值表驱动（唯一高匹配/多匹配/低匹配/空集）；`find_superseded_insights`（同 scope+type+同主题命中、跨 type 不命中）；事件钩子成功/异常路径。
- Integration：反驳表述变体集（「其实我最近不累」「并不是这样」等 ≥5 变体）→ 对应 Insight invalidated 且 reason 带 memory_id；重复触发幂等；REF-004 事务内 supersede 端到端（旧 Insight.superseded_by 指向新 id）。
- FailureInjection：监听器抛异常 → 迁移保持、流程不中断。
- 指标：变体集上误失效率 = 0（tasks.md Risk 的量化口径）。

## 验收标准

- 给定「其实我最近不累」，当匹配到对应 Insight，那么其 invalidated 且当轮退出 Context 且 DEV 收到失效事件（tasks.md 原文；「当轮退出」按冲突记录第 6 条口径 = 该轮 post_process 完成后，后续任一 Context 装配 0 出现；「DEV 收到事件」按 P2 口径 = 失效事件钩子被调用且参数完整，P3 注册消费方）。
- 给定模糊澄清，那么不失效任何 Insight，trace 记录 ignored 原因。
- 给定新反思结论与旧 Insight 同主题，那么旧 Insight `superseded` 且 `superseded_by` 指向新行，原行不删除。
- 给定同一澄清话语重复处理，那么状态只迁移一次。

## Implementation Constraints

- 不删除行（审计保留）；不直接改 Development/Goal（只发事件，P2 无消费方）；不修改 memory2 任何函数（negate 在 Memory 侧的 contradicts 并存语义保持不变）。
- 匹配歧义保守不失效；失效阈值必须高于记忆冲突阈值且进 settings；误失效率 0 为硬指标（E-REF-04）。
- 0 LLM：不新增独立链，识别复用既有 extractor 信号；禁止前台同步调用失效通道。
