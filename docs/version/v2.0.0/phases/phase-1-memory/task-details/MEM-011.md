# MEM-011 Task Detail — Working Memory 装配接线

> 上游：[../tasks.md](../tasks.md) MEM-011 ｜ [../../architecture/context-architecture.md](../../../architecture/context-architecture.md) §1/§3 ｜ 依赖：MEM-006

## Task 目标

在 `context_builder` 内实现双层装配：Working Memory（最近 N 条 + 本轮结构化信号 + 活跃 Scene/Action，每轮重建、不落表）与 Long-term 检索段（MEM-006 输出）分层；分层预算裁定（检索类合并 ≤800）；Flag OFF 装配与 v1 逐字节一致。

## 背景 / 为什么需要

v1 的 context_builder（`app/services/context_builder.py`）已按段装配（persona/state/goal/relationship/world/memory/summary），且 `memory_recent_context_messages=4`（settings L172）控制最近消息数——「Working Memory」事实上存在但与长期记忆混装在 memory 段，无法对检索段单独施加 Freshness/预算策略（context-architecture.md §1 的 P0–P3 分级无法落地）。双层层化是 design.md §1「Memory ≠ RAG：支撑角色认知」在装配侧的落点。

## 当前代码涉及位置

| 位置 | 现状 | 本 Task 动作 |
|---|---|---|
| `app/services/context_builder.py` L38-44 | retrieve → select_for_context → 拼 memory 段 | Flag 内改为：Working 段（既有最近消息+信号）与检索段（MEM-006 RankedMemories）分层输出 |
| `app/services/memory_service.py` L343 `select_for_context` | v1 段内容组装 | 保留（Flag OFF）；v2 层内复用其输出作为 Working 段素材 |

| `app/services/summary_service.py` 滚动摘要 | Working 旧段压缩 | 不改，作为 Compression 策略既有实现 |
| prompt_snapshots 落库 | 既有 | 分层后每段实际内容照常记录 |

## 设计方案

1. **分层定义**（对齐 context-architecture §1）：
   - Working 段 = 最近 `memory_recent_context_messages` 条 + 本轮 turn_analysis 结构化信号 + 活跃 Scene/PendingAction 概要（均既有数据，不新建查询）。
   - 检索段 = MEM-006 top-5（含分数），按 Freshness（last_reinforced_at/recency）排序。
2. **预算裁定顺序**：Persona/State(P0) → 意图/关系/世界(P1) → Working(P2) → 检索段(P2, ≤800) → 超限从最低优先级压缩/截断；`_fit_variable_parts` 承接最终裁剪。
3. **不落表**：Working 段全部即时组装，无任何持久化（domain-boundaries §2 Runtime Context）。
4. **trace/snapshot**：分层预算占用记入 prompt_snapshots；v2 记 `context_assemble_v2` 步骤。

## 数据模型 / 接口变化

- 无表变化；`context_builder.build()` 内部分支 + 新增装配参数（RankedMemories 注入），对外签名不变。

## 核心处理流程

```text
消息 → 既有各段组装（不变）
 → v2_memory_enabled?
   ├ OFF → v1 memory 段（retrieve+select_for_context）字节级原样
   └ ON  → Working 段(近期消息+信号+Scene/Action) ∥ 检索段(MEM-006)
          → 分层预算裁定(检索类 ≤800) → _fit_variable_parts(12000) → sections + snapshot
```

## 与现有模块的关系

- 只动 `context_builder` 一处接线；依赖 MEM-006 输出；`summary_service`/prompts 结构沿用。
- 被依赖：P2 REF-007、P4 REL-002/003 的注入段将复用同一分层预算框架（本 Task 预留检索类合并预算的通用入口，不实现其内容）。

## 异常与边界情况

- 检索段为空 → 仅 Working 段，正常出 prompt。
- 双段总量超预算 → 按 P2→P3 优先级压缩/截断，P0/P1 永不砍（context-architecture §1）。
- Flag 半开（vector 子闸 OFF）→ 检索段来自结构化打分，装配逻辑相同。
- 长对话（50+ 轮）→ Working 段被 `memory_recent_context_messages` 与 summary 滚动约束，不无限增长。

## 测试要求

- Unit：分层预算裁定表驱动（各段边界值）。
- Integration：50+ 轮长对话装配；检索空/超预算路径。
- Regression：Flag OFF 下 prompt_snapshots 与 v1 字节级对比；Flag ON 时 sections 总量 ≤12000。

## 验收标准

- 给定 50+ 轮对话，当装配当轮 Context，那么 Working 段仅含预算内近期消息、检索段仅含 top-5 且总量 ≤12000。
- 给定 Flag OFF，那么 sections 与 v1 逐字节一致。
- 给定检索段超 800，那么按 Freshness 截断且 trace 可见裁剪明细。

## Implementation Constraints

- Working Memory 不落任何长期表；不新增 LLM；不改 summary 滚动与 v1 分段结构；不提前实现 P2+ 注入段（Insight/Shared Experience 各属其 Phase）。
