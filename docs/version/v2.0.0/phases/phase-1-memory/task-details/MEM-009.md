# MEM-009 Task Detail — 周期任务接入 background_jobs

> 上游：[../tasks.md](../tasks.md) MEM-009 ｜ [../../architecture/data-flow.md](../../../architecture/data-flow.md) §3 ｜ 依赖：MEM-001, MEM-005

## Task 目标

实现 `background_jobs` 的通用执行器（认领/重试/死信），并把 Memory 2.0 的周期任务（decay、embedding backfill）迁入该调度；kill -9 后不丢不重。P5 Life Loop 复用同一协议。

## 背景 / 为什么需要

v1 的周期设施是 `main.py` lifespan 里 5 个裸 `asyncio.create_task` 循环（memory reclaim / autonomy worker / observability retention / world maintenance / action retry），无持久化、无重试策略——v1 审计问题 6。`background_jobs` 表（MEM-001 建）是 v2 的最小持久化底座：P1 先落协议，P5 换执行器，P3.0 可外移 Worker 进程（overview.md §5「Job 表即协议」）。

## 当前代码涉及位置

| 位置 | 现状 | 本 Task 动作 |
|---|---|---|
| `app/main.py` L22-41 lifespan（5 个 create_task） | 裸循环注册 | **不改既有 5 循环**；新增第 6 个循环 `run_background_job_worker()`（v2_memory_enabled 门控） |
| `app/services/memory_service.py` L329 `run_memory_reclaim_loop` | v1 TTL 回收循环 | 保留不动（Flag OFF 路径） |
| `app/core/db.py` `BackgroundJob` ORM + settings | 表在（MEM-001） | 新增执行器服务 `app/services/memory2/job_worker.py` |
| `app/services/memory2/lifecycle.py` `run_decay_cycle` / `embeddings.backfill_scan` | 任务函数 | 注册为 job_type 处理器 |

## 设计方案

1. **job_type 注册表**：`{memory_decay, embedding_backfill}`（dict 注册，新处理器一行注册）。
2. **认领**：`SELECT ... WHERE status='pending' AND run_at<=now() ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT n` → 置 running；单进程下 SKIP LOCKED 为 P5 多执行器预留。
3. **重试**：异常 → attempts+1，`run_at=now()+backoff(attempts)`（指数），attempts≥5 → failed(终态)+last_error。
4. **僵尸回收**：running 超 `v2_job_running_timeout`（默认 10min）→ 视为崩溃，重置 pending 重跑（处理器必须幂等，MEM-004/005 已保证）。
5. **调度入队**：decay 按日桶（job_key=`memory_decay:{user}:{date}`）、embedding 由 MEM-004 失败路径入队；重复入队被 UNIQUE 约束拦截。
6. **周期入队器**：轻量循环只负责「到点插 job」（纯 SQL），执行统一走认领——调度与执行分离。

## 数据模型 / 接口变化

- 新服务模块 `memory2/job_worker.py`；新 settings：`v2_job_poll_interval`、`v2_job_max_attempts=5`、`v2_job_running_timeout`。
- main.py lifespan 新增 1 个受 Flag 门控的循环；无新表。

## 核心处理流程

```text
周期入队器（60s SQL 扫描）→ 到点 INSERT background_jobs(pending)
job_worker 循环: SKIP LOCKED 认领 → running → 分发 job_type 处理器
 → done ｜ 异常→attempts+1 退避重试 ｜ attempts≥5→failed(死信+last_error)
running 超时 → 回收重置 pending（幂等重跑安全）
```

## 与现有模块的关系

- 消费 MEM-004（embedding backfill）、MEM-005（decay）两个处理器；不改 v1 5 循环与 `run_memory_reclaim_loop`。
- P5 LIFE-001/002 直接复用本执行器协议（version-boundary：Extend→Replace 仅在 P5 发生）。

## 异常与边界情况

- 进程 kill -9：running job 超时回收后重跑——幂等由处理器保证（decay 按日桶、embedding 条件更新）。
- DB 失败 → 循环记日志下轮继续（沿 v1 worker 容错模式）。
- 死信堆积 → 计数指标暴露，不自动清理（人工排查）。
- 时钟：一律用数据库时间（TimeProvider 思路，data-flow §3 禁散落 datetime.now()）。

## 测试要求

- Unit：状态机（pending/running/done/failed/重试/回收）表驱动。
- Integration：kill -9 演练（提交后杀进程→重启→未完成 job 续跑且不重复）。
- Idempotency：同 job_key 重复入队被拦截；僵尸回收重跑无副作用。

## 验收标准

- 给定执行中进程被 kill -9，当重启，那么未完成 job 继续执行且无重复副作用。
- 给定同一 job_key 两次入队，那么表中仅一行。
- 给定 attempts 达 5 的 job，那么终态 failed 且 last_error 可查。
- 给定 Flag OFF，那么 worker 循环不启动，v1 行为不变。

## Implementation Constraints

- 不改变单进程执行模型（执行器重构属 P5）；不引外部队列/Redis；不改 v1 既有循环；处理器必须幂等方可注册。

## Implementation Ruling

decay job 采用全局日桶键 `memory_decay:{date}`（run_decay_cycle 为全局处理器，按用户入队会重复执行）；P5 多执行器时再按用户拆分：详见 [../decisions.md](../decisions.md) D3。
