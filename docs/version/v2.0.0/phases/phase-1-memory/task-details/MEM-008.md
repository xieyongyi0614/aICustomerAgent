# MEM-008 Task Detail — Memory Trace

> 上游：[../tasks.md](../tasks.md) MEM-008 ｜ [../../architecture/context-architecture.md](../../../architecture/context-architecture.md) §5 ｜ 依赖：MEM-003, MEM-005, MEM-006

## Task 目标

在 `trace_collector` 体系内新增 `memory_*` 步骤族（ingest/evaluate/lifecycle/retrieve/command），并扩展 debug API，使「为什么记住/没记住/为什么召回这条」三问可答，且任一记忆可查全链归因。

## 背景 / 为什么需要

v1 已有完整观测底座：`trace_collector.py`（`TraceStep`/`TurnTraceSession`/`TraceCollector`）+ `runtime_traces`/`llm_call_records`/`prompt_snapshots` 表 + retention 清理循环（main.py lifespan）。`context_builder` 已记录 `memory_retrieval` 计时步骤（L44），但只有耗时没有决策内容——候选为何被拒、为何降级、检索分数构成全部不可见。无归因则 MEM-010 的评估无法定位失败环节，灰度期无法回答「为什么行为变了」。

## 当前代码涉及位置

| 位置 | 现状 | 本 Task 动作 |
|---|---|---|
| `app/services/trace_collector.py` `TurnTraceSession.record` | 通用步骤记录 | 扩展步骤 payload schema（memory_* 步骤的结构化字段），不改记录机制 |
| `app/api/v1/debug.py` | v1 debug 查询 | 新增按 memory_id / candidate_id 的归因查询端点 |
| `app/services/memory2/*`（MEM-002~007） | 各环节已产出 trace 事件 | 本 Task 定义统一 payload 结构并聚合 |
| `app/application/observability.py` retention | trace 清理 | 新步骤类型纳入既有保留策略，不改清理逻辑 |

## 设计方案

1. **payload schema（每步骤统一）**：`{step, user_id, memory_id|candidate_id, decision, reason, scores{...}, llm_used, llm_calls, ts}`；步骤族：`memory_ingest` / `memory_evaluate` / `memory_lifecycle` / `memory_retrieve` / `memory_command`。
2. **归因查询**：debug API `GET /debug/memory/{id}/attribution` → 聚合该 memory_id 关联的全部步骤（源→转正→强化→历次召回分数→状态迁移）；候选同理。
3. **六问映射**：为什么记住（evaluate.decision+scores）/没记住（reject/defer reason）/召回这条（retrieve.scores）/没召回（落选 penalty）/谁触发（ingest.source_ref / command）/LLM 调用几次（llm_used）。
4. **零阻塞**：trace 写失败只记日志（沿 v1 旁路语义）；不写业务状态。

## 数据模型 / 接口变化

- `runtime_traces` 步骤类型扩展（无新表，沿 V7.8 体系）。
- debug API 新增 2 个只读端点（memory/candidate 归因）。

## 核心处理流程

```text
memory2 各环节 → TurnTraceSession.record(memory_* 步骤, payload)
 → runtime_traces 落库（既有管道） → retention 照常
debug API: 按 id 聚合步骤 → 归因视图
```

## 与现有模块的关系

- 纯只读旁路扩展，复用 V7.8 trace 体系（version-boundary：Extend）；依赖 MEM-002~007 产出事件；被 MEM-010 与全部 Evaluation 依赖。
- 不新建存储、不改 trace_collector 既有函数签名（仅 payload 约定）。

## 异常与边界情况

- payload 序列化失败 → 降级记摘要字符串。
- 高频 retrieve 步骤量大 → 采样策略进 settings（golden 对比期全量）。
- trace 缺失（历史数据）→ 归因视图标注 no_data，不报错。

## 测试要求

- Integration：端到端 trace 完整性（一次「记住→召回→遗忘」全链步骤齐全）。
- Unit：payload 序列化/降级。
- Regression：trace 扩展不改变任何 golden 输出。

## 验收标准

- 给定任一已转正记忆，当查 debug 归因端点，那么返回源、转正原因、最近强化、历次召回分数。
- 给定任一被拒候选，那么可查到拒绝 reason 与分数。
- 给定 trace 写失败注入，那么业务流程不受影响。

## Implementation Constraints

- 只读旁路；复用 runtime_traces 不新建存储；不阻塞主链路；不提前设计 Reflection/Goal trace（P2+ 域）。
