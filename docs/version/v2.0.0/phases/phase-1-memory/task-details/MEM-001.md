# MEM-001 Task Detail — 存储与向量基座

> 上游：[../tasks.md](../tasks.md) MEM-001 ｜ [../../design.md](../../design.md) §2 ｜ 依赖：无

## Task 目标

为 Memory 2.0 建立全部持久化与索引基座：`memories` 表扩列、`memory_candidates`/`memory_links`/`background_jobs` 三张新表、pgvector 扩展与 HNSW 索引、`core/settings.py` 全量 v2_memory 配置项。本 Task 完成后其余 10 个 Task 才有落点。

## 背景 / 为什么需要

v1 的记忆存储是单表 `memories`（ORM 见 `app/core/db.py` L80 `class Memory(Base)`，`__tablename__="memories"`），只有 content/type/importance/confidence/source/status/superseded_by/last_accessed_at/expires_at 字段（Pydantic 侧见 `app/models/memory.py` L19 `UserMemory`）。无显著度、无向量、无候选表、无任务表——design.md §2 的生命周期与混合检索全部无处落地。Alembic 当前最新版本为 `migrations/versions/0021_action_records.py`，本 Task 产出 0022。

| 位置 | 现状 | 本 Task 动作 |
|---|---|---|
| `apps/backend/app/core/db.py` L80 `Memory` ORM | v1 列集 | 扩 6 列（可 NULL） |

## 设计方案

1. **0022 迁移**（ Alembic，up/down 完整）：
   - `memories` 扩列：`embedding vector(768) NULL`、`salience numeric NULL`、`last_reinforced_at timestamptz NULL`、`merge_chain jsonb NULL`、`source_ref jsonb NULL`、`visibility text NULL`（全部可 NULL，v1 代码不可见——version-boundary「只增列不改义」）。
   - 新表 `memory_candidates`：id/user_id/character_id/content/proposed_type/source/source_ref jsonb/salience/status(pending|approved|rejected|promoted)/reason/visibility/created_at；唯一约束 `(source_table, source_id)`（source_ref 内两字段生成列或独立列，取独立列 `source_table`+`source_id` 更利于约束）。
   - 新表 `memory_links`：id/memory_id/related_memory_id/relation(supersedes|merges|contradicts)/created_at。
   - 新表 `background_jobs`：id/job_type/payload jsonb/status(pending|running|done|failed)/attempts/run_at/idempotency_key UNIQUE/last_error/created_at。
   - pgvector：`CREATE EXTENSION IF NOT EXISTS vector` + `memories` embedding 列 HNSW 索引（cosine ops）。
2. **settings 新增**：`v2_memory_enabled=False`、`v2_memory_vector_enabled=False`、`v2_memory_eval_threshold_high/low`、`v2_memory_llm_fallback_rate_cap=0.3`、`v2_memory_decay_batch_size`、`v2_memory_forget_retention_days=30`、`v2_embedding_batch_size=32`、`v2_embedding_batch_window_seconds=60`、`v2_memory_retrieval_budget=800`。
3. **SQLite 兜底**：生产仅 Postgres 的声明写入迁移 docstring；SQLite 兼容路径 = vector 列以 BLOB/jsonb 模拟（仅保证迁移可跑，向量检索不启用）。

## 数据模型 / 接口变化

- 仅 DDL + 配置；不新增/修改任何 Python 接口签名。
- ORM 新类与列对既有 repo（`app/repositories/memory_repository.py`）零影响（新列 NULL）。

## 核心处理流程

`alembic upgrade head` → 扩列/建表/索引 → `get_settings()` 可读取新配置 → v1 服务全部照常运行。

## 与现有模块的关系

- `memory_repository` / `memory_service` / `memory_policy` / `memory_conflict`：零改动。
- `main.py` lifespan：零改动（MEM-009 才接 background_jobs 执行器）。

## 异常与边界情况

- Postgres 无 pgvector 可用（老镜像）→ 迁移显式报错并提示安装（fail-fast，不静默降级建表）。
- downgrade 必须完整删除三表与列，且先删索引再删列。
- 重复执行 upgrade 由 alembic 版本表保证幂等。

## 测试要求

- Unit：迁移 up→down→up 往返，逐表/逐列断言。
- Integration：0022 后跑 v1 全量 pytest，输出零差异。
- Idempotency：升级脚本二次执行安全。

## 验收标准

- 给定 v1 数据库，当 upgrade→downgrade→upgrade，那么 v1 表数据逐行相等且 v1 全量测试通过。
- 给定 settings，当加载，那么全部 v2_memory_* 项存在且 default=false。
- 给定 pgvector 就绪的 Postgres，当查询索引，那么 HNSW 索引存在于 memories.embedding。

## Implementation Constraints

- 不写任何业务逻辑；不改任何既有列语义/类型；不引入独立向量库（version-boundary Preserve 约束）；ORM 新类跟随 `core/db.py` 单文件既有风格，不新建 models 目录。
