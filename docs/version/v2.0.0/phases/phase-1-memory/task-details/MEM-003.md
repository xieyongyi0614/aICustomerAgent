# MEM-003 Task Detail — 候选评估器（Evaluator）

> 上游：[../tasks.md](../tasks.md) MEM-003 ｜ [../../design.md](../../design.md) §5 ｜ 依赖：MEM-002

## Task 目标

实现 `memory2/evaluator.py`：pending 候选经规则打分 → 转正（写入 `memories`）/拒绝/留 pending；仅规则分落灰区时调 lite LLM 一次兜底；显式 remember 直通；决策全量 trace。

## 背景 / 为什么需要

v1 的「评估」分散在两处且都无条件放行：`memory_policy.py` `apply_policy` 只做精确去重（`_is_exact_duplicate` L44）与置信门槛（`memory_min_confidence`，settings L86）；`memory_conflict.py` `resolve_candidate`（L77）用 LCS 判同主题后做 update/invalidate。没有统一的「这条值不值得长期记」判定，v1 什么都被存（v1 审计问题 1 的根源之一）。v2 需要在「候选 → 记忆」之间加一道可控闸，并保证 LLM 只兜规则不确定的灰区（llm-orchestration.md §1 记忆转正行）。

## 设计方案

1. **规则打分**（0~1，各维权重进 settings）：`score = w_s·源权重(user_stated=1.0/user_derived=0.7/ai_inferred=0.4) + w_n·新颖性(1-与既有 active 最高 same_topic 相似度) + w_t·类型亲和(复用 memory_service L218 `_detect_query_types` 同源词表思路) + w_e·事件类显著度`。
2. **三段判定**：`score ≥ high → approve`；`score < low → reject(reason)`；灰区 → LLM 兜底一次。
3. **LLM 兜底 Prompt 输入输出**：输入=候选内容+既有同主题记忆列表；输出=`{approve, type, reason}` 结构化（复用 `build_structured_chain` 风格）；**type 终值由代码映射规则决定，LLM 输出仅作参考**。
4. **显式 remember 直通**：候选 source_kind=explicit_remember → score=1.0 直接 approve，salience=1.0，0 LLM。
5. **转正单事务**：INSERT memories(status=active, salience, source_ref, visibility) + UPDATE candidates.status=approved + trace，一个事务（design.md §7）。
6. **兜底率护栏**：滑动窗口统计 LLM 兜底率，超 `v2_memory_llm_fallback_rate_cap`（0.3）时灰区样本直接留 pending（不调 LLM），记 trace。

## 数据模型 / 接口变化

- 新接口：`memory2/evaluator.evaluate(candidate) -> Decision`（Decision=approve/reject/defer + reason + llm_used）。
- `memories` 行新增携带 salience/visibility/source_ref（列来自 MEM-001）。

## 核心处理流程

```text
pending 候选 → 同主题初检(memory_conflict.same_topic)
 → 规则打分 → [≥high: approve | <low: reject | 灰区→兜底率检查→Lite LLM ×1→approve/reject/defer]
 → approve: 单事务(create_memory + candidate.status=approved + trace)
 → reject/defer: candidates.status / 留 pending + trace
```

## 与现有模块的关系

- 复用（只读）：`memory_conflict.same_topic`、`memory_repository.create_memory`、`trace_collector`。
- 不触碰：`memory_service.extract_and_save`、`memory_policy`（Flag OFF 路径完整保留）。
- 被依赖：MEM-004（新转正记忆进 embedding 队列）、MEM-005（冲突转 lifecycle 链）。

## 异常与边界情况

- LLM 失败/超时/输出不合法 → 候选留 pending，attempts+1；≥5 次转 rejected(reason=llm_failed)。
- DB 失败 → 整个转正事务回滚（不留「半转正」状态）。
- 重复评估同一候选 → 以候选 id 幂等，approved 后再评估直接跳过。
- 兜底率超限 → 灰区降级 defer（成本护栏优先于吞吐）。
- hypothetical 候选 → 只走词表路径，永不调 LLM、永不转正为 normal。

## 测试要求

- Unit：打分权重表驱动；三段阈值边界值；type 映射规则。
- Integration：标注集（偏好/事实/瞬时/假设/错误信息各 20 条，design.md §5 信号表）。
- FailureInjection：LLM 500/超时/坏输出；DB 断连事务回滚。
- Idempotency：同一候选重放两次。

## 验收标准

- 给定显式 remember 候选，当评估，那么 0 次 LLM 转正且 salience=1.0。
- 给定离线标注集，当批量评估，那么 LLM 兜底率 ≤30% 且错误信息类 100% 被拒或 defer。
- 给定 LLM 持续 500，当灰区候选评估，那么 5 次后转 rejected 且无 memories 脏行。
- 给定 Flag OFF，那么本模块完全不执行。

## Implementation Constraints

- LLM 兜底仅灰区且每候选 ≤1 次，禁止前台调用；不改 v1 三个 memory 服务与 extractor 链本体；type 枚举仍用 `models/memory.py` L6 的 4 类 Literal（v2 7 类类型体系在 v2 层扩展，不破坏 v1 Pydantic 校验）；P2+ 反思/发展语义一律不做。

## Implementation Ruling

hypothetical 候选直接 Rejected（不调 LLM、不写 memories）、兜底率窗口只记成功兜底/护栏让位、type 归一化至 v2 规范 7 类：详见 [../decisions.md](../decisions.md) D1/D2/D5。
