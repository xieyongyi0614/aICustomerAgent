## 2. Background

### 2.1 为什么需要这个 Task

`Observe → Reason → Plan → Act → Reflect → Update` 的认知闭环当前**隐式散落在四处**：

| 位置 | 事实 |
|---|---|
| `application/chat_pipeline.run_chat_pipeline` | 前台 22 步硬编码在函数体内 |
| `application/life_loop.run_life_loop_tick` | 后台 tick：工作发现 → `run_autonomous_cycle` → 维护步 |
| `application/agent_runtime/controller.run_autonomous_cycle` | 按 `spec.stages` 顺序执行 + `_autonomous_stage_runner` 名字映射 |
| `application/post_process.run_post_process` | 后处理步骤列表（回写路由） |

结果：阶段顺序没有唯一权威（其实 `profiles.py` 已是权威，但只覆盖后台），**段级**语义（哪一段失败算什么、可选段何时不进）没有落点，段级事件也无人发出。

### 2.2 当前架构问题（architecture §1.2 M1 / §1.3 S2）

| # | 问题 | 证据（当前代码） |
|---|---|---|
| 1 | 循环形状不显式 | `controller.run_autonomous_cycle` 里是 `for name in spec.stages` 的线性循环；前台另有形状 |
| 2 | 阶段与「认知环节」无映射 | `perception` / `state_snapshot` / `decision` 等阶段名与六段环节无对照表 |
| 3 | 段级降级语义未成文 | `run_stage_async(critical=...)` 抛错即整体 aborted；非关键失败只记 `status="error"` |
| 4 | 可选段不可控 | `spec.stages` 是静态元组，Plan / Reflect 无法按预算或配置进出 |

### 2.3 在 V3.0 Runtime 中的位置

RT-006 是 Runtime Core 的**骨架**：它消费 RT-001 契约、RT-002 Session、RT-003 状态、RT-004 上下文、RT-005 事件，并把六段（RT-007 ~ RT-012）作为可插拔实现挂上去。RT-015（前台收编）与 RT-016（后台收编）都只是「换调用方」，循环本体在此定型。

## 3. Scope

### 3.1 In Scope

1. **`AgentLoop`**（`loop.py`）：`observe` / `reason` / `plan` / `act` / `reflect` / `update` 六段方法 + `run()` 驱动。
2. **段执行原语**：`_run_stage(name, phase, coro_factory, critical=...)` —— 计时（`duration_ms`）、异常归一为 `RuntimeFailure`、按 `terminal_status_for` 决定 degraded / aborted、`loop_runs.steps` 落账（复用 `controller.append_step` / `run_stage_async` 语义）。
3. **阶段适配器注册表**：`STAGE_RUNNERS`（既有阶段名 → async callable）+ `STAGE_TO_PHASE`（阶段名 → 六段环节），`fail-closed`（未注册阶段抛 `ValueError`，沿用既有纪律）。
4. **可选段裁决**：`resolve_stages(spec)` —— Plan / Reflect 由 `runtime_loop_optional_stages` + Profile 声明共同裁决（Q4）。
5. **段级事件**：经 RT-005 发 `RunOpened` / `StageCompleted` / `RunClosed`（开关关闭时空操作）。
6. **既有语义保留**：`logical_clock.bind/unbind`、`memory_digest_var` 复位、`agent_state_assembler.reset_run_state`、后台 `get_user_write_lock`、`close_run` 成本汇总全部沿用。

### 3.2 Out of Scope（明确禁止扩张）

- **不实现任何段的业务语义**（Observe/Reason/Plan/Act/Reflect/Update 归 RT-007 ~ RT-012）；本任务段方法只允许调用既有阶段本体或占位。
- 不新增 Run Profile / `run_kind`；不改 `profiles.py` 既有三 Profile 的 `stages` 元组内容。
- 不改 `RunContext` / `loop_runs` 模型与 `close_run` 语义。
- 不做前台收编（RT-015）、不做后台 tick 收编（RT-016）、不改维护步。
- 不改 `chat_pipeline` / `life_loop` / `post_process` 的内部实现。
- 不引入新设置字段（除 `runtime_loop_optional_stages`）与任何 LLM 调用（LLM 仍只在 `decision` / 生成段内，经 LLM Gateway）。

## 4. Technical Design Requirements

### 4.1 循环接口与段映射（`loop.py`）

```python
PHASE_OBSERVE, PHASE_REASON, PHASE_PLAN = "observe", "reason", "plan"
PHASE_ACT, PHASE_REFLECT, PHASE_UPDATE = "act", "reflect", "update"
PHASES: tuple[str, ...] = (PHASE_OBSERVE, PHASE_REASON, PHASE_PLAN,
                           PHASE_ACT, PHASE_REFLECT, PHASE_UPDATE)

STAGE_TO_PHASE: dict[str, str] = {
    "perception": PHASE_OBSERVE,
    "turn_decisions": PHASE_REASON, "mode_stabilize": PHASE_REASON,
    "scene_resolve": PHASE_REASON, "behavior_resolve": PHASE_REASON,
    "goal_check": PHASE_REASON, "goal_stack": PHASE_REASON,
    "goal_supply": PHASE_REASON, "goal_advance": PHASE_REASON,
    "memory_retrieval": PHASE_REASON, "state_update": PHASE_REASON,
    "state_snapshot": PHASE_REASON, "decision": PHASE_REASON,
    "action_planning": PHASE_ACT, "reply_generation": PHASE_ACT,
    "reflection_check": PHASE_REFLECT,
    "record_handoff": PHASE_UPDATE, "world_experience": PHASE_UPDATE,
    "event_pregate": PHASE_UPDATE,
}
OPTIONAL_PHASES: frozenset[str] = frozenset({PHASE_PLAN, PHASE_REFLECT})

def stage_phase(name: str) -> str: ...                    # 未注册阶段 fail-closed
def resolve_stages(spec: ProfileSpec) -> tuple[str, ...]: ...   # 可选段裁决（Q4）

class AgentLoop:
    def __init__(self, spec: ProfileSpec, *, user_id: str | None,
                 run: RunContext, llm=None, now: datetime | None = None,
                 trace=None) -> None: ...

    async def run(self, runtime_input: RuntimeInput | None = None,
                  session_context: SessionContext | None = None, *,
                  runtime_context=None) -> RunResult: ...
    async def observe(self) -> object | None: ...
    async def reason(self, observation) -> object | None: ...
    async def plan(self, intention) -> object | None: ...
    async def act(self, intention, plan=None) -> object | None: ...
    async def reflect(self, action_result=None) -> list | None: ...
    async def update(self, action_result=None, insights=None) -> object | None: ...
```

**段方法在 RT-006 内只做委派**：调用 `STAGE_RUNNERS` 中的既有阶段本体（语义同 `controller.run_stage_async`）；RT-007 ~ RT-012 再把各段替换为显式实现。段方法返回 `object | None`，具体类型由各段 Task 收窄（对齐 RT-001 裁决 A3）。

### 4.2 段执行语义

- **计时与落账**：每段记 `duration_ms` 并 `append_step`（`loop_runs.steps`，口径与既有 `_record_step_async` 一致）。
- **异常归一**：段异常 → `RuntimeFailure(kind=..., stage=name, recoverable=name not in spec.critical)` → `terminal_status_for()` 决定降级或中断。
- **降级传播**：recoverable 失败置 Run = `degraded` 且继续；`critical` 段失败 → 抛错由调用方收口为 `aborted`（沿用既有 `run_autonomous_cycle` 的 try/except 形状）。
- **可选段**：`resolve_stages` 过滤 `OPTIONAL_PHASES`；未启用时不执行、不记 error、不消耗预算。
- **事件**：`RunOpened`（开始）/ `StageCompleted`（每段）/ `RunClosed`（收口），经 RT-005 发出；开关关闭时零副作用。

### 4.3 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | 六段是**环节**、既有阶段名是**实现**；`STAGE_TO_PHASE` 显式映射（一环节可含多阶段） | 不重命名既有阶段 → 零回归，同时获得六段视角（architecture §2.1） |
| D2 | `profiles.py` 仍是段序列**唯一声明处**；`loop.py` 不得内联段序列 | V2.1 红线「无第二套 Agent Pipeline」 |
| D3 | 未注册阶段 `fail-closed` 抛 `ValueError` | 沿用既有 `_autonomous_stage_runner` 纪律，注册表与实现不一致必须暴露 |
| D4 | 前台不加 per-user 写锁、后台保留 `get_user_write_lock` | 沿用既有并发语义，本任务不改锁策略 |
| D5 | 本任务**不切换生产路径**：`run()` 供测试与后续 RT-015 / RT-016 调用 | 循环先可驱动再收编，避免中间态双跑 |
| D6 | 段方法只委派、不承载业务；类型收窄归各段 Task | 防止 RT-006 变成「大杂烩」 |

### 4.4 依赖

- 允许依赖：`profiles` / `contracts`（RT-001）/ `events`（RT-005）/ `controller`（`run_stage_async` / `append_step` / `close_run`）/ `logical_clock` / `life_loop_budget` / `post_process.get_user_write_lock` / `app.core.settings`。
- **禁止**依赖：`app.repositories`（写面经既有 controller / 仓储）、`app.chains`、`app.prompts`、具体渠道实现。
