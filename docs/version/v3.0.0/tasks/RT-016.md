## 2. Background

### 2.1 为什么需要这个 Task

后台自治有**两套节奏**：`run_life_loop_worker`（常驻，先 sleep 后 tick）+ `run_life_loop_tick`（工作发现 → 逐用户 `run_autonomous_cycle` → `run_event_pregate` → `_run_maintenance`）。其中 per-user 周期由 `controller.run_autonomous_cycle` 按 `profiles.py` 的 11 段顺序执行（`_autonomous_stage_runner` 名字映射）。

RT-006 建好了显式六段循环，RT-015 已在前台完成收编；后台仍是旧的线性执行体 —— 这就是 M1 残留的最后一半。

### 2.2 当前架构问题

| # | 问题 | 影响 |
|---|---|---|
| M1 | 后台独享线性执行体 | 前后台形状不同，循环能力（段级事件 / RunResult）后台拿不到 |
| — | 阶段映射与循环映射两处 | `_autonomous_stage_runner` 与 `STAGE_TO_PHASE` 需保持同步 |
| — | tick 编排与循环编排混在 `life_loop` | 调度（何时跑）与循环（跑什么）耦合 |

### 2.3 在 V3.0 Runtime 中的位置

本任务把「何时跑、跑什么、跑多少」中的**跑什么**交给 `AgentLoop`（autonomous Profile），**何时跑 / 跑多少**留在调度器（tick + 工作发现 + 维护步）。这是 architecture §2.2「Session 包裹 Run，Run 内驱动循环」在后台的落点。

## 3. Scope

### 3.1 In Scope

1. **循环驱动切换**：`run_autonomous_cycle` 内部改为 `AgentLoop(spec=autonomous_tick, …).run(runtime_input=None, …)`；对外签名与返回（`str` 终态）不变。
2. **阶段映射统一**：`_autonomous_stage_runner` 的 11 个阶段全部纳入 `STAGE_TO_PHASE`（RT-006 已含），循环成为唯一执行形状。
3. **调度保留**：tick 节拍、`_collect_work_users` 工作发现、idle 短路（无 due 工作时 **0 LLM / 0 Run 行**）、`_run_maintenance` 维护步清单与间隔语义**完全保留**。
4. **预算三闸**：`check_daily_budget` → `_cycle_llm_budget_exhausted` → `llm_gateway.acquire`（`decision` 阶段）逐级生效；超预算跳过并记 degraded。
5. **开关门控**：`runtime_autonomous_cycle_enabled` 默认 `False`（走既有 `run_autonomous_cycle` 执行体）；开启后走 `AgentLoop`。两条路径行为必须逐字段等价。
6. **事件**：后台 Run 同样发 `RunOpened` / `StageCompleted` / `RunClosed`（RT-005，开关关闭时空操作）。

### 3.2 Out of Scope（明确禁止扩张）

- 不改自治决策数学（`autonomy_policy` / `trigger_evaluator` / `decision_pipeline`）与 `decision` 阶段的 LLM 语义。
- 不新增自治行为类型、不改 `life_loop_storm_daily_limit` / cooldown / idle 判定。
- 不改 `_run_maintenance` 的维护步清单与间隔（world_maintenance / world_simulation / action_retry / action_schedule / outbox_consume / trigger_reconcile）。
- 不改 `run_event_pregate` 的白名单预闸语义（保留既有实现，只在其内部走循环）。
- 不新增常驻 worker / 表 / 列 / 迁移。
- 不做「世界自治时钟产事件」（V2.3 既有能力，Non-Goal）。

## 4. Technical Design Requirements

### 4.1 接口契约（`controller.py` 收编 + `loop.py` 复用）

```python
# 对外签名不变（life_loop / 测试均按此调用）
async def run_autonomous_cycle(user_id: str, llm=None, now=None,
                               trigger_type: str | None = None,
                               reason: str | None = None) -> str: ...

# 内部形状（开关开）：open_run → AgentLoop(spec=autonomous_tick).run() → close_run
def legacy_cycle_runnable() -> Callable[..., Awaitable[str]]: ...  # 开关关的既有执行体（保留）
```

### 4.2 调度与循环的分工

| 职责 | 归属 | 保留内容（零改动） |
|---|---|---|
| 何时跑（节拍） | `run_life_loop_worker` / `life_loop_tick_seconds` | 先 sleep 后 tick |
| 跑不跑（工作发现） | `_collect_work_users` / `_due_trigger_present` / `_goal_work_due` / `_inactivity_eligible` / `_goal_catchup_due` | 判据与顺序 |
| 空转短路 | idle 分支 | 0 LLM / 0 Run 行 / 仅时钟检查 |
| 事件预闸 | `run_event_pregate`（白名单升级） | 0 消耗语义 |
| 维护步 | `_run_maintenance` + `_maintenance_due` / `_mark_maintenance` | 六类清单与间隔 |
| 跑什么（循环形状） | autonomous_tick 11 段 → `AgentLoop` | 段序列与 `critical` |
| 跑多少（预算） | `check_daily_budget` → `_cycle_llm_budget_exhausted` → `llm_gateway.acquire` | 三道闸逐级 |

### 4.3 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | 收编**只换执行形状**：11 个阶段本体（`_step_perception` … `_step_world_experience`）零改动，仍经 `STAGE_RUNNERS` 调用 | 循环等价可证；决策语义 Preserve |
| D2 | 开关默认关：关闭走既有执行体；开启走 `AgentLoop`，两者**逐字段等价**（steps 键集 / 终态 / budget_state） | 灰度安全，可回退 |
| D3 | 三道闸在两条路径**同时存在**（legacy 保留；循环路径内嵌同序） | 预算语义唯一，不因路径分裂 |
| D4 | `run_event_pregate` 的升级 Run 仍调 `run_autonomous_cycle`（经同一开关分派） | 预闸语义不变，入口统一 |
| D5 | 前台不加写锁、后台保留 `get_user_write_lock`（与 RT-006 D4 一致） | 并发语义零变化 |
| D6 | 不新增维护步 / 不改间隔；孤儿扫描挂载属 RT-018 | 维护面零扩张 |

### 4.4 依赖

- 允许：`loop`（RT-006）、`profiles`、`controller`（open/close / 阶段 runners）、`life_loop`（调度与工作发现）、`life_loop_budget`、`llm_gateway`、`logical_clock`、`post_process.get_user_write_lock`、`events`（RT-005）。
- 禁止：`app.chains` / `app.prompts` 直调、`autonomy_policy` / `trigger_evaluator` 内部改动、写仓储直调、具体渠道实现。
