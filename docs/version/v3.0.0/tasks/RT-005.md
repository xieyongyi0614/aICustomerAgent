## 2. Background

### 2.1 为什么需要这个 Task

当前模块间通信有三种形态并存，但**没有统一语义**：

| 形态 | 现状 | 语义缺失点 |
|---|---|---|
| 函数直调 | `post_process` 步骤互不感知、`action_engine` 直调桥接 | 何时该直调、何时该发事件无规则 |
| Outbox（事务投递） | `outbox_events` + `outbox_consumer` | 只解决**跨域延迟可靠投递**，不解决同 Run 内通知 |
| 世界广播 | `world_events` | 只服务世界域对外广播 |

「ActionCompleted → 记忆摄取 / 关系桥 / 决策面」这类**编排订阅**目前散落在 `post_process` 与 `action_engine` 的调用顺序里，既不可观测也不可枚举——这正是 architecture §1.2 的 M2。

### 2.2 当前架构问题

| # | 问题 | 证据 |
|---|---|---|
| M2 | 模块通信语义缺位 | 直调与 Outbox 混用，无「同步事件」一等概念 |
| — | 生命周期无通知 | Run 开/关只有台账行，无同进程可订阅的钩子（RT-019 需要它做段级 Trace） |
| — | 订阅关系不可枚举 | 谁消费 `ActionCompleted` 无法从代码回答（只在 `post_process` 步骤列表里隐含） |

### 2.3 在 V3.0 Runtime 中的位置

Event System 是四个运行时组件中唯一的**通信层**（architecture §3.4）：RT-006 用它发段级 / 生命周期事件；RT-012 用 `ActionCompleted` 订阅做回写路由；RT-017 用触发 / 投递事件；RT-019 消费事件做 Trace 与因果链（`correlation_id`）。

**边界铁律**：总线是**进程内同步层**，**不替换** `outbox_events`（事务内可靠投递）与 `world_events`（世界广播），也**不引入** Event Sourcing / MQ（architecture §3.4 裁决 + §0.3 Non-Goal）。

## 3. Scope

### 3.1 In Scope

1. **总线**（`events.py`）：`subscribe` / `unsubscribe` / `clear_subscribers` / `handler_count` / `subscribers` / `emit`。
2. **便利构造器**（薄、零业务逻辑）：`emit_run_opened` / `emit_stage_completed` / `emit_run_closed`。
3. **投递语义**：同步派发、注册顺序确定、订阅幂等、单订阅者失败隔离、`emit` 返回成功投递数。
4. **Trace 接线**：`emit(event, trace=session)` 把事件作为一步写入既有 `TurnTraceSession`（`services.trace_collector`），携带 `event_type` / `run_id` / `correlation_id`。
5. **开关**：`runtime_event_bus_enabled`（默认 `False`）；关闭时 `emit` 立即返回 0（零派发、零 Trace）。
6. **事件常量复用**：`EVENT_*` / `EVENT_TYPES` 由 RT-001 的 `contracts.py` 提供，本模块**不重复定义**。

### 3.2 Out of Scope（明确禁止扩张）

- **不持久化事件**：零新表、零列、零迁移；事件只落 Trace（内存 → 既有 `runtime_traces.events` 链路）。
- **不引入** MQ / Redis / Kafka / Event Sourcing / 异步队列 / 重试队列。
- 不替换、不改造 `outbox_events`（含 `outbox_consumer`）与 `world_events`；总线不得写二者。
- **不接线域订阅**：记忆摄取 / 关系桥 / 决策面的 `ActionCompleted` 订阅属 RT-012；触发与投递事件属 RT-017。本任务只交付机制 + 测试内订阅者。
- 不做装饰器自动扫描 / 配置化订阅（Q2 裁决：代码静态注册）。
- 不做跨进程 / 跨线程通知；不承诺进程重启后的事件重放。
- 不实现事件回放引擎（RT-019 的只读取材面）。

## 4. Technical Design Requirements

### 4.1 接口契约（`events.py`）

```python
Handler = Callable[[RuntimeEvent], None]

def subscribe(event_type: str, handler: Handler) -> None:
    """代码静态注册；同 (event_type, handler) 重复注册幂等；未知 event_type 抛 ValueError。"""

def unsubscribe(event_type: str, handler: Handler) -> bool: ...
def clear_subscribers() -> None: ...                      # 测试助手
def handler_count(event_type: str) -> int: ...
def subscribers(event_type: str) -> tuple[Handler, ...]: ...   # 只读快照（注册顺序）

def emit(event: RuntimeEvent, trace=None) -> int:
    """同步派发；开关关 → 立即返回 0；返回成功投递数（失败订阅者不计入）。"""

# 薄构造器（零业务逻辑，供 RT-006 / RT-017 复用）
def emit_run_opened(run_id: str, session_id: str | None, trace=None) -> int: ...
def emit_stage_completed(run_id: str, session_id: str | None, stage: str, *,
                         duration_ms: float, status: str = "ok",
                         correlation_id: str | None = None,
                         payload: Mapping[str, Any] | None = None,
                         trace=None) -> int: ...
def emit_run_closed(run_id: str, session_id: str | None, status: str,
                    trace=None) -> int: ...
```

### 4.2 与既有设施边界（**不得越界**）

| 能力 | 归属 | 本任务是否触碰 |
|---|---|---|
| 事务内可靠投递 | `outbox_events` + `outbox_consumer`（既有） | **否**（零改动、零写入） |
| 世界事件广播 | `world_events`（既有） | **否** |
| 行为台账 | `loop_runs`（Run 唯一写面） | **否** |
| 段级 / 生命周期足迹 | `runtime_traces`（既有，经 `TurnTraceSession` / `observability`） | 只**追加 Trace step**（内存），落库仍由既有链路完成 |
| 进程内同步事件 | **本任务** | 是 |

### 4.3 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | 事件常量与值对象归 `contracts.py`（RT-001），总线只做派发 | 契约与机制分离；避免两处定义事件名 |
| D2 | **同步派发、无队列、无重试**：`emit` 内联调用全部订阅者 | architecture §3.4：进程内同步通信；可靠投递归 Outbox |
| D3 | 订阅为**代码静态注册**（Q2）；未知 `event_type` 直接 `ValueError` | 早失败优于静默丢事件；避免过度配置化 |
| D4 | **订阅者失败隔离**：单订阅者抛异常 → 记日志 + Trace step（`status="error"`），继续派发其余订阅者，`emit` 不外抛 | 对齐既有「后处理失败不得影响已产出回答」纪律 |
| D5 | **零写入**：`events.py` 不 import 任何 repository / 不碰 DB | architecture 附：边界不变量 5（Event System 只做进程内同步通信） |
| D6 | handler 契约：同步、非阻塞（毫秒级）、不得写业务表、不得抛异常（抛了也被隔离）；重活由调用方在 emit 之后自行编排 | 保持循环时序可预测；避免事件总线变成隐式后台执行器 |
| D7 | 注册表变更用 `threading.Lock` 保护；派发遍历**不可变快照**（`tuple`） | 允许从线程池侧注册（如 world 维护）而不破坏派发顺序与一致性；不引入 async 复杂度 |

### 4.4 数据流

```text
RT-006 Agent Loop
   → emit_run_opened(run_id, session_id, trace)
   → emit_stage_completed(run_id, session_id, "observe", duration_ms=…, trace=trace)
        ↓
   EventBus.emit(event, trace)
        ├── 开关关？ → return 0（零副作用）
        ├── trace 非空 → trace.record("runtime_event", 0.0, event_type=…, run_id=…, correlation_id=…)
        └── for handler in subscribers(event.event_type)（注册顺序）
                try: handler(event)  → delivered += 1
                except Exception: 记日志 + trace.record(..., status="error")
   → return delivered

RT-012（后续）在自身模块 import 时 subscribe(EVENT_ACTION_COMPLETED, 记忆摄取/关系桥/决策面)
```

### 4.5 依赖

- 允许依赖：标准库（`logging` / `threading` / `collections.abc`）、`app.application.agent_runtime.contracts`、`app.core.settings`、`app.services.trace_collector`（仅 `record` 调用）。

## 5. Implementation Plan

1. **创建模块** `app/application/agent_runtime/events.py`：`Handler` 类型别名 + 模块级 `_SUBSCRIBERS: dict[str, list[Handler]]` + `threading.Lock`。
2. **实现注册面**：`subscribe`（校验 `event_type in EVENT_TYPES`、幂等去重）/ `unsubscribe` / `clear_subscribers` / `handler_count` / `subscribers`（返回 `tuple(...)` 快照）。
3. **实现派发面**：`emit`（开关判断 → Trace 记录 → 快照遍历 → 逐 handler 隔离 + 计数）+ 三个薄构造器（用 `RuntimeEvent` 组装，`occurred_at=datetime.now()`）。

5. **编写测试** `tests/v30/test_runtime_event_bus.py`（§7）：含 `autouse` 的 `clear_subscribers()` 清理，避免测试间订阅泄漏。
6. **逐级执行**：Focused → Module → Fast。
7. **提交**（§9）。
