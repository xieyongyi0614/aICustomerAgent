## 2. Background

### 2.1 为什么需要这个 Task

前台 22 步（`run_chat_pipeline`）是**唯一在跑真实流量**的编排路径，它内部硬编码了阶段顺序与降级策略；后台走 `profiles.py` + `run_autonomous_cycle`。两套形状并存正是 M1「编排路径分裂残留」——认知循环没有唯一权威。

RT-006 ~ RT-014 已把循环、六段与出入站网关建好，但**没有任何生产路径使用循环**（RT-006 明确「不切换生产路径」）。本任务完成切换。

### 2.2 当前架构问题

| # | 问题 | 影响 |
|---|---|---|
| M1 | 两套编排形状 | 前台改动无法自动受益于循环能力（段级降级 / 事件 / TurnResult） |
| — | 阶段顺序两处维护 | 前台 22 步在函数体内，后台在 Profile 中 |
| — | 双入口残留 | `agent_service.stream_chat` 兼容壳（baseline §9 P2 技术债）与新 Run 入口并存 |

### 2.3 在 V3.0 Runtime 中的位置

RT-015 是「前后台统一」的落点：收编后 `foreground_chat` 与 `autonomous_tick` 共用 `AgentLoop`，差异只在 Profile（段组成 / 预算档 / 候选构成）。它同时是 RT-016（后台收编）的前置——先在前台验证循环等价性，再收编后台。

**风险定位**：这是本版本**唯一触碰真实流量**的任务，必须以「逐字段等价 + 全量回归」为验收底线。

## 3. Scope

### 3.1 In Scope

1. **段序列收编**：`foreground_chat` Profile 的 `stages` 与六段循环对齐（Observe → Reason〔`turn_decisions` / `mode_stabilize` / `scene_resolve` / `behavior_resolve`〕→ Act〔`action_planning` / `reply_generation`〕→ Update〔`record_handoff`〕）。
2. **`chat_pipeline` 薄壳化**：`run_chat_pipeline(...)` 保留为**对外签名不变**的入口，内部改为驱动 `AgentLoop.run(...)`。
3. **流式契约冻结**：`turn_meta` 键集与顺序、token 流、`done` 字段、错误 → HTTP 映射**零变化**。
4. **上下文与状态接入**：前台 Run 开始处调用 RT-004 `assemble` 与 RT-003 `activate`（受各自开关控制，默认关 → 沿用既有装配）。
5. **兼容壳处置**：枚举 `agent_service.stream_chat` 调用点，登记去向（直连 `chat_pipeline` 或 Run 入口）；壳是否退役需显式记录，**不得静默保留双入口**。
6. **零回归保障**：22 步内部业务实现逐字节保留（只改「调用方与顺序声明」）。

### 3.2 Out of Scope（明确禁止扩张）

- 不改 22 步内部业务实现、不改提示词与 `PromptBuilder`、不改 golden 快照期望。
- 不改前端控制台、不改 `api/v1/chat.py` 的 SSE 装配与错误映射。
- 不收编后台（RT-016）；不改维护步。
- 不删除 `agent_service`（除非调用点全部迁移完毕且登记完成；退役属本任务可选动作，需显式说明）。
- 不新增设置字段；不改 `loop_runs` 模型；不改出入站契约。

## 4. Technical Design Requirements

### 4.1 收编入口（对外签名不变）

```python
async def run_chat_pipeline(
    session_id: str, user_id: str, content: str, *,
    llm=None, trace=None,
    runtime_input: RuntimeInput | None = None,        # 由 RT-013 Gateway 提供（可空）
    session_context: SessionContext | None = None,    # 由 RT-013 Gateway 提供（可空）
) -> AsyncIterator[dict]: ...
```

内部形状：`open_foreground_run(user_id, session_id=…)` → `AgentLoop(spec=profiles.get_profile("foreground_chat"), run=…, llm=llm, trace=trace)` → `loop.run(runtime_input, session_context)`；流式产出仍经既有 yield 协议（`turn_meta` / token / `done`），**键集与顺序不变**。

### 4.2 前台六段映射（段本体全部保留）

| 环节 | 既有阶段（本体不动） |
|---|---|
| Observe | `perception` |
| Reason | `turn_decisions` → `mode_stabilize` → `scene_resolve` → `behavior_resolve` |
| Act | `action_planning`（行动意图检测 / 行动规划） → `reply_generation`（流式回答，critical） |
| Update | `record_handoff`（`conversation_service.save_turn` + `schedule_post_process`） |
| Plan / Reflect | **前台默认不启用**（`optional_stages` 为空） |

### 4.3 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | 对外签名与流式契约**零变化**：`turn_meta` 键集与顺序、token 流、`done` 字段、错误映射逐字段一致 | 前端与飞书解析不动；唯一真实流量路径不容契约漂移 |
| D2 | 22 步**本体实现零改动**：只改「调用方与顺序声明」（改由 Profile 声明） | 降低回归面；业务语义保持 Preserve |
| D3 | 前台不加 per-user 写锁（沿用既有并发语义）；`logical_clock` / `memory_digest` / `reset_run_state` 收尾逻辑由循环统一执行 | 行为等价 + 资源清理不漏 |
| D4 | RT-003 / RT-004 的开关默认关 → 收编后前台装配与 V2.6.1 逐字段等价；开启才获得冻结与版本视图 | 收编与能力开启解耦，便于定位回归 |
| D5 | 兼容壳**显式登记**：枚举 `services/agent_service.stream_chat` 调用点（已知：`api/v1/chat.py`、`channels/feishu/adapter.py`）与其去向；退役需在验收报告登记 | baseline §9 P2 债不得静默保留 |
| D6 | 若等价性无法在整批证明 → 允许**按渠道灰度**（飞书先切、Web 后切），与 RT-013 的 csv 开关一致 | 提供退路，避免一次切换阻塞版本 |

### 4.4 依赖

- 允许：`loop`（RT-006）、`session` / `state` / `context` / `events`（RT-002 ~ RT-005）、`stages/*`（RT-007 ~ RT-012）、`profiles`、既有 22 步本体（`context_builder` / `mode_service` / `scene_service` / `behavior_engine` / `answer_chain` / `conversation_service` / `post_process`）。
- 禁止：改写步骤本体、`prompts/**`、`api/v1/chat.py` 的 SSE 装配、`channels/feishu` 内部实现。

## 5. Implementation Plan

1. 冻结验收基线：先跑 `tests/e2e -m "not slow"` + `tests/golden` 并存档当前结果（作为等价对照）。
2. 在 `profiles.py` 校准 `foreground_chat` 的段序列与六段映射一致（不新增阶段名）。

6. 回归：Focused（`tests/v30`）→ Module（`tests/e2e`）→ golden → Fast；逐项与步骤 1 基线对照。
7. 提交（§9）。
