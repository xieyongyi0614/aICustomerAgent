## 0. 结论先行

1. **需求可做，但不是「照着原型写 UI」。** 原型里最核心的两个体验——**Tool Call 过程卡**（步骤逐项打勾）与**首页 AI 总结**——在后端**没有任何接口来源**，必须先补 API 才能动客户端。§3 缺口 2 / 缺口 11 是硬阻塞。
2. **三份材料对「健康 / 手环」的排期互相矛盾**（设计稿 §07 把它列为「可以延后 V2」，但调研报告 Phase 1 就做、原型首页又把它当首屏证据）。**必须先裁决**，否则影响首页信息架构定型。见 §3 冲突 1。
3. **App 化有三个硬前置**：① 身份与鉴权（当前 API 强制单用户，客户端传 `user_id` 直接 403）；② 推送通道（「08:00 早间简报」是系统级推送语义，现有真实出口只有飞书）；③ **隐私文案与存储架构必须对齐**（原型写「全部本地可见 / 本地优先」，而实际是服务端 PG 存储）。
4. **原型视觉规范里有 4 处无法 1:1 平移**（渐变描边、`mix-blend-mode`、PingFang 字体、等宽数字），需在 Flutter 侧给出替代实现，见 `flutter-architecture.md` §5。
5. **需求可拆为 41 个任务 / 5 个里程碑**，关键路径 = 身份鉴权 → 工具步骤事件 → 设计系统 → 首页装配。见 `tasks.md` §8。
6. **设计稿自身有 4 处色值三方不一致**（`:root` vs §06 色卡 vs 原型），**必须定稿后再开工设计系统**，否则改色会波及全部视觉回归测试。见 §3 冲突 14。
7. **命名歧义已处置**：设计稿用 `V1~V4` 表示**产品阶段**，与仓库版本号（`V4.0.0`）撞车 → 设计稿路线改称**「产品阶段 P1~P4」**（决策 D10）。
8. **11 条决策已全部拍定**（§6，无"待拍板"项）。**设计稿 119 条要求已逐条核对**：82 条直接覆盖、17 条有条件覆盖、7 条明确不做、15 条为设计意图；核对中新发现 5 个遗漏缺口并已全部处置。见 `traceability.md`。

## 1. 产品定位与需求主线（复述，用于对齐）

**一句话**：朝夕不是聊天 / 记账 / 健康工具的集合，而是**一个有长期记忆的 AI 生命助手**，最终形态是用户的 Personal AI OS。

**设计原则（5 条，作为验收时判断「像不像」的标准）**：

| 原则 | 含义 | 可验收形式 |
|---|---|---|
| AI 叙事优先 | 每个页面先讲「AI 帮你理解了什么」，再展示原始数据 | 每页首屏必须存在一个 AI 结论块，且位于原始数据之前 |
| 卡片即结论 | 一卡 = 一个 AI 结论 + 最少支撑数据；拒绝 Dashboard 表格堆叠 | 无「纯表格页」；每个数据卡有结论文案 |
| 记忆可见 | AI 记住了什么、为什么记住，对用户永远透明 | 每条记忆有来源追溯 + 用途回执；可编辑 / 可遗忘 |
| 主动但克制 | 主动出现有固定节奏与关闭开关 | 三个主动开关（早间 / 晚间 / 异常）默认可见可关 |
| 温暖而非企业 | 圆角 18–24、暖纸白底、柔和投影 | 无冷灰蓝、无密集边框、无后台式表格 |

**视觉基因配比**：Apple Health 60%（安静与品质）× ChatGPT 20%（对话直觉）× Notion 10%（结构）× SAO 10%（科技感，**只允许出现在 AI 核心球与工具调用瞬间**）。

**AI 角色裁决（沿用设计稿方案 A）**：AI 核心球 The Orb 作为本体视觉，四态语义：

| 状态 | 动效 | 色彩 | 出现位置 |
|---|---|---|---|
| 待机 / 陪伴 | 缓慢呼吸 4.2s | 蓝紫渐变 | 首页英雄区、对话头像 |
| 思考 / 执行 | 旋转加速 + 色相流动 | conic 渐变 | 配合 Tool Call 过程卡 |
| 主动关怀 | 转暖橙轻脉冲 | 暖橙 | 早间简报、异常提醒 |
| 完成 / 成长 | 绿色一次绽放 | 青绿 | 任务完成、记忆新增、关系升级 |

> **演进路线（设计稿）**：V1 抽象 Orb → V2 光晕表情（微波纹 = 情绪）→ V3 可选 3D 虚拟形象（Live2D / 3D Avatar）作为人格皮肤，Orb 退居状态指示器。
> ⚠️ 本产品不支持 3D 模型 / 视频生成类能力；V3 的 3D 形象若要做，属**外部资产引入**（美术产出 Live2D 模型后由 Flutter 渲染），需单独立项评估，不在本版本范围。

## 3. 冲突与缺口清单（14 条，按阻塞程度排序）

> 每条给出：**现象 → 证据 → 后果 → 建议裁决**。带 🚫 的是**开工前必须裁决**项。

### 🚫 冲突 1：三份材料对「健康 / 手环」的排期互相矛盾

- **现象**：设计稿 §07「必须开发（V1）」**不含**健康；§08 Roadmap 把手环接入放 **V2**。但原型 `#home` 首屏就写「来自小米手环 9 Pro」+ 三宫格指标，`#profile` 有「设备连接 · 小米手环 9 Pro」，`#life` 有「健康」模块；调研报告 Phase 1（4–6 周）就把**健康事实域 + 只读管家**做进来。
- **证据**：`design/ai-life-agent-design.html:412-416`（MVP 三分栏）、`:429-432`（Roadmap）、`ai-life-agent-prototype.html:336,646,500`、`REPORT.md:170`。
- **后果**：首页信息架构无法定型——健康三宫格占首屏黄金位，是 V1 就做（需新建健康域）还是先占位（需明确的空态设计），直接决定任务量与工期。
- **建议裁决**：**采纳调研报告口径**——V1 只做「健康事实域 + 只读展示」，不做异常主动提醒与评分算法；首页三宫格在 V1 用真实数据。理由：调研已确认 Health Connect / HealthKit 是合规主路径，且**该路径有一项未闭合的实机验证**（Mi Fitness 国内版是否原生写入系统健康平台），需尽早暴露风险。若你希望 App 先快出，则 V1 三宫格走「空态 + 引导授权」，健康页整体后移。

### 🚫 缺口 2：Tool Call 可视化没有后端事件来源（**最大技术缺口**）

- **现象**：设计要求「步骤逐项打勾、当前步旋转、未来步灰显、结果落点明示」，原型 `#chat`（旅行规划 4 步）与 `#chatLedger`（记账 4 步）以此为**核心体验**，设计稿 §04++ 明确写「可见 = 可控 = 信任」。
- **证据**：`apps/backend/app/api/v1/chat.py` 的 NDJSON 仅 3 类事件；工具执行过程只有 `GET /debug/tools/executions`（事后查询、debug 命名空间）。
- **后果**：客户端**无法**渲染过程卡；只能事后补一个「已完成」的结果卡，产品核心差异化体验直接丢失。
- **建议裁决**：新增流式工具步骤事件（如 `tool_step`：`{step_id, tool_id, label, status: running|done|failed, detail, target}`）。⚠️ **两条仓库铁律必须遵守**：① 新事件类型须登记 `tests/v30/runtime_contracts.py::EXPECTED_EVENT_TYPES`（未知类型 fail-closed）；② `test_agent_loop_core.py` 断言 loop 与 legacy 的 `loop_runs.steps` **键集完全相同**，故**不得**在产线侧加键——事件须走独立通道而非塞进 `steps`。

### 🚫 冲突 5：「本地优先」文案 vs 服务端存储架构

- **现象**：原型 `#memory` 隐私承诺写「记忆是你的资产：**全部本地可见**、可逐条编辑或遗忘」；`#profile` 隐私设置写「**本地优先** · 一键清空 · 导出数据」。而实际架构是 FastAPI + PostgreSQL 服务端存储，`/life/export`、`/life/data` 是**服务端**治理端点。
- **证据**：`ai-life-agent-prototype.html:618,660`；`apps/backend/app/api/v1/governance.py`。
- **后果**：**这是合规风险，不只是文案问题**。健康信息属 PIPL 敏感个人信息，需单独同意；「本地优先」若被理解为「数据不出设备」而实际上传服务端，属误导性陈述。App Store 与国内安卓商店审核均会关注。
- **建议裁决**：二选一并**同时改文案**：
  - **方案 A（推荐，改动小）**：服务端存储，文案改为「你的数据只属于你：可随时查看、导出、删除；未经你授权，健康数据不会上传」——强调**用户控制权**而非物理位置。
  - **方案 B**：真本地优先（本地库 + 可选云同步），成本高，且与现有服务端 AI 能力（跨域合成需要服务端数据）冲突，不推荐在 V1 做。

### 🚫 冲突 7：身份与鉴权缺位（App 化的硬前置）

- **现象**：`_current_user()` 逻辑：客户端传 `user_id` 且不等于 `default_user` → **403「不得读写他人数据」**；传 `None` → 落到 `resolve_user(None)` = `default_user`。V4.0.0 裁决 7 明确「本版本不做注册 / 登录 / 鉴权」。
- **证据**：`apps/backend/app/api/v1/ledger.py:141-149`；`docs/version/v4.0.0/tasks.md` §0.7。
- **后果**：桌面/局域网阶段无所谓；**一旦 App 装到真机、连公网，等于把账本与记忆敞开**。
- **建议裁决**：V1 引入**设备绑定 + 长期令牌**（首次扫码/配对换取 token，存 `flutter_secure_storage`），服务端新增鉴权依赖，把 `user_id` 从「请求参数」改为「从 token 解析」。这是**纯新增**，不动既有域行为，符合 V4.0.0「加实体、不加约束」的兼容策略。

### 🚫 冲突 8：主动关怀的推送通道

- **现象**：原型 `#profile` 有三个开关：早间简报（08:00）、晚间总结（21:30）、状态异常提醒；`#briefing` 是一个**独立的深色全屏页**，语义是「推送点进来看到的落地页」。但现有 `proactive/pending` + `ack` 是**拉取式**，真实投递出口只有飞书。
- **后果**：V1 若不做推送，早间简报只能在用户主动打开 App 时出现，「主动但克制」的核心卖点退化为「App 内一个入口」。
- **建议裁决**：V1 做**本地通知**（`flutter_local_notifications`，按用户设定时刻本地触发，服务端预生成简报内容）+ App 内红点；**服务端推送（FCM/APNs 或国内厂商通道）列 V1.1**。理由：本地通知零基础设施成本、零合规增量，且能完整表达「固定节奏 + 可关闭」的设计意图。

### 🚫 冲突 4：「128 条记忆」与后端记忆容量模型不一致

- **现象**：原型记忆页显示「128 条 · 本周 +6」，隐私卡写「一键清空」；每条记忆有「遗忘」操作。
- **证据**：记忆域单用户 active **软上限 200 条**，超出走 `capacity_drop` 丢弃；且有 `salience · exp(-λ·Δdays)` 衰减与 `decayed` / `forgotten` 生命周期（V4.0.0 裁决 2 的对照表已列明）。
- **后果**：「128 条」是 active 数还是历史累计数？「遗忘」是置 `forgotten` 还是硬删？「本周 +6」按什么统计？**不定义清楚，产品承诺会与引擎行为打架**（例如用户看到「遗忘」后刷新又出现）。
- **建议裁决**：记忆页只展示 **active 且未 forgotten** 的条目，标题写「我记住了你 N 件事」（不暴露 200 上限）；「遗忘」= 置 `forgotten`（可审计、不可见于列表）；「一键清空」= 走 `/life/data` 服务端删除。**上限与衰减机制不向用户暴露**。

### 🚫 冲突 6：首页「今日任务 · AI 已排序」缺实体

- **现象**：原型首页任务行有三类属性：完成勾选、「14:30 提醒」（时间提醒）、「晚间」（AI 排序标签）、「已完成」；副文案还带 AI 生成内容（「亚丝娜已拟好草稿，确认即可发送」「上次通话是 9 天前」）。
- **证据**：后端有 `services/planning/` + Goal Stack，但只有 `GET /debug/plans`；**无面向用户的任务实体**。
- **后果**：任务行无法落库，勾选状态无处保存，提醒无处注册。
- **建议裁决**：**新建轻量任务域**（`life_tasks`），不复用 plan step（plan 是 Agent 内部推理结构，语义与生命周期都不匹配；V4.0.0 裁决 5 也禁止写计划表之外的既有业务表，新增须走新领域）。任务排序的「AI 已排序」由服务端在首页聚合接口里给出 `order_reason` 文案，客户端只渲染。

### 缺口 3：记忆页「来源追溯 / 用途回执」只有 debug 接口

- **现象**：原型每条记忆下方写「来源：6 次对话提及 · 最近更新 9/21」「已用于任务排序」。设计稿称这是「记住 → 帮到 → 更信任」的飞轮，是**核心护城河**。
- **证据**：`GET /debug/memory/{id}/attribution`、`GET /debug/insights/{id}/attribution`（debug 命名空间）。
- **建议裁决**：新增产品级 `GET /memory/items`（含 `source_kind` / `source_count` / `last_updated` / `usage_receipts[]`），且**必须零 `repositories` 依赖**（V4.0.0 已记的 L3 债，新 API 不得扩大）。

### 缺口 10：产品级洞察（Insight）读接口缺失

- **现象**：「亚丝娜的观察」（账本页）、「今天状态不错 + 一段叙事」（健康页）、「今日 AI 总结」（首页）、简报四张卡，全部是**跨域合成的 AI 结论**，而设计稿把「AI 叙事优先」列为第一条设计原则。
- **证据**：`services/reflection/`、`services/development/` 存在（走 Insight 三闸），但无产品出口；只有 debug attribution。
- **建议裁决**：新增 `GET /insights?domain=ledger|health|home&limit=N`，返回 `{id, domain, headline, narrative, evidence[], generated_at, source_refs[]}`。**「AI 叙事优先」这条设计原则能否成立，取决于这个接口**。

### 缺口 11：首页聚合接口不存在

- **现象**：首页一屏需要：日期问候、Orb 状态语、模式/记忆状态 chip、AI 总结卡、健康三宫格、今日任务（含 AI 排序标签）、今日消费（含预算进度）、输入丸入口。
- **后果**：客户端需发 5+ 请求（`state` / `memories` / `ledger/summary` / `ledger/budgets` / `debug/plans` / `proactive/pending`）并自行拼装，其中 1 个还是 debug 接口；**冷启动首屏必然慢，且跨域合成逻辑泄漏到端上**。
- **建议裁决**：新增 `GET /home/summary` 一次返回首页全部区块（含各区块的 AI 结论文案）。**跨域合成必须在服务端**——这也是「AI 叙事优先」原则的架构保障。

### 缺口 9：健康域整体缺失 + 一项未闭合的实机验证

- **现象**：无健康数据表 / API / 服务；「综合 86 分」评分算法、睡眠分期口径均需自建。
- **调研已给路径**（`REPORT.md:61-77`）：小米手环 9 Pro → Mi Fitness → **Android Health Connect / Apple HealthKit** → App 侧 ingest → 结构化落库（`health_*` 三件套，**不进 memory**）→ Agent 解读 → 主动投递。
- **⚠️ 未闭合项**：Mi Fitness **国内版**是否原生写入系统「健康互联 / Health Connect」、可同步字段与延迟，一手文档未证实，**需真机验证**（`REPORT.md:87`）。→ 应立为 **Phase 0 前置任务**，先验证再决定健康模块排期。
- **合规硬约束**（`REPORT.md:93-102`）：医疗健康信息 = 敏感 PI，**需单独同意**；文案**不得**宣称医疗级血压/血糖/血氧诊断；必须固定「非医疗建议，请咨询医生」；HealthKit 禁广告/出售健康数据。

### 缺口 12：视觉规范无法 1:1 平移到 Flutter 的 4 处

| 设计稿要求 | CSS 实现 | Flutter 落地问题 | 替代方案 |
|---|---|---|---|
| AI 结论卡 1.5px 渐变描边 | `mask-composite: xor` | `Container.border` **不支持渐变** | `CustomPainter` 画 `Gradient` 描边，或 `ShaderMask` + 内缩白底 |
| Orb 内层高光 `mix-blend-mode: screen` | CSS blend | 无直接对应 | `Canvas.saveLayer(BlendMode.screen)` 后绘制两层径向渐变 |
| 字体 `-apple-system / PingFang SC` | 系统栈 | Android 无 PingFang | 定义跨端字体回退链 + 数字用 `FontFeature.tabularFigures()` |
| 「数字用等宽特性」 | — | 需显式开启 | `TextStyle(fontFeatures: [FontFeature.tabularFigures()])` |

### 🚫 冲突 14：设计稿自身的色值三方不一致（开工前必须定稿）

### 缺口 13：非功能需求完全未定义

设计稿与原型均为纯视觉/交互稿，**未提任何非功能要求**。以下需在本版本补齐并写入验收：

## 7. 明确不做（反范围，来自设计稿 §07 + 本方案补充）

**设计稿明确的反范围**：传统数据 Dashboard / 报表页；社交、社区、排行榜；手动分类编辑器等重表单记账；运动课程 / 健康计划等重健康功能；多 AI 角色市场；3D 虚拟形象（V3 再说）。

**本方案补充的反范围**：

- **不做**移动端与现有 React 调试控制台的代码复用——后者是内部调试工具（`apps/frontend/README.md`），定位不同，强行复用会把调试语义带进产品。
- **不做**把跨域合成逻辑放到客户端——必须服务端合成（§3 缺口 11）。
- **不做**医疗级健康宣称（血压 / 血糖 / 血氧诊断），文案统一「趋势 / 参考」+ 固定免责声明（`REPORT.md:99`）。
- **不做**健康数据进 memory 域（`REPORT.md:71` 明确「不进 memory」，与 V4.0.0 裁决 2 同源纪律）。
- **不做**多语言（V1 中文单语），但字符串不硬编码。
- **不做** Offline-first 的写路径（V1 只做读缓存 + 写排队重试）。
