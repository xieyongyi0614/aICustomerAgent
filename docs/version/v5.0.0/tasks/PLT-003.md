## 2. Background

### 2.1 现状：非功能需求（含可观测）在设计稿中**完全未定义**

| 事实 | 证据 |
|---|---|
| 设计稿与原型均为纯视觉/交互稿，**未提任何非功能要求**；可观测需在本版本补齐 | `requirements-analysis.md:213-227`（缺口 13） |
| **可观测**建议基线：崩溃上报 + 首屏耗时 + 对话成功率 | `requirements-analysis.md:224`（缺口 13 可观测行） |
| **安全**建议基线：`flutter_secure_storage`；HTTPS；**日志禁打账目金额与健康数值** | `requirements-analysis.md:222`（缺口 13 安全行） |
| `core/analytics/` 是**已冻结的目录落点**：「埋点与崩溃上报（PLT-003）」 | `flutter-architecture.md:173`（§2 目录结构） |
| 拦截器职责已含「令牌 / 错误映射 / **日志脱敏**」 | `flutter-architecture.md:108`（§1.1 Dio 行）；`APP-003.md`（拦截器脱敏） |
| 导出内容**禁写日志 / 埋点**（可能含账目金额与健康数值） | `APP-021.md:149`（§4.1.4）；`APP-021.md:214`（D12） |
| CI 每次提交跑 `analyze` + 单元 + golden | `flutter-architecture.md:405`（§9） |
| 性能基线四项（冷启动 ≤ 2.5s / 首 token ≤ 1.5s / 列表 60fps / Orb 功耗）归 `PLT-006` | `tasks.md:219` |
| `PLT-006` 验收要求「有可复现的测量方法」，且本任务与其**共用测量口径** | `tasks.md:219`；本任务 §4.2 D2 |
| `PLT-003` 交付面与验收口径（崩溃上报 / 首屏耗时 / 对话成功率 / 关键漏斗；**日志禁打金额与健康数值**） | `tasks.md:216` |
| `PLT-003` 来源 = `REPORT.md` §3 合规 + 工程实践 | `traceability.md:303` |
| 反范围：不做 Offline-first 写路径；不做医疗级宣称 | `requirements-analysis.md:395-398` |
| 埋点数据若含健康数值 → 触发 PIPL 敏感 PI 约束 | `requirements-analysis.md:187`（敏感 PI）；`REPORT.md:93-102` |

**结论**：仓库当前**没有任何客户端可观测实现**（`apps/mobile/` 尚未创建，`APP-001.md:32`）。本任务不是改造既有埋点，而是**从零建立可观测基线**，其最关键的交付不是「能统计」，而是**「统计时不泄漏敏感数值」**。

### 2.2 为什么必须做

1. **它是「性能基线」能否成立的前提。** `PLT-006` 要求四项性能指标**可复现测量**（`tasks.md:219`），而测量数据的采集、打点、上报全部落在本任务的 `core/analytics/`。若本任务与 `PLT-006` 各建一套口径，性能数据将**互不可比**，验收无法裁定。故 `tasks.md:219` 与本任务共同要求「**共用测量口径**」。
2. **它是唯一能兜住「敏感数值外泄」的防线。** 账目金额与健康数值分属两个域，散落在网络层、导出层、健康层。若不做**统一的脱敏层 + 可执行校验**，任何一处 `print` / 日志都会把 PIPL 敏感 PI（`requirements-analysis.md:187`）写进崩溃报告或埋点平台——这是**合规事故**，不只是工程问题。
3. **它是「关键漏斗」的唯一观测点。** 产品主路径（冷启动 → 首页渲染 → 发一句话 → 首个 token → 过程卡完成 → 记账落库）横跨 4 个 feature 域（home / chat / ledger）。按分层纪律 L1，`features/*` 不得互相 import（`flutter-architecture.md:195`），因此漏斗打点**只能**在 `core/analytics/` 统一承载，否则会击穿分层。
4. **它是「对话成功率」的度量面。** 流式对话有断流场景（`flutter-architecture.md:229` 明确「`done` 未到就结束 → 标记 turn 为不完整」）；没有可观测，断流率不可知，`PLT-004` 的契约回放 fixture（`flutter-architecture.md:392`）也无真实分布依据。

### 2.3 在 V5.0.0 中的位置

PLT 第 3 个任务，依赖 `APP-001`（工程骨架，`tasks.md:216`）。它是 M0 之后**最早可启动的横切任务之一**（与 `PLT-004` / `PLT-005` 并列依赖 `APP-001`）。它与 `PLT-006` 构成一对：本任务负责**采集与口径定义**，`PLT-006` 负责**阈值判定与优化**；与 `PLT-004` 的关系是：本任务定义的事件 schema 成为后者**契约回放 fixture** 的断言对象。

## 4. Technical Design Requirements

### 4.1 可观测契约

#### 4.1.1 崩溃上报契约

| 项 | 契约 | 依据 |
|---|---|---|
| 上报通道 | 全局错误捕获（Flutter framework error + 平台侧未捕获异常）→ `core/analytics/` 统一入口 → 上报 | `flutter-architecture.md:173` |
| 附带信息**白名单** | 应用版本 / flavor / 设备型号 / OS 版本 / 堆栈 / 时间戳 / 会话 id | 最小必要原则 |
| **禁带** | 账目金额、健康数值、令牌、导出内容、对话正文原文 | `tasks.md:216`；`requirements-analysis.md:222`；`APP-021.md:149` |
| 去重与限流 | 同一堆栈指纹合并计数；上报失败不得阻塞主流程 | 工程质量 |
| 可用性判据 | 能**可复现**触发一次上报（调试入口或注入异常），并在上报出口观察到记录 | AC1 |
| 与 `dev` flavor | `dev` 日志级别 verbose，但**仍禁打金额与健康数值** | `APP-001.md:112`（flavor 契约） |

#### 4.1.2 计时契约（★ 与 `PLT-006` 共用口径）

| 指标 | 起点 | 终点 | 口径要求 |
|---|---|---|---|
| **首屏耗时** | 应用进程启动（或 Flutter engine 初始化） | 首页首帧可见 | 必须**明确含 / 不含网络**：`tasks.md:219` 要求「冷启动首屏 ≤ 2.5s（**含网络**）」——本任务打点须能区分「本地首帧」与「数据填充后首帧」两个时刻 |
| **首 token 延迟** | 用户发送消息（请求发出） | 收到第一个 `token` 事件 | 与 `PLT-006` 的「首 token ≤ 1.5s」同口径（`tasks.md:219`） |
| 打点位置 | `core/analytics/` 提供计时器 API；调用点在 `app/bootstrap`（启动）与 `features/chat`（发送/首个 token）——**接线**由相应任务完成 | 分层纪律 L1/L3（`flutter-architecture.md:195-197`） |
| **单一真源** | 本任务定义的计时事件名与字段是**唯一**口径；`PLT-006` **不得**另建计时 | 本任务 D2；`tasks.md:219` |

#### 4.1.3 对话成功率契约

| 状态 | 定义 | 计数 |
|---|---|---|
| 成功 | 收到 `done` 事件且 turn 正常收口 | `chat_turn_success` |
| 失败 | 收到 `failure` / `detail` 错误事件 | `chat_turn_failure` |
| **断流** | `done` 未到就结束（网络中断）——**不得静默当作正常结束** | `chat_turn_broken` |
| 取消 | 用户返回 / 切页触发 `CancelToken` | `chat_turn_cancelled`（不计入失败） |
| 成功率口径 | `成功 /（成功 + 失败 + 断流）`（**取消不计入分母**） | 契约冻结 |

> 依据：`flutter-architecture.md:229`（断流必须标记「不完整」，不得静默当正常）；`flutter-architecture.md:230`（取消持 `CancelToken`）。

#### 4.1.4 关键漏斗契约（六步）

| # | 步骤 | 事件名（建议） | 触发点 |
|---|---|---|---|
| 1 | 冷启动 | `funnel_cold_start` | `app/bootstrap` |
| 2 | 首页渲染 | `funnel_home_rendered` | `features/home` 首帧 |
| 3 | 发一句话 | `funnel_message_sent` | `features/chat` 发送 |
| 4 | 首个 token | `funnel_first_token` | `features/chat` 首个 `token` |
| 5 | 过程卡完成 | `funnel_tool_steps_done` | `features/chat` 过程卡末步 `done` |
| 6 | 记账落库 | `funnel_ledger_persisted` | `features/ledger` 落库成功 |

> **纪律**：漏斗对齐**产品主路径**（本任务 4.1.4 与 `tasks.md:216` 一致）；每一步**只记「是否发生」**，**不记**金额 / 健康数值等载荷。事件顺序不可乱（用于计算转化率）。

#### 4.1.5 事件 schema 契约

| 字段 | 必填 | 说明 | 禁止 |
|---|---|---|---|
| `event` | ✅ | 事件名（snake_case） | — |
| `ts` | ✅ | 时间戳（毫秒） | — |
| `session_id` | ✅ | 会话标识（匿名） | 不得含用户可识别信息 |
| `app_version` | ✅ | 应用版本 | — |
| `flavor` | ✅ | `dev` / `prod` | — |
| `props` | ⬜ | 属性对象，**仅白名单键** | **禁止**金额 / 健康数值 / 令牌 / 对话正文 |
| `duration_ms` | ⬜ | 计时事件专用 | — |

#### 4.1.6 脱敏层契约（★ 本任务核心）

> **硬约束**：日志**禁打**账目金额与健康数值（`tasks.md:216`；`requirements-analysis.md:222`）。

**三层防线（缺一即视为实现缺陷）**：

| 层 | 机制 | 说明 |
|---|---|---|
| L1 **白名单** | 只有登记在案的 `props` 键才允许进入日志 / 埋点载荷；未登记键**默认丢弃**（fail-closed） | 与后端 `EXPECTED_EVENT_TYPES` fail-closed 纪律同源（`tasks.md:28`） |
| L2 **序列化层统一过滤** | 所有出站日志 / 埋点载荷**必须**经 `core/analytics/` 的单一序列化出口；禁止绕过（禁止直接 `print` / 直接调第三方 SDK） | 单点收口，便于审计 |
| L3 **静态断言** | CI 静态扫描：禁止 `print(` / `debugPrint(` 出现在 `lib/`（`core/analytics/` 白名单出口除外）；禁止在埋点载荷中出现金额 / 健康字段名模式 | 可 grep / 可测试 |

**禁止进入日志 / 埋点的数据类别**：

| 类别 | 示例 | 依据 |
|---|---|---|
| 账目金额 | `amount_minor` / `*_text` / `consumed` / `remaining` | `tasks.md:216` |
| 健康数值 | 睡眠时长 / 心率 / 步数 / SpO2 / HRV 的**原始值** | `tasks.md:216`；`requirements-analysis.md:222` |
| 凭据 | 令牌 / API Key | `flutter-architecture.md:402` |
| 导出内容 | `/life/export` 返回体 | `APP-021.md:149`、`:214` |
| 对话正文原文 | token 累积文本 | 最小必要；正文可能含金额 / 健康陈述 |

> **允许采集的等价物**：只允许「**是否发生**」类布尔 / 计数 / 枚举（如 `has_amount: true` 不允许 → 改为 `ledger_persisted: true`）。即：**记事件，不记数值**。

#### 4.1.7 校验命令契约（可执行）

| 校验 | 命令思路 | 期望 |
|---|---|---|
| 无裸打印 | `grep -rnE "\b(print\|debugPrint)\(" apps/mobile/lib/ --include=*.dart` | 仅命中 `core/analytics/` 白名单出口，其余为空 |
| 无敏感字段名 | `grep -rniE "(amount\|balance\|sleep_minutes\|heart_rate\|spo2\|hrv\|token)" apps/mobile/lib/core/analytics/` | 无命中（白名单键除外） |
| 脱敏层单点 | 静态断言：`lib/` 内调用第三方埋点 SDK 的位置**仅**在 `core/analytics/` 内 | 断言通过 |
| 白名单 fail-closed | 单测：投递未登记 `props` 键 → 被丢弃且不报错 | 用例通过 |

> 上述为**校验思路**；具体命令在 `PLT-005` 的 CI 中固化（本任务只提供可被调用的命令）。

#### 4.1.8 与 `PLT-006` 的口径共享契约（★ 不得各测一套）

| 项 | 契约 |
|---|---|
| 唯一测量真源 | 首屏耗时 / 首 token 延迟的事件名、起点终点、单位（ms）由**本任务**冻结 |
| `PLT-006` 的职责 | 只做**测量执行与阈值判定**（工具：Flutter DevTools / `integration_test` + `traceAction`），**不得**重新定义口径 |
| 数据可比性 | 两者的数值必须可直接对比（同口径、同单位、同起点终点） |
| 冲突处置 | 若 `PLT-006` 发现口径需修正 → **回改本任务**，不各自修正 |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **日志禁打账目金额与健康数值**为**硬约束**，用「白名单 + 单点序列化 + 静态断言」三层落实 | `tasks.md:216`；`requirements-analysis.md:222`；单靠约定必然被赶工期绕过 |

### 4.3 数据流（谁产出、谁消费）

```text
【采集】（本任务交付 core/analytics/）
  各 feature / app 层 → core/analytics 计时器 / 漏斗 / 崩溃入口（仅事件名 + 白名单 props）
      → 脱敏层 L1 白名单（fail-closed，未登记键丢弃）
      → 序列化层 L2（单点出口；禁止裸 print / 直调第三方 SDK）
      → 出站：崩溃上报 / 埋点平台（无金额、无健康数值、无令牌、无正文）

【校验】（CI 调用，PLT-005 固化）
  静态断言 L3：无裸打印 / 无敏感字段名 / 脱敏层单点 → 通过

【消费方 —— 本任务存在的理由】
  ① PLT-006（性能基线）
       ← 消费「首屏耗时 / 首 token 延迟」的口径与采集数据（D2，不得各测一套）
  ② PLT-004（测试策略）
       ← 消费事件 schema，作为契约回放 fixture 的断言对象
  ③ PLT-005（CI/CD）
       ← 消费 §4.1.7 校验命令，作为 CI 门禁
  ④ 产品 / 工程决策
       ← 消费「对话成功率 / 漏斗转化」，定位断流与流失点（不含敏感载荷）

装配红线：
  ✗ 日志 / 埋点出现金额或健康数值（D1/D3）
  ✗ 绕过 core/analytics 单点出口直接 print / 直调 SDK（D4/L2）
  ✗ PLT-006 另建计时口径（D2）
  ✗ 埋点用于广告 / 出售 / 训练（D8）
```
