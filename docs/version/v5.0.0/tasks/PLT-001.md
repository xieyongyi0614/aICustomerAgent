## 2. Background

### 2.1 现状：健康接入路径有一项**一手未证实**的关键假设

| 调研明确「Mi Fitness **国内版**是否原生写入系统『健康互联 / Health Connect』、可同步字段与延迟，**一手文档未证实，需真机验证**」 | `research/personal-ai-butler-miband/REPORT.md:87`（§2.5 必做实机验证） |
| 推荐主路径已给出：手环 → Mi Fitness → **Health Connect / HealthKit** → App 侧 ingest → `health_*` 三件套（不进 memory） | `REPORT.md:61-77`（§2.3 推荐主路径） |

| 决策 D1：健康段**门控**——先做 `PLT-001` 实机验证再定排期；`M4 全部任务 + APP-023` 不得先于 `PLT-001` 开工 | `tasks.md:78` |

**结论**：本任务**不产出代码**，它的唯一产物是一份**一手实测结论**。这份结论是 M4 整段的**开关**——在它出结论前，M4 的 5 个任务（`API-009` / `API-010` / `APP-023` / `APP-024` / `APP-025` 中的健康实现部分）**全部处于门控状态**（`tasks.md:194`）。

### 2.2 为什么必须做（本任务存在的理由）

1. **它是整条健康链路唯一未验证的假设。** 调研把接入路径画得很完整（`REPORT.md:61-77`），但**整条链路的起点**——「Mi Fitness 国内版是否真的把数据写进系统健康中枢」——只有一句「需真机验证」（`REPORT.md:87`）。若起点不成立，后面所有设计（`health_*` 三件套、健康页、三宫格）都是空中楼阁。
2. **它直接决定 M4 排期与首页三宫格形态（决策 D1）。** 结论分叉已在 `tasks.md:78` 与 `tasks.md:195-196` 写死：
   - **通过** → 健康事实域 + 只读展示进 V1（`API-009` / `API-010` / `APP-023` / `APP-024` 启动）；
   - **未通过** → M4 整体后置；`APP-014` 三宫格走**空态 + 引导授权**分支（该分支属 M2 范围，**不因本段后置而缺席**，`tasks.md:196`）。
3. **它是「先验证再投入」纪律的示范。** 健康域被裁决为「中低可行性」（`requirements-analysis.md:357`）；在可行性未闭合时投入 5 个任务，一旦 R1 触发就是整段返工。**用 1–2 周验证换取避免整段返工**，是本任务的核心价值主张（`REPORT.md:167-168`）。
4. **它同时闭环 R1 的降级方案可行性。** 若验证未通过，`tasks.md:266` 给出三条降级路径（手动导入 / Gadgetbridge / 后置）。这三条是否**真的可用**，也需在本任务实测中一并给出结论，否则「未通过」之后的 M4 会陷入无路可走。

### 2.3 在 V5.0.0 中的位置

`PLT-001` 位于 `tasks.md:226` 依赖图的**最上游**，是**唯一一个先于一切任务、且能反过来决定其他任务是否开工**的验证任务。它不依赖任何任务（`tasks.md:214`），但被 M4 整段依赖（`tasks.md:194`）。它同时为 `APP-014`（M2）提供三宫格分支的**输入结论**——注意三宫格双分支在 M2 就要实现（`APP-014.md:124-142`），本任务的结论决定**走哪一支**。

## 4. Technical Design Requirements

### 4.1 验证契约

#### 4.1.1 验证命题契约（三个待证命题）

| # | 命题 | 精确表述 | 判定口径 |
|---|---|---|---|
| P1 | **原生写入** | Mi Fitness **国内版**（非国际版、非 Zepp Life）在真机上是否**原生**把健康数据写入系统健康中枢（Android「健康互联 / Health Connect」；iOS「健康」App / HealthKit） | 打开系统健康应用 → 数据来源列表**是否出现 Mi Fitness**；出现即「原生写入成立」（无需第三方桥） |
| P2 | **可同步字段** | 成立时，**哪些字段**被写入、单位是什么、采样频率是多少 | 逐字段核对系统健康应用中的记录；字段名 + 单位 + 频率三要素齐备才算「可同步」 |
| P3 | **同步延迟** | 从手环产生数据到系统健康中枢**可见**的时间差 | 按 §4.1.4 测量；给实测值（分钟级 / 小时级 / 仅手动触发） |

> **背景事实（不得混淆）**：`REPORT.md:7` 明确本机型**不在 Zepp OS 开放体系内**，配套 App 是 Mi Fitness；因此 P1 的验证对象**只能是 Mi Fitness**，不得用 Zepp Life / Zepp OS API 替代验证。

#### 4.1.2 可复现验证方法契约（★ 本任务的核心纪律）

> **裁决（§4.2 D1）**：验证方法必须**可复现**，不得写成「试一下看看」。下表每一列都是报告的**必填字段**。

| 项 | 要求 | 记录格式示例 |
|---|---|---|
| 设备型号 | 精确型号 + 固件版本 | 「小米手环 9 Pro · 固件 `<版本号>`」 |
| 手机型号 | 精确型号 | 「`<机型>`」 |
| 操作系统版本 | Android / iOS 精确版本（含补丁） | 「Android `<14/15>`（`<build>`）」 |
| Mi Fitness 版本 | App 版本号 + 来源商店 | 「Mi Fitness `<版本号>` · `<应用商店>`」 |
| 区域版本 | **必须声明为国内版**（命题 P1 的前提） | 「国内版 / 国际版」 |
| 系统健康中枢 | 平台 + 版本 | 「Health Connect `<版本>`」/「iOS 健康 `<版本>`」 |
| 采集步骤 | **编号步骤**，可被第三方照做 | 见下「标准采集步骤」 |
| 判定标准 | P1/P2/P3 各自的通过阈值 | 见 §4.1.1 与 §4.1.4 |
| 证据 | 截图 / 录屏 / 导出记录（可复现的原始材料） | 附件目录见 §6.1 |

**标准采集步骤（报告须逐条执行并记录结果）**：

1. 手环与手机完成配对，Mi Fitness 中确认**健康数据同步已开启**（含心率 / 睡眠 / 步数 / 血氧等，逐项记录开关状态）。
2. 在系统健康应用中确认「数据来源 / 已连接应用」列表，**记录是否出现 Mi Fitness**（P1 的直接证据）。
3. 若出现：逐项核对可读类型（对照 `REPORT.md:77` 的清单），记录**字段名 + 单位 + 采样频率**（P2）。
4. 延迟测量：按 §4.1.4 执行（P3）。
5. 若**未出现**：记录 Mi Fitness 内是否存在「同步到健康平台 / 健康互联」的**显式开关或引导**（区分「原生不支持」与「需用户手动开启」）。
6. 记录异常与阻塞（如权限被系统限制、需 root、需特定系统版本）。

> **判定纪律**：第 5 步是**区分「未通过」与「需用户操作后才通过」的关键**——两者对 M4 的含义不同（前者触发 R1 降级，后者只需在 `APP-023` 加引导）。

#### 4.1.3 字段清单契约（P2 产出）

| 列 | 必填 | 说明 |
|---|---|---|
| 字段名 | ✅ | 系统健康中枢中的类型名（如 `Heart Rate` / `Sleep Sessions`） |
| 单位 | ✅ | 如 `bpm` / `count` / `minutes` |
| 采样频率 | ✅ | 如 `smart` / `1min` / `10min` / `30min` / `手动` |
| 是否可读 | ✅ | 是 / 否（系统健康应用中有无数据） |
| 对照调研清单 | ✅ | 对应 `REPORT.md:77` 中的哪一项；调研有而实测无的，标「**实测缺失**」 |
| 备注 | ⬜ | 如「仅当日」「需 advanced monitoring」 |

> **字段范围基线**（`REPORT.md:77` 的 Health Connect 可读类型）：Steps、Distance、Heart Rate、SpO2、HRV、Skin/Body Temp、Respiratory rate、Resting HR、Sleep Sessions、Weight、VO2 Max、Exercise Sessions。**产品文案不得宣称医疗级血压 / 血糖 / 血氧诊断**（`REPORT.md:83`、`requirements-analysis.md:187`），字段清单亦不得暗示诊断能力。

#### 4.1.4 延迟测量契约（P3 产出）

| 项 | 要求 |
|---|---|
| 测量对象 | 手环产生数据 → 系统健康中枢可见 的时间差 |
| 测量方法 | 记录「数据产生时刻」（手环端 / Mi Fitness 端可见）与「系统健康中枢首次可见时刻」，取差值；两次时间以同一时钟为准 |
| 采样次数 | **≥ 3 次**，覆盖至少两类数据（如步数类高频 + 睡眠类低频） |
| 记录字段 | 数据类目 / 产生时刻 / 可见时刻 / 延迟 / 是否需手动打开 App 触发 |
| 判定档 | 「实时（≤ 5 min）」/「近实时（≤ 1 h）」/「延迟（> 1 h）」/「**仅手动触发**」四档，取最差档作为报告结论 |
| 已知干扰 | 官方 App 与 Gadgetbridge **互斥**（抢连 / 清数据，`REPORT.md:157`）；测量期间**不得**同时连接第三方 App |
