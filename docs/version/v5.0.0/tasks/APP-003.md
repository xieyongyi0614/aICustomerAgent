## 2. Background

### 2.1 现状：后端事件面只有 3 类，且工具过程无流式来源

| 事实 | 证据 |
|---|---|
| `/chat/message` 现有 NDJSON 事件**仅 3 类**：`turn_meta` / `token` / `done` | `requirements-analysis.md:69`；`:100`（「`chat.py` 只 yield `turn_meta` / `token` / `done`」） |
| **Tool Call 过程卡无流式来源**（本版本最大技术缺口） | `requirements-analysis.md:121-126`（缺口 2）；`tasks.md:131` |
| 工具执行记录现有形态是**事后查询式**（debug 命名空间），无法驱动「步骤逐项打勾」 | `requirements-analysis.md:93` |
| `tool_step` 事件由 `API-002` 新增，且**必须走独立通道**（不得塞进 `loop_runs.steps`） | `tasks.md:128`、`:131` |
| `turn_meta` 将增 `memory_refs`（`API-003`） | `tasks.md:129` |
| Freezed **3.x 语法已变**（`sealed class` + `abstract class X with _$X`），2.x 示例编译不过 | `flutter-architecture.md:44` |
| 错误文案规范「不暴露技术细节」由 `APP-008` 定义，本任务负责**映射出口** | `tasks.md:113` |
| 日志**禁打**账目金额与健康数值 | `tasks.md:216`（PLT-003）；`requirements-analysis.md:222` |
| NDJSON 事件回放 fixture **必须包含 `tool_step` 序列与断流场景** | `flutter-architecture.md:392` |

**结论**：仓库中**不存在** Flutter 侧网络层；后端事件面在 `API-002` 交付前只有 3 类。本任务必须**按最终 5 类事件建模**（而不是等后端），否则 `APP-013` 的过程卡无法开工。

### 2.2 为什么必须做

1. **它是 M1 与 M2 的共同前置**：`APP-010`（流式渲染）依赖本任务（`tasks.md:138`），而 `APP-013`（过程卡）依赖 `API-002` + `APP-007`，其事件解析能力由本任务提供。
2. **客户端对侧必须 fail-closed**：后端新增事件类型会 fail-closed（未登记 `EXPECTED_EVENT_TYPES` 即转红，`tasks.md:28`）。若客户端静默忽略未知类型，就会出现「后端加了事件、端上悄悄丢掉」的静默故障。用 `sealed union` + `switch` 穷尽检查，把这类故障提前到**编译期**（`flutter-architecture.md:42`）。
3. **错误文案是合规与体验的双重要求**：统一错误模型必须映射为**用户可读文案**，不暴露技术细节（`tasks.md:113`），与 `APP-008` 的口径一致。
4. **脱敏是硬约束**：日志禁打账目金额与健康数值（`tasks.md:216`）。这条必须在拦截器层面一次性实现——散落各处必然漏。

### 2.3 在 V5.0.0 中的位置

关键路径上：`APP-001 → APP-003 → APP-010`（`tasks.md:228-232`）。同时它是 `APP-004`（存储层的网络依赖）、`APP-009~013`（对话闭环）、`APP-016`（记账页数据）的共享基建。

## 3. Scope

### 3.1 In Scope

1. **dio 客户端**：基址经 `--dart-define` 注入（`APP-001` 约定）、超时策略、`ResponseType.stream` 支持。
2. **三件拦截器**：令牌注入（从 `APP-004` 的 secure storage 读，本任务只定义读取接口）、错误映射（`DioException` → 统一错误模型）、日志脱敏（白名单字段）。
3. **NDJSON 流解析**：`ResponseType.stream` → `utf8.decoder` → `LineSplitter` 逐行 → `jsonDecode` → 事件构造。处理跨 chunk 半行、空行、非法 JSON。
4. **`ChatEvent` sealed union**：5 类事件（`turn_meta` / `token` / `tool_step` / `done` / `failure`），字段契约见 §4.1.4。
5. **统一错误模型**：错误分类 + **用户可读文案**映射表；技术细节只进日志（且脱敏）。
6. **`CancelToken` 生命周期**：请求级取消、页面 dispose 取消、避免泄漏。
7. **重试队列接口**：为 V1「写失败进重试队列 + UI 明示待同步」提供接口与状态枚举（**不含离线写逻辑**）。
8. **契约回放 fixture**：录制 / 构造的事件序列 fixture，**必含 `tool_step` 序列与断流场景**。

## 4. Technical Design Requirements

### 4.1 接口契约

#### 4.1.1 dio 客户端契约

| 项 | 契约 |
|---|---|
| 基址 | 来自 `--dart-define`（`APP-001` D5）；**禁止硬编码** |
| 默认响应类型 | JSON（普通接口）；流式接口显式指定 `ResponseType.stream` |
| 超时 | 连接超时与接收超时分离；**流式请求的接收超时按「首 token 预算」单独设置**，不得用普通接口的短超时 |
| 重试 | 仅对幂等读接口自动重试；**写接口不自动重试**（避免重复记账） |
| 取消 | 每个流式请求持有独立 `CancelToken`（见 §4.1.6） |

#### 4.1.2 拦截器契约

| 拦截器 | 职责 | 硬约束 |
|---|---|---|
| **令牌注入** | 从存储层读取长期令牌，写入请求头 | 只经 `APP-004` 定义的读取接口；**令牌值不得进日志** |
| **错误映射** | `DioException` / HTTP 状态码 → 统一错误模型（§4.1.5） | 映射结果**只含用户可读文案**；技术细节只进脱敏日志 |
| **日志脱敏** | 请求 / 响应日志 | **禁打**：账目金额、健康数值、令牌、用户标识；命中即替换为占位符 |

**日志脱敏白名单（允许打印）**：请求方法、路径（**不含 query 值**）、状态码、耗时、事件类型名、错误分类。
**日志脱敏黑名单（禁止打印）**：令牌、金额类字段、健康指标类字段、记忆正文、用户标识、`Authorization` 头。

来源：`tasks.md:216`；`requirements-analysis.md:222`。

#### 4.1.3 NDJSON 流解析契约

| 环节 | 契约 |
|---|---|
| 传输 | `ResponseType.stream` → `Stream<Uint8List>` |
| 解码 | `utf8.decoder`（**必须处理多字节字符跨 chunk 截断**） |
| 分行 | `LineSplitter`（后端每行一个 JSON） |
| 解析 | 逐行 `jsonDecode` |
| 半行 | 跨 chunk 的半行**必须缓冲到下一 chunk**，不得丢弃或提前解析 |
| 空行 | 跳过（不报错） |
| 非法 JSON | 记为解析失败事件，**不得中断整个流** |
| 未知 `type` | **fail-closed**：抛出「未登记事件类型」错误，不得静默忽略（见 §4.2 D4） |
| 断流 | `done` 未到即流结束 → 标记 turn 为**不完整**，允许重试；**不得静默当作正常结束** |

来源：`flutter-architecture.md:207-230`。

#### 4.1.4 `ChatEvent` sealed union 契约（5 类事件）

> 用 Freezed 3.x 的 `sealed class ChatEvent` + `abstract class X with _$X` 形态（`flutter-architecture.md:33-44`）。**`switch` 必须无 `default` 分支**。

| 事件 `type` | 字段 | 语义 | **UI 落点** |
|---|---|---|---|
| `turn_meta` | `role_mode`、`analysis`、`scene_*`、`intention`、`current_goal`、`behavior`、`mode`、`action_intent`、**`memory_refs`**（`[{id, kind, label}]`，`API-003` 新增，**无引用时字段缺省**） | 本轮元信息 | **`APP-012`**（人格状态栏与 Role Mode）；`memory_refs` 亦供 `APP-009` 记忆提示条 |
| `token` | `delta` | 正文增量 | **`APP-010`**（流式渲染引擎） |
| `tool_step` | `step_id`、`tool_id`、`label`、`status`（`running` / `done` / `failed`）、`detail`、`target` | 工具执行步骤（`API-002` 新增，独立通道） | **`APP-013`**（Tool Call 过程卡） |
| `done` | 收口标记（无正文负载） | 本轮正常结束 | **落会话历史**（供 `APP-009` 回放） |
| `failure` | `detail`、`error` | 本轮失败 | **`APP-008`**（错误态与文案） |

**状态模型的结构性约定**（本任务只定义，不实现 UI）：

| 字段 | 说明 |
|---|---|
| `status` | `idle` / `streaming` / `toolRunning` / `done` / `failed` |
| `text` | 正文累积（由 `APP-010` 消费 `token`） |
| `memoryRefs` | 来自 `turn_meta`（`API-003`） |
| `toolSteps` | 来自 `tool_step`（`API-002`） |
| `chips` | 结果卡快捷操作（服务端下发） |
| `error` | 统一错误模型（§4.1.5） |

> ⚠️ **`todo`（未来步）由服务端一次性下发还是客户端推导，必须在 `API-002` 的 Detail 里冻结**（`flutter-architecture.md:252`）。本任务只按契约解析 `running` / `done` / `failed` 三态；`todo` 的渲染属 `APP-013`，其数据来源以 `API-002` 契约为准。

来源：`flutter-architecture.md:29-42`、`:232-252`；`tasks.md:108`、`:128-129`。

#### 4.1.5 统一错误模型契约

| 错误分类 | 触发 | 用户可读文案口径 | 是否可重试 |
|---|---|---|---|
| 网络不可达 | 连接失败 / DNS | 「网络好像断了，检查一下再试」 | 是 |
| 超时 | 首 token 超预算 / 请求超时 | 「等太久了，要不要再试一次」 | 是 |
| 鉴权失效 | 401 / 403 | 「需要重新登录一下」 | 否（走重新配对） |
| 请求非法 | 4xx（非 401/403） | 「这个操作我没法完成，换个说法试试」 | 否 |
| 服务异常 | 5xx | 「我这边有点小问题，稍后再试」 | 是 |
| 流中断 | `done` 未到即结束 | 「刚才没说完，要我接着说吗」 | 是 |
| 解析失败 | 非法 JSON / 未知事件类型 | 「我收到了一条看不懂的消息」 | 否 |

**硬约束**：
1. 文案**不得**出现技术细节（异常类名、状态码数字、字段名、堆栈）。
2. 文案语气沿用设计系统 `principles.md` §5.3 的口径——**用「建议 / 可以 / 别忘了」，不用「必须 / 请立即」**；AI 用第一人称（`principles.md:69-75`）。
3. 技术细节只进脱敏日志。

#### 4.1.6 `CancelToken` 生命周期契约

| 场景 | 契约 |
|---|---|
| 发起流式请求 | 创建独立 `CancelToken`，与 turn 一一对应 |
| 用户主动停止 | 调 `cancel()`，当前 turn 标记为已取消（非失败） |
| 页面 dispose / 切页 | **必须**在 dispose 时取消，避免流与回调泄漏 |
| 新 turn 覆盖旧 turn | 旧 `CancelToken` 先取消再新建 |
| 取消后 | 不得再向上游发出事件；已累积文本按「已取消」终态保留 |

来源：`flutter-architecture.md:230`（「持有 `CancelToken`，在页面 dispose 时取消，避免泄漏」）。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| **D1** | **用 Freezed `sealed class` 建模 `ChatEvent`，而非手写 `sealed class` + 手工 `fromJson`** | 5 类事件字段各异，手写解析会产生大量样板且极易漏字段；Freezed 提供 `union` + JSON 生成，配合 Dart 3 `switch` 穷尽检查得到**编译期**保障（`flutter-architecture.md:29-42`） |
| **D2** | **锁定 Freezed 3.x，并统一在 `APP-001` 声明** | 3.x 语法为 `sealed class` + `abstract class X with _$X`，与网上大量 2.x 示例不兼容（`flutter-architecture.md:44`）。版本由 `APP-001` 冻结，本任务不得自行升降 |
| **D3** | **逐行解析用 `LineSplitter`，不自研分行器** | 后端契约是「每行一个 JSON」（`flutter-architecture.md:211`）；`LineSplitter` 已正确处理 `\n` / `\r\n` 与跨 chunk 缓冲，自研只会引入边界 bug |
| **D4** | **未知事件类型 fail-closed：抛错而非静默忽略** | 这是后端 `EXPECTED_EVENT_TYPES` fail-closed 纪律的**客户端对侧**（`flutter-architecture.md:42`）。静默忽略会让「后端加了事件、端上悄悄丢掉」的故障不可观测 |
| **D5** | **错误模型对外只暴露用户可读文案**；技术细节只进脱敏日志 | `APP-008` 的错误文案规范要求「不暴露技术细节」（`tasks.md:113`）；也是安全要求（避免泄露内部结构） |
| **D6** | **日志脱敏在拦截器层一次性实现，采用「白名单放行 + 黑名单兜底」双保险** | 单靠黑名单会漏（新字段不断出现）；单靠白名单会让排障困难。白名单放行安全字段，黑名单兜底拦截金额 / 健康 / 令牌 / 记忆正文 |
| **D7** | **合帧节流与 Markdown 增量解析不在本任务** | 属 `APP-010`（`flutter-architecture.md:227-228`）。本任务只保证事件按行、按时序产出，不做渲染层优化 |
| **D8** | **重试队列只建接口与状态枚举，不实现离线写** | V1 明确不做 Offline-first 写路径（`requirements-analysis.md:398`）。接口预留是为了 `APP-016` 记账页能显示「待同步」 |
| **D9** | **不新增、不重命名任何后端事件类型或字段** | 事件契约由 `API-002` / `API-003` 定义。客户端发现契约不足时应**回改 `API-*` 的 Detail**，而不是在端上自行扩字段 |
| **D10** | **契约回放 fixture 必须含 `tool_step` 序列与断流场景** | 这两条是最容易在真实环境出问题、又最难手工复现的路径（`flutter-architecture.md:392`） |
| **D11** | **`memory_refs` 缺省语义按 `API-003` 契约处理：无引用时字段缺省（非空数组）** | 空数组会让端上误判「有引用但为空」（`tasks.md:129`）；解析层必须把「缺省」与「空数组」区分开 |

### 4.3 数据流（NDJSON 链路）

```text
features/*/data（repository）
   → core/network/dio_client.post('/chat/message', responseType: stream, cancelToken)
   → 拦截器链：令牌注入 → 发送 → 日志脱敏（请求）
        ↓ Stream<Uint8List>
   → utf8.decoder.bind(stream)              # 处理多字节跨 chunk
        ↓ Stream<String>
   → LineSplitter()                          # 按行切分（后端每行一个 JSON）
        ↓ 逐行
   → jsonDecode(line)
        ↓ 读 type 字段
   → ChatEvent.fromJson（Freezed union）
        ├── turn_meta → 更新模式 / 意图 / memory_refs        （APP-012 / APP-009）
        ├── token     → 追加正文                              （APP-010）
        ├── tool_step → 追加 / 推进过程卡步骤                  （APP-013）
        ├── done      → 收口，落会话历史                       （APP-009）
        └── failure   → 统一错误模型 → 用户可读文案            （APP-008）
        ↓ 未知 type → fail-closed 抛错（D4）
   → Riverpod Notifier 更新 ChatTurnState（状态模型见 §4.1.4）
        ↓
   → 拦截器链：日志脱敏（响应，白名单 / 黑名单，D6）
```

来源：`flutter-architecture.md:207-221`。

### 4.4 依赖与边界

## 7. Testing Requirements

### 7.1 NDJSON 解析单元测试

| 用例名 | 断言 |
|---|---|
| `test_parse_single_line_event` | 单行合法 JSON → 构造出对应 `ChatEvent` 子类型，字段值逐一相等 |
| `test_parse_multiple_lines_in_one_chunk` | 一个 chunk 含多行 → 逐行产出多个事件，顺序不变 |

| `test_skip_blank_lines` | 空行 / 纯空白行被跳过，不报错、不产出事件 |
| `test_invalid_json_does_not_abort_stream` | 一行非法 JSON → 记为解析失败事件，**后续行仍继续解析** |
| `test_unknown_event_type_fails_closed` | 未知 `type` → 抛出「未登记事件类型」错误，**不得静默忽略**（D4） |

## 8. Acceptance Criteria

| # | 判据 | 验证方式 |
|---|---|---|
| AC1 | NDJSON 解析用例全绿，含跨 chunk 半行与多字节截断 | `flutter test` 输出 |
