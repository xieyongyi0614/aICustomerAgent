### 2.2 为什么必须做

1. **它是 M3 收口点 C4 的判定对象。** C4 判据「本地通知准时、可关、不重复」（`tasks.md:258`）三条全部由本任务交付；不达标则 M3 不算完成。
2. **它是「主动但克制」原则能否成立的关键。** 冲突 8 明确：不做推送，「主动但克制」的核心卖点退化为「App 内一个入口」（`requirements-analysis.md:146-148`）。决策 D4 选本地通知的理由是**零基础设施成本、零合规增量**，且能完整表达「固定节奏 + 可关闭」的设计意图。
3. **「不重复」是最易漏、也最像 bug 的一条。** C4 把它与「准时」「可关」并列，意味着它不是「顺带」，而是**判定项**：需显式处理「同一时刻重复注册」（多次 set 同 id）与「App 重启后重复调度」（重启后未清旧调度就再注册）两条路径。
4. **它携带一条安全红线。** 通知内容可能含金额 / 健康数值，而 `requirements-analysis.md:222` 与 `tasks.md:216` 明确「日志禁打账目金额与健康数值」——本任务的埋点必须遵守。

### 2.3 在 V5.0.0 中的位置

M3 客户端第 2 个任务（`tasks.md:183`），是 **C4 收口点**（`tasks.md:258`）。它消费 `APP-004`（偏好存储）与 `API-008`（内容 + 时刻偏好），落地到 `APP-018` 的简报页；与 `APP-020`（主动关怀三开关）共享「可关」语义——开关状态由 `APP-020` 读写，本任务**只读取并据此调度**。

## 3. Scope

### 3.1 In Scope

1. **通知调度器**（§4.1.1）：按用户设定时刻本地触发；两种通知（早间 / 晚间）各一条。
2. **深链落地契约**（§4.1.2）：点击通知 → 落地简报页 `#briefing?type=...`。
3. **「可关」契约**（§4.1.3）：关闭开关后**不再触发**（原则 4 可判定规则）。
4. **「不重复」契约**（§4.1.4）：同一时刻**只有一条**；App 重启后**不重复调度**。
5. **权限引导契约**（§4.1.5）：`permission_handler`；被拒不静默失败、不反复弹窗。
6. **时区与重启契约**（§4.1.6）：`timezone` 处理 + 重启后重新注册策略 + Android 12+ 精确闹钟权限处置。
7. **埋点与可观测契约**（§4.1.7）：对齐 `PLT-003`；**日志禁打账目金额与健康数值**。

## 4. Technical Design Requirements

### 4.1 契约

#### 4.1.1 调度契约

| 项 | 契约 |
|---|---|
| 库 | `flutter_local_notifications` + `timezone`（`flutter-architecture.md:85`、`:134`） |
| 触发方式 | **本地触发**（端侧定时），不依赖服务端推送（决策 D4） |
| 通知种类 | 早间简报（`morning`，默认 `08:00`）/ 晚间总结（`evening`，默认 `21:30`） |
| 时刻来源 | 用户偏好 `briefing_morning_time` / `briefing_evening_time`（参数类；由 `API-008` 落库，端侧经 `APP-004` 偏好层读取） |
| 内容来源 | `API-008` **服务端预生成**（端侧只投递，不生成）；**可离线取到**（`tasks.md:181`） |
| 重复策略 | 每天固定时刻重复（`DateTimeComponents.time` 语义，非 one-shot） |
| 时区 | 统一走 `timezone` 包；默认 `Asia/Shanghai`；时区变化时**重新注册**（§4.1.6） |
| 落点 | `core/notify/notification_scheduler`（`flutter-architecture.md:171`） |

#### 4.1.2 深链落地契约

| 项 | 契约 | 依据 |
|---|---|---|
| payload schema | `{ "route": "/briefing", "type": "morning" \| "evening" }`（最小载荷；**不含**金额 / 健康数值原文） | 避免敏感值经通知载荷外泄；`requirements-analysis.md:222` |
| 点击落地 | 解析 payload → `go_router` 跳 `#briefing?type=...` | `tasks.md:183`；`APP-005` 导航骨架 |
| 前台点击 | 冷启动 / 后台唤醒两种入口都要能落地（冷启动需等路由就绪再跳） | 端侧健壮性要求 |
| 落地失败 | payload 缺失 / 路由未就绪 → 落地**首页**并给轻提示；**不得**静默丢弃 | 不静默失败纪律 |
| 与 `APP-018` 边界 | 本任务只负责**投递 + 跳转**；简报页渲染归 `APP-018` | `tasks.md:182` |

#### 4.1.3 「可关」契约（★ 原则 4 可判定规则）

| 项 | 契约 | 依据 |
|---|---|---|
| 开关状态 | 由 `APP-020` 读写（早间 / 晚间 / 异常三开关），本任务**只读取** | `tasks.md:184`；`principles.md:14` |
| 关闭语义 | 对应开关关闭 → **取消该条已注册的调度** + **不再注册** → 到点**无通知** | `principles.md:14`（可判定规则：关掉开关 → 到点无通知） |
| 判定方式 | 「关掉开关 → 到点无通知」是**可判定**规则，须有可执行用例 | `principles.md:14` |
| 时刻为空 | `briefing_morning_time` 为空 / 未设 → 视为**关闭**（参数类表达，**不用** `*_enabled`） | 裁决 9（`tasks.md:26`） |
| 恢复 | 重新打开开关 → 重新注册调度（立即生效，不必等到次日） | 可判定 |
| 异常提醒 | 第三开关（状态异常提醒）在 V1 **不注册任何调度**（行为归 P2） | `traceability.md:162`（异常主动告知列 V2） |

#### 4.1.4 「不重复」契约（★ C4 判据）

| 路径 | 问题 | 契约 |
|---|---|---|
| ① 同一时刻**重复注册** | 多次调用 `zonedSchedule` 且未指定稳定 id → 同 id 覆盖或产生多条 | **为每条通知分配稳定 id**（如 `morning = 1001` / `evening = 1002`）；**注册前先按 id `cancel`**；同 id 注册 = 覆盖，**不叠加** |
| ② App **重启后重复调度** | 进程重启后若不清旧调度就再注册 → 出现两条 | 启动时**先读 `pendingNotificationRequests()`** 对齐：已存在的同 id 调度**不重复注册**（或先 `cancel` 再 `schedule`）；注册逻辑**幂等** |
| ③ 时区 / 时刻变更 | 用户改时刻 → 旧调度残留 | 时刻变更 → **先 cancel 该 id 再按新时刻注册** |
| 判定 | 到点**只有一条**通知；重启后 `pendingNotificationRequests` 中**无重复 id** | 可判定（见 §7） |
| 依据 | C4 判据「准时、可关、不重复」（`tasks.md:258`） |

#### 4.1.5 权限引导契约

| 项 | 契约 | 依据 |
|---|---|---|
| 库 | `permission_handler`（`flutter-architecture.md:87`） |
| Android 13+ | 通知权限 `POST_NOTIFICATIONS` 为**运行时权限**，须在**首次需要时**申请（非启动即申请） |
| 被拒处置 | **引导**用户去系统设置开启；**不得静默失败**（用户看不到任何提示） | `flutter-architecture.md:87`（权限被拒时无引导路径是缺口） |
| **不骚扰** | 拒绝后**不反复弹窗**；同一会话内最多引导一次；再次需要时经用户主动操作（如打开开关）再引导 | 原则 4「绝不打扰」（`principles.md:14`） |
| 引导文案 | 沿用 `principles.md` §5.2 语气（建议 / 可以，非命令）；**不出现**「必须」「请立即」 | `principles.md:71-72` |
| 权限态与调度 | 权限被拒时**不注册**调度（避免无效调度堆积）；权限恢复后按偏好重新注册 | 幂等 |
| 与「可关」区分 | 权限是**系统级**；开关是**产品级**。两者独立：系统权限开但产品开关关 → 仍不通知 | 语义清晰 |

#### 4.1.6 时区与重启契约

| 项 | 契约 | 依据 |
|---|---|---|
| 时区库 | `timezone` 包；App 启动时 `initializeTimeZones()` + 设本地时区 | `flutter-architecture.md:85` |
| 时区变化 | 监听时区 / 系统时间变化 → **重新注册**（按新时区计算下次触发） | 端侧健壮性 |
| 重启后有效 | 本地通知由系统持有，**进程被杀后仍触发**；但**重启后须重新注册**以修正时区并去重（§4.1.4 路径 ②） | 重启策略 |
| 注册时机 | 启动完成（`bootstrap`）后、且**偏好已就绪**时注册；注册为**幂等**操作 | `flutter-architecture.md:166` |
| Android 12+ 精确闹钟 | Android 12+ 精确闹钟需 `SCHEDULE_EXACT_ALARM`（或 `USE_EXACT_ALARM`）权限；**须处理未授权分支**：降级为**非精确**调度（`AndroidScheduleMode.inexactAllowWhileIdle`）并**告知用户**可能有分钟级偏差；**不得**因未授权而完全静默失败 | Android 12+ 处置 |
| 降级标注 | 降级为非精确时，在设置项说明文案中体现（如「系统限制了精确定时，可能有几分钟偏差」） | 透明，不欺骗 |

#### 4.1.7 埋点与可观测契约（对齐 `PLT-003`）

| 项 | 契约 | 依据 |
|---|---|---|
| 埋点事件 | 通知**注册成功 / 失败**、**触发**（实际展示）、**点击**（落地）、权限**申请 / 结果**；均为**计数与状态**，不含内容 | `tasks.md:216` |
| 🚨 **禁打内容** | 日志 / 埋点**禁打账目金额与健康数值**（通知正文可能含「本月消费 ¥3,420」「睡了 7h12m」） | `requirements-analysis.md:222`；`tasks.md:216` |
| 脱敏 | 若必须记录正文，只记**长度 / 是否为空 / 模板 id**，**不记原文** | 最小化原则 |
| 崩溃上报 | 调度失败须上报（可观测），但**载荷脱敏** | `PLT-003` |
| 对齐 | 埋点经 `core/analytics`（`flutter-architecture.md:173`），不散落 | 分层纪律 |

### 4.3 数据流

```text
app/bootstrap（启动）
   → initializeTimeZones()（timezone）
   → core/notify/notification_scheduler.bootstrap()
        · 读权限态（permission_handler）→ 未授权：不注册 + 待用户操作时引导
        · 读偏好（APP-004 / API-008）：briefing_morning_time / briefing_evening_time + 开关态
        · 读 pendingNotificationRequests() → 与期望调度对齐（去重）
        · 逐条：cancel(stableId) → zonedSchedule(stableId, 时刻, payload)
        · Android 12+：精确闹钟未授权 → inexactAllowWhileIdle + 标注

用户改开关 / 改时刻（APP-020 触发）
   → 重新计算期望调度 → cancel(stableId) → zonedSchedule(...)（幂等）

到点触发（系统）
   → 通知展示（内容来自 API-008 预生成，可离线取到）
   → 用户点击
        → payload {route:/briefing, type} → go_router 跳 #briefing?type=...
        → features/briefing（APP-018）渲染

埋点（core/analytics）：
   仅记「注册/触发/点击/权限」计数与状态；正文脱敏（禁打金额与健康数值）
```
