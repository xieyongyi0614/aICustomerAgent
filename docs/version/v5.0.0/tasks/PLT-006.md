**结论**：**本任务的性能基线不来自设计稿**——设计稿与原型从未提非功能要求（`requirements-analysis.md:213-227`）。四项阈值是**本方案在缺口 13 中补齐的**（`requirements-analysis.md:219`），并在 `tasks.md:219` 被列为验收口径。这一点必须在 §4.2 显式声明，**不得假装它来自设计稿**。

### 2.2 为什么必须做

1. **它是「非功能需求完全未定义」这一缺口的性能面收口。** 缺口 13 指出 8 类非功能需求全缺（`requirements-analysis.md:213-227`）；性能是其中最直接决定用户留存的一类，且已被 `tasks.md:219` 明确验收口径。
2. **它是 R5 风险的唯一验证手段。** R5「Flutter 端渲染性能不达标」（概率中 / 影响中）的触发信号即「首 token 延迟 / 掉帧」（`tasks.md:270`）。没有可复现测量，R5 只能靠主观感觉判断。
3. **它是首屏性能结构性前提的检验点。** 首屏 ≤ 2.5s（含网络）**结构性地依赖**「跨域合成在服务端 + 单请求聚合」（`requirements-analysis.md:394`；`tasks.md:154`）；若客户端自行拼装 5+ 请求，首屏必然超时。本任务把该依赖写成**显式依赖**（§4.4），使性能目标与架构裁决相互印证。
4. **它是「优化项」的裁定面。** `tasks.md:270` 已给出两条优化落点（`APP-010` 节流+虚拟化、`APP-006` `RepaintBoundary`+`TickerMode`）；本任务负责**测出哪项未达标**并驱动对应落点修复——没有测量，优化是盲目的。
5. **它与 `PLT-003` 构成「测量口径单一真源」的闭环。** `tasks.md:219` 明确要求两者**共用口径**；若各测一套，性能数据不可比，验收无法裁定。

### 2.3 在 V5.0.0 中的位置

PLT 第 6 个任务，依赖 `APP-014`（`tasks.md:219`）——因为首页是首屏性能的主战场（`APP-014.md:22` 完成判据即冷启动单请求渲染）。它是 `PLT-005` 发布前的**性能回归**输入，也是 R5 的裁定点。它消费 `PLT-003` 的计时口径，反向驱动 `APP-010` / `APP-006` / `API-004` 的优化。

## 4. Technical Design Requirements

### 4.1 性能契约

#### 4.1.1 四项指标基线契约

| # | 指标 | 阈值 | 口径 | 判定 |
|---|---|---|---|---|
| 1 | **冷启动首屏** | **≤ 2.5s** | **含网络**（冷启动 → 首页首帧可见；须区分「本地首帧」与「数据填充后首帧」，`PLT-003.md:§4.1.2`） | 中位数达标（§4.1.2 采样规则） |
| 2 | **首 token 延迟** | **≤ 1.5s** | 用户发送（请求发出）→ 收到第一个 `token` 事件 | 中位数达标 |
| 3 | **列表帧率** | **60fps** | 长列表滚动期间帧耗时 ≤ 16.7ms（无持续掉帧） | 无连续丢帧（jank 计数达标） |
| 4 | **Orb 功耗** | 待测量后与基线对比（见 §4.1.6） | 可见时动画 vs 不可见时停表；单位时间耗电 / CPU 占用 | 不可见 / 后台**必须**停表 |

> **来源声明**：阈值 1~3 来自 `requirements-analysis.md:219`（缺口 13，**本方案补齐**）；指标 4 无文档阈值，本任务**先建立基线值**再定优化目标（§4.1.6）。**四项均非来自设计稿**（§4.2 D1）。

#### 4.1.2 可复现测量方法契约（★ `tasks.md:219` 原文要求）

> **必填项**：测量设备 / 工具 / 采样次数 / 判定阈值 / 报告格式。**缺一即视为测量不合格。**

| 项 | 契约 |
|---|---|
| **测量设备** | 明确机型 + OS 版本 + 构建模式（**必须 `--profile`**，`debug` 模式数据无效）+ flavor（`prod`） |
| **测量工具** | ① **Flutter DevTools**（Performance / CPU profiler / Timeline）；② **`integration_test` + `traceAction`**（自动化采集时间线）；③ **Android Profiler / Instruments**（功耗与 CPU） |
| **采样次数** | 每项 **≥ 5 次**，取**中位数**；同时记录 **p95**（避免只看均值掩盖抖动） |
| **环境控制** | 冷启动测量前**杀进程 / 清后台**；同设备同网络；记录网络类型；禁止与其它重负载任务并发 |
| **判定阈值** | 见 §4.1.1（首屏 ≤ 2.5s / 首 token ≤ 1.5s / 列表 60fps） |
| **报告格式** | 逐指标一行：指标 / 中位数 / p95 / 采样次数 / 设备 / 工具 / 是否达标 / 证据（截图或时间线文件） |
| **不可复现的写法** | **禁止**「感觉卡」「看起来快」等主观判断（`README.md:84`） |

#### 4.1.3 测量口径一致性契约（★ 与 `PLT-003` 共用）

| 项 | 契约 |
|---|---|
| 单一真源 | 首屏耗时 / 首 token 延迟的**事件名、起点、终点、单位（ms）**由 `PLT-003` 冻结（`PLT-003.md:§4.1.2`） |
| 本任务职责 | **只做测量执行与阈值判定**，**不得**重新定义口径 |
| 数据可比性 | 本任务的实测值**必须**能与 `PLT-003` 的采集数据直接对比（同口径 / 同单位 / 同起点终点） |
| 冲突处置 | 若本任务发现口径需修正 → **回改 `PLT-003`**，不各自修正（`PLT-003.md:§4.1.8`） |
| 禁止 | 「各测一套」（`tasks.md:219` 原文） |

#### 4.1.4 首屏性能结构性依赖契约（★ 写成依赖）

| 依赖 | 为什么是首屏性能的前提 | 依据 |
|---|---|---|
| **`API-004` 单请求聚合** | 首屏 ≤ 2.5s（含网络）**结构性地依赖**「一次请求拿到全部区块」；客户端自行拼装 5+ 请求必然超时 | `tasks.md:154`（API-004 验收 ①②）；`requirements-analysis.md:176-180` |
| **跨域合成在服务端** | 合成逻辑放客户端 = 请求数增加 + 端上计算，直接击穿首屏基线；亦违反反范围 | `requirements-analysis.md:394`；`SKILL.md`/`principles.md:52`（反范围） |
| **drift 只读缓存** | 冷启动先渲染骨架 / 旧数据，再等网络 → 降低「首屏可见」感知时延 | `flutter-architecture.md:374`（§7） |
| 区块级降级 | 任一子域不可用**不整体 500**，避免首屏因单域故障整体失败 | `tasks.md:154`（API-004 验收 ④） |

> **纪律**：若首屏未达标且根因指向请求数或服务端合成，本任务**必须**把该根因记入优化项并指向 `API-004`，**不得**在客户端用「加缓存掩盖」或「减少区块」来达标（后者属范围蔓延）。

| D6 | 首屏性能**结构性依赖** `API-004` 单请求 + 服务端跨域合成 + drift 缓存，**写成依赖** | `requirements-analysis.md:394`；`tasks.md:154`；`flutter-architecture.md:374` |

### 4.3 数据流（谁产出、谁消费）

```text
【测量】（本任务，可复现方法）
  设备（明确机型 / OS / --profile / prod flavor）
    → 工具：
        Flutter DevTools（Performance / CPU / Timeline）
        integration_test + traceAction（自动化时间线）

  未达标 → 优化项（指向落点）→ 复测 → 记录闭环
    · 首 token / 流式     → APP-010（合帧节流 16ms + 长文本虚拟化）
    · 列表帧率            → APP-010（虚拟化）
    · Orb 功耗            → APP-006（RepaintBoundary + TickerMode + 滚动降频）
    · 首屏请求数 / 合成   → API-004（单请求 + 服务端合成）
    · 冷启动缓存          → APP-004 / APP-014（drift 只读缓存）

【消费方 —— 本任务存在的理由】
  ① APP-010 / APP-006 / API-004 / APP-014  ← 消费「未达标项 + 优化落点」，驱动修复
  ② PLT-005（发布流水线）                  ← 消费性能回归命令（发布前门禁）
  ③ PLT-003（可观测）                      ← 双向：本任务复用其口径；实测数据可反哺其基线
  ④ 产品决策                               ← 消费「四项指标是否达标」作为发布依据

装配红线：
  ✗ 另建一套计时口径（D2）
  ✗ 主观判断 / 单次最优值充当结论（D3/D5）
  ✗ 用 debug 模式数据（D4）
  ✗ 减少区块 / 加缓存掩盖首屏根因（D9）
  ✗ Orb 后台不停表（D7）
```
