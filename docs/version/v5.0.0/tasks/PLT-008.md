**结论**：本任务补的是**「签名 APK → 可消费制品」这一段**——它是 `tasks.md:639` 明确登记但无人承接的缺口，且**在 `PLT-005` 的交付面之外**（`PLT-005.md:18` 的 Objective 只到「产出可安装产物」为止）。不补这一段，`API-022` 的表将没有可信数据可写。

### 2.2 为什么必须做

1. **它是「产物即真相」的唯一执行点。** `update-system-architecture.md` §3.2 的版本真相链要求「客户端读到的新版本号」与「制品实际版本」同源。若靠人工从 `pubspec.yaml` 抄写 `versionCode` 到发布记录，就会引入**第二真相源**——而 `pubspec.yaml` 与最终产物之间还存在 flavor、`--dart-define`、手工覆盖三层偏差（`self-distribution-guide.md:101-102` 记录的两次事故正是这三层的产物）。
2. **它是「签名即身份」从纪律变成门禁的唯一手段。** `self-distribution-guide.md:111` 写了「出包后必须核对签名指纹」，但缺 `key.properties` 时 `android/app/build.gradle.kts:60-67` 是**静默**回退 debug 签名。只要校验是人工步骤，就必然有漏做的发布；本任务必须把「指纹为空 / 等于 debug 指纹」变成**硬失败**。
3. **它是 `API-022` 的唯一上游。** `API-022` 的表字段（`size_bytes` / `sha256` / `signature_fingerprint` / `storage_path`）全部由本任务产出。没有本任务的 `release-manifest.json` 规范，`API-022` 只能靠猜字段语义。
4. **它是差分演进的低成本前置。** `update-system-architecture.md` §10 的演进路径第 ① 步（服务端出补丁）落在本任务。若本期不把「制品产出」收敛到脚本，将来接差分时会出现「全量手工、补丁脚本」的双轨。
5. **它是「打包脚本」缺口的关账点。** `tasks.md:639` 已把该缺口登记在册并等待归属；本任务是它的合理承接方（比并入 `PLT-005` 更合适——`PLT-005` 的交付面是 CI 与流水线，而本任务交付的是**制品规范与发布操作**，两者的验收方式完全不同）。

### 2.3 在 V5.0.0 中的位置

PLT 第 8 个任务，与 `APP-044` / `API-022` 同批立项。它是发布链的**中段**：`PLT-005`（构建签名）→ **`PLT-008`（制品与元数据）** → `API-022`（存储与下发）→ `APP-044`（消费与安装）。

不阻塞任何 M0~M4 开发（P1）；但**阻塞第一次真实分发**：没有本任务的制品与 manifest，`API-022` 的表是空的，`APP-044` 的检查永远返回 `has_update:false`。

## 4. Technical Design Requirements

### 4.1 制品与发布契约

#### 4.1.1 目录布局与命名契约

| 项 | 契约 | 依据 |
|---|---|---|
| 产物命名 | `zhaoxi-<versionName>+<versionCode>-<flavor>.apk` | `self-distribution-guide.md:112`（已有规范，**不新造第二套**） |
| 归档根 | `{app_release_storage_dir}`（`API-022` 的设置项；脚本以 `--storage-dir` 入参接收） | `update-system-architecture.md` §6.3 |
| 归档布局 | `{storage_dir}/{channel}/{version_code}/full/zhaoxi-...apk` | `update-system-architecture.md` §6.3（`{channel}/{version_code}/{type}/`） |
| manifest 位置 | 与 APK **同目录**：`{storage_dir}/{channel}/{version_code}/full/release-manifest.json` | 本任务 D2 |
| 幂等性 | 同 `(channel, version_code, type)` 重复发布 → **覆盖** APK 与 manifest（不追加、不重命名） | 本任务 D3 |
| 禁止项 | 不得把制品写入仓库工作区（`git status` 必须干净） | `self-distribution-guide.md:110`（签名与制品不进库）+ `tasks.md` §0.4 删除纪律 |

#### 4.1.2 ★ 产物反读契约

| 项 | 契约 | 理由 |
|---|---|---|
| `version_code` | **从 APK 反读**（`aapt2 dump badging` 的 `versionCode`，或等效的 `apkanalyzer manifest version-code`） | 见本任务 D1 |
| `version_name` | 同上（`versionName`） | 同上 |
| **禁止来源** | 禁止从 `apps/mobile/pubspec.yaml` 文本解析；禁止从命令行参数接收 | `pubspec.yaml:4` 与产物间存在 flavor / 注入 / 手工覆盖三层偏差（`self-distribution-guide.md:101-102`） |
| 一致性断言 | 若入参显式给了期望 `--expect-version-code`，则必须与反读值**相等**，否则失败退出 | 发布者可在 CI 中传入期望值做双重确认 |

#### 4.1.3 校验信息契约

| 字段 | 产出方式 | 校验口径 |
|---|---|---|
| `size_bytes` | 文件字节数（非 KB / MB 换算后的近似值） | 与 `Get-Item <apk> | Select-Object -ExpandProperty Length` / `stat -c%s` 一致 |
| `sha256` | 对 **APK 文件整体**计算，十六进制**小写**、无分隔 | 与 `Get-FileHash -Algorithm SHA256` / `sha256sum` 输出一致（大小写归一后） |
| `signature_fingerprint` | 由 `apksigner verify --print-certs <apk>` 的 **SHA-256 证书指纹**归一化为**大写、冒号分隔**（如 `AB:CD:…`）。⚠️ `apksigner` 原始输出是**连续小写十六进制**（无冒号），归一化是**格式变换**而非改字符 | 与 `apksigner` 原始输出**去分隔符、统一大小写后**逐字符一致（用例 `test_manifest_fingerprint_matches_apksigner`）。**统一口径的理由**：客户端从 `PackageManager` 读到的运行时签名证书用同一种格式化方式，写入侧与比对侧必须同形 |
| 工具缺失 | `apksigner` 不可用 → **失败退出并给出安装指引**，不回退到 `keytool`、不跳过 | 本任务 D4 |

> **纪律**：三个字段必须来自**对 APK 的直接测量**，任何字段都不得由人填写或从构建日志抓取。

#### 4.1.4 ★ 签名指纹门禁契约

| 判定 | 处置 |
|---|---|
| `key.properties` 不存在（`build.gradle.kts:59-67` 会静默回退 debug 签名） | **失败退出**（退出码非 0），错误信息点名 `key.properties` 缺失 |
| 指纹等于 **Android debug 签名指纹**（`CN=Android Debug`，常见固定值 `61:ED:37:…` 系列） | **失败退出**，错误信息点名「疑似 debug 签名回退」 |
| 指纹为空 / 无法解析 | **失败退出** |
| 指纹合法（既非 debug 亦非空） | 通过，写入 manifest |

**理由**：`self-distribution-guide.md:111` 把它定为纪律，但纪律需要门禁；出过一次 debug 签名的包，**已分发用户将永久无法覆盖升级**（`self-distribution-guide.md:110`），代价不可逆。

#### 4.1.5 ★ `release-manifest.json` 契约（本任务 → `API-022` 的交接物）

| 字段 | 类型 | 必填 | 来源 / 语义 |
|---|---|---|---|
| `schema_version` | `int` | 是 | 固定 `1`；将来契约变更时递增，`API-022` 遇未知版本**拒绝入库**（fail-closed） |
| `platform` | `string` | 是 | 固定 `android`（本期）；取值域与 `app_releases.platform` 的 CHECK 一致 |
| `channel` | `string` | 是 | 脚本入参，取值域 `dev` / `prod`（与 `app_releases.channel` 的 CHECK 一致） |
| `version_name` | `string` | 是 | §4.1.2 反读 |
| `version_code` | `int` | 是 | §4.1.2 反读 |
| `min_supported_version_code` | `int` | 是 | 脚本入参（发布决策）；必须 `>= 0` 且 `<= version_code` |
| `force_update` | `bool` | 是 | 脚本入参（发布决策）；默认 `false` |
| `release_notes` | `string` | 否 | 纯文本；长度受 `API-022` 的 `app_release_notes_max_chars` 约束（`update-system-architecture.md` §6.4） |
| `published_at` | `string` | 是 | ISO-8601 UTC（脚本以 UTC 生成） |
| `commit` | `string` | 是 | `git rev-parse HEAD`（可追溯性，`self-distribution-guide.md:112` 要求） |
| `built_at` | `string` | 是 | 构建时间（ISO-8601 UTC） |
| `artifact.type` | `string` | 是 | 本期固定 `full`（与 `artifact_type` 的 CHECK 取值域一致） |
| `artifact.file_name` | `string` | 是 | §4.1.1 命名 |
| `artifact.size_bytes` | `int` | 是 | §4.1.3 |
| `artifact.sha256` | `string` | 是 | §4.1.3（小写、64 字符） |
| `artifact.signature_fingerprint` | `string` | 是 | §4.1.3（大写冒号分隔） |
| `artifact.from_version_code` | `int` \| `null` | 是 | 本期恒 `null`（`patch` 专用，与 `app_release_artifacts.from_version_code` 对齐） |
| `artifact.storage_path` | `string` | **否**（可选） | 相对存储根的路径。**缺省时由入库侧按 `{channel}/{version_code}/{type}/{file_name}` 推导**；显式给出时必须仍在存储根之下（绝对路径 / `..` / 反斜杠一律拒绝）。存在的意义：允许将来把制品放到自定义子目录而不改布局推导规则 |

> **纪律**：`artifact` 是**对象**而非数组——manifest 描述**一次发布的一个制品**；未来出 `patch` 时由发布流程产出**第二份 manifest**（`artifact.type = "patch"`、`from_version_code = <基线>`），由 `API-022` 侧聚合进同一 `release` 行的 `artifacts[]`。这样 manifest 保持单制品语义，避免「一次发布多制品」在脚本层的复杂度。

#### 4.1.6 发布前置校验契约

| 检查 | 判据 | 失败处置 |
|---|---|---|
| `versionCode` 单调递增 | 与 `{storage_dir}/{channel}` 下已有的最大 `version_code` 比较，必须**严格更大** | **失败退出**；提供 `--allow-republish` 显式跳过（用于同号重发场景） |
| ABI 完整性 | APK 内含 `lib/arm64-v8a/libflutter.so` | **失败退出**（`self-distribution-guide.md:102` 的白屏闪退根因） |
| flavor 隔离 | `applicationId` 与 `channel` 匹配（`prod` ↔ `com.zhaoxi.app`；`dev` ↔ `com.zhaoxi.app.dev`） | **失败退出**（`self-distribution-guide.md:114`） |
| 工作区干净 | `git status --porcelain` 为空（除被 gitignore 的产物目录） | **警告**（不阻断，允许带上未提交改动出包以便内测） |

#### 4.1.7 发布操作手册契约

产出 `docs/version/v5.0.0/release-runbook.md`（**已落地**），覆盖：前置检查（版本号递增 / 签名配置 / `dart_defines/prod.json` 缺口 / build-tools）→ 出包命令（含 `--flavor prod` / `--target-platform android-arm64` / `--dart-define-from-file`）→ 发布脚本调用与入参表 → `release-manifest.json` 逐字段核对 → 入库命令（`scripts/import_release.py`）→ 真机验证清单（安装、覆盖安装、签名不一致、`dev` 只检测）→ 回滚与同号重发 → 差分扩展位（**明确标注不实现**）。

**消费方**：`API-022`（按手册的 manifest 路径与字段实现入库）、`APP-044`（按手册的真机清单做端到端验证）、后续运营/分发执行者。

#### 4.1.8 差分扩展位契约（**只登记，不实现**）

未来接差分时，本任务需要追加的能力（**本期不写实现**）：

| 项 | 未来契约 |
|---|---|
| 补丁制品命名 | `zhaoxi-<versionName>+<versionCode>-<flavor>-patch-from-<fromVersionCode>.patch` |
| 补丁制品布局 | `{storage_dir}/{channel}/{version_code}/patch/` |
| 补丁 manifest | **第二份** `release-manifest.json`（同 §4.1.5 字段，`artifact.type = "patch"`、`artifact.from_version_code` 非空） |
| 校验口径 | 补丁文件本身也要 `sha256`；**合成后**的新 APK 走与 `full` **完全相同**的双校验链（`update-system-architecture.md` §10 ⑤） |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **`version_code` / `version_name` 从 APK 反读，不从 `pubspec.yaml` 解析** | ① 「制品即真相」是 `update-system-architecture.md` §3.2 版本真相链的收口点；② `pubspec.yaml:4` 与产物间存在 flavor / `--dart-define` / 手工覆盖三层偏差，`self-distribution-guide.md:101-102` 两次事故正是这三层的产物；③ 若人工抄写，发布记录与制品可静默不一致，而客户端**只认 versionCode**，不一致将直接导致「永远提示更新」或「永远不提示」 |
| D2 | manifest 与 APK **同目录**，不集中在一处 | ① 制品自包含，拷贝目录即可迁移/备份，无「manifest 与包体分离」的悬空状态；② `API-022` 入库时可按目录扫描，无需维护第二套索引 |
| D3 | 同 `(channel, version_code, type)` 重复发布**覆盖**，不追加版本后缀 | ① `versionCode` 单调递增（`self-distribution-guide.md:109`）已保证标识唯一性；② 追加后缀会让 `storage_path` 与 `version_code` 解耦，`API-022` 无法靠目录推导；③ 真要重发同号包属异常流程，用 `--allow-republish` 显式表达，不靠文件堆叠兜底 |
| D4 | `apksigner` 缺失时**硬失败**，不回退 `keytool` | ① `keytool` 读的是 keystore 而非**已签名产物**，与「核对产物」目的不符（`self-distribution-guide.md:111` 明确要求核对**出包后**的指纹）；② 静默降级会让人误以为做了校验 |
| D5 | debug 签名回退 → **硬失败**（退出码非 0） | 见 §4.1.4 理由：一次 debug 签名的分发是**不可逆**事故 |
| D6 | `artifact` 是**对象**不是数组 | 保持「一次发布一份 manifest」的单制品语义；多制品（`full` + `patch`）由**多份 manifest** 表达，由 `API-022` 聚合。避免脚本层过早引入「一次发布多制品」的复杂度，同时不影响 §4.1.8 的扩展 |
| D7 | 脚本产 manifest，**不直连数据库** | ① 保持发布侧与运行时的解耦（脚本可在无 DB 环境跑）；② 入库的校验与 idempotency 归 `API-022`，避免两处各写一套 upsert；③ 与用户裁决「后端自建」不冲突——「后端自建」指**托管方式**，不是「脚本直连 DB」 |
| D8 | `schema_version` 必填且 `API-022` 遇未知版本拒绝入库 | 对齐仓库既有 fail-closed 纪律（同 `EXPECTED_EVENT_TYPES` 思路，`tests/v30/test_runtime_contracts.py:27-42`）：未知契约版本**不猜** |
| D9 | 工作区不干净只**警告**不阻断 | 内测期常带未提交改动出包；阻断会迫使人用 `--no-verify` 之类的旁路，反而削弱纪律。改为在 manifest 里带 `commit`（§4.1.5）留痕 |
| D10 | 手册落 `docs/version/v5.0.0/release-runbook.md`（而非 `apps/mobile/docs/`） | 本任务跨「客户端出包 + 后端入库」两侧（消费方是 `API-022`），放进版本目录与两份 Detail 同处，便于交叉引用；`apps/mobile/docs/` 面向客户端工程细节 |

### 4.3 数据流

```text
① flutter build apk --flavor prod --target-platform android-arm64 \
     --dart-define-from-file=dart_defines/prod.json          ← PLT-005 / APP-001 的产物
        ↓  build/app/outputs/flutter-apk/app-prod-release.apk
② 发布脚本（本任务）
     ├─ 反读 versionCode / versionName（§4.1.2）
     ├─ 前置校验：单调递增 / ABI / flavor 隔离（§4.1.6）
     ├─ 测量：size_bytes / sha256 / signature_fingerprint（§4.1.3）
     ├─ 门禁：指纹非空、非 debug（§4.1.4）★ 任一不过 → 失败退出
     ├─ 归档：{storage_dir}/{channel}/{version_code}/full/
     └─ 产出：release-manifest.json（§4.1.5）
        ↓
③ API-022 入库（读 manifest + 目录，写 app_releases / app_release_artifacts）
        ↓
④ APP-044 消费（GET latest → artifacts[].sha256 / signature_fingerprint）
```

**装配红线**：

- ✗ 发布脚本**不得**读 `apps/mobile/pubspec.yaml` 取版本号（§4.1.2）。
- ✗ 发布脚本**不得**写数据库、不得调 `API-022` 的接口（D7）。
- ✗ 发布脚本**不得**修改 APK（重签名 / 替换 manifest / 二次压缩）；它只做「测量 + 归档 + 记录」。
- ✗ 制品**不得**落在仓库工作区内（§4.1.1）。
