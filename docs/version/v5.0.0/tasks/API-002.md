## 2. Background

### 2.1 现状：过程**不可见**，而「过程可见」是本产品的核心差异化

| 事实 | 证据 |
|---|---|
| 对话 NDJSON **只有三类事件**：`turn_meta`（带 `type` 字段）、`token`（`{"delta": ...}`，**无 `type` 字段**）、`done`（`{"done": true, ...}`，**无 `type` 字段**） | `apps/backend/app/api/v1/chat.py:54-98`（`turn_meta` 在 `:54-78`，`token` 在 `:79-80`，`done` 在 `:95-98`） |
| 工具执行过程只有 `GET /debug/tools/executions`：**查询式、debug 命名空间、非流式** | `apps/backend/app/api/v1/debug.py:237-243` |
| 工具执行是**五段固定短路**：`① resolve → ② permission → ③ validate → ④ invoke → ⑤ normalize` | `apps/backend/app/services/tool/executor.py:1-12` |
| 记账工具已注册：`builtin.ledger.record` / `builtin.ledger.query` / `builtin.ledger.revise`；工具有面向用户的中文描述（可作 `label` 语义来源） | `apps/backend/app/services/tool/builtin.py:487`、`:557`、`:591`；`apps/backend/app/character/asuna/tool.py:101-103` |
| 🚨 `test_agent_loop_core.py` 断言 loop 与 legacy 的 `loop_runs.steps` **键集完全相同** | `apps/backend/tests/v30/test_agent_loop_core.py:492-521`（`test_steps_key_set_matches_controller_accounting`，`:520` 断言 `set(recorded) == set(legacy_steps[0])`） |
| 运行时事件类型冻结于 `EXPECTED_EVENT_TYPES`，`contracts.EVENT_TYPES` 必须与之**完全相等** | `apps/backend/tests/v30/test_runtime_contracts.py:27-41`；`:151-153`（`test_event_types_are_unique_and_complete`） |
| `RuntimeEvent` 对未知 `event_type` **fail-closed**（抛 `ValueError`）；追加须显式登记 | `apps/backend/app/application/agent_runtime/contracts.py:57` |
| 设计要求「过程全程可见、结果落点明示」 | `traceability.md:163`；`requirements-analysis.md:121-126` |

### 2.2 为什么必须做

1. **这是最大技术缺口。** `requirements-analysis.md:121` 明确：`Tool Call 过程卡`（步骤逐项打勾）**在后端没有任何接口来源**，客户端「无法渲染过程卡；只能事后补一个『已完成』的结果卡，产品核心差异化体验直接丢失」。
2. **它是 M1 收口点 C2 的关键路径。** C2 判定标准即「工具事件打通：`tool_step` 流式产出且 `loop_runs.steps` 键集未变」（`tasks.md:256`）。
3. **它决定 APP-013 能否成立。** `APP-013`（Tool Call 过程卡与结果卡）依赖本任务（`tasks.md:165`）；M1 验收口径要求「说『午饭 35 元』能看到 4 步过程卡逐项打勾且末步标注『已同步到生活 · 记账』」（`tasks.md:142`）。
4. **它的实现方式被两条铁律强约束，不能随手塞。** 见 §2.3。

### 2.3 两条必须遵守的仓库铁律（本任务的全部难点）

| # | 铁律 | 后果 |
|---|---|---|
| 1 | **不得给 `loop_runs.steps` 加键**（`test_agent_loop_core.py` 断言键集完全相同） | 一旦把工具步骤塞进 `steps`，C2 收口点直接阻塞（`tasks.md:29`、`tasks.md:131`） |
| 2 | 新事件类型**必须登记** `EXPECTED_EVENT_TYPES`，未知类型 **fail-closed** | 不登记 → `test_event_types_are_unique_and_complete` 转红（`test_runtime_contracts.py:153`）；乱发 → 运行时 `ValueError`（`contracts.py:57`） |

**结论**：事件必须走**独立通道**——从工具执行侧（`services/tool/` 五段执行）上报至 `chat.py` 的流，与 loop 的 `steps` 记账**完全分离**。

## 3. Scope

### 3.1 In Scope

1. **`tool_step` 事件 schema**（§4.1.1）：`{step_id, tool_id, label, status, detail, target}`。
2. **独立上报通道**：从 `services/tool/` 五段执行侧到 `chat.py` 的流（§4.1.2）。
3. **事件类型登记**：`contracts.EVENT_TOOL_STEP` + `contracts.EVENT_TYPES` + `tests/v30/test_runtime_contracts.py::EXPECTED_EVENT_TYPES`（§4.1.4）。
4. **`todo`（未来步）契约冻结**：服务端一次性下发 vs 客户端推导（§4.2.2）。
5. **流内顺序契约**：`turn_meta` → `tool_step`（含 `todo` 占位与 `running` / `done` / `failed` 推进）→ `token` → `done`。

7. **未知类型仍 fail-closed**（不改 `RuntimeEvent.__post_init__` 的严格性）。

## 4. Technical Design Requirements

### 4.1 接口契约

#### 4.1.1 `tool_step` 事件 schema

NDJSON 行（每行一个 JSON，末尾 `\n`，`chat.py:20-21` 的 `_stream_json`）：

| 字段 | 类型 | 必填 | 语义 | 缺省 |
|---|---|---|---|---|
| `type` | `string` | 是 | 固定 `"tool_step"`（与 `turn_meta` 同款显式类型字段，`chat.py:56`） | — |
| `step_id` | `string` | 是 | 本 turn 内**稳定**的步骤标识（同一逻辑步骤的多次状态推进共用同一 `step_id`） | — |
| `tool_id` | `string` | 是 | 工具标识（如 `builtin.ledger.record`；`builtin.py:487`） | — |
| `label` | `string` | 是 | 步骤的**用户可读**名称（如「提取金额」「保存账单」） | — |
| `status` | `string` | 是 | `todo` \| `running` \| `done` \| `failed`（枚举语义见 §4.1.5） | — |
| `detail` | `string \| null` | 否 | 右侧明细（如「¥35.00」「餐饮 · 午餐」「今天 12:32」） | `null` |
| `target` | `string \| null` | 否 | **落点明示**（如「已同步到「生活 · 记账」」）；仅末步或产生副作用的步骤给出 | `null` |

**禁止出现在事件中的字段**（与 `/debug/*` 的分工边界）：

| 禁止字段 | 理由 |
|---|---|
| 工具入参原文（`params` / `arguments`） | 可能含用户隐私与内部 prompt 结构；调试信息走 `debug.py:142 _project_executions` |
| 异常堆栈 / 异常类名 | 面向用户的事件不得携带技术细节（与 APP-008 的文案纪律同源） |
| `loop_run_id` / `step_index` | 会把流式事件与 loop 记账耦合，诱导「塞进 `steps`」的误实现 |

#### 4.1.2 独立上报通道契约（**本任务的核心设计**）

| 项 | 契约 |
|---|---|
| 载体 | 新增 `app/services/tool/step_events.py`：`ToolStepEvent`（不可变 dataclass）+ `ToolStepSink`（协议：`emit(event)`） |
| 绑定方式 | **每 turn 一个 sink**；`chat.py` 在发起流式对话时创建 sink，并把它经既有调用链传给工具执行侧（**不引入全局单例、不改 `services` 的既有入参语义**） |
| 上报点 | `ToolExecutor` 五段执行的**段边界**（`executor.py:1-12`）：`① resolve` 前发 `todo` 占位 → `②/③` 进入发 `running` → `④ invoke` 完成发 `done` → 任一段失败发 `failed` |
| 消费点 | `chat.py` 的 `generate()` 在事件循环中**排空 sink**，把每个 `ToolStepEvent` 序列化为一行 `tool_step` 并 `yield` |
| **禁止** | 写 `loop_runs` / 写任何表（本任务零 DB 写）；改 `loop_runs.steps` 的键集；把 sink 做成模块级全局单例（会串 turn） |
| 失败隔离 | sink 不可用 / 序列化失败 → **只记日志，不阻断**主回答流（对齐既有「后处理失败不影响已产出回答」纪律，`PLA-007.md:161`） |
| 并发 | sink 为 turn 局部对象；同一 session 并发 turn 互不干扰 |

#### 4.1.3 记账链路 4 步契约（验收 ③ 的判定依据）

来源：原型 `#chatLedger`（`components.md:329-341`）。`tool_id` 取 `builtin.ledger.record`（`builtin.py:487`）。

| 序 | `step_id` | `label` | `detail` | `target` | 触发段 |
|---|---|---|---|---|---|
| 1 | `ledger.extract_amount` | 提取金额 | `¥35.00` | `null` | `③ validate` 后 |
| 2 | `ledger.classify` | 识别分类 | `餐饮 · 午餐` | `null` | `④ invoke` 中 |
| 3 | `ledger.resolve_time` | 确认时间 | `今天 12:32` | `null` | `④ invoke` 中 |
| 4 | `ledger.persist` | 保存账单 | `null` | `已同步到「生活 · 记账」` | `⑤ normalize` 后 |

> **纪律**：4 步是**契约数量**（验收 ③ 断言「流式产出 4 步」），不是硬编码清单——不同工具链路的步数由服务端按实际计划下发（§4.2.2）。

#### 4.1.4 事件类型登记契约

| 项 | 契约 |
|---|---|
| 新增常量 | `contracts.EVENT_TOOL_STEP = "ToolStepRecorded"`（命名沿用既有 `EVENT_*` 风格，`contracts.py:57` 注明「追加须显式登记」） |
| 登记位置 | `contracts.EVENT_TYPES` 追加该常量；同批登记 `tests/v30/test_runtime_contracts.py::EXPECTED_EVENT_TYPES`（`test_runtime_contracts.py:27-41`） |
| NDJSON 侧 | `tool_step` 行的 `type` 字面量**由同一常量派生**，避免两套字面量漂移 |
| fail-closed / `runtime_*` | **不改** `RuntimeEvent.__post_init__` 的严格性：未知类型仍抛 `ValueError`（`contracts.py:57`）。本任务**零新增 `runtime_*` 字段**；若实现中确需新增，须登记 `tests/v30/runtime_support.py::V30_RUNTIME_FIELDS`（`runtime_support.py:10-24`） |

#### 4.1.5 `status` 枚举语义

| 值 | 语义 | 客户端渲染（APP-013 的输入，`components.md:146-152`） |
|---|---|---|
| `todo` | 尚未执行的未来步 | 1.6px 边框 `#DDDCD4`、无内容、步骤名灰显（`ink3`） |
| `running` | 正在执行 | 2px 环、顶边 `aiPrimary`、0.9s 旋转 |
| `done` | 已完成 | 底 `rgba(51,188,140,.14)` + 绿色对勾 |
| `failed` | 执行失败 | 失败标记 + `detail` 给出用户可读原因 |

> **契约追加说明**：`tasks.md:128` 列举为 `running|done|failed` 三值；`flutter-architecture.md:246` 的状态模型为 `running|done|failed|todo` 四值。**本任务裁决取四值**（理由见 §4.2.2），属**契约追加**而非私改，须在 §4.2.3 留痕。

#### 4.2.2 `todo` 契约冻结（**本任务必须回答的问题**）

> 问题（`flutter-architecture.md:252`）：若服务端只下发**已发生**的步骤，客户端需要知道**总步数**才能渲染灰显的「未来步」——这是**接口契约问题**，不是 UI 问题。

| 候选 | 优点 | 缺点 | 裁决 |
|---|---|---|---|
| A. **服务端一次性下发**（先发全部 `todo` 占位，再逐条推进 `running` → `done`/`failed`） | 客户端无需知道总步数；未来步天然灰显；步数由服务端按实际计划决定 | 首帧会一次出现 N 个占位 | ✅ **采纳** |
| B. 客户端推导（服务端只发已发生步骤） | 流更省 | 客户端必须**预知总步数**，等于把服务端计划泄漏到端上；不同工具链路步数不同，端上无法推导 | ❌ 否决 |

**冻结结论（D7）**：`todo` 由**服务端一次性下发**。契约如下：

| 项 | 契约 |
|---|---|
| 下发时机 | 工具计划确定后（`② permission` 通过、`③ validate` 之前），**一次性**下发该链路全部步骤的 `status: "todo"` 占位行 |
| 推进方式 | 每条步骤随后按 `todo → running → done/failed` 单向推进；**同一 `step_id` 复用**，客户端按 `step_id` 覆盖 |
| 步数来源 | 由服务端按实际工具计划决定（记账链路为 4 步，§4.1.3） |
| 客户端责任 | **只渲染，不推导**；不得自行补 `todo` 行 |
| 无计划的工具 | 若工具链无显式步骤计划 → **不下发 `todo` 占位**，直接发 `running` / `done`；客户端对「无 todo 的链路」不得假设步数 |

### 4.3 数据流

```text
POST /api/v1/chat/message（chat.py:35-108）
   → chat.py::generate() 创建 turn 局部 ToolStepSink
   → agent_service.stream_chat(..., step_sink=sink)          ← 新增透传参数
        → 工具计划确定
        → ToolExecutor.run(...)（executor.py:136+，五段短路）
             ① resolve  → sink.emit(todo × N)               ← 一次性下发全部占位
             ② permission → 通过后 sink.emit(running)
             ③ validate  → 通过后 sink.emit(running, detail=…)
             ④ invoke    → 过程中 sink.emit(running/done, detail=…)
             ⑤ normalize → sink.emit(done, target="已同步到…")
             任一段失败 → sink.emit(failed, detail=用户可读原因)
   ← 每次 emit 入队；generate() 在事件循环中排空 sink
   → yield _stream_json({"type": "tool_step", ...})           ← 与 token / turn_meta 同流
   → 最终 yield {"done": true, ...}（chat.py:95-98，不变）

独立通道的红线：
   ✗ 不写 loop_runs / 不写任何表
   ✗ 不改 loop_runs.steps 键集（test_agent_loop_core.py:520 断言键集相同）
   ✗ 不把 sink 做成全局单例
```
