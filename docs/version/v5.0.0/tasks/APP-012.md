### 2.2 为什么必须做

1. **它是 `REQ-CHAT-02` 与 `REQ-CHAT-07` 的唯一落点。** `traceability.md:42` 明确「② 对话 · 人格状态栏（三模式）」→ `APP-012`。
2. **它是「不是普通聊天页」的视觉标识。** `components.md:315` 明确对话页「不是普通聊天页」，头部的人格状态栏（Orb + 名字 + 在线态 + 模式）是这一判断的第一眼依据。
3. **它是 M1 验收口径的一条。** `tasks.md:142` 要求「切到 professional 模式后 `turn_meta.role_mode` 变化且回复风格可见差异」——本任务是该口径的 UI 与交互承载方（但**受写路径缺口阻塞**，见 §4.2 D4）。
4. **`A28` 必须一次做成共用组件。** 它在**两处**被使用（对话页切换 + 我的页人格卡，`components.md:43-50`）；若各做一套，必然漂移（`tasks/APP-007.md:168` D12 的同款纪律）。
5. **「在线」语义必须先裁决。** 后端无该字段（§2.1），若不裁决，实现会去猜一个不存在的接口。

### 2.3 在 V5.0.0 中的位置

M1 客户端第 4 个任务，依赖 `APP-006`（Orb）与 `APP-009`（装配）；`APP-020`（我的页）**复用**本任务的 `A28` 组件。

#### 4.1.5 数据源与切档契约

**读路径（完整）**：

| 来源 | 字段 | 用途 | 证据 |
|---|---|---|---|
| `GET /state` | `mode`（`str \| None`） | 进页快照：当前确认模式 | `schemas.py:106`；`state.py:19-21`、`:121` |
| `GET /state` | `last_behavior.mode`（`confirmed` / `effective` / `switched`） | 进页快照：模式元信息（是否已切换） | `schemas.py:87-90`；`state.py:43-50` |
| `turn_meta`（流式） | `role_mode`（`{mode, intent, confidence, reason}`） | 每轮**实时**更新副标中的档位名 | `chat.py:57`；`models/router.py:6-9` |
| 优先级 | 有 `turn_meta.role_mode` → 用其 `mode`；否则用 `/state.mode`；都为 `None` → 展示 `default` | 实时值优先于快照 | `chat_pipeline.py:95`（服务端亦以 `default` 兜底） |

**写路径（缺失 → 必须登记）**：

| 项 | 事实 / 契约 |
|---|---|
| 端上「期望模式」 | 切档后写入**端上偏好**（`shared_preferences`，`flutter-architecture.md:93`）；键名建议 `chat.role_mode_preference`，取值 ∈ 三档；**参数类偏好，非 `*_enabled` 开关**（裁决 9 合规，`tasks.md:26`） |
| 端上乐观展示 | 切档后**立即**更新 chip 与副标（乐观 UI）；**但**不得把该值当作服务端 `role_mode` |
| 服务端确认模式 | **当前无客户端写路径**：`ChatRequest` 无 mode 参数（`schemas.py:6-9`）；无 mode 设置端点；唯一写回在管线内部（`chat_pipeline.py:809-810` → `conversation_repository.py:111-117`） |
| **禁止** | 在端上伪造 `turn_meta.role_mode`；在端上缓存里写「服务端已切档」的假状态；为切档私自扩后端字段或新增端点 |
| **待定 + 阻塞条件** | 「切档后 `turn_meta.role_mode` 变化且回复风格可见差异」（M1 口径，`tasks.md:142`）**需后端提供写路径**（新增 API 任务，或 `ChatRequest` 增 mode 参数）→ **阻塞条件**：`tasks.md` 任务总览不增项（`tasks/README.md:5`）；在此之前，本任务交付 **UI + 端上偏好 + 读路径同步**，并以「缺口已登记且未被伪造」为验收（§8 AC5） |
| 回退行为 | 阻塞项未解决时，切档后**服务端 confirmed 模式不变**；端上**必须**以服务端返回的 `role_mode` / `/state.mode` 为准回写展示（避免「切了但没生效」的静默不一致——须在 UI 上以「待生效」语义提示，文案待定） |

#### 4.1.6 「在线」判定契约

| 项 | 契约 |
|---|---|
| 后端字段 | **无**（`StateSnapshotOut` 无 online / connectivity 字段，`schemas.py:101-107`） |
| 判定 | **端上本地判定**：以「最近一次请求是否成功 / 网络是否可达」推导（`core/network` 的连通性状态，`APP-003`） |
| 在线 | `●` + 文字色 `health`（`tokens.md:24`） |
| 离线 | `●` 色改中性（`ink3`），副标文案改为**离线语义**；**具体文案设计稿未给** → 见 D6（**待人工确认**） |
| 禁止 | 凭空调用不存在的后端在线接口 |

#### 4.1.7 切档写路径缺口登记（**本任务最重要的产出之一**）

| 项 | 内容 |
|---|---|
| 缺口 | 客户端无任何方式写入服务端确认模式（`state.mode` / `conversation.mode`） |
| 影响 | `REQ-CHAT-07` 的「三档切换」在**服务端侧不可由用户直接触发**；M1 验收口径（`tasks.md:142`）当前**不可由客户端保证** |
| 处置 | ① 本任务交付 UI + 端上偏好 + 读路径同步；② 缺口以**待定 + 阻塞条件**登记；③ **不得**在端上伪造 |
| 升级路径（供上层决策，本任务不实施） | 新增 API 任务提供 `PUT /state/mode`（或等价）**或**在 `ChatRequest` 增 `mode` 参数（二者均属 `tasks.md` 层面的任务变更） |

### 4.3 数据流

```text
进页（APP-009 装配的对话页头部槽位）
   → features/chat/data（经 APP-003 的 dio 客户端）
        → GET /state（state.py:52）
              · mode（str | None）                      → 副标档位（快照）
              · last_behavior.mode{confirmed, effective, switched}
   → 本任务：状态栏渲染
        · Orb md 34px（APP-006）
        · 「亚丝娜」16.5px/700（principles.md:63）
        · 「●在线 · <档位> 模式」11.5px 色 health（● 由端上连通性判定，D6）
        · 右侧 A10 mode-chip（点击 → 展开 A28 三选，D3）

流式期间
   → turn_meta.role_mode（chat.py:57）→ 副标档位**实时更新**（优先级最高，D10）

切档（用户点 A28 选项）
   → 端上偏好写入（shared_preferences，D9）
   → 乐观更新 chip / 副标（**仅端上展示**）
   → ✗ 无服务端写路径（§4.1.7）→ 不得伪造 role_mode
   → 下一轮 turn_meta.role_mode / 下次 /state 到达时**以服务端为准回写展示**（D4 回退行为）

分层红线：
   ✗ 组件不 import core/** / features/**（L2，D8）
   ✗ 不新增后端端点 / 不改 ChatRequest（D4）
```
