### 2.2 为什么必须做

1. **它是本产品与普通助手的核心差异。** `requirements-analysis.md:123` 明确：设计要求「步骤逐项打勾、当前步旋转、未来步灰显、结果落点明示」，设计稿 §04++ 写「可见 = 可控 = 信任」。缺了它，对话就退化为普通聊天。
2. **它是 C2 收口点的客户端半边。** C2 判定标准为「工具事件打通：`tool_step` 流式产出且 `loop_runs.steps` 键集未变」（`tasks.md:256`）。服务端半边由 API-002 交付，**客户端半边即本任务**；只有两者合上，M1 验收口径「说『午饭 35 元』能看到 4 步过程卡逐项打勾且末步标注『已同步到生活 · 记账』」（`tasks.md:142`）才成立。
3. **它决定 M2 首页的信息密度上限。** `APP-014` 依赖本任务（`tasks.md:166`）；过程卡是首页 → 对话之间的「AI 正在做事」证据链。
4. **它必须把 `tasks.md` 与 `A14` 的三态与 `flutter-architecture` 的四值这一处不一致显式处置。** 见 §4.2 D1 与 §4.1.3。

### 2.3 在 V5.0.0 中的位置

本任务在任务注册表中列于 M2 客户端首位（`tasks.md:165`），但**同时是 M1 末收口点 C2 的客户端半边**（`tasks.md:121`「M1 的收口点是 Tool Call 过程卡」）。两条口径不矛盾：服务端 `tool_step` 在 M1 打通（API-002），客户端渲染在 M2 合上。关键路径为 `APP-007 → APP-013 → APP-014`（`tasks.md:246`）。

## 3. Scope

### 3.1 In Scope

1. **`A14 proc` 过程卡**（§4.1.1 / §4.1.2）：容器、头部、步骤行三段的尺寸 / 内边距 / 圆角 / 投影 / 层级，逐条照 `components.md:133-153`。
2. **步骤四态契约**（§4.1.3，本组件的灵魂）：`done` / `running` / `todo` / `failed` 的图标表现、步骤名颜色、动效；**其中 `failed` 的视觉规格由本任务裁决给出**（`A14` 与 `tasks.md` 只写了三态）。
3. **明细列「结果落点」契约**（§4.1.4）：右侧明细位渲染 `detail`；末步渲染 `target`（落点明示）。
4. **记账链路 4 步真实文案**（§4.1.5）：照 `#chatLedger` 逐条落地，作为验收 ① 的判定依据。
5. **结果卡 + `A12 chip-btn` 快捷操作 chips**（§4.1.6）：chips **由服务端下发**，客户端只渲染。
6. **步骤状态机装配**（`features/chat/presentation/`）：按 `step_id` 覆盖推进，**不推导总步数**。
7. **数字等宽与动效纪律**：明细位数值走 `AppTypography.numeric`；`running` 的 0.9s 循环属「循环指示器」，不受 400ms 限制。

| # | 禁止项 | 理由 |

#### 4.1.3 步骤四态契约（★ 本组件的灵魂）

> **前置**：`status` 枚举的**语义**由 API-002 冻结为四值（`API-002.md:148-157`）；本表给出**视觉规格**。
> **不一致处置**：`tasks.md:165` 与 `components.md:146-152` 只写三态（`done` / `running` / `todo`），而 `flutter-architecture.md:246` 的状态模型为四值（含 `failed`）。**本任务裁决取四值**（§4.2 D1），并为 `failed` 补齐与前三态**并列**的视觉定义。

| 态 | 图标位（20px 圆） | 步骤名色 | 右侧明细色 | 头部右侧状态 | 动效 |
|---|---|---|---|---|---|
| `done` | 底 `rgba(51,188,140,.14)` + 对勾 `12px` 色 `health` | `ink`（正常） | `ink3` | 绿对勾 `13px` | 无 |
| `running` | `2px` 环，色 `rgba(122,92,255,.25)`，**顶边为 `aiPrimary`** | `ink`（正常） | `ink3` | 旋转圈 `15px` | `0.9s` 线性循环 |
| `todo` | `1.6px` 边框 `toggleOff`（值 `#DDDCD4`），**无内容** | **`ink3`（灰显）** | `ink3` | —（未开始） | 无 |
| `failed` | 底 `rgba(255,157,118,.16)`（`warm` 语义底，`tokens.md:66`）+ `✗` `12px` 色 `warm` | **`ink`（正常，不灰显）** | **`ink2`** | `✗` `13px` 色 `warm` | 无 |

**`failed` 视觉规格的四条裁决依据**：

| # | 规则 | 理由 |
|---|---|---|
| 1 | 步骤名**不灰显**，保持 `ink` | `failed` 是**已发生**的步骤，与 `todo`（未发生）语义相反；灰显会与 `todo` 混淆，用户无法区分「没做」与「做失败了」 |
| 2 | 右侧明细用 **`ink2`** 而非 `ink3` | 失败原因是需要用户读到的关键信息；`ink3 on canvas` 对比度仅约 `2.4:1`，明确「仅可用于装饰性文字与单位，不可承载关键信息」（`tokens.md:259`） |
| 3 | 用 **`warm`（暖橙，语义「关怀/提醒」）** 而非红色告警 | 设计系统**无 error 色 token**；红线 5 禁止「后台系统式的冷灰蓝」与刺眼告警；`warm` 的既定语义是「关怀/提醒」（`tokens.md:23`），与「温暖而非企业」一致。**不新增色值 token**——若设计侧后续要求更强警示，须走 `APP-002` 的 token 扩展（独立决策） |
| 4 | `todo` 边框用 **`AppColors.toggleOff`** 而非字面量 `#DDDCD4` | `A14` 写的是字面量，但该值恰等于既有 token `toggleOff`（`tokens.md:38`）；红线 2 禁止硬编码色值（`SKILL.md:43`） |

#### 4.1.4 明细列「结果落点」契约

> `components.md:153`：「明细列**必须写结果落点**」。落点来源是事件的两个字段：`detail`（过程明细）与 `target`（落点明示，仅末步或产生副作用的步骤给出，`API-002.md:104`）。

| 步骤位 | 渲染字段 | 示例文案 | 说明 |
|---|---|---|---|
| 过程步（非末步） | `detail` | `¥35.00` / `餐饮 · 午餐` / `今天 12:32` | 取自 `tool_step.detail` |
| 末步 / 副作用步 | `target` | `已同步到「生活 · 记账」` | 取自 `tool_step.target`；渲染在**同一右侧明细位**，`12px`，带书名号 |
| 字段为 `null` | 不渲染右侧明细 | — | 不得填 `—` / `--` 等占位（会被误读为数据） |

#### 4.1.5 记账链路 4 步真实文案契约（验收 ① 的判定依据）

来源：原型 `#chatLedger`（`components.md:333-337`）。头部文案「正在记账」；末步完成后头部右侧转为绿对勾。

| 序 | `step_id` | 步骤名（`label`） | 右侧明细（`detail`） | 落点（`target`） |
|---|---|---|---|---|
| 1 | `ledger.extract_amount` | 提取金额 | `¥35.00` | — |
| 2 | `ledger.classify` | 识别分类 | `餐饮 · 午餐` | — |
| 3 | `ledger.resolve_time` | 确认时间 | `今天 12:32` | — |
| 4 | `ledger.persist` | 保存账单 | — | `已同步到「生活 · 记账」` |

> **纪律**：4 步是**契约数量**（服务端按实际计划下发，`API-002.md:137`），不是客户端硬编码清单——不同工具链路步数不同（旅行规划为 4 步，`components.md:322-324`）。

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| D1 | **步骤四态（含 `failed`），并给出 `failed` 视觉规格** | `flutter-architecture.md:246` 的状态模型为四值，而 `tasks.md:165` / `A14` 只写三态；取四值可覆盖 API-002 的事件契约（`API-002.md:151` 明列 `failed`），属**契约补齐**而非私改（§4.1.3 已留痕） |
| D2 | `todo` 总步数**由服务端一次性下发**，客户端**不推导** | API-002 §4.2.2 D7 已冻结（`API-002.md:187-195`）；客户端只按 `step_id` 覆盖渲染 |
| D3 | `failed` 用 **`warm`** 而非红色 / 新增 error token | 设计系统无 error token；红线 5 禁止刺眼告警；`warm` 语义即「关怀/提醒」（`tokens.md:23`）；新增 token 须独立决策 |
| D4 | `failed` 步骤名**不灰显**、明细用 `ink2` | 区分「失败」与「未做」；`ink3` 对比度不足承载关键信息（`tokens.md:259`） |
| D5 | `todo` 边框走 **`AppColors.toggleOff`**，不写 `#DDDCD4` 字面量 | 红线 2（`SKILL.md:43`）；该值恰为既有 token（`tokens.md:38`） |
| D6 | **chips 由服务端下发**，客户端零生成 | `REQ-CHAT-05`；`traceability.md:46` 的 ⚠️；本地生成会与服务端建议脱节 |
| D7 | 左边距 **31**、最大宽 **86%** 固定，不随屏幕自适应 | 与 AI 气泡对齐是本组件「看起来像 AI 在说话」的关键（`components.md:137`） |
| D8 | `running` 环 `0.9s` 无限循环**不受** 400ms 限制 | 循环指示器是 400ms 纪律的既定例外（`tokens.md:231`、`:235`） |
| D9 | 组件**无状态**；步骤推进由 `features/chat` 的状态机驱动 | 无状态组件才能 golden 稳定渲染（沿用 APP-007 D3） |
| D10 | 组件**不得 import `core/` 或 `features/`** | 分层纪律 L2（`flutter-architecture.md:196`）；否则 golden 需要网络桩 |
| D11 | 无 `todo` 占位的链路**不得假设步数** | API-002 §4.2.2 末行：无显式步骤计划时服务端不发 `todo`（`API-002.md:195`） |
| D12 | 新增设置 = **无** | 裁决 9（`tasks.md:26`） |

### 4.3 数据流

```text
POST /chat/message（NDJSON 流）
   → dio ResponseType.stream → utf8.decoder → LineSplitter → jsonDecode（flutter-architecture.md:208-220）
   → Freezed sealed union ChatEvent：ToolStep 分支（flutter-architecture.md:31-42）
   → features/chat/data/chat_repository（L3：presentation 不得直调 dio）
   → Riverpod Notifier：ChatTurnState.toolSteps 按 step_id 覆盖推进（flutter-architecture.md:239-249）
        · 收到 status=todo 行 → 追加占位（灰显）
        · 收到 status=running 行 → 覆盖为运行态（环旋转）
        · 收到 status=done / failed 行 → 覆盖为终态
        · 客户端**不补行、不推算总步数**
   → design_system/components/proc_card.dart（A14，纯数据入参）
   → 结果卡 + A12 chips（chips 来自服务端下发的 QuickAction 列表）

装配红线：
   ✗ 不推导 todo 总步数（D2）
   ✗ 不本地生成 chips 文案（D6）
   ✗ 过程卡不渲染 tool_id / step_id（§3.2 #6）
```
