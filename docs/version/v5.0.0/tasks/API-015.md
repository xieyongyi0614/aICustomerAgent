## 2. Background

**机制已完成，只缺出口。** 待确认登记薄在 V4.0.0 `PLA-010` 已交付，语义完整：

| 事实 | 证据 |
|---|---|
| 前缀常量与挂载位置 | `app/services/ledger/pending.py:18`（`PENDING_PREFIX = "ledger_confirm:"`）、`:84-96`（写 `scene_state.pending_action`） |
| 登记载荷 = `ConfirmationRequest` + `LedgerExtraction` | `pending.py:62-65`（`ActionRecord.params = {"confirmation": …, "extraction": …}`） |
| 读取 / 清除 / 到期 | `pending.py:100`（`load_pending`）、`:123`（`clear_pending`）、`:133`（`expire_if_due`） |
| 待确认触发条件与候选 | `app/services/ledger/confirmation.py:59`（`should_confirm`）——5 种 reason：`missing_amount` / `low_confidence` / `direction_ambiguous` / `category_ambiguous` / `amount_over_threshold`（`:15-19`） |
| 到期 TTL | `confirmation.py:13`（`CONFIRM_TTL_HOURS = 24`） |

**但产品面完全没有出口**：`app/api/v1/` 下 `pending` 命中只有 `proactive.py:18`（待投递主动消息）与 `debug.py:1222`（`/debug/plans/pending`），**均与 ledger 待确认无关**；`load_pending` / `register_pending` / `ledger_confirm` 的调用点全部落在 services / models / engines / chains / application 层。

**为什么用 `action_records` 而不是 `scene_state` 做读面入口**：`load_pending` 需要 `session_id`（`pending.py:100-103`），而 `scene_state` 是按会话分片的，产品面拿不到"该用户全部会话"。而 `ActionRecord` 自带 `user_id`（`pending.py:51`）、`session_id`（`:52`）、`gate_reason="pending_confirmation"`（`:67`）、`status="planned"`（`:66`）四个可枚举字段 —— **读面以 `action_records` 为入口，写面再用 `record.session_id` 回到既有 `clear_pending`**，即可零改既有语义。

**为什么必须做**：`REQ-LEDG-11` 是 `tasks.md` §15.3 一期验收口径的核心（"进 34 能看到真实待确认条目并可确认 / 修改 / 忽略"）；不做则 34 页只能造假，直接违反 `APP-014` 确立的假数据红线。

## 4. Technical Design Requirements

### 4.1 接口契约（字段级）

#### 4.1.1 `GET /ledger/pending`

| 参数 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `limit` | int | 50 | `ge=1, le=200`（沿用 `ledger.py:22` 的 `LIMIT_MAX = 200`） |

响应（信封，对齐 `memory.py` 先例）：

| 字段 | 类型 | 语义 |
|---|---|---|
| `generated_at` | str(ISO8601) | 生成时刻 |
| `total` | int | 待确认总数（与 `items` 同快照） |
| `items` | list | 见下 |
| `items[].pending_key` | str | **对外主键**（=`ConfirmationRequest.pending_key`，`confirmation.py:39-41` 的 16 位 sha1 前缀） |
| `items[].reason` | str | 五选一：`missing_amount` / `low_confidence` / `direction_ambiguous` / `category_ambiguous` / `amount_over_threshold` |
| `items[].question` | str | 澄清问句（服务端模板渲染，`confirmation.py:44-56`）——**端上零拼接** |
| `items[].candidates` | list[{`value`,`label`}] | 候选选项（`confirmation.py:22-25`） |
| `items[].amount_minor` | int \| null | 已解析出的整数分（`confirmation.py:35`） |
| `items[].source_ref` | str | 来源引用（`confirmation.py:36`） |
| `items[].expires_at` | str(ISO8601) | 到期时刻（`confirmation.py:34`） |
| `items[].ai_guess` | object | **AI 判断**，来自 `extraction`：`{category_hint, direction, merchant_hint, confidence}`（`app/models/ledger.py:105-117`）。字段缺省时**整块缺省**（不返空对象） |
| `items[].occurred_at_hint` | str \| null | 时间提示（`models/ledger.py:112`） |

#### 4.1.2 `POST /ledger/pending/{pending_key}/confirm`

请求体（全部可选，缺省 = 采纳 AI 判断）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `category_name` | str \| null | 用户改后的分类名；与 AI 判断不同时触发**规则沉淀**（`add_alias`） |
| `direction` | `"expense"` \| `"income"` \| `"transfer"` \| null | 方向 |
| `amount_minor` | int \| null | `gt=0`（`models/ledger.py:69`） |
| `occurred_at` | str(ISO8601) \| null | 发生时间 |

响应：

| 字段 | 类型 | 语义 |
|---|---|---|
| `entry_id` | str | 落账后的账目 id |
| `created` | bool | 是否新产生（幂等重放时 `false`，对齐 `RecordOutcome.created`，`service.py:25-29`） |
| `learned_alias` | str \| null | 本次沉淀的别名（未沉淀则缺省） |

**错误语义**：`pending_key` 不存在 / 已过期 / 已确认 → **404**（不得 500）；`amount_minor <= 0` → 422。

#### 4.1.3 `POST /ledger/pending/{pending_key}/ignore`

响应：`{ "ok": true, "pending_key": str }`。**不产生账目**、不写 `learned_alias`。

#### 4.1.4 鉴权与降级

| 项 | 约定 |
|---|---|
| 身份 | 三端点均 `user_id: str = Depends(require_user)`（`app/api/v1/auth.py`），**不接 `user_id` 请求参数**（`tasks.md` §14 D3） |
| 越权 | `record.user_id != user_id` → **404**（不泄露存在性） |
| 降级 | 单条载荷解析失败（`params` 缺键，`pending.py:114`）→ **跳过该条**并在响应中计入 `degraded` 计数，**不整体 500** |

### 4.2 关键裁决

| # | 裁决 | 理由 |
|---|---|---|
| 1 | **读面入口用 `action_records`（`user_id` + `gate_reason="pending_confirmation"`），不用 `scene_state` 枚举** | `scene_state` 按 `session_id` 分片（`pending.py:103`），产品面无法枚举用户全部会话；`ActionRecord` 自带 `user_id`（`pending.py:51`）与 `session_id`（`:52`），一次查询即可拿到写面所需会话号 |
| 2 | **对外主键用 `pending_key` 而非 `record.id`** | 端上只应看到业务标识；`pending_key` 已是幂等键（`ActionRecord.dedupe_key`，`pending.py:61`），且 `source_ref|reason` 派生（`confirmation.py:39-41`）天然去重 |
| 3 | **确认时"改分类"即沉淀别名** | 直接兑现 `pages/34-ledger-auto.html:132` 的 hint「确认后我会记住」与 `:170` 的「我学会的规则」；复用既有 `category.py:106` 的 `add_alias`，**不新建学习机制** |
| 4 | **`question` / `candidates` 由服务端下发，端上零拼接** | 澄清问句来自模板渲染（`confirmation.py:50-56`），端上拼接会制造第二套文案真相（`progress-audit-2026-09-29.md` §6.3 偏离 2 的教训） |
| 5 | **不改 `pending.py` 既有四函数** | 它们已被对话链路消费；新增函数而非改造，符合"加实体、不加约束"的兼容策略（`tasks.md` §0.2 前提二） |
| 6 | **不新增设置项** | 阈值类已存在（`app/core/settings/ledger.py:10-12`）；新增功能位会违反 `tasks.md` §0.2「不加功能开关」 |

### 4.3 数据流

```text
对话链路（既有）
  chat → ledger 工具 → should_confirm(confirmation.py:59)
        → register_pending(pending.py:30) → ActionRecord(planned) + scene_state 指针 + action_schedule

产品面（本任务）
  GET /ledger/pending
    ledger.py → pending.list_pending(user_id)
      → [先 expire_if_due(session) 清过期]
      → action_repository 按 user_id + gate_reason + status=planned 枚举
      → 逐条解出 ConfirmationRequest + LedgerExtraction → 组装信封

  POST /ledger/pending/{pending_key}/confirm
    ledger.py → pending.confirm_pending(...)
      → 定位 ActionRecord → user_id 比对（越权 404）
      → clear_pending(record.session_id, status="confirmed")   # 既有函数，不改语义
      → ledger/service.record_entry(draft, idempotency_key=pending_key)  # 既有入口
      → 若用户改了分类 → category.add_alias(...)              # 规则沉淀
    → {entry_id, created, learned_alias}

  POST /ledger/pending/{pending_key}/ignore
    → clear_pending(record.session_id, status="ignored") → {ok}
```
