**实际后果**：健康文案已经出现在 `#home` 三宫格 hint 与空态引导、`#life` 健康模块卡、`#profile` 设备连接行、`#health` 健康页；**若免责与同意流程缺失，任何一个页面都可能构成合规缺口**——而 M4 后置**不会**让这些文案消失。

### 2.2 为什么必须做

1. **它是上架合规的硬前置，且交付与健康模块是否上线无关。** 健康信息属 PIPL 敏感 PI，**必须单独同意**（`REPORT.md:95`；`requirements-analysis.md:132`、`:187`）；缺少免责与单独同意，App Store 与国内安卓商店审核均会拒（风险 R6，`tasks.md:271`）；`tasks.md:204` 原文已明确交付与 M4 后置无关，且后置**不会**移除首页三宫格文案与 `APP-014` 空态引导（`tasks.md:196`）。
2. **它是「免责 ≠ 同意」这条规则的唯一落点。** 用户**拒绝**健康数据授权后，App 内**仍会**出现健康表述（空态引导文案、模块卡摘要）——因此免责**不能**挂在同意态上（§4.1.3）。
3. **它是三个任务边界的收口点，也是红线 8 与 `REQ-HLTH-05` 的实现面。** 本任务 = 健康**专项**同意页 + rationale + 免责常驻；通用授权治理与导出 / 清空归 `APP-021`；隐私政策法律文案与备案归 `PLT-002`（`tasks.md:204`、`:215`；`APP-021.md:191`），三者**不得重复实现**（§4.1.4）；设计系统走查清单第 9 条即为本任务的验收形式（`principles.md:120`）。

### 2.3 在 V5.0.0 中的位置

M4 客户端第 3 个任务（`tasks.md:204`），**P0 且与门控解耦**。它只依赖 `APP-021`（M3），是 `APP-014` / `APP-015` / `APP-020` / `APP-021` / `APP-024` 各页面健康文案的**合规底座**；它与 `APP-021`、`PLT-002` 的分工见 §4.1.4。

## 3. Scope

### 3.1 In Scope

1. **独立同意流程**（§4.1.1）：健康数据专项同意页（**独立成页 / 独立成项**，不与总同意混）+ 同意 / 拒绝态回传。
2. **隐私政策 rationale**（§4.1.2）：说明为何需要健康数据、数据如何被保护（按决策 D2 口径：强调**用户控制权**）、如何回收。
3. **免责常驻组件**（§4.1.3）：固定文案「非医疗建议，请咨询医生」；**免责 ≠ 同意**（拒绝同意后仍常驻）。
4. **边界契约**（§4.1.4）：与 `APP-021`（通用授权治理 / 导出 / 清空）、`PLT-002`（法律文案 / 备案）的职责切分，**不重复实现**。
5. **逐页走查清单**（§4.1.5）：枚举所有含健康表述的页面，逐页确认免责覆盖。
6. **文案合规**（§4.2.5）：禁用词清单 + 必含词；按决策 D2 删除「本地优先 / 本地可见」。
7. **授权态回传**：向 `APP-021` / `APP-023` 回传同意结果（供健康授权独立项与平台权限申请衔接）。
8. **红线自检**（§7.3）：无硬编码色值 / 无医疗级措辞 / 无「本地优先」/ 无 `*_enabled`。
