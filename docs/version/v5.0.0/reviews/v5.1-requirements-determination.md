## 3. 冲突与缺口清单（编号接续 §3 的 1~14，本轮为 15~28）

> 每条给出：**现象 → 证据 → 后果 → 裁决**。带 🚫 的为**开工前必须闭**项。

### 🚫 冲突 15：设计系统 skill 与 `design/pages/` 在相册数值上三处不一致

- **现象**：同一批相册数据在三处写法不同。
  - `components.md:631`（B14）：「38 张截图 + **12 张相似照片**可清理，腾出 1.4 GB」
  - `components.md:650-653`（B15）：「已选 **12 张**」「过期截图 **8 张** + 相似照片 **4 张**」
  - `components.md:688`（B17）与 `pages/62-album-ai.html:112`：「**76** 张可清理（截图 **38** / 连拍 **26** / 重复 **12**）」
  - `pages/37-album.html:128`：「38 张过期截图、26 张相似连拍和 12 张重复保存」
  - `pages/38-album-manage.html:112`：「已选 **76** 张」
- **证据**：上列行号。B17 / B18 与 `pages/` 一致（38+26+12=76 自洽），B14 / B15 的 12 张与 8/4 张为**旧稿残留**——**skill 自身内部即不一致**，故"以 skill 为准"这条优先级规则在本例中无法直接套用。
- **后果**：组件 golden 与页面验收会各钉一套数字；若照 B15 实现批量管理，AI 预选分组会与 62 页的 76 张对不上。
- **裁决**：**以 B17 / B18 与 `pages/` 的自洽口径为准**（`76 = 过期截图 38 + 相似连拍 26 + 重复保存 12`），B14 / B15 的 12 张 / 8 张 / 4 张视为待修正残留；**回写 skill** 登记为待办（skill 是 UI 唯一真源，须由设计侧修正，不由端侧擅自改规格）。

### 🚫 冲突 16：「车辆档案都在本机」文案 vs 服务端 car 域

- **现象**：`pages/39-car-profile.html:125` 写「所有档案都在本机，可以随时改」；`components.md:665`（B16）复述同句。而本版本裁决为**新建服务端 car 域 + 迁移 `0003`**（车辆档案若落服务端，此文案即为误导性陈述）。
- **证据**：`pages/39-car-profile.html:125`、`components.md:665`；裁决见下文 D12 / D13。

- **裁决**：二选一（见 D13），**推荐 A**：服务端存储 + 文案改口径，对齐既有 D2「强调用户控制权而非物理位置」。无论哪种，**"都在本机"这四个字不得原样落地**。

### 🚫 冲突 17：相册「不需要联网权限」表述 vs 登录态 App

- **现象**：`pages/37-album.html:166` 写「相册完全离线：…**不需要联网权限**，也不会上传服务器」；`components.md:641-642` 复述。
- **证据**：`pages/37-album.html:166`。而朝夕 App 主体（对话 / 记账 / 记忆）**必须联网**，Android 清单必然声明 `INTERNET`。
- **后果**：「不需要联网权限」在系统层不成立（App 整体需要网络权限），属**不可验证的承诺**；合规审核与用户信任双输。
- **裁决**：文案改为**「相册功能无需联网即可使用，照片不会上传服务器」**——把承诺收敛到"相册这一功能"的范围内，既真实又可验证。**"不上传服务器"必须保留**（红线 9 不可谈判项）。

### 🚫 冲突 18：生活模块宫格把「日历 / 旅行」提升为常规模块 vs V5.0.0 已裁决 🚫 后置

- **现象**：`pages/30-life.html:145-152` 的「日历 / 旅行」两卡已**不再是 `.soon` 虚线占位**，而是与记账 / 任务同级的常规 `.mod` 卡，并带文案「15:00 方案对齐」「十一行程规划中」；`components.md:459-461`（B4）同步为 **3×3 九模块**（记账/备忘录/任务/日历/旅行/健康/车辆/相册）。而 `requirements-analysis.md:270` 的 `REQ-LIFE-05` 已裁决日历 / 旅行为 **🚫 后置（设计稿列 V2）**，`tasks.md` §7.3 反范围清单亦未包含此项解禁。

### 🚫 缺口 19：AI 自动记账的「自动同步来源」在平台层不可行

- **现象**：`pages/34-ledger-auto.html:146-168` 要求「微信账单 / 支付宝账单 / 银行卡短信」三种自动同步来源，并显示「今天同步 6 笔」等动态；`components.md:580-581`（B11）同样要求。
- **证据**：后端全仓 `微信|支付宝|账单同步|短信` 相关零命中；平台层：微信 / 支付宝**无公开账单 API**；Android 读短信需 `READ_SMS`，Google Play 对该权限（尤其非默认短信应用）**严格限制甚至拒审**；iOS **完全无**短信读取与第三方账单读取能力。
- **后果**：**这不是排期问题，是能力不可实现**。若照设计稿渲染"已连接 / 今天同步 6 笔"，即为伪造数据，直接违反 `APP-014` 确立的红线。
- **裁决**：见 **D14**——三条来源降级为**「未接入」诚实态**，并明确每个来源"为什么不可用"；同时把**真实可用**的第四条（语音记账，走既有对话链路 `builtin.ledger.record`）标为**已开启**；真实账单的一键导入（CSV / 文件）列 **V2**。

### 缺口 20：「我学会的规则」的修正计数无数据源

- **现象**：`pages/34-ledger-auto.html:170-175` 要求「来自你的 9 次修正」与每行「修正 3 次后学会」；`components.md:582-583`（B11）同样要求。
- **证据**：后端 `app/services/ledger/category.py:106` 有 `add_alias`（别名 = 规则的本体），但**全仓无"修正次数"的计数与暴露读面**。
- **后果**：不成对给数则页面缺信息；编造计数则违反假数据红线。
- **裁决**：本期由后端新增读面返回**真实存在的别名规则**（关键词 → 目标类目）；「修正 N 次」这一计数**若无法真实取得则不显示该 hint**（区块 hint 改为"来自你的分类修正"或不带数字），**不得编造**。

### 缺口 21：车辆「限行提醒」需要城市政策数据源

- **现象**：`pages/35-car.html:175-179` 要求「下周三 · 尾号 4 和 9 · 建议地铁通勤」；`components.md:601-602`（B12）同样要求。
- **证据**：限行规则是**各城市动态政策**，无统一开放数据源；后端零相关命中。
- **后果**：编造"尾号 4 和 9"即为假数据；真实接入需外部数据服务（成本 + 合规 + 维护）。
- **裁决**：见 **D19**——限行走**用户手动配置**（城市 + 限行车牌尾号 + 限行日），未配置时呈引导态；**不接入城市政策数据**。

### 缺口 22：「养车支出」的子类目层级未定义

- **现象**：`pages/35-car.html:155-161` 的「本月养车支出」按**子类目**分条（洗车/小保养 ¥200、停车 ¥180、过路费 ¥130、充电费 ¥102），而记账域的分类是**每用户一层的 DB 行**（`category.py:37` 经 `ledger_repository.list_categories` 取），汇总只到单层。
- **证据**：`app/services/ledger/category.py:30-36`、`apps/mobile/lib/features/ledger/data/ledger_repository.dart:62`（`fetchSummary` 只解析单层 `by_category`）。
- **后果**：不定义层级，车辆页的四个子条要么取不到数（全落"养车"一条），要么端侧自行拼装（跨域逻辑泄漏到端上，违反 `traceability.md:312` 的评审纪律）。
- **裁决**：见 **D15**——在 `app/character/asuna/ledger_categories.py::SEED_CATEGORY_TREE` 新增**「养车」父类目 + 子项**（充电 / 加油 / 停车 / 过路 / 保养 / 洗车），车辆页的支出条按**子类目**聚合，聚合在**服务端**完成。

### 缺口 23：相册「最近删除 30 天」的实现主体未定

- **现象**：`pages/37-album.html:166`、`pages/38-album-manage.html:162`、`pages/61-photo-view.html:143`、`components.md:656/711/727` 均承诺「删除进『最近删除』保留 30 天可恢复」。
- **证据**：红线 9（`SKILL.md:52`）把"可恢复口径"列为必填。而 `photo_manager` 类库**只提供"移入系统回收站 / 删除"两种系统能力**，不提供自定义保留策略。
- **后果**：若按"App 自建回收站"实现，需自行复制 / 管理原图（存储翻倍，与本页"省空间"的目的一字段矛盾）；若沿用系统回收站，则"30 天"由系统策略决定，文案需准确措辞。
- **裁决**：见 **D17**——**沿用系统「最近删除」**（Android 10+ / iOS 均原生 30 天保留），App **不自建回收站**；文案统一为**「删除后进系统『最近删除』，30 天内可恢复」**。

### 🚫 缺口 24：相册「相似连拍」分析的成本未评估

- **现象**：`pages/38-album-manage.html:132`「相似连拍 · 9 月 12 日（AI 预选 · 共 26 张）」、`pages/60-album-detail.html:118`「12 组连拍，每组我留了最清楚的一张」、`pages/62-album-ai.html:124`「9 月 12 日青海湖 12 组」。而"过期截图"（目录 / 元数据启发式）与"重复保存"（哈希）都有低成本实现路径。
- **证据**：相似连拍需**感知哈希（pHash/dHash）或图像相似度**，须解码全部原图，在数千张量级上耗时长、耗电高，且"哪种更清楚"（清晰度评分）无成熟离线算法；三者的实现成本**不在同一量级**。
- **后果**：把两类与一类混做，会让相册期工期与耗电不可控，且极易用"看起来像"的数据蒙混过关。
- **裁决**：见 **D16**——本期只做**过期截图 + 重复保存**两类（低本机成本、判定可解释）；**「相似连拍」本期不做**，相关区块呈诚实未支持态（不是假数据、也不是空白），列 **V2**。**同时回写 skill B14/B15/B17/B18 与 `pages/60/62` 的口径待办**。

### 🚫 缺口 25：「相册仅本机」红线的可验收性无技术手段

- **现象**：红线 9（`SKILL.md:52`）要求「明示仅本机存储、不上传服务器」，且「AI 整理必须注明本机分析」。但"不上传"目前**只有文案，没有可验证的约束**。
- **证据**：`apps/mobile/test/scaffold/layer_guards_test.dart` 现有 9 条守卫（L20~L127）中，**没有**关于相册域网络访问的规则；`PLT-004` 的 golden / 走查规则也未覆盖此项。
- **后果**：红线沦为文案承诺，任何后续改动（比如"顺手加个云端备份"）都不会被测试拦住。
- **裁决**：见 **D18**——新增**分层守卫**：`lib/features/album/**` **禁止 import** `core/network/**` 与 `package:dio`；相册页测试断言**零网络调用**；`PLT-004` 的走查规则表新增一条「相册族页面无云同步字样、有仅本机口径」。

### 🚫 缺口 26：本机 Flutter 工具链故障是相册期的硬前置

- **现象**：本机 `flutter pub get / analyze / test` **全部不可用**；根因是 flutter_tools 在 `generateCommands` 阶段急切定位 Android SDK，`where.EXE aapt` 子进程创建失败（`CreateFile failed 231`，`process_win.cc:744`）。
- **证据**：`reviews/progress-audit-2026-09-29.md` §7.7（含绕过尝试失败的记录）；实测设 `ANDROID_HOME` 指向空目录仍走 `_which('aapt')`（`android_sdk.dart:127`）。
- **后果**：记账期与车辆期**不需要新增 Flutter 依赖**，可在现有依赖面内完成（但 `analyze` / `test` 仍不可跑，只能静态核验——这本身已不可接受）；**相册期必须新增 `photo_manager` 等原生依赖，`pub get` 是硬门槛**。叠加缺口 25 的守卫测试也需 `flutter test` 才能生效。
- **裁决**：登记 **`PLT-007`** 为相册期开工硬前置；未修复前**不得以静态检查替代**真实 `analyze` / `test`（`tasks.md` §0.4 与 `progress-audit` §6.2 已明文禁止）。

### 缺口 27：车辆提醒的投递通道未登记

- **现象**：`pages/35-car.html:163-180` 的保养 / 车险 / 限行三类提醒需要"我会提前告诉你"的投递路径。
- **证据**：`APP-019` 已实现 `flutter_local_notifications` 本地调度（见 `tasks.md` §4 与 `progress-audit` §2.2 #7 已修）。
- **后果**：若不显式纳入，车辆提醒会变成"只在页面里写一行字"的假承诺。
- **裁决**：见 **D20**——车辆提醒**复用既有本地通知调度**，不新增推送通道；提醒时刻 / 提前量作为**参数类设置**（禁 `*_enabled` 形态功能位）。

### 缺口 28：大相册性能基线未定义

- **现象**：设计稿以 `2,847 张` 为量级（示例值），但本机分析（分组 / 哈希 / 缩略图解码）与照片墙渲染都需要基线。
- **证据**：`tasks.md` §7 `PLT-006` 只定义了首屏 / 首 token / 列表帧率 / Orb 功耗四项，未覆盖相册。
- **后果**：无基线则"卡不卡"只能主观判断，且容易把编译期 / 首扫耗时当成崩溃。
- **裁决**：写入相册期验收——本机分析在**后台 isolate** 执行、**可中断**、中断**不改变任何照片**；缩略图按需解码（不一次载入原图）、照片墙虚拟化 + 分页；首扫进度对用户可见。
