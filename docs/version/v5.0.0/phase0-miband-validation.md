- 官方 App 与 **Gadgetbridge 互斥**（抢连设备 / 清空未拉取数据，`F5[12]`）→ 测量期间**不得**同时安装或连接 Gadgetbridge。

## 2.5 根因复核（推翻 §2.2 结论 · 决定性）

> 触发：用户指出「貌似并没有健康互联 App」，并追问小米手环 9 Pro 数据获取方案。
> 复核方式：查官方 FAQ + 反编译证据（社区 LSPosed 模块 `Blade-gen/mi-health-healthconnect-unlock` 附带了 `com.mi.health` 3.58.0 的反编译结论）+ 实测日志三段印证。

### 2.5.1 关键事实：开关存在，但被区域门控

**小米官方 FAQ 明确写有该开关的位置**（KA-230357 / KA-232395，多区官网一致）：

```
Mi Fitness APP → [我的 / Profile] → [设置 / Settings] → [Sync with the cloud]  → 开启
Mi Fitness APP → [我的 / Profile] → [第三方数据 / Third-party data] → 打开 [Health]
                → 勾选要同步的数据项
```

中文路径即：**我的 → 设置 → 三方数据管理 → 授权 Health Connect**（社区教程 `JoiiSports` 亦一致）。

**为何国行版看不到这一项**：小米运动健康在**大陆区域**（`currentRegion == "cn"`）把 Health Connect
**主动跳过**了。该判断函数为 `RegionExtKt.isInland(RegionManager)`，全应用共 **81 处**调用；
其中与 Health Connect 相关的两处门控如下（源码级证据，适用版本 3.58.0 / versionCode 358000 国行版）：

| 门控 | 位置 | 反编译行为 |
|---|---|---|
| **① 入口（主进程）** | `AuthConfigListAdapter.convertAuthConfigListToUiModelList()` | 仅在 `MineUtil.isGlobalRegion() == true` 时才调 `addHealthConnectToUiModelIfNeeded()` 展示「Health Connect」条目 → **大陆区域该条目根本不渲染** |
| **② 数据同步（`:device` 进程）** | `HealthConnectComponent$checkAndStartSync$1.invokeSuspend()` | `if (isInland() \|\| !isHealthConnectInstalled()) { Logger.i(TAG, "main land do not use health connect!!"); return; }` → **直接 return，永不发起同步** |
| **③ 授权持久化（重启清零）** | `HealthConnectUtils.hasHealthConnectAuthed()` → `PermissionController.getGrantedPermissions()` | 判断的是 `android.permission.health.*` **运行时权限**（带 **`ONE_TIME`** 标志）；**HyperOS 不持久化这些权限**（真机 `runtime-permissions.xml` 甚至不存在），故每次重启后 `granted=true` 由 **10 项归零**。⚠️ 平台 HC 库里的授权记录**并未丢失**（`healthconnect.db` 的 `application_info_table` 中该记录重启前后 MD5 一致）—— 丢的是**应用侧权限位** |

> **门控 ① 的一个隐蔽陷阱**：`MineUtil.isGlobalRegion()` 返回的是**类加载时缓存**的静态布尔
> （`isGlobalRegion = !RegionExtKt.isInland(...)`），因此**不能**只 Hook `isInland()` 来放行入口 ——
> 必须直接 Hook `isGlobalRegion()` 方法本身。它全应用仅 4 处调用（都在该数据管理页），改它不会波及其它界面。
>
> **门控 ③ 对本项目的启示（重要）**：我们的 App 也在清单里声明了 15 项 `android.permission.health.READ_*`。
> 若国行 HyperOS 对这些 `ONE_TIME` 权限同样不做持久化，则**我们的授权也会在每次重启后丢失** ——
> 这与本次实测「授权 18/18」并不矛盾（实测是在**未重启**的会话内完成的）。
> ⚠️ **待验证**：重启设备后重跑 `/health/diagnostics`，看 ③ 是否仍为 18/18。
> 若同样归零，则 `APP-025` 的授权流程必须**每次冷启动后重新校验并引导重授权**，不能假设授权持久。

> 门控 ② 源码：
> ```java
> boolean zIsInland = RegionExtKt.isInland(RegionExtKt.getInstance(companion));
> boolean zIsHealthConnectInstalled = ...isHealthConnectInstalled(...);
> Logger.i(TAG, "init hc info:" + zIsInland + " - " + currentRegion + " - " + installed);
> if (zIsInland || !zIsHealthConnectInstalled) {
>     Logger.i(TAG, "main land do not use health connect!!");
>     return;   // ← 跳过 HC 数据同步
> }
> ...updateTriggersIfNeeded → syncDailyRecords(step,hr,spo2,calorie,sleep) → syncReport()...
> ```

**这完美解释了本次实测的全部现象**：

| 实测现象 | 门控解释 |
|---|---|
| 找不到「同步到健康平台」开关 | 门控 ① 不渲染该 UI 条目 |
| 18/18 权限可正常授权 | 权限是**系统侧**能力，与我们 App 的清单声明有关，与小米 App 是否写入无关 |
| 365 天宽窗读到 0 条 | 门控 ② 从未发起过 `syncDailyRecords`，健康互联库中自然无小米写入 |
| SDK 状态 `sdkAvailable(native=3)` | 健康互联框架本身正常，与小米门控无关 |

### 2.5.2 推论：这不是「机型不支持」，是「区域策略」

- 同一台小米手环 9 Pro、同一个 `com.mi.health`，**在非大陆区域该同步是开启的**（官方 FAQ 面向全球）。
- 因此 PLT-001 的 P1 命题「Mi Fitness 原生写入健康互联」在**能力层面成立**；
  在**国行 + 大陆区域**默认配置下被关闭，属**可变更的配置问题**，不是能力缺失。
- ⚠️ 这推翻了 `REPORT.md:87` 的 Open 项假设方向 —— 该 Open 项问的是「国内版是否写入」，
  答案是「**代码具备该能力，但被区域门控主动跳过**」，比「根本没有」更乐观。

### 2.5.3 解锁路径（用户侧配置，三选一）

| 路径 | 做法 | 合规/风险 | 适合 |
|---|---|---|---|
| **A. 切非大陆区域**（推荐先试） | 小米运动健康内把账号/地区改为非大陆区域（如新加坡/欧洲），开关即出现 | ⚠️ 会影响小米账号其它服务；部分国内机型/账号可能切不了 | 个人验证 |
| **B. LSPosed 模块解锁**（不改区域） | `Blade-gen/mi-health-healthconnect-unlock`：Hook `MineUtil.isGlobalRegion()` 放行入口 + 精确放行 `HealthConnectComponent` 调用栈的 `isInland()` | ⚠️ **需 root + LSPosed**；仅解锁 HC 两处门控，大陆服务器/设备连接逻辑不变；卸载即还原 | 极客验证 |
| **C. 第三方桥接 App**（不 root） | `ilyasaftr/better-mi-fitness-sync`（MIT，Kotlin）：登录小米账号 → 拉云端数据 → 写入 Health Connect | ⚠️ 第三方 App 处理你的小米账号凭据；**需自行审查** | **最可行的个人路径** |

**路径 C 细节**（本次已审查源码）：
- 支持区域含 `cn`（`MiRegion.ALL_REGIONS = cn/sg/us/de/ru/i2`，大陆 host 为 `hlth.io.mi.com`）；
- 可同步：步数、心率、静息心率、睡眠（**含分期**）、SpO₂、体重/体脂、运动（含 GPS 轨迹）、体温、VO₂Max 等；
- 凭据处理：`MiCredentials{userId, ssecurity, serviceToken, passToken, deviceId, region, cUserId}`
  → 存入 **AndroidX DataStore（明文）**。⚠️ **未用加密存储**，属已知弱点；
- 权限清单仅声明 `health.WRITE_*` 与少量 `READ_*`，`queries` 与本项目一致（仅
  `<package com.google.android.apps.healthdata>` + rationale intent，无多余 `<provider>`）；
- `usesCleartextTraffic="true"` 交由 `network_security_config.xml` 收窄，仅对
  `10.0.2.2` / `localhost`（模拟器调试）放开 —— **对小米的流量仍是 HTTPS**，不构成风险；
- 社区体量：v1.0.5（2026-09-24），42 stars，MIT，个人维护。

## 5. 总体结论（三档之一 · 必选）

> 契约：`PLT-001.md` §4.2 D3。二值结论无法表达「写入成立但字段不全 / 延迟过高」这类中间态。

- [ ] **通过** — P1 成立，字段面足以支撑健康页与三宫格，延迟可接受
- [ ] **部分通过** — P1 成立，但字段缺失 / 延迟过高 / 需手动触发 → 需裁剪字段面
- [ ] **未通过** — P1 不成立且无开关引导 → 触发 R1 降级
- [x] **（修正后）通过** — P1 能力成立，受阻于大陆区域门控，用户侧一条配置即可打通

**总体结论**：⚠️ **通过（附前置条件）** —— 修正 §2.2/§5 初判

**理由（修正后）**：
1. §2.2 初判「P1 不成立」的**唯一支撑是「找不到同步开关」**；§2.5 已证明该开关**存在**，
   其缺席原因是 `com.mi.health` 在大陆区域对 Health Connect 施加了两处**代码级门控**
   （入口不渲染 + `checkAndStartSync` 直接 `return`），而非能力缺失。
2. 同一 App、同一机型在非大陆区域该同步是开启的（官方 FAQ 面向全球），
   故 **P1 在能力层面成立**；国行版的「0 条」是**配置被区域策略关闭**的结果，
   不是「读不到」也不是「设备不支持」。
3. 实测的 ③ 授权 18/18 + ④ 读取成功 0 条**依然有效**，只是其解释从
   「数据从未写入」修正为「小米 App 因区域门控从未发起写入」—— 二者都是「库中无数据」，
   但**归因不同，因此处置方式完全不同**：前者无解，后者一条配置可解。

## 5.5 判定纪律（本次教训 · 供后续验证者）

> 本节是本次验证**最重要的方法论产出**，其价值高于结论本身。

| # | 教训 | 具体表现 |
|---|---|---|
| 1 | **不要从「UI 里找不到某项」推出「能力不存在」** | 本次最大失误。区域门控、灰度、A/B、灰度开关都会让功能「在代码里但在 UI 里看不见」。正确做法：**先查官方文档确认该功能是否被承诺**（小米 FAQ 一次就查到了），再去 UI 里找；找不到时应怀疑「被门控」而非「不存在」 |
| 2 | **「0 条」的归因必须交叉验证，不能单点收口** | 本次「SDK 可用 + 权限 18/18 + 读取成功 0 条」看似三方闭环，实际只证明了「**健康互联库里没有小米写的数据**」这一个事实，**没有**证明「小米不具备写的能力」。把「库里没有」等同于「写不进去」是逻辑跳跃 |
| 3 | **区分「能力」与「配置」** | 门控关闭的是**配置**，不是**能力**。二者的处置成本差几个数量级：能力缺失 → 项目降级；配置未开 → 加一条引导 |
| 4 | **优先查一手官方文档** | 用户提供的两篇社区文章（火山引擎转载的 StackExchange）指向 BLE 直连与抓包，方向偏且含法律风险；而**小米官方 FAQ 一页就说清了开关的准确路径**。查证顺序应为：官方 FAQ → 官方开发者文档 → 官方机型页 → 社区 → 逆向 |

**复测前置检查（新增，必须逐条确认）**：
- [ ] 已确认小米运动健康内**确实已开启**「三方数据管理 → 授权 Health Connect」（或已走出 §2.5.3 路径）
- [ ] 已确认授权后**产生过新数据**（走一走让步数增加），并等待一次小米 App 同步
- [ ] 已知「首次授权只同步当天之后的数据」（历史数据不回填，社区实测结论）

## 12. 复测指引（用户完成区域门控配置后）

> 本次结论有时效性：**绑定小米运动健康国行版 3.58.0 的区域门控行为**。
> 若小米后续版本放开大陆区域的 Health Connect 同步，或用户完成了 §2.5.3 任一路径，需重新验证。

### 12.0 前置条件（**必做，否则复测必然仍是 0 条**）

按 §2.5.3 任选一条走通：
- **A** 切非大陆区域 → 「我的 → 设置 → 三方数据管理」出现「Health Connect」条目；
- **B** LSPosed 模块解锁 → 同上条目出现；
- **C** 第三方桥接 App → 数据由该 App 直接写入。

完成后**必须**：
1. 在小米运动健康内**开启**「Health Connect」授权，并勾选要同步的数据项；
2. **走一走让步数增加**（首次授权只同步**当天之后**的数据，历史不回填）；
3. 等一次小米 App → 健康互联的同步（建议睡前手动打开小米 App 确认一次）。

### 12.1 复测步骤（1 分钟）

复测**不需要**重跑本文 §2.1 的 UI 流程，直接用已交付的诊断工具：

1. 真机启动 App → 健康页 → 「PLT-001 手环数据探针」→ 「读取链路诊断」
2. 看 ③ 授权态（应仍为 18/18）与 ④ 读取态（关注是否有非 0 命中）
3. 判定：
   - ④ 任一类目命中 > 0 → **P1 确认成立**，继续补测 §3（字段面）与 §4（延迟）
   - ④ 仍全 0 且 ③ 仍 18/18 → 回到 §12.0 检查前置条件是否真的完成

### 12.2 若走路径 C（第三方桥接）的额外验收点

- 在健康互联「数据来源」中，出现的数据来源是**桥接 App 的包名**（而非 `com.xiaomi.wearable`）
  → 这会影响本报告 §2.2 中「`miFitnessPackage` 写入」的判据，需按实际来源名调整；
- 核对字段完整性：重点看**睡眠分期**（深/浅/REM）是否完整，这是社区反馈最容易缺失的项。
